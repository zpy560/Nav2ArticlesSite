给 Codex 装上专业能力：MCP、Skills、Plugins、Hooks 与多代理全解 ​

Codex 的扩展体系看起来名词很多，但每一层解决的问题不同：AGENTS.md 记录项目规则，Memory 保存跨任务经验，Skill 封装工作流，MCP 连接工具与数据，Plugin 负责打包分发，Hook 在生命周期节点执行机械检查，Subagent 用隔离上下文并行处理独立任务。

一、先按信息寿命选择承载层 ​

1.1 Prompt 保存一次性要求 ​

当前目标、临时范围和本次特殊输出只在当前 Thread 有效，不需要永久写入项目。

1.2 AGENTS.md 保存仓库规则 ​

构建、测试、目录边界、工程规范和完成标准由团队版本化维护。它是显式指令，不是自动推断的记忆。

1.3 Memory 保存可复用经验 ​

Memory 适合跨任务保留用户偏好、稳定上下文和历史经验，但任何会变化的事实都应在使用前重新验证。敏感值和未经确认的推断不应长期保存。

二、MCP 连接外部工具与数据 ​

2.1 MCP 是协议边界 ​

它允许 Codex 发现并调用外部工具、读取资源或使用服务提供的能力。MCP 解决“怎样连接”，不自动解决数据质量、身份、权限和审计。

2.2 工具描述决定代理怎样调用 ​

清晰名称、参数 Schema、返回结果和副作用标记能减少误用。破坏性工具必须显式标注，并进入审批链。

2.3 接入前先画数据流 ​

明确请求会带出哪些上下文、服务能访问什么、结果保存在哪里、失败如何处理。远程 MCP 和本地 STDIO Server 的信任面不同。

三、Skill 把重复经验封装成流程 ​

3.1 Skill 适合重复且边界稳定的任务 ​

源码审查、发布检查、固定格式报告和特定调试流程，都可以用 SKILL.md 描述触发条件、步骤、资源与验证。

3.2 渐进式披露控制上下文成本 ​

代理先看到能力摘要，确认匹配后再读取完整说明，只有需要时才加载参考和脚本。这样能力库可以增长，而不必把全部内容塞入每次会话。

3.3 Skill 必须拥有完成证据 ​

只有指导语而没有检查方法的 Skill，容易把错误流程稳定复用。可靠 Skill 应说明输入、产物、失败条件和验证。

四、Plugin 是能力分发单元 ​

4.1 一个 Plugin 可以携带多种能力 ​

Skills、MCP、Hooks、应用连接和资产可以被统一打包，便于团队安装、更新与停用。

4.2 安装会扩大信任边界 ​

管理员和用户需要审查来源、负责人、权限、数据流、版本与撤销方式。安装插件不等于批准其所有连接器动作。

4.3 公共能力优先组合而不是复制 ​

同一流程若在多个插件内复制，会产生版本漂移。稳定基础能力应共享，项目差异放进更靠近仓库的规则或 Skill。

五、Rules 与 Hooks 管理动作边界 ​

5.1 Rules 负责命令策略 ​

规则可以识别允许、需要审批或禁止的命令模式，减少低风险重复确认，同时保留高风险关口。

5.2 Hooks 负责生命周期检查 ​

Hook 在工具调用、命令执行或会话事件前后运行机械逻辑，适合格式检查、策略校验、日志记录和阻断。

5.3 机械执行必须保持简单 ​

Hook 的输入输出、退出码、超时和失败行为要明确。不要把复杂业务决策塞进难以观察的钩子。

六、Subagent 用隔离换取并行 ​

6.1 独立子任务才适合委派 ​

资料检索、互不重叠模块分析和独立测试调查可以并行。频繁共享状态或修改同一文件的任务更适合顺序执行。

6.2 子代理返回证据而不是只报结论 ​

主线程需要知道读取了哪些来源、得到什么结果、有哪些不确定项。验收责任不能外包给子代理。

6.3 并行数量受整合成本限制 ​

代理越多，协调、冲突和上下文回传成本越高。吞吐提升来自任务可分解，而不是盲目增加执行者。

七、建立扩展体系的推荐顺序 ​

先让 Prompt 与 AGENTS.md 稳定单代理工作，再把重复流程提炼为 Skill；确需外部数据时连接最小权限 MCP；需要团队分发时封装 Plugin；需要机械拦截时使用 Rules 和 Hooks；任务真正独立后才增加 Subagent。

八、扩展能力必须可撤销 ​

每项扩展都要有版本、负责人、复查日期和停用方法。外部服务失效、权限扩大或协议变化时，团队应能移除单项能力，而不是让整个 Codex 环境不可用。

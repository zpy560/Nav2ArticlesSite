别再乱调 config.toml：Codex 配置、模型选择与速度优化全解 ​

许多“模型不听话”的问题，根因其实是配置层级、工作目录、权限、工具或项目规则不一致。OpenAI Docs 把 Codex 配置拆成个人默认、项目配置、Profile 与一次性覆盖，并强调不同入口共享主要配置层。理解覆盖关系，比背诵某个版本的全部配置键更重要。

一、配置与项目知识不是同一层 ​

1.1 配置决定默认运行姿势 ​

模型、推理强度、权限、功能开关、MCP、Hooks 和界面行为属于配置。它们回答“Codex 默认怎样运行”。

1.2 AGENTS.md 决定项目做事规则 ​

构建命令、代码风格、目录边界和完成标准属于项目指令。它回答“在这个仓库应该怎样工作”。把项目百科塞进 config.toml，会让规则难以审查与共享。

1.3 Prompt 决定本次任务 ​

一次性的目标、文件范围和特殊约束应留在当前会话。不要为了一个临时任务修改全局默认。

二、配置优先级必须可解释 ​

2.1 个人配置提供跨项目默认 ​

用户级 config.toml 适合模型偏好、常用 Profile 和个人工具连接。默认值应保守，避免一个高权限项目习惯扩散到所有仓库。

2.2 项目配置提供可信仓库默认 ​

仓库级 .codex/config.toml 可以共享项目需要的配置，但只有在信任仓库时才应加载。外部仓库中的配置本身也属于不可信输入。

2.3 命令行覆盖只服务一次运行 ​

临时参数适合诊断或比较，不应成为团队不可见的长期事实。任务结束后要能从版本化配置重建行为。

2.4 Profile 让场景切换显式化 ​

只读审计、本地开发和 CI 可以使用不同 Profile。Profile 名称应表达用途，并与实际权限、模型和工具条件一致。

三、模型选择从任务特征开始 ​

3.1 复杂度决定推理需求 ​

机械修改、查找符号和固定格式转换通常不需要最高推理强度；跨模块设计、陌生系统诊断和长时间 Agent 任务需要更强规划。

3.2 风险决定验证强度 ​

简单但涉及身份、支付、迁移或公开接口的任务，仍需要严格 Review。模型强度不能替代安全与测试。

3.3 工具条件可能比模型更关键 ​

无法读取真实日志、运行测试或获取正确目录时，更强模型也只能基于缺失信息推断。先修复环境，再判断是否需要换模型。

3.4 用团队真实任务建立基准 ​

比较完成率、人工修正、验证通过率、总耗时和成本，而不是只看单次演示。官方可用模型和推荐会变化，选择应定期重测。

四、推理强度不是越高越好 ​

较低强度适合范围明确、反馈快速的任务；较高强度适合需要计划、权衡和多轮工具验证的任务。盲目提高强度会增加延迟和成本，却无法修复错误上下文。

可以在代表性任务上比较多个档位，并把结果记录为团队经验。具体档位名称和模型支持情况以当前界面与官方文档为准。

五、速度要看端到端链路 ​

5.1 缩小搜索范围 ​

指出入口、相关目录、错误日志和验证命令，是最便宜的加速方式。它减少无目的搜索和无关文件读取。

5.2 建立快速局部反馈 ​

先运行目标单元测试或静态检查，局部通过后再扩大验证。每轮全量构建会浪费时间，永远不跑集成验证又会遗漏风险。

5.3 使用可重建缓存 ​

依赖缓存和构建产物能减少等待，但必须有失效规则。来源不明的旧缓存会制造假通过。

5.4 分离独立任务 ​

互不依赖的调查或实现可以并行，修改同一接口的任务不应为了“多代理”强行并行。并行的收益来自独立性，不是代理数量。

六、诊断配置问题要看实际生效值 ​

遇到行为与预期不一致，依次核对当前工作目录、加载的配置层、选中 Profile、模型与推理强度、权限模式、Feature 状态、MCP 和项目规则。不要只盯着某一个 config.toml 文件，因为更高优先级覆盖可能已经改变结果。

七、配置治理的最终目标是可重建 ​

团队成员和 CI 应能从版本化仓库、明确个人前置条件和官方当前版本重建同类行为。任何只有某台机器“碰巧能跑”的配置，都不是可靠工程能力。

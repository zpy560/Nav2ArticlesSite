Nav2 的两张地图怎样驱动规划与控制？全局与局部 Costmap 全数据流拆解 ​

在 Nav2 中，“地图”至少有三种含义。

第一种是磁盘里的 YAML 和 PGM／PNG，它描述静态世界；第二种是 /map 上的 OccupancyGrid，它是 ROS 2 能传输的静态占用栅格；第三种是 Planner 和 Controller 真正使用的 Costmap，它把静态地图、实时传感器、机器人位姿、Footprint 和语义过滤器融合成不断变化的风险场。

最容易产生误解的地方是：全局地图和局部地图并不是两个 Map Server，也不是 Planner、Controller 分别订阅一张图片。

真实关系是：

text
Map Server 发布 /map
       ↓
Global Costmap 与 Local Costmap 各自按配置融合数据
       ↓
Planner 直接读取 Global Master Costmap
Controller 直接读取 Local Master Costmap

本文基于当前 navigation2/ 源码，把磁盘地图、Map Server、Static Layer、Obstacle Layer、Layered Costmap、Planner Server、Controller Server以及全部外部接口串成一条完整数据流。

一、先给结论：Nav2 同时维护“静态世界”和“两张风险地图” ​

磁盘地图只负责提供长期不变的环境底图：墙、固定障碍、未知区和可通行区域。

Global Costmap 面向全局路径搜索，通常覆盖整张地图，重点回答：

text
从当前位置到目标点，哪条长距离路线可以走？

Local Costmap 面向实时运动控制，通常是以机器人为中心的滚动窗口，重点回答：

text
未来几秒怎样运动，才不会撞上眼前障碍？

二者都可以使用 nav2_costmap_2d 的 Layer 插件，但窗口、坐标系、频率和传感器范围通常不同。为了适配微信公众号手机端阅读，关键差异改用分组条目呈现。

1.1 Global Costmap ​

  • 所有者：Planner Server。
  • 主要消费者：全局规划插件。
  • 常见窗口：固定整图。
  • 常见输入：/map、TF 和较远障碍。
  • 主要目标：路径可达性与全局绕行。
  • 常见更新频率：较低。

1.2 Local Costmap ​

  • 所有者：Controller Server。
  • 主要消费者：局部控制插件。
  • 常见窗口：机器人中心滚动窗口。
  • 常见输入：TF 和近场 LaserScan／PointCloud2。
  • 主要目标：轨迹碰撞与实时避障。
  • 常见更新频率：较高。

二、第一段主链：磁盘地图怎样变成 /map ​

Map Server 不直接把图片字节发给导航系统。它先把 YAML 和图像翻译成 nav_msgs/msg/OccupancyGrid。

2.1 YAML 是地图的解释规则 ​

典型 YAML 包含：

yaml
image: map.pgm
mode: trinary
resolution: 0.05
origin: [-10.0, -10.0, 0.0]
negate: 0
occupied_thresh: 0.65
free_thresh: 0.25

resolution 决定每个像素代表多少米；origin 决定图片左下角在 map 坐标系中的位置；两个阈值决定灰度怎样解释为占用和空闲。

2.2 map_io 完成像素到栅格的翻译 ​

map_io 读取图片宽高和颜色，计算占用概率，再生成：

text
0    空闲
100  占用
-1   未知

图像以左上角为常见原点，OccupancyGrid 以地图左下角组织，因此转换过程中会做 Y 轴翻转。图片能打开，不等于坐标语义一定正确；分辨率、原点和 Y 轴任一错误，最终路径都会整体偏移。

2.3 Map Server 缓存并发布 ​

Map Server 在 Lifecycle configure 阶段读取地图并写入 msg_ 缓存，在 activate 阶段激活 Publisher 并发布。

/map 通常采用：

text
KeepLast(1)
reliable
transient_local

因此后启动的 Static Layer 仍能收到最近一次地图。

Map Server 还提供：

text
/<map_server>/map       nav_msgs/srv/GetMap
/<map_server>/load_map  nav2_msgs/srv/LoadMap
/map                    nav_msgs/msg/OccupancyGrid

Map Saver 则反向临时订阅某个 OccupancyGrid Topic，把消息写回图片和 YAML。

三、Global Costmap：整张静态地图怎样变成规划风险场 ​

Planner Server 在构造阶段创建名为 global_costmap 的 Costmap2DROS。这张图不是独立进程里的一份远程数据，而是 Planner Server 拥有的运行时对象。

3.1 Static Layer 接收 /map ​

Static Layer 订阅完整 /map，也可以选择订阅 /map_updates 增量消息。收到地图后，它检查：

text
width／height
resolution
origin
frame_id

对于固定窗口 Global Costmap，如果 Master Costmap 尺寸还没有锁定，它可以根据静态地图调用 resizeMap()，让 Master 与 /map 对齐。

OccupancyGrid 的 0～100／-1 不会原样写入内部数组，而是由 interpretValue() 按以下参数转换：

text
track_unknown_space
unknown_cost_value
lethal_cost_threshold
trinary_costmap

3.2 动态障碍也可以进入全局图 ​

Global Costmap 并不等于“只有静态地图”。只要配置 Obstacle Layer 或 Voxel Layer，它也可以融合 LaserScan 和 PointCloud2。

这让全局规划器能够绕过持续存在的动态封路区域，但代价是更高更新开销和更容易受临时观测影响。是否在 Global Costmap 中加入动态障碍，应由导航距离、传感器范围和重规划频率共同决定。

3.3 Planner 不订阅 global_costmap/costmap ​

关键调用关系是：

text
PlannerServer
  └─ costmap_ros_
      └─ LayeredCostmap
          └─ Master Costmap2D

规划插件初始化时获得 Costmap ROS 对象或其底层 Costmap 指针。执行 createPlan(start, goal) 时直接读取进程内 Master Costmap。

/global_costmap/costmap 主要提供给 RViz 和外部调试工具，不是 Planner Server 自己的数据回路。

四、Local Costmap：实时传感器怎样变成控制约束 ​

Controller Server 同样在构造阶段创建 local_costmap。它通常开启 rolling_window，窗口中心随机器人移动。

4.1 Rolling Window 只保留机器人附近区域 ​

每次更新先通过 TF 获取机器人在 Local Costmap global_frame 中的位姿。随后 updateOrigin() 移动窗口原点，同时尽量保留重叠区域中的已有代价。

滚动窗口的意义不是缩放地图，而是把固定数量的栅格持续放在机器人附近，使 Controller 能以更高频率处理近场风险。

4.2 LaserScan 和 PointCloud2 先进入 ObservationBuffer ​

Obstacle Layer 为每个 observation_source 创建订阅和 ObservationBuffer。

LaserScan 先经 TF Message Filter 等待坐标转换可用，再投影成 PointCloud2；原生 PointCloud2 则直接转换到目标坐标系。统一观测保存：

text
传感器原点
转换后的点云
障碍标记距离
射线清除距离
高度范围
观测有效时间

4.3 Clearing 与 Marking 是两条不同路径 ​

clearing: true 时，从传感器原点向测量端点做 raytrace，把射线穿过的旧障碍清为自由空间。

marking: true 时，满足距离、高度和边界条件的端点被写成 LETHAL_OBSTACLE。

因此动态障碍消失后能否从 Costmap 中消失，取决于新的清除射线，而不是单纯等待某个固定超时。

4.4 Controller 同样直接读取内部 Costmap ​

Controller 插件在初始化时获得 local_costmap 对象。每轮控制：

text
接收 FollowPath
→ 设置全局路径
→ 获取当前位姿
→ 检查 Local Costmap 是否 current
→ computeVelocityCommands()
→ 发布 cmd_vel

轨迹打分、碰撞检查和速度约束直接读取 Local Master Costmap。外部发布的 /local_costmap/costmap 仍然主要服务于可视化和调试。

五、一轮 Costmap 更新为什么分成两阶段 ​

Global 和 Local Costmap 使用相同的核心更新框架。

5.1 updateBounds() 先决定改哪里 ​

Layered Costmap 依次调用每个普通 Layer 和 Filter 的 updateBounds()，收集这轮需要更新的世界坐标范围。

Static Layer 报告地图变化范围；Obstacle Layer 报告新观测、清除射线和机器人 Footprint 范围；Inflation Layer 将边界向外扩展到膨胀半径。

最后，世界坐标边界被裁剪并转换成栅格索引窗口。

5.2 updateCosts() 再决定写什么 ​

普通插件按参数中的顺序写入：

text
Static Layer
→ Obstacle／Voxel Layer
→ Denoise 等普通插件
→ Inflation Layer

Costmap Filter 在普通插件之后处理 combined costmap，用于 Keepout、Speed、Binary 等语义约束。

插件顺序会改变最终结果。例如 Inflation 必须看到前面已经写入的致命障碍，才能向外传播代价梯度。

六、输入接口总表：数据到底从哪里进入 ​

6.1 共同基础输入 ​

6.1.1 TF ​

  • 类型：tf2。
  • 作用：获取机器人位姿，转换传感器数据和 Footprint。

6.1.2 footprint ​

  • 类型：geometry_msgs/msg/Polygon。
  • 作用：动态更新机器人几何轮廓。

6.1.3 参数中的 robot_radius／footprint ​

  • 类型：参数。
  • 作用：初始化机器人碰撞边界。

6.1.4 Filter Info ​

  • 类型：nav2_msgs/msg/CostmapFilterInfo。
  • 作用：指定 Mask Topic、过滤类型和换算参数。

6.1.5 Filter Mask ​

  • 类型：nav_msgs/msg/OccupancyGrid。
  • 作用：描述禁行、限速或二值过滤区域。

6.2 静态地图输入 ​

6.2.1 /map ​

  • 类型：nav_msgs/msg/OccupancyGrid。
  • 消费者：Static Layer。

6.2.2 /map_updates ​

  • 类型：map_msgs/msg/OccupancyGridUpdate。
  • 消费者：Static Layer，可选接口。

6.2.3 LoadMap 服务 ​

  • 类型：nav2_msgs/srv/LoadMap。
  • 消费者：Map Server。

6.2.4 GetMap 服务 ​

  • 类型：nav_msgs/srv/GetMap。
  • 消费者：外部地图客户端。

6.3 动态障碍输入 ​

6.3.1 /scan ​

  • 类型：sensor_msgs/msg/LaserScan。
  • 消费者：Obstacle Layer 或 Voxel Layer。

6.3.2 点云 Topic ​

  • 类型：sensor_msgs/msg/PointCloud2。
  • 消费者：Obstacle Layer 或 Voxel Layer。

6.3.3 Range Topic ​

  • 类型：sensor_msgs/msg/Range。
  • 消费者：Range Sensor Layer。

Topic 名称不是写死的，由每个 Costmap 的 observation_sources 参数决定。

七、输出接口总表：内部地图怎样暴露给外部 ​

每个 Costmap 的 Costmap2DPublisher 通常提供：

7.1 costmap ​

  • 类型：nav_msgs/msg/OccupancyGrid。
  • 含义：适合 RViz 显示的完整占用图。

7.2 costmap_raw ​

  • 类型：nav2_msgs/msg/Costmap。
  • 含义：保留原始 0～255 代价值和元数据。

7.3 costmap_updates ​

  • 类型：map_msgs/msg/OccupancyGridUpdate。
  • 含义：只发布发生变化的地图窗口。

7.4 published_footprint ​

  • 类型：geometry_msgs/msg/PolygonStamped。
  • 含义：当前机器人位姿下的外轮廓。

7.5 get_costmap ​

  • 类型：nav2_msgs/srv/GetCostmap。
  • 含义：按照服务请求返回当前 Costmap。

清理服务由 ClearCostmapService 提供，常见接口包括：

text
clear_entirely_*_costmap
clear_around_*_costmap
clear_except_*_costmap

全量清图会重置可清理 Layer，但静态层、传感器层随后会根据输入重新写回。它不是永久删除环境障碍。

八、内部调用与 ROS Topic 必须分开理解 ​

Nav2 地图链路同时存在两种完全不同的数据访问方式。

8.1 ROS 接口 ​

text
Map Server → /map → Static Layer
传感器 → /scan／points → Observation Layer
Costmap → costmap／raw／updates → RViz 和外部工具

8.2 进程内直接调用 ​

text
Planner Plugin → Global Costmap2D 指针
Controller Plugin → Local Costmap2D 指针
Goal／Progress Checker → Costmap ROS 对象

因此排障时要先问清楚：问题发生在 ROS 消息链，还是内部共享对象更新链。

/global_costmap/costmap 没有订阅者，不代表 Planner 没有使用 Costmap；相反，/map 在 RViz 显示正常，也不代表 Static Layer 已经把它正确融合进 Master Costmap。

九、五类最常见的数据流断点 ​

9.1 /map 有数据，但 Global Costmap 没静态层 ​

重点检查：

text
Static Layer 是否加载
map_topic 是否正确
QoS 是否匹配
frame_id 是否符合预期
地图尺寸是否允许 resize

9.2 /scan 有频率，但地图没有障碍 ​

重点检查传感器时间戳和 TF。Message Filter 只有在消息时间点能够完成坐标转换时，才会把数据交给 ObservationBuffer。

9.3 障碍物出现后一直不消失 ​

确认该观测源是否开启 clearing，以及 raytrace_max_range 是否足以覆盖旧障碍。没有新的清除射线，旧标记可能继续保留。

9.4 Local Costmap 正常显示，Controller 却拒绝运行 ​

Controller Server 还会检查 Costmap 是否 current。某个配置了 expected_update_rate 的传感器长期不更新，可能让 Costmap 被判定为过期。

9.5 规划路径贴墙或控制器过度保守 ​

这通常不是 Planner 或 Controller 单独的问题。应联合检查：

text
robot footprint
footprint padding
inflation radius
cost scaling factor
规划器的代价权重
控制器的碰撞和代价权重

十、把完整链路压缩成一句话 ​

Nav2 地图系统的完整主链是：

text
YAML + 图像
→ Map Server
→ /map OccupancyGrid
→ Static Layer
→ Global／Local Layered Costmap
← TF + LaserScan／PointCloud2 + Footprint + Filter
→ Master Costmap2D
→ Planner／Controller 进程内直接读取
→ Path／cmd_vel

Global Costmap 负责从全局视角回答“路从哪里走”，Local Costmap 负责从实时视角回答“下一步怎样安全地动”。

真正理解这两张图，关键不是记住 Topic 名字，而是分清三层边界：磁盘地图是静态资产，ROS Topic 是跨节点数据通道，Master Costmap 是规划和控制真正读取的运行时风险场。

机器人明明没撞上，速度为什么先被“截胡”？一份可落地的 Nav2 Collision Monitor 配置指南 ​

关键词：碰撞监视器、碰撞监控、Collision Monitor

机器人还没有真正碰到障碍物，/cmd_vel 却已经变小甚至归零，这不是规划器突然“改主意”，而可能是 Nav2 的 Collision Monitor 在速度出口前加了一道安全门。它不重新规划路径、不维护 Costmap，也不替代控制器；它接收控制器产生的 Twist 和传感器观测，在机器人坐标系中判断安全区域，再决定速度是原样放行、按比例缩小，还是直接清零。

本文以当前 checkout 中的 navigation2/nav2_collision_monitor 为事实基线，沿着 collision_monitor_node.cpp、polygon.cpp、三类 Source、Launch 和示例 YAML，整理一套可以落地的 Nav2 配置方法。重点不是把参数表抄一遍，而是说明参数怎样改变数据流、哪些配置看起来存在却没有真正启用，以及为什么速度平滑器、恢复行为和遥控链都可能让安全门失效。

一、先给结论：Collision Monitor 是速度安全门 ​

1.1 安全边界不是规划边界 ​

Collision Monitor 的输入是速度指令和传感器数据，输出是过滤后的速度指令。它不会搜索 Global Path，不会打分局部轨迹，也不会写入 Costmap。它关心的是“这条马上要送到底盘的速度，在当前观测下是否还允许”。

从源码看，传感器回调只保存最新消息；真正的安全判断由速度输入回调触发。每当 cmd_vel_in_topic 收到一帧 Twist，节点才读取各个有效 Source，把障碍物统一成二维点，再遍历配置的安全区域。

1.2 最终安全门应位于速度平滑之后 ​

标准 Nav2 通常把 Controller Server 的输出重映射为 /cmd_vel_nav，Velocity Smoother 再把它平滑成 /cmd_vel。如果 Collision Monitor 放在平滑器之前，平滑器仍可能在减速度约束下继续输出一小段速度；如果放在平滑器之后，最终发送到底盘的每一帧都要再经过安全区域判断。

因此推荐使用下面的数据流：

text
Controller Server / regulated_navigator
        ↓ /cmd_vel_nav
Velocity Smoother
        ↓ /cmd_vel_pre_collision
Collision Monitor
        ↓ /cmd_vel
controlpub 或底盘驱动

如果系统还运行 Behavior Server 的 Spin、BackUp 等恢复行为，恢复速度也必须汇入同一条安全门输入，或者先经过一个能够统一仲裁速度来源的 mux。否则控制器速度经过了 Collision Monitor，恢复速度却可以直接发布到最终底盘 Topic。

1.3 当前项目还没有自动接入这道安全门 ​

当前 nav2_regulated_modules 的导航分支是 /cmd_vel_nav → velocity_smoother → /cmd_vel → controlpub，但 Launch 没有启动 collision_monitor。因此只安装包或只修改参数 YAML，并不会让现有导航自动获得碰撞监控能力；必须把节点加入启动链，并明确它的输入输出 Topic。

当前 remote 模式还把键盘速度直接发往 /control_to_uart，它也不经过上述 Nav2 速度链。若希望遥控同样受到安全区域保护，就必须让遥控速度也经过统一的安全门，不能只启动一个监听 /cmd_vel_pre_collision 的 Collision Monitor。

二、Lifecycle 启动与参数重写 ​

2.1 包自带 Launch 启动了什么 ​

nav2_collision_monitor/launch/collision_monitor_node.launch.py 同时创建 Collision Monitor 和一个 Lifecycle Manager。Launch 内部把 lifecycle_nodes 设为 ['collision_monitor']，并将 autostart 设为 True，所以独立运行时会主动配置并激活节点。

独立启动可以使用：

bash
source /opt/ros/humble/setup.bash
source /path/to/nav2_demo/nav2_ws/install/setup.bash

ros2 launch nav2_collision_monitor collision_monitor_node.launch.py \
  params_file:=/absolute/path/collision_monitor.yaml \
  use_sim_time:=False

这里的 params_file 可以指向项目外部的专用配置，避免直接覆盖包内示例。实际机器人应使用 use_sim_time:=False；Gazebo 或 rosbag 场景才使用仿真时钟。

2.2 RewrittenYaml 会覆盖 use_sim_time ​

Launch 声明了 namespace、use_sim_time 和 params_file 三个参数，然后通过 nav2_common::RewrittenYaml 把 namespace 作为参数根键，并对 use_sim_time 做重写。这意味着命令行 Launch 参数的优先级高于 YAML 中的同名值。

例如 YAML 里写了：

yaml
use_sim_time: false

但命令行使用默认的 use_sim_time:=True，最终节点仍可能收到 True。配置仿真和实车时，必须同时检查 Launch 参数和参数文件。

2.3 不要让两个 Lifecycle Manager 管理同一个节点 ​

如果直接 Include 包自带的 Launch，它会启动自己的 Lifecycle Manager；如果又把 collision_monitor 添加到已有 lifecycle_manager_navigation 或 lifecycle_manager_regulated_modules 的 node_names，就会出现两个管理者同时操作一个 Lifecycle 节点的风险。

集成方式应在两种方案中选择一种：保留包自带 Launch，让它独立管理 Collision Monitor；或者只在主 Bringup 中创建 Collision Monitor，把它加入已有 Lifecycle Manager，同时不再启动包自带的管理器。

三、三类传感器怎样变成统一二维障碍点 ​

3.1 LaserScan 只保留有效射线端点 ​

Scan 使用 sensor_msgs::msg::LaserScan 和 SensorDataQoS。每条有效量测根据 angle_min 和 angle_increment 计算成传感器坐标系下的二维端点，再通过 TF 转到 base_frame_id。超出消息自身 range_min 到 range_max 的数据不会进入碰撞点集合。

它没有额外的角度参数，安全区域的覆盖范围由激光消息、传感器安装 TF 和 Polygon／Circle 几何共同决定。配置中的：

yaml
observation_sources: [scan]
scan:
  type: "scan"
  topic: "/scan"
  enabled: true

只有 scan 出现在 observation_sources 中，它才会被创建和处理。

3.2 PointCloud2 先做 TF 再做高度裁剪 ​

PointCloud 读取 x、y、z 三维字段，先把点变换到 base_frame_id，再用 min_height 和 max_height 筛选高度，最后把保留下来的点压缩成二维 x、y。这样做的原因是相机坐标系的 z 轴不一定与机器人基座坐标系重合。

典型配置为：

yaml
observation_sources: [scan, depth]
depth:
  type: "pointcloud"
  topic: "/camera/depth/points"
  min_height: 0.10
  max_height: 0.50
  enabled: true

点云越密，Polygon 点内判断和 APPROACH 仿真的计算量越高。工程上通常先在相机驱动或前置节点做体素下采样、距离裁剪和高度裁剪，再把较小的点集送入 Collision Monitor。

3.3 Range 会把一个扇区离散成一串点 ​

Range 订阅 sensor_msgs::msg::Range。一条 Range 消息携带一个距离和一个视场角，Collision Monitor 用 obstacles_angle 在扇区内生成多个障碍点。角度步长越小，弧线越密，碰撞覆盖更细，但每个速度回调需要处理的点也更多。

例如：

yaml
observation_sources: [front_range]
front_range:
  type: "range"
  topic: "/front_range"
  obstacles_angle: 0.0174533
  enabled: true

Range 消息自身的 min_range 和 max_range 仍然有效；超出传感器声明能力的量测不会被虚构成碰撞点。

3.4 超时和 TF 失败不会自动变成 STOP ​

每个 Source 都保存最新消息。source_timeout 判断消息时间戳与当前时间的差值，超过阈值就忽略该 Source。若传感器没有首帧、消息已经过期，或者 TF 查询失败，源数据都会被跳过。

这里有一个很容易被误解的边界：忽略过期数据不等于自动停车。没有有效碰撞点时，主节点默认动作仍然是 DO_NOTHING，输入速度可能继续透传。因此，底盘自身的速度超时看门狗、安全控制器或硬件急停仍不可省略。

四、Polygon、Circle 与真正生效的活动列表 ​

4.1 polygons 列表决定区域是否实例化 ​

Collision Monitor 不是看到 YAML 里有参数块就会加载它。节点先读取顶层 polygons 数组，再按数组中的名字查找 <name>.type 并创建 Polygon 或 Circle。

示例文件虽然定义了 PolygonStop、PolygonSlow 和 FootprintApproach，但顶层配置只有：

yaml
polygons: ["PolygonStop"]

因此只有 PolygonStop 会进入区域遍历。把未列入数组的区域内部 enabled: true 改成任何值，都不能让它开始工作。

4.2 Polygon 的顶点坐标属于机器人基座坐标系 ​

STOP 和 SLOWDOWN Polygon 需要一个扁平的双精度数组：

yaml
points: [x1, y1, x2, y2, x3, y3, x4, y4]

源码要求数组长度为偶数且至少包含四个顶点。顶点顺序必须沿区域边界排列，坐标原点是 base_frame_id，正 x 通常表示机器人前方，正 y 取决于机器人坐标约定。

4.3 APPROACH Polygon 使用动态 Footprint ​

当 Polygon 的 action_type 是 approach 时，它不再读取静态 points，而是订阅 footprint_topic。常见配置为：

yaml
FootprintApproach:
  type: "polygon"
  action_type: "approach"
  footprint_topic: "/local_costmap/published_footprint"
  time_before_collision: 2.0
  simulation_time_step: 0.1
  max_points: 1
  visualize: false
  enabled: true

这使 APPROACH 可以跟随机器人 footprint 的动态变化。STOP 和 SLOWDOWN 仍然使用 YAML 中的静态顶点。

4.4 Circle 用半径换取更低计算量 ​

Circle 读取必填的 radius，用平方距离判断点是否进入区域，不订阅动态 Footprint：

yaml
ApproachCircle:
  type: "circle"
  action_type: "approach"
  radius: 0.45
  time_before_collision: 2.0
  simulation_time_step: 0.1
  max_points: 1
  visualize: true
  polygon_pub_topic: "/collision_monitor/approach_circle"
  enabled: true

如果机器人可以近似为圆形，Circle 通常比通用 Polygon 更适合高频 APPROACH。

4.5 enabled 和 visualize 的职责不同 ​

enabled 决定区域是否参与安全判断，并且当前实现支持运行时动态切换。visualize 只决定是否发布 geometry_msgs::msg::PolygonStamped，它不会改变碰撞判定。关闭可视化不会关闭安全区域，打开可视化也不会创建未列入 polygons 的区域。

五、STOP、SLOWDOWN、APPROACH 如何争夺最终速度 ​

5.1 STOP：点数超过阈值就清零 ​

STOP 区域调用 getPointsInside() 统计进入区域的障碍点。当点数严格大于 max_points 时，processStopSlowdown() 把线速度和角速度都写成零，并将动作类型设为 STOP。

这意味着：

text
max_points = 0  -> 1 个以上障碍点触发
max_points = 3  -> 4 个以上障碍点触发

主循环发现已经是 STOP 后会提前结束区域遍历，后面的 SLOWDOWN 或 APPROACH 无法把零速度重新放大。

5.2 SLOWDOWN：比例作用于原始输入速度 ​

SLOWDOWN 使用：

text
safe_velocity = input_velocity × slowdown_ratio

slowdown_ratio: 0.3 的含义是输出原速度的 30％，而不是“减少 30％后剩下 70％”。它会同时缩放线速度和角速度。

多个 SLOWDOWN 区域同时成立时，不会把已经减速的结果再次串乘。每个区域都从本次输入速度独立生成候选，再由 Velocity::operator<() 比较 x²+y²+tw²，选择更小的候选。

5.3 APPROACH：用碰撞时间构造速度比例 ​

APPROACH 会在 time_before_collision 时间窗内预测机器人运动。如果预测到的碰撞时间为 collision_time，速度比例为：

text
safe_ratio = collision_time / time_before_collision
safe_velocity = input_velocity × safe_ratio

如果在当前姿态就已经达到碰撞阈值，碰撞时间为零，输出速度也会趋近于零。如果整个预测窗口内没有碰撞，函数返回负值，APPROACH 不产生候选速度。

5.4 最终仲裁不是简单的配置顺序 ​

STOP 有明确的短路优先级。SLOWDOWN 与 APPROACH 没有一个固定的“枚举优先级”，而是比较候选速度平方和，选择更保守的结果。这种比较能处理线速度和原地旋转同时存在的情况，但它不是制动距离、障碍物运动模型或各轴风险的完整安全证明。

六、APPROACH 的离散前向仿真到底算了什么 ​

6.1 projectState() 推进一个小时间步 ​

APPROACH 从机器人初始姿态 {0, 0, 0} 开始，每次按 simulation_time_step 推进 x、y 和 theta，同时旋转线速度方向。它假设输入 Twist 在一个小时间步内保持不变，再继续计算下一个姿态。

这不是 Costmap 重新规划，也不是把动态障碍物预测成新的轨迹。实现实际上是在预测的机器人坐标系中重新观察已有障碍点：机器人向前移动后，同一个障碍点在新车体坐标下的位置发生变化。

6.2 time_before_collision 是时间裕量，不是停车时间 ​

time_before_collision: 2.0 表示希望机器人始终至少保持两秒的预测碰撞时间。它不是“检测到障碍后延迟两秒停车”，也不是“停车后等待两秒再恢复”。

如果障碍物已经很近，碰撞时间可能只有 0.4 秒，APPROACH 会把速度缩放为 0.4 / 2.0 = 0.2。如果碰撞预测为负值，代表时间窗内没有碰撞，输入速度不被 APPROACH 改动。

6.3 步长越小不一定越安全 ​

减小 simulation_time_step 会让预测更细，但每个速度回调要执行更多次姿态推进、点坐标变换和区域判断。PointCloud2 点数、Footprint 顶点数、预测时间窗和仿真步长会共同决定计算量。

工程上应先用真实传感器频率、实际点数和 CPU 预算验证延迟，再选择步长。不要为了追求小数点级别的预测精度，把控制回调拖到传感器下一帧之后。

6.4 Polygon 和 Circle 是两种不同的性能选择 ​

Polygon APPROACH 适合需要精确表达机器人 footprint 的场景；Circle APPROACH 适合近似圆形的底盘，并且用半径平方判断，通常更快。两者都应该配合 visualize 观察区域是否与真实车体一致。

七、从最小可用到多传感器的 YAML 配置 ​

7.1 节点级参数决定速度和 TF 边界 ​

节点级参数位于 collision_monitor.ros__parameters 下：

  • use_sim_time：是否使用 /clock；实车通常为 false。
  • base_frame_id：区域坐标和传感器点转换目标，必须与真实 TF 一致。
  • odom_frame_id：时间补偿所使用的 TF Frame，通常是 odom，不是 /odometry Topic。
  • cmd_vel_in_topic：输入速度，例如 /cmd_vel_pre_collision 或 /cmd_vel_nav。
  • cmd_vel_out_topic：最终安全速度，例如 /cmd_vel。
  • transform_tolerance：TF 查询容忍时间，需覆盖传感器和 TF 发布延迟。
  • source_timeout：消息年龄阈值，建议根据传感器频率设置，而不是盲目使用很大的数值。
  • base_shift_correction：是否补偿传感器采样时刻到当前时刻的机器人运动。
  • stop_pub_timeout：进入零速度后继续发布零消息的时间，不是停车保持时间。

代码默认值和示例 YAML 不完全相同，最终以 Launch 传入的参数文件和命令行重写结果为准。

7.2 区域级参数决定安全动作 ​

顶层 polygons 先决定哪些名字会被创建；每个名字的参数块再决定几何和动作：

  • type：polygon 或 circle。
  • action_type：stop、slowdown 或 approach。
  • enabled：是否参与判断，当前支持运行时切换。
  • max_points：内点阈值，STOP／SLOWDOWN 使用严格大于判断。
  • points：静态 Polygon 顶点，按 x、y 交替排列。
  • radius：Circle 半径。
  • slowdown_ratio：SLOWDOWN 的速度缩放比例。
  • time_before_collision：APPROACH 的目标碰撞时间。
  • simulation_time_step：APPROACH 的离散步长。
  • footprint_topic：APPROACH Polygon 的动态 Footprint Topic。
  • visualize 和 polygon_pub_topic：区域可视化配置。

7.3 数据源级参数决定观测质量 ​

顶层 observation_sources 决定真正创建的数据源；每个数据源至少需要：

  • type：scan、pointcloud 或 range。
  • topic：传感器消息 Topic。
  • enabled：是否参与当前点集合。

PointCloud2 额外使用 min_height、max_height；Range 额外使用 obstacles_angle；LaserScan 没有包内额外参数。三类 Source 都会把结果变换成 base_frame_id 下的二维点。

7.4 一份可以作为起点的配置 ​

下面模板假设速度平滑器先输出 /cmd_vel_pre_collision，Collision Monitor 最终输出 /cmd_vel，机器人 TF 使用 base_link 和 odom：

yaml
collision_monitor:
  ros__parameters:
    use_sim_time: false
    base_frame_id: "base_link"
    odom_frame_id: "odom"
    cmd_vel_in_topic: "/cmd_vel_pre_collision"
    cmd_vel_out_topic: "/cmd_vel"
    transform_tolerance: 0.2
    source_timeout: 0.3
    base_shift_correction: true
    stop_pub_timeout: 0.5

    polygons: ["StopFront", "SlowFront"]

    StopFront:
      type: "polygon"
      points: [0.55, 0.30, 0.55, -0.30, 0.05, -0.30, 0.05, 0.30]
      action_type: "stop"
      max_points: 0
      visualize: true
      polygon_pub_topic: "/collision_monitor/stop_front"
      enabled: true

    SlowFront:
      type: "polygon"
      points: [0.90, 0.45, 0.90, -0.45, -0.20, -0.45, -0.20, 0.45]
      action_type: "slowdown"
      max_points: 2
      slowdown_ratio: 0.3
      visualize: true
      polygon_pub_topic: "/collision_monitor/slow_front"
      enabled: true

    observation_sources: ["scan"]
    scan:
      type: "scan"
      topic: "/scan"
      enabled: true

这个模板中的 StopFront.max_points: 0 表示一个有效点即可触发停车；SlowFront.max_points: 2 表示三个以上点才触发减速。实际阈值应根据传感器噪声、点密度和区域面积校准。

八、接入标准 Nav2 与当前规控链 ​

8.1 只有 Collision Monitor 的最小链路 ​

如果没有 Velocity Smoother，可以让 Controller Server 的输出直接进入 Collision Monitor：

yaml
cmd_vel_in_topic: "/cmd_vel_nav"
cmd_vel_out_topic: "/cmd_vel"

此时必须保证 Controller Server 不再同时向 /cmd_vel 发布，底盘只订阅过滤后的 /cmd_vel。

8.2 带 Velocity Smoother 的推荐链路 ​

如果使用标准 Nav2 或当前 nav2_regulated_modules 的速度平滑器，应让平滑输出改名为中间 Topic，再由 Collision Monitor 占有最终出口：

text
Controller: cmd_vel -> cmd_vel_nav
Velocity Smoother: cmd_vel -> cmd_vel_nav
Velocity Smoother: cmd_vel_smoothed -> cmd_vel_pre_collision
Collision Monitor: /cmd_vel_pre_collision -> /cmd_vel
Base or controlpub: subscribe /cmd_vel

这里的关键不是 Topic 名字本身，而是最终底盘速度只能有一个明确的安全发布者，不能让平滑器和 Collision Monitor 同时发布 /cmd_vel。

8.3 标准 Behavior Server 需要额外接线 ​

标准 Nav2 的 Behavior Server 恢复动作拥有自己的速度发布路径。若它直接发布最终 /cmd_vel，Collision Monitor 无法拦截这条旁路。正确做法是把恢复速度送到 /cmd_vel_pre_collision，或者通过一个统一速度 mux 把 Controller、恢复和遥控来源合成一条待过滤速度。

8.4 当前 nav2_regulated_modules 的 remote 分支需要单独考虑 ​

当前 remote 模式由键盘节点直接输出 /control_to_uart，导航分支的 velocity_smoother、controlpub 和 Collision Monitor 都不在这条路径上。如果安全要求覆盖遥控，必须重画遥控链；只给自动导航链加 Collision Monitor，不代表手动驾驶也受到同样保护。

九、五个最容易误判的配置边界 ​

9.1 参数块存在不等于实例启用 ​

PolygonSlow 写在 YAML 中，但不在 polygons 数组里，它不会被创建。pointcloud 写了 Topic，但不在 observation_sources 数组里，它也不会订阅。排查时先看活动列表，再看具体参数。

9.2 odom_frame_id 不是 /odometry ​

Collision Monitor 通过 TF 做时间补偿，不读取里程计消息 Topic。当前项目 Controller Server 和 CLOSED_LOOP Velocity Smoother 使用 /odometry，这不意味着 Collision Monitor 的 odom_frame_id 应改成 /odometry。这里应该填写实际 TF Frame，例如 odom。

9.3 source_timeout 不是失效即停车 ​

源数据过期、TF 查询失败或传感器还没有首帧时，该源会被忽略。若所有源都被忽略，节点不一定主动发布零速度。底盘命令超时、硬件安全控制器和独立急停仍然是必要的失效兜底。

9.4 stop_pub_timeout 不是障碍物清除时间 ​

进入 STOP 后，节点会在一段时间内重复发布零速度；超过 stop_pub_timeout 后，它可能停止重复发布零消息。这是发布心跳策略，不是“障碍物消失后多久恢复”，也不是“停车延迟”。底盘如果依靠周期性零速度维持看门狗，必须协调这个值。

9.5 Topic、QoS、TF 和时钟必须一起正确 ​

Topic 名称正确但 QoS 不兼容，仍然等于没有传感器数据；消息 Frame 正确但没有到 base_frame_id 的 TF，点也不会进入区域判断；仿真时钟和消息时间戳不一致，source_timeout 和时间变换也会出现假失效。Collision Monitor 的调参不能只盯着 YAML 数值。

9.6 这是 CPU 安全辅助层，不是硬实时认证防线 ​

包 README 明确说明该节点在 CPU 层运行，不提供硬实时安全认证。它适合补足普通 Costmap、规划器和控制器对突发障碍的响应，但不能替代安全额定激光、安全控制器、底盘急停和独立速度看门狗。

十、现场验证要沿着数据流闭环 ​

10.1 先验证 Lifecycle 和参数是否真的加载 ​

bash
ros2 lifecycle get /collision_monitor
ros2 param dump /collision_monitor

节点应处于 active，参数转储中应能看到实际的输入输出 Topic、活动区域和活动数据源。不要只查看原始 YAML，要查看运行时节点实际收到的参数。

10.2 再验证速度 Topic 的唯一性 ​

bash
ros2 topic info -v /cmd_vel_pre_collision
ros2 topic info -v /cmd_vel

确认平滑器是中间速度的唯一发布者，Collision Monitor 是最终 /cmd_vel 的唯一安全发布者，底盘或 controlpub 只订阅最终出口。

10.3 无障碍时验证透传 ​

在没有障碍物时记录输入和输出速度，确认没有区域误触发、没有比例被重复缩放，也没有由于 base_frame_id 或 TF 错误而丢失所有观测。

10.4 有障碍时验证三类动作 ​

让一个或多个传感器点进入 STOP 区域，确认输出为零；让点只进入 SLOWDOWN 区域，确认输出等于输入乘 slowdown_ratio；启用 APPROACH 后，逐步改变障碍距离和输入速度，观察输出是否随预测碰撞时间平滑变化。

10.5 故障场景必须单独测试 ​

bash
ros2 topic hz /scan
ros2 run tf2_ros tf2_echo odom base_link
ros2 topic echo /collision_monitor/stop_front

还应暂停传感器、制造 TF 暂时不可用、停掉 Collision Monitor、发送恢复速度和切换 remote 模式，确认底盘自身的超时停车与唯一速度出口仍然成立。

十一、总结：把安全门放对，比把参数写满更重要 ​

11.1 一句话理解整个包 ​

Collision Monitor 的完整主线是：传感器消息缓存最新快照，速度回调触发 Source 归一化，所有有效点进入机器人基座坐标系，Polygon／Circle 产生 STOP、SLOWDOWN 或 APPROACH 候选，主节点选择更保守的速度，最后把结果送到唯一底盘出口。

11.2 一套配置是否可靠，看四个问题 ​

  • 上游速度是否真的进入 cmd_vel_in_topic。
  • polygons 和 observation_sources 是否列出了真正想启用的实例。
  • 传感器 Frame、base_frame_id、odom_frame_id、消息时间和 QoS 是否一致。
  • Collision Monitor 是否位于所有自动、恢复和遥控速度来源的最终出口，并由底盘看门狗提供失效兜底。

参数不是越多越安全，图形也不是越复杂越安全。真正决定效果的是速度接线唯一、活动列表明确、传感器点能到达 base frame、阈值与点密度匹配，并且把 CPU 节点和硬件安全边界分开看待。

一条 Path，如何被 53 个函数炼成速度？逐函数拆解 Nav2 Controller Server ​

全局规划器只给出一条 Path，机器人并不会因此自动运动。真正持续读取位姿、观察局部障碍、调用控制算法、检查进度并发布速度的，是 nav2_controller。

本文以当前本地 nav2_controller 1.1.20 为实现基线，覆盖 53 个生产函数：main() 1 个，ControllerServer 21 个，两个 Progress Checker 共 12 个，三个 Goal Checker 共 19 个。测试函数和 pluginlib 注册宏不计入。

一、本包是控制任务容器，不是某一种局部算法 ​

1.1 输入、输出与包外边界 ​

上游通过 nav2_msgs/action/FollowPath 提供 Path、controller_id 和 goal_checker_id。运行期输入还包括 Odometry 速度、TF 机器人位姿、Local Costmap 和 SpeedLimit。输出是 cmd_vel、Action Feedback，以及成功、失败或取消终态。

本包不实现 DWB、RPP、MPPI 或 TEB。真正计算速度的是包外 nav2_core::Controller 插件；Costmap、TF、OdomSubscriber、SimpleActionServer、Lifecycle Manager 和 Velocity Smoother 也不在本包内。本包负责把这些对象装进同一控制闭环，并提供两个 Progress Checker 与三个 Goal Checker。

二、八个入口如何建立和销毁服务器 ​

2.1 main()、ControllerServer() 与析构函数 ​

main() 接收进程参数，调用 rclcpp 与 Spdlog 初始化，创建 ControllerServer，把节点基础接口交给 rclcpp::spin()，退出时关闭 ROS 2 和日志。它没有控制算法，只负责独立进程入口；组件方式则由文件末尾的注册宏交给包外 class_loader。

ControllerServer() 接收 NodeOptions，构造 Lifecycle 节点。它声明控制频率、三个 Odom 速度阈值、插件 ID、限速 Topic、失败容忍时间和是否发布零速度；同时建立 Progress Checker、Goal Checker、Controller 三个 pluginlib Loader，并创建名为 local_costmap 的 Costmap2DROS 对象。此时插件、订阅和 Action 尚未创建。

~ControllerServer() 是兜底清理路径，重置 Progress Checker，清空 Goal Checker 和 Controller 容器，停止 Costmap 线程。正常 Lifecycle cleanup 已经释放资源时，这些操作仍然安全。

2.2 on_configure() ​

输入是 Lifecycle transition，输出是 SUCCESS 或 FAILURE。函数读取插件列表与 Server 参数，必要时声明默认插件类型，配置包外 Local Costmap 并创建独立 NodeThread。

它用 pluginlib 创建一个 Progress Checker、多个 Goal Checker 和多个 Controller。Checker 的 initialize() 获得父节点和插件名，Controller 的 configure() 额外获得 TF Buffer 与 Costmap 共享指针。任一 pluginlib 创建异常都会让 configure 失败。

配置成功后，它创建包外 OdomSubscriber、Lifecycle cmd_vel Publisher、follow_path SimpleActionServer 和 SpeedLimit Subscription。节点进入 inactive，资源存在但还不接任务。

2.3 on_activate() 与 on_deactivate() ​

on_activate() 激活 Costmap、全部 Controller、速度 Publisher 和 Action Server，注册 Server 动态参数回调，再创建 bond。Progress Checker 与 Goal Checker 没有独立 activate 接口，它们在 initialize 后即可被服务器调用。

on_deactivate() 反向停止 Action、Controller 和 Costmap，然后调用 publishZeroVelocity()，再关闭 Publisher、注销参数回调并销毁 bond。零速度发布发生在 Publisher 停用之前，但仍要求 Topic 存在订阅者。

2.4 on_cleanup() 与 on_shutdown() ​

on_cleanup() 调用每个包外 Controller 的 cleanup()，清空 Controller 与 Goal Checker，清理 Costmap，并释放 Action、Odom、Costmap 线程、速度 Publisher 和限速 Subscription。当前实现没有显式 reset() Progress Checker，但后续重新 configure 会创建新实例。

on_shutdown() 只记录日志并返回成功，不编排额外停车或资源释放；停车主要依赖 deactivate、Action 异常路径和析构兜底。

三、四个函数如何接住 Goal 和 Path ​

3.1 findControllerId() 与 findGoalCheckerId() ​

两个函数都输入 Action Goal 中的字符串 ID，并通过引用输出本次使用的实例 ID。请求命中容器时直接选中；只有一个插件且请求 ID 为空时，才回退到唯一实例并打印一次警告。

非法的非空 ID 不会因为“只加载一个插件”而自动回退，而是返回 false。computeControl() 随后终止 Action。这与当前 Planner Server 在单插件环境下对错误 ID 的回退策略不同。

3.2 setPlannerPath() ​

输入是 nav_msgs::msg::Path。空 Path 抛出 PlannerException；非空 Path 调用包外当前 Controller 的 setPlan()，把末端 Pose 保存为 end_pose_，重置当前 Goal Checker，并复制到 current_path_。

该函数既建立 Controller 的跟踪输入，也建立 Goal Checker 的终点和 Feedback 的剩余路径基准。它不做 TF 变换，具体 Controller 如何把 Path 变到局部坐标系由插件自己决定。

3.3 computeControl() ​

这是 follow_path Action 的执行回调。函数入口用 lock_guard 持有 dynamic_params_lock_，锁会覆盖整个 Goal 生命周期。它读取当前 Goal，调用两个 ID 查找函数，再执行 setPlannerPath() 和 Progress Checker 的 reset()。

函数记录最近有效命令时间，并用 rclcpp::WallRate(controller_frequency_) 建立控制周期。循环检查 Action Server 是否 active、是否取消，再以 100 Hz 等待 Costmap current。这个等待没有超时，也没有循环内取消检查。

每周期调用 updateGlobalPath()、computeAndPublishVelocity() 与 isGoalReached()。控制频率错过时只告警并重置 Rate。捕获 PlannerException 或标准异常时发布零速度并终止 Action；正常到达后根据 publish_zero_velocity_ 决定是否停车，再设置 Action 成功。

3.4 updateGlobalPath() ​

它是抢占处理函数。没有 pending Goal 时无副作用；存在抢占时调用包外 SimpleActionServer 的 accept_pending_goal()，重新验证 Controller 与 Goal Checker ID，再用新 Path 调用 setPlannerPath()。

setPlannerPath() 会重置 Goal Checker，但 updateGlobalPath() 不会重置 Progress Checker。因此新 Path 继承旧任务的进度基准和计时，这是当前实现边界。

四、一个控制周期怎样产生速度和 Feedback ​

4.1 computeAndPublishVelocity() ​

该函数没有显式输入参数，输入全部来自成员与包外对象。它取得机器人 Pose，检查是否持续前进，读取 Odom，调用 Controller 插件，然后发布 Feedback 和速度。

包外 Controller 的 computeVelocityCommands() 接收当前 Pose、阈值化速度和当前 Goal Checker 指针，返回 TwistStamped。成功时更新 last_valid_cmd_time_。插件抛出 PlannerException 时，failure_tolerance_ 为正值或 -1.0 会暂时构造零速度；正值超时后重新抛错，-1.0 则可以无限容忍。

Feedback 的 speed 是本周期命令的平面线速度模长，不是 Odom 实测速度。distance_to_goal 先搜索当前 Pose 最近的 Path 索引，再由包外几何工具累计剩余路径长度，因此也不是到终点的直线距离。

4.2 getRobotPose() ​

输入是待写入的 PoseStamped 引用。函数调用包外 Costmap2DROS::getRobotPose()；失败返回 false，成功复制当前 Pose 并返回 true。它不直接操作 TF Listener，但 Costmap 内部使用自己的 TF Buffer 完成坐标获取。

4.3 getThresholdedVelocity() 与 getThresholdedTwist() ​

两个函数定义在头文件中。getThresholdedVelocity() 输入一个速度分量和阈值，绝对值大于阈值时保留原值，否则输出零。

getThresholdedTwist() 输入 nav_2d_msgs::msg::Twist2D，分别用 X、Y、Theta 阈值调用前一个函数，输出滤除微小噪声的 Twist。这个结果同时传给 Controller 与 Goal Checker，阈值过大可能让真实低速被视为静止。

4.4 publishVelocity() 与 publishZeroVelocity() ​

publishVelocity() 输入 TwistStamped，只取其中 Twist，转换为 geometry_msgs::msg::Twist。只有 Lifecycle Publisher active 且至少有一个订阅者时才真正发布 cmd_vel。

publishZeroVelocity() 没有输入，构造六个分量全为零的 TwistStamped，填写 Base Frame 和当前时间，再复用 publishVelocity()。它被取消、异常、deactivate 和可选成功停车路径调用。

4.5 isGoalReached() ​

函数先通过 getRobotPose() 获取当前 Pose，再读取并阈值化 Odom 速度。它用包外 nav_2d_utils::transformPose() 把 end_pose_ 变到 Costmap Global Frame，最后调用当前 Goal Checker 的 isGoalReached(current, goal, velocity)。

输出是 bool。false 让控制循环继续；true 让 computeControl() 退出循环。Goal Checker 决定的是任务完成条件，不计算速度。

五、两个回调怎样改变运行中的 Controller ​

5.1 speedLimitCallback() ​

这是 nav2_msgs::msg::SpeedLimit Topic 回调。输入包含数值与“百分比还是绝对值”标志。函数遍历全部 Controller，调用包外 setSpeedLimit()，不只更新当前实例。

Server 本身不裁剪 cmd_vel，各 Controller 插件负责解释和执行限速。没有实现限速语义的插件，其行为取决于插件自身。

5.2 dynamicParametersCallback() ​

输入是候选 Parameter vector，输出 SetParametersResult。名称含点号的参数被跳过，让插件自己的动态回调处理。Server 参数则对 dynamic_params_lock_ 执行 try_lock()；由于 computeControl() 整个任务期间持锁，FollowPath 正在执行时会返回失败。

成功获得锁后，它可更新 controller_frequency、三个 Odom 阈值和 failure_tolerance。每处理一个非插件参数就解锁一次，因此批量参数不是成员级事务；controller_frequency 也只会影响下一次创建 WallRate 的任务。publish_zero_velocity 和 speed_limit_topic 当前不在动态分支中。

六、SimpleProgressChecker 的七个函数 ​

6.1 初始化、检查与基准状态 ​

initialize() 输入父 Lifecycle 节点弱指针和插件名，取得 Clock，声明并读取 required_movement_radius 与 movement_time_allowance，注册插件动态参数回调。输出通过成员状态体现。

check() 输入当前 PoseStamped，用包外 poseToPose2D() 转换。没有基准或移动足够时调用 resetBaselinePose() 并返回 true；否则比较当前时间与允许时间，未超时返回 true，超时返回 false。

reset() 只把 baseline_pose_set_ 置为 false，下一次检查会重建基准。resetBaselinePose() 保存 Pose、当前时间和有效标志。

6.2 距离判断与参数回调 ​

isRobotMovedEnough() 输入当前 Pose2D，把它与基准 Pose 交给 pose_distance()，距离严格大于半径才算有进展。pose_distance() 计算 XY 差并用 std::hypot() 输出欧氏距离。

dynamicParametersCallback() 接收 Parameter vector，热更新移动半径和允许时间，始终返回成功。它没有独立互斥锁，与 check() 并发时的成员读写由当前执行模型承担。

七、PoseProgressChecker 的五个函数 ​

7.1 在平移之外承认旋转进度 ​

initialize() 先调用父类初始化，继承距离、时间和父类动态回调，再声明角度阈值并注册自己的回调。由于父类和子类各保存一个回调句柄，两组参数都能处理。

check() 与父类流程相同，但显式调用本类 isRobotMovedEnough()。该函数只要父类 pose_distance() 超过半径，或 poseAngleDistance() 超过角度阈值，就返回 true。

poseAngleDistance() 输入两个 Pose2D，用包外 angles::shortest_angular_distance() 计算最短角差并取绝对值。dynamicParametersCallback() 只处理 required_movement_angle，并返回成功。

八、三个 Goal Checker 的十九个函数 ​

8.1 SimpleGoalChecker 的六个函数 ​

SimpleGoalChecker() 设置 XY、Yaw 容差、stateful、对称朝向和平方容差默认值。initialize() 声明并读取这些参数，缓存 XY 容差平方并注册动态回调。reset() 让 check_xy_ 恢复 true。

isGoalReached() 输入当前 Pose、目标 Pose 和速度，但本类不使用速度。它先比较 XY 平方距离；stateful=true 时，XY 一旦达标就不再复查。随后用包外 TF 和 angles 工具检查 Yaw；对称模式还接受目标朝向加 180°。

getTolerances() 输出位置与朝向容差，速度字段写入无效哨兵。参数回调更新 XY、Yaw、stateful 与对称朝向，并在 XY 改变时同步平方缓存。

8.2 StoppedGoalChecker 的五个函数 ​

StoppedGoalChecker() 在父类默认值上增加平移和旋转停稳阈值。initialize() 先调用父类初始化，再声明停稳参数并注册派生类回调，因此父类几何参数和本类速度参数都可热更新。

isGoalReached() 输入当前 Pose、目标 Pose 与 Odom Twist。父类几何判定失败就返回 false；通过后，角速度绝对值与平面线速度模长还必须分别低于阈值。

getTolerances() 先取得父类 Pose 容差，再覆盖线速度与角速度容差。参数回调更新两个停稳阈值。

8.3 PositionGoalChecker 的八个函数 ​

PositionGoalChecker() 设置 XY 容差、平方缓存、stateful 和位置锁存默认值；~PositionGoalChecker() 是默认析构函数，不增加资源操作。initialize() 声明 XY 与 stateful 参数，读取初值、更新平方缓存并注册回调。reset() 清除 position_reached_。

isGoalReached() 忽略速度与目标朝向，只计算 XY 平方距离。stateful 模式下，一旦位置达标，后续调用直接返回 true。getTolerances() 输出 XY 容差，把不参与判断的字段设置为无效值或单位四元数。

setXYGoalTolerance() 是直接 C++ 接口，同时更新容差和平方缓存。参数回调完成同样更新，并可切换 stateful。

九、从故障现象反推责任边界 ​

9.1 控制闭环的分层判断 ​

Action 拒绝先检查 Controller ID、Goal Checker ID 与空 Path；没有速度再检查 Lifecycle active、Costmap current、TF、Odom、Progress Checker 和包外 Controller 异常；到点不停或提前成功则检查 Goal Checker、Odom 阈值与 stateful；速度发布后机器人不动则继续查 Velocity Smoother、Topic remap 和底盘驱动。

这 53 个函数的核心价值不是实现某一种控制公式，而是把路径执行的状态、数据和插件边界固定下来。只有先判断故障属于 Server、Checker、Controller 插件还是速度下游，调参和源码修改才不会找错层。

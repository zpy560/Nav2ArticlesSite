一条 /cmd_vel 是怎样诞生的？从 entry.launch.py 拆解 Nav2 全数据流 ​

myworld_bringup/launch/entry.launch.py 看起来只有一百多行，但它不是一个普通的“启动脚本”。它是整个仿真导航系统的装配入口：Ignition Gazebo、ROS 2 bridge、机器人模型、地图与 AMCL、Nav2 行为树、全局规划、TEB 局部控制、速度平滑和 RViz，都从这里被串成一个闭环。

本文不按文件逐行解释，而是沿着数据真正流动的方向，回答三个问题：数据从哪里来，经过哪些节点，最后如何变成机器人左右轮的运动。

一、entry.launch.py 到底启动了什么 ​

入口首先解析三个顶层参数：

  • use_sim_time=true：所有节点使用 /clock 仿真时间。
  • world_name=myworld2：目前只声明，没有参与 world 文件选择。
  • use_rviz=true：控制 RViz 是否启动。

随后它设置 IGN_GAZEBO_RESOURCE_PATH，让 Ignition 能找到系统模型和 myworld_bringup/models 下的资源；设置 IGN_PARTITION=myworld_bringup，隔离当前 Ignition 通信域；最后用 ign gazebo -r -v 3 world_only.sdf 启动仿真。

入口本身还启动 robot_state_publisher、robot_description_publisher.py 和 RViz，并包含三个子 launch：

1.1 ros_ign_bridge.launch.py ​

连接 Ignition Transport 与 ROS 2 topic。

1.2 localization_launch.py ​

启动 map_server、AMCL 和定位生命周期管理器。

1.3 navigation_launch.py ​

启动 Nav2 导航服务器和导航生命周期管理器。

这里的关键设计是“入口负责装配，子 launch 负责领域”。仿真、定位、导航分别保持独立，而 params/myworld2.yaml 是定位与导航共享的参数源。

二、仿真数据如何进入 ROS 2 ​

Ignition 中的 diffbot 模型包含差速驱动、里程计、关节状态、激光雷达和 IMU 等系统插件。它们产生的是 Ignition Transport 消息，Nav2 不能直接消费，因此需要 ros_gz_bridge/parameter_bridge 做双向类型转换。

桥接方向必须看清：

  • ROS 2 → Ignition：/cmd_vel，类型从 geometry_msgs/msg/Twist 转为 gz.msgs.Twist。
  • Ignition → ROS 2：/clock、/odom、/odom/tf、/joint_states、/scan、/scan/points、/imu、相机图像和相机内参。
  • /odom/tf 在 bridge 中 remap 为 tf，进入 ROS 2 TF 通道。

因此 bridge 是整个闭环的“协议边界”：一边是仿真传感器和执行器，另一边是 Nav2 能够理解的标准 ROS 2 消息。

三、地图、AMCL 与 TF 如何组成定位链 ​

localization_launch.py 使用 RewrittenYaml 把入口传入的地图路径和 use_sim_time 写入临时参数视图，然后启动：

  • map_server：读取 models/myworld2/myworld2.yaml 及其栅格图，发布 /map。
  • amcl：消费 /map、/scan 和 TF，估计机器人在地图中的位姿。
  • lifecycle_manager_localization：按顺序 configure、activate 两个生命周期节点。

完整坐标链由三部分拼起来：

text
AMCL                         Ignition odometry          robot_state_publisher
map -> odom                  odom -> base_footprint     base_footprint -> base_link -> base_scan

最终 Nav2 查询的是：

text
map -> odom -> base_footprint -> base_link -> base_scan

当前仿真机器人在 world_only.sdf 中以 x=-3.071, y=3.583, yaw=-pi/2 生成，AMCL 参数中的初始姿态也采用相同数值。这两处必须一致，否则仿真真值与定位初值会出现固定偏差。

需要特别注意：entry.launch.py 向 localization_launch.py 传入的 localization_x/y/z/yaw 等参数，子 launch 当前并未声明或读取。它们不会改变 AMCL 初始姿态，真正生效的是 myworld2.yaml 中的 amcl.initial_pose。

四、同一份激光如何生成两张代价地图 ​

Nav2 同时维护 global costmap 和 local costmap，但两者目标不同。

global costmap 工作在 map 坐标系，组合 StaticLayer、ObstacleLayer 和 InflationLayer：静态地图提供长期环境结构，/scan 更新实时障碍，TF 提供机器人位姿。它是全局规划器搜索路径的空间。

local costmap 工作在 odom 坐标系，是 3 m × 3 m 的 rolling window，更新频率 5 Hz。VoxelLayer 使用 /scan 标记和清除附近障碍，InflationLayer 扩张安全距离。它服务于 controller 和 behavior 的局部碰撞判断。

两张图都使用 robot_radius=0.28 m。当前 TEB 自身的圆形 footprint 半径为 0.22 m，两者并不一致：TEB 优化阶段可能认为某些间隙可通行，但 costmap 的碰撞检查更保守。调参时应明确这是有意安全裕量，还是需要统一的模型误差。

五、导航目标如何变成全局路径 ​

RViz 或上层系统发送 NavigateToPose 后，真正接收任务的是 bt_navigator。它加载行为树，在树中调用规划、平滑、控制和恢复 Action。

当前 planner_server 同时加载 Navfn、Smac 2D、Hybrid-A*、Lattice 和 Theta* 等插件，但自定义参数 selected_planner=GridBasedAstar 会固定选择 nav2_navfn_planner/NavfnPlanner，并设置 use_astar=true。

规划器的输入是当前位姿、目标位姿和 global costmap，输出是 map 坐标系的 nav_msgs/msg/Path。路径可交给 smoother_server 的 SimpleSmoother 做几何平滑，再通过行为树黑板传给 FollowPath。

如果规划或控制失败，行为树会调用 behavior_server 的 Spin、BackUp、DriveOnHeading、AssistedTeleop 或 Wait 等恢复行为，然后决定重试、重新规划或终止。

六、TEB 如何把路径变成速度 ​

controller_server 接收 FollowPath Goal。当前 bt_navigator.selected_controller=TEB，因此实际调用 teb_local_planner::TebLocalPlannerROS。

TEB 每个控制周期主要完成：

6.1 保存并裁剪全局路径 ​

保存并裁剪已经走过的全局路径。

6.2 转换局部路径坐标系 ​

把局部路径变换到 local costmap 的 odom 坐标系。

6.3 提取障碍物与 Via Points ​

从 local costmap 提取障碍物，并生成路径 via points。

6.4 构建轨迹图结构 ​

用位姿顶点和时间间隔顶点表示轨迹。

6.5 执行 g2o 联合优化 ​

构建 g2o 图，联合优化障碍距离、速度、加速度、时间、路径长度和非完整运动学。

6.6 检查并输出速度 ​

检查优化发散和 footprint 碰撞，从轨迹前端计算速度指令。

controller_server 以 20 Hz 运行，并把内部 cmd_vel remap 为 /cmd_vel_nav。velocity_smoother 再以 20 Hz 接收该指令，按照最大速度、加速度和减速度约束平滑，输出最终 /cmd_vel。

bridge 把 /cmd_vel 转给 Ignition DiffDrive 插件，插件计算左右轮运动；仿真随后产生新的 /odom、TF 和 /scan。这些反馈再次进入定位、代价地图和控制器，闭环形成：

text
目标 -> 规划 -> 路径 -> TEB -> /cmd_vel_nav -> 速度平滑 -> /cmd_vel
     -> DiffDrive -> /odom + TF + /scan -> 定位/代价地图/TEB

七、生命周期和时间是两条隐形主线 ​

系统能否工作，不只取决于 topic 是否存在。

7.1 生命周期 ​

定位管理器负责 map_server 和 AMCL；导航管理器负责 controller、smoother、planner、behavior、bt_navigator、waypoint_follower 和 velocity_smoother。只有节点完成 configure 并进入 active，Action、publisher 和插件才真正可用。

7.2 仿真时间 ​

Ignition 发布 /clock，bridge 转为 ROS 2 Clock，所有配置了 use_sim_time=true 的节点据此计算 TF 时间、控制周期、传感器时间戳和 Action 超时。缺失 /clock 时，系统可能“节点都在，但数据永远对不上时间”。

八、这条数据流的核心结论 ​

entry.launch.py 的价值不在于启动节点数量，而在于建立五个边界：

8.1 Ignition 与 ROS 2 之间的消息边界 ​

8.2 map、odom、base_footprint 之间的坐标边界 ​

8.3 Global Costmap 与 Local Costmap 之间的规划尺度边界 ​

8.4 行为树调度与 Planner／Controller 插件之间的算法边界 ​

8.5 /cmd_vel_nav 与最终 /cmd_vel 之间的速度安全边界 ​

理解这五个边界后，排查 Nav2 问题就不再是“看哪个节点报错”，而是沿数据链逐段验证：时钟是否前进、TF 是否连通、传感器坐标是否正确、代价地图是否更新、规划器是否返回路径、控制器是否输出速度、bridge 是否把速度送到底盘。完整数据流，本身就是最有效的调试地图。

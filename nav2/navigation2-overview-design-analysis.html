Nav2 为什么要把导航拆成任务？拆解 Navigation 2 Overview 的任务架构、环境模型与 Behavior Tree ​

导航系统真正难的地方，往往不是把 A*、DWA 或某个控制器跑起来，而是让一套系统能够持续适应不同的地图、机器人、任务、部署方式和故障场景。2018 年的 Navigation_2_Overview.pdf 正是在回答这个问题：Nav2 是否应该只是“规划器加控制器”，还是应该成为一套可组合的机器人任务执行平台？

本文先解释这份设计稿想解决什么问题，再沿着 Command Chain、Task Hierarchy、Environmental Model、ROS Action 和 Behavior Tree 展开完整数据流，最后对照当前 checkout 中的 bt_navigator、planner_server、controller_server、Costmap 和组合式启动方式，区分设计愿景与现行实现。

一、先定位这份 PDF：它是架构愿景，不是算法说明 ​

1.1 设计稿的时间和范围 ​

这份 PDF 位于 navigation2/doc/design/Navigation_2_Overview.pdf，共 13 页，封面时间是 2018-08-02。第 11 页记录的是当时的研发状态，第 13 页的 TaskServer<CommandMsg, ResultMsg> 还是实现草图，因此阅读时必须把“设计目标”“早期实现”和“当前 Nav2”分开。

PDF 第 2 页把目标场景从二维仓库机器人扩展到带高程的搜索救援机器人、多层建筑室内机器人、校园配送机器人，甚至把无人机三维导航列为 Stretch Target。这些场景的共同点不是都使用同一种算法，而是都需要任务、环境、运动模型和执行状态之间保持清晰边界。

1.2 A* 和 DWA 只是验证样例 ​

第 10～11 页用 AStar 和 Dwa 展示从导航任务到规划、控制的调用关系，并记录了当时对 A* 和 DWA 的 ROS 2 移植工作。它们是当时用于验证架构的算法样例，不是这份设计稿最重要的结论。

真正重要的问题是：如果明天把 A* 换成 Smac，把 DWA 换成 MPPI，把差速底盘换成 Ackermann，把“导航到目标点”扩展成“取货、乘梯、对接、交付”，上层任务代码是否仍然可以保持稳定？

二、设计起点：从固定导航栈转向任务执行平台 ​

2.1 传统耦合边界在哪里 ​

传统导航栈很容易形成一条过于紧密的调用链：任务逻辑直接调用规划器，规划器和控制器直接依赖某种地图表示，控制器再直接连接某一种机器人底盘。恢复行为则经常散落在这些模块内部，导致上层很难判断到底是哪一层失败。

这种结构的直接后果是，算法替换、地图替换、机器人替换和任务扩展会相互影响。一个看似只改变控制器的需求，可能需要同时修改参数、插件加载、任务状态机和异常处理。

2.2 四个核心抽象 ​

这份 PDF 实际上提出了四个互相配合的抽象：

  • Task：用“导航到目标”“计算路径”“跟踪路径”“恢复”这样的业务语义组织功能。
  • ROS Action：用 Goal、Feedback、Result 和 Cancel 定义长时间异步任务的通信契约。
  • Environmental Model：把感知、预测、建图、定位等输入封装成任务需要的环境语义。
  • Behavior Tree：在任务变复杂时，负责组合子任务、重试、恢复、抢占和条件分支。

其中 Task 是架构语义，Action 是通信边界，Plugin 是一种实现手段，Behavior Tree 是一种编排手段。把这四者混为一谈，就会误解 PDF 的设计目标。

2.3 从“算法调用”变成“任务契约” ​

设计稿希望上层只依赖稳定的任务契约：

text
ComputePathToPose：输入起点和终点，输出 Path
FollowPath：输入 Path，输出执行结果
NavigateToPose：输入目标位姿，协调规划、控制和恢复

上层不需要知道下层究竟使用 A*、Dijkstra、DWA、MPPI 还是其他算法。只要输入、输出、取消和失败语义稳定，内部实现就可以替换。

三、两张平面：Command Chain 与 Environmental Model ​

3.1 Command Chain 负责“要做什么” ​

PDF 第 5～7 页的高层架构，可以理解为一条垂直的任务指挥链：

text
Robot Management
        ↓
Mission Planning
        ↓
Mission Execution
        ↓
Tasks
        ↓
Robot

Robot Management 和 Mission Planning 负责产生任务计划，Mission Execution 负责执行计划，Tasks 负责把任务进一步拆成可以执行和监控的子任务，Robot 是最终动作执行者。

这条链条解决的是控制问题：当前任务是什么，应该调用哪个子任务，哪个子任务失败后应该恢复还是终止，新的 Goal 到达后是否抢占当前任务。

3.2 Support Infrastructure 负责提供环境事实 ​

Perception、Prediction、Mapping 和 Localization 不属于某个具体导航任务，它们是支持基础设施。它们不断产生环境信息，再由 Environmental Model 或相应的服务接口提供给任务层。

这使任务逻辑不必直接依赖某个激光雷达 Topic、某个地图文件格式或某个预测算法的内部对象。任务需要的是“当前有什么障碍”“目标可能移动到哪里”“这块区域是否安全”，而不是传感器数据在内存中具体长什么样。

3.3 Environmental Model 负责抽象和封装 ​

PDF 第 8～9 页把 Environmental Model 描述成环境知识的聚合层，同时强调两个关键词：Abstraction 和 Encapsulation。

Abstraction 表示任务看到的是高层语义，例如对象信息、对象跟踪信息、对象预测信息、安全区域和静态地图。Encapsulation 表示这些信息的内部表示可以变化，任务不需要知道它们来自 OccupancyGrid、点云、对象列表、预测轨迹还是远程服务。

这里最重要的判断是：Environmental Model 不应该被理解成一张“什么都塞进去”的巨型地图。它更像面向任务的语义访问层，负责隐藏数据来源和内部表示，同时给出稳定的查询接口。

四、任务层级如何组合执行 ​

4.1 Task 是有生命周期的语义单元 ​

一个 Task 不只是一个同步函数，它通常具有 Goal、执行状态、Feedback、Result、Cancel、Failure 和 Recovery。它还可以调用其他 Task，因此可以构成父子层级。

例如 NavigateToPoseTask 不必亲自实现路径搜索和速度计算，它只需要协调 ComputePathToPoseTask 和 FollowPathTask，然后把子任务结果转换成自己的导航结果。

4.2 Mission 到 Robot 的任务树 ​

PDF 第 10 页给出了最清晰的示意：

text
MissionExecutionTask
        ↓
NavigateToPoseTask
        ├── ComputePathToPoseTask
        └── FollowPathTask
                ↓
              Robot

MissionExecutionTask 的输入是 MissionPlan，它可以包含多个导航任务，也可以包含对接、等待、开门和乘梯等非导航任务。NavigateToPoseTask 接收目标位姿，先获得 Path，再把 Path 交给路径跟踪任务。

这种层级的价值在于，任务可以复用。一个“去充电桩”的任务可以复用“导航到目标点”，一个“配送到房间”的任务可以复用“取货、导航、交付、返回”这些更小的任务。

4.3 简单代码、状态机和 Behavior Tree ​

设计稿没有规定所有 Task 都必须使用 Behavior Tree。它给出了三种协调方式：

  • 简单任务使用手写逻辑。
  • 中等复杂任务使用状态机。
  • 需要条件分支、循环、恢复、并行或动态抢占时使用 Behavior Tree。

Behavior Tree 的位置是任务编排器，而不是全局规划器或局部控制器。它决定何时调用规划、何时调用控制、何时执行恢复，以及何时把失败向上返回。

4.4 Recovery 也是 Task ​

恢复行为被提升为正式任务后，清理 Costmap、旋转、后退、等待、重新规划就不再是某个函数内部的隐藏分支，而是可以单独配置、组合、测试和观测的节点。

这也是为什么 PDF 强调“把恢复行为作为任务或 ROS Action”：恢复过程同样需要取消、超时、反馈和最终结果。

五、从 Goal 到 cmd_vel 的数据闭环 ​

5.1 外部 Goal 进入 Mission 或 NavigateToPose ​

在 PDF 的理想链路中，外部管理器发送 ExecuteMissionCommand(MissionPlan)，Mission Execution 再发送 NavigateToPoseCommand。这说明高层任务和底层导航之间也是异步协议关系，而不是直接调用 C++ 函数。

当前 Nav2 的 NavigateToPose.action 仍然保留了类似的边界。它的 Goal 是 geometry_msgs/PoseStamped pose 和 string behavior_tree，Feedback 包含当前位姿、导航时间、预计剩余时间、恢复次数和剩余距离。

因此当前调用可以表达两层意图：

  • pose 表示机器人要去哪里。
  • behavior_tree 表示这次导航应该采用哪套任务编排逻辑。

5.2 ComputePathToPose 产生 Path ​

Behavior Tree 的 ComputePathToPose 节点从 Blackboard 读取目标和 planner_id，向 compute_path_to_pose Action Server 发送 Goal。当前 Action 的输入包括 goal、start、planner_id 和 use_start，结果是 nav_msgs/Path 与规划耗时。

Planner Server 收到 Goal 后，需要完成 Costmap 有效性检查、起点获取、坐标变换、规划器选择、路径生成、路径合法性验证和 Result 发布。源码中的 PlannerServer::computePlan() 就是这一层的任务服务器执行入口。

Planner Server 对外提供 ROS Action，对内通过 Pluginlib 加载 nav2_core::GlobalPlanner。因此上层看到的是统一的 Path 契约，内部仍可以使用不同的规划器实现。

5.3 FollowPath 把 Path 变成速度 ​

规划成功后，Path 被写回 Behavior Tree Blackboard，FollowPath 节点读取 Path，并发送包含 path、controller_id 和 goal_checker_id 的 Action Goal。

Controller Server 收到 Goal 后选择控制器和目标检查器，保存全局 Path，进入控制周期。每个周期获取机器人 Pose、里程计和局部 Costmap，调用当前 Controller 的 computeVelocityCommands()，再把结果发布为速度指令。

这条链路的接口责任非常清楚：

层级主要输入主要输出责任
bt_navigatorPose、Behavior Tree子 Action Goal任务编排
planner_server起点、终点、Planner ID、Costmapnav_msgs/Path全局路径计算
controller_serverPath、Pose、里程计、局部 Costmapcmd_vel高频速度计算
Robot速度指令、底盘状态里程计、传感器数据物理执行与反馈

5.4 Feedback、Result、Cancel 和 Recovery 返回上层 ​

底层控制器的速度、剩余距离和执行状态可以形成 Feedback，Planner 和 Controller 的成功、失败、取消可以形成 Result，任务管理器据此决定继续、重试还是终止。

取消方向与数据方向相反。上层取消导航后，Behavior Tree 需要取消当前 Action，Controller Server 需要停止控制循环并发布零速度，Planner Server 则需要终止当前规划请求。

当前 BtActionNode 的通用实现已经包含异步发送 Goal、等待服务、接收 Result、处理 Feedback 以及在 halt() 中取消 Action 的逻辑。这正是 PDF 所描述的“长时间任务通信边界”的现行演化。

六、2018 设计与当前 Nav2 源码如何对应 ​

6.1 MissionExecutionTask 演化为 BT Navigator 和上层任务系统 ​

PDF 中的 MissionExecutionTaskServer 是一个明确的高层任务服务器，输入是 MissionPlan。当前 Nav2 核心并没有一个完全同名、覆盖所有业务任务的通用 Mission Execution Server。

当前更接近的组合是：bt_navigator 负责 NavigateToPose 和 NavigateThroughPoses，Behavior Tree 负责导航内部编排，Waypoint、Route 或外部应用负责更高层任务。充电、开门、乘梯、配送等任务通常仍需要应用层或自定义 BT 节点加入。

因此，PDF 讨论的是“Nav2 可以成为任务执行引擎”的方向，而当前核心更多提供“导航任务执行器”和可扩展的 BT 入口。

6.2 NavigateToPoseTask 演化为 ROS Action 加行为树 ​

当前 NavigateToPose.action 的 behavior_tree 字段允许每个 Goal 指定行为树文件。NavigateToPoseNavigator::goalReceived() 会读取该字段，加载行为树并初始化目标。

这与 PDF 中“一个任务可以由不同的任务计划驱动”的思想一致。变化在于，早期设计中任务计划可能是一个更抽象的 MissionPlan 或 Command 消息，当前实现中常见形式是 Behavior Tree XML 加 Blackboard 数据。

6.3 ComputePathToPose 和 FollowPath 保留了任务边界 ​

当前 Planner Server 和 Controller Server 都以 ROS Action 作为外部接口：

text
BT ComputePathToPose
        ↓ Action
planner_server
        ↓ Pluginlib
GlobalPlanner

BT FollowPath
        ↓ Action
controller_server
        ↓ Pluginlib
Controller

因此，PDF 中“通过语言无关的 ROS Node 和 Action 取代直接 C++ API 调用”的目标，在外部模块边界上已经得到实现。但当前高频算法内部仍使用 C++ Plugin，这是一种工程折中，不应描述成“当前 Nav2 已经完全取消 Plugin”。

6.4 Environmental Model 以分布式能力部分落地 ​

当前 Nav2 没有一个统一的全局 EnvironmentalModel 节点，把所有地图、感知、预测和语义对象集中到一个服务里。它的能力被分散在 Costmap、TF、Map Server、定位节点、传感器输入、Costmap Filters、Route 和各类 Action／Service 中。

Costmap 负责构建二维环境代价，StaticLayer 接收 OccupancyGrid，VoxelLayer 用体素保存三维障碍信息，Costmap Filters 负责禁行、限速和优选车道等空间语义。这些都是 PDF 中“环境信息抽象”的部分实现，但还不是一个统一的环境知识接口。

6.5 TaskServer 是历史草图和测试遗留的交界 ​

PDF 第 13 页的通用 TaskServer<CommandMsg, ResultMsg> 体现了早期设计对异步执行、取消和 Result 设置的关注。当前生产代码主要使用 ROS 2 Action Server、BtActionServer、Planner Server 和 Controller Server。

当前仓库的 nav2_system_tests/src/dummy_planner 和 dummy_controller 中仍可以检索到 ComputePathToPoseTaskServer、FollowPathTaskServer 和 Command 类型。这些名称说明早期任务接口曾参与系统测试，但它们不应替代对当前生产入口 planner_server、controller_server 和 nav2_msgs/action 的判断。

七、这套设计为什么值得保留 ​

7.1 算法和机器人可以替换 ​

只要 ComputePathToPose 和 FollowPath 的语义契约稳定，上层就不必关心使用的是 A*、Smac、DWA、RPP、MPPI 还是其他算法。机器人从差速、全向切换到 Ackermann 时，也可以把运动学差异留在规划器、控制器和底盘适配边界内。

这比把“某个算法类的 C++ 方法”直接暴露给任务层更容易维护，因为替换对象被限制在明确的接口后面。

7.2 导航可以和非导航任务组合 ​

真实机器人任务通常不是“导航到一个 Pose 后结束”，而是：

text
取货
  → 导航到交付点
  → 对接
  → 等待工艺完成
  → 导航到充电点
  → 充电

如果每个动作都具备 Goal、Feedback、Result、Cancel 和 Failure 语义，就可以把导航、对接、开门、乘梯、充电和工艺等待放进同一套任务编排模型。

7.3 恢复行为可复用、可观测 ​

恢复行为成为 Task 或 Action 后，系统可以清楚记录恢复发生在哪个子任务、执行了多少次、是成功后重试还是最终失败。它也可以被不同导航任务复用，而不必在每个导航函数中重复实现。

当前默认行为树中的 RecoveryNode、ClearEntireCostmap、Spin、Wait 和 BackUp，就是这种思想的具体体现。

7.4 支持多种部署形态 ​

ROS Node 和 Action 让任务、规划、控制和环境服务能够独立部署，也允许把多个节点组合进同一进程。当前 navigation_launch.py 同时支持独立 Node 和 ComposableNode，说明“分布式边界”和“进程内优化”可以同时存在。

7.5 更容易测试和定位故障 ​

清晰的任务边界让测试可以替换真实规划器和控制器，分别验证任务编排、Action 状态、恢复逻辑和算法结果。出现失败时，也更容易区分：

  • Goal 是否被接受。
  • Behavior Tree 是否加载成功。
  • Planner 是否返回有效 Path。
  • Controller 是否生成有效速度。
  • Robot 是否真正执行并产生里程计。

八、不能忽略的工程边界 ​

8.1 Action 边界会带来通信和状态管理成本 ​

把所有函数都拆成独立 Action 并不一定更好。高频控制循环需要稳定的周期和较低的延迟，当前 Nav2 把 Controller Plugin 留在 controller_server 内部，就是为了避免每个控制周期都跨 ROS 通信边界。

Action 还会引入 Goal 接受、抢占、取消、超时、Result 顺序和旧回调隔离等状态管理问题。接口越多，系统越需要统一的生命周期和错误语义。

8.2 Environmental Model 需要时间和坐标一致性 ​

感知、预测、地图和定位信息的更新频率不同，时间戳不同，坐标系也可能不同。如果环境模型只做数据转发而不定义时间、坐标、置信度和冲突处理规则，任务层得到的“统一语义”仍可能是不一致的。

因此，Environmental Model 的价值不在于把所有数据集中起来，而在于定义任务真正需要的稳定语义和有效性边界。

8.3 Behavior Tree 需要控制复杂度 ​

Behavior Tree 能表达重试、并行、恢复和动态分支，但树过大后也会变成新的难以维护对象。简单任务仍然应该使用直接逻辑或小型状态机，只有任务关系确实复杂时才引入更大的行为树。

8.4 抽象不等于自动获得三维能力 ​

PDF 把无人机三维导航列为 Stretch Target，说明架构希望保留扩展空间，但三维地图、六自由度运动模型、三维碰撞检查、轨迹优化和飞控接口仍然需要专门实现。把地图字段从二维换成三维，并不能自动得到可飞行路径。

九、结论：Nav2 的核心价值是“可编排的导航能力” ​

这份 PDF 最值得保留的不是某个具体算法，而是下面这条分层关系：

text
环境事实
    ↓
Environmental Model
    ↓
Task Hierarchy
    ↓
Behavior Tree / State Machine
    ↓
ROS Action
    ↓
Planner / Controller / Recovery
    ↓
Robot

它把导航从“规划器加控制器”提升成了“面向任务的执行框架”：任务层决定做什么，环境模型提供世界知识，Action 提供稳定边界，Behavior Tree 组织复杂行为，Planner 和 Controller 负责具体算法，Robot 完成物理执行。

当前 Nav2 并没有完全照搬 PDF 中的通用 MissionExecutionTaskServer 和统一 Environmental Model，也没有完全取消内部 C++ Plugin。但 nav2_msgs Action、bt_navigator、Planner／Controller Server、恢复行为树、Costmap Filters 和组合式部署，已经把这份早期设计的主要思想拆开并落到了不同模块中。

理解这份 PDF 的正确方式，不是把它当作当前代码的类图，而是把它当作 Nav2 设计演化的坐标系：凡是涉及任务组合、算法替换、恢复行为、环境语义和多种部署方式，都可以回到这套“任务契约＋环境抽象”的基本判断上。

机器人明明在动，却被 Nav2 判定“卡住”？拆解 5 个进展与到点检查器 ​

机器人原地转向时明明一直在动，Nav2 却可能抛出 Failed to make progress；机器人已经进入目标点附近，FollowPath 又可能迟迟不结束。问题往往不在控制器有没有算出速度，而在 Controller Server 内部还有两道判定：ProgressChecker 保护导航过程，GoalChecker 定义任务终点。

本文以当前 learningnav2/nav2_controller 源码为基线，沿着 5 个插件的头文件、实现、plugins.xml、Controller Server 调用点和两组 GTest，把每个函数的职责、输入输出、内部状态、参数边界和选型方法串成一条完整数据流。这里讨论的是源码实际语义，不把参数名当成结论，也不把“位置到了”误写成“机器人已经停稳”。

一、两个问题，两类检查器 ​

1.1 ProgressChecker 保护的是导航过程 ​

ProgressChecker 回答的是“机器人在允许时间内是否取得了足够进展”。Controller Server 在每次调用局部控制器计算速度之前，把当前机器人位姿传给 check()。如果它返回 false，控制循环会抛出 PlannerException("Failed to make progress")，当前 FollowPath 进入失败路径。

这类插件不判断目标是否到达，也不关心局部控制器输出了什么速度。它只观察位姿相对内部基准是否发生了足够变化，以及这次变化是否发生在允许时间窗内。

1.2 GoalChecker 定义的是任务终点 ​

GoalChecker 回答的是“当前位姿和速度是否满足本任务的终止条件”。Controller Server 在一个控制周期完成速度计算与发布后，读取当前位姿、路径终点和经过最小速度阈值处理的里程计速度，再调用当前 GoalChecker 的 isGoalReached()。

返回 true 不只是一个提示，而会直接让 FollowPath 控制循环结束。PositionGoalChecker、SimpleGoalChecker 和 StoppedGoalChecker 对“完成”的定义不同，所以同一台机器人、同一个目标点，换一个 GoalChecker 就可能得到完全不同的结束时刻。

1.3 它们都是进程内插件 ​

5 个实现通过 PLUGINLIB_EXPORT_CLASS 导出，并在 plugins.xml 中声明基类类型。Controller Server 使用 pluginlib::ClassLoader 创建它们，因此这些检查器没有独立 ROS 节点，不发布 Topic，不订阅传感器，也不会生成 /cmd_vel。

它们拿到的数据来自 Controller Server：ProgressChecker 得到当前 PoseStamped；GoalChecker 得到当前 Pose、目标 Pose 和当前 Twist。真正的位姿获取、TF 变换、里程计订阅和控制循环调度都在 Controller Server 中完成。

二、SimpleProgressChecker：一段会不断滚动的移动时间窗 ​

2.1 initialize() 只准备规则，不建立基准 ​

initialize(parent, plugin_name) 从 Controller Server 的 LifecycleNode 获取时钟，声明并读取两个插件私有参数：

  • required_movement_radius：构成有效进展的最小 XY 位移，默认 0.5 m。
  • movement_time_allowance：未达到最小位移时允许持续运行的最长时间，默认 10.0 s。

函数还会注册 dynamicParametersCallback()。初始化阶段没有当前机器人位姿，因此它不会设置基准点；真正的基准位姿和基准时间要等首次 check() 才建立。

2.2 check() 同时维护距离窗口和时间窗口 ​

check(current_pose) 先把三维 Pose 转成平面 x、y、theta，随后检查基准是否存在。首次调用时 baseline_pose_set_ 为 false，短路求值会阻止代码读取尚未初始化的基准位姿，函数直接调用 resetBaselinePose()，并返回 true。

基准有效后，判定可写成：

text
distance = hypot(current.x - baseline.x, current.y - baseline.y)

distance > required_movement_radius
    -> 刷新基准位姿和基准时间，返回 true

distance <= required_movement_radius
    -> elapsed <= movement_time_allowance 时返回 true
    -> elapsed > movement_time_allowance 时返回 false

这里有两个很关键的边界。位移使用严格大于，恰好等于 required_movement_radius 不会刷新基准；时间只有严格超过 movement_time_allowance 才失败，恰好位于时间边界时仍返回 true。

2.3 reset() 与 resetBaselinePose() 不是同一件事 ​

reset() 只把 baseline_pose_set_ 清为 false，不改参数，也不立即采样机器人位姿。新 FollowPath 任务开始后，下一次 check() 才会从真实当前位置重新计时。

resetBaselinePose(pose) 则在一次操作中写入 baseline_pose_、baseline_time_ 和有效标志。把位姿与时间同时更新非常重要，否则距离窗口和时间窗口会来自不同采样时刻。

2.4 isRobotMovedEnough() 与 pose_distance() 明确忽略朝向 ​

pose_distance() 使用 std::hypot(dx, dy) 计算 XY 欧氏距离，isRobotMovedEnough() 再判断该距离是否严格大于 radius_。虽然输入被转换成包含 theta 的 Pose2D，这两个函数都不读取朝向。

因此，机器人即使持续原地旋转，只要 XY 累计变化没有超过半径，SimpleProgressChecker 仍会在时间窗结束后判定“没有进展”。这不是 TF 丢失，也不是控制器没发速度，而是插件对“进展”的定义本来就只有平移。

2.5 dynamicParametersCallback() 立即改阈值，但不重开窗口 ​

动态回调只处理本插件命名空间下的 double 参数。修改半径会直接写入 radius_，修改允许时间会转换为新的 ROS Duration。回调不会调用 reset()，所以新阈值立即作用于当前基准窗口。

运行中把允许时间从 10 s 缩短到 2 s 时，如果当前窗口已经持续超过 2 s，下一次 check() 就可能立刻失败；把移动半径调大，也不会把基准时间重新归零。

三、PoseProgressChecker：让原地转向也能证明“我在工作” ​

3.1 继承父类时间窗，只扩展有效进展条件 ​

PoseProgressChecker 继承 SimpleProgressChecker，继续使用父类的时钟、平移半径、允许时间、基准位姿、基准时间和 resetBaselinePose()。它新增的核心参数只有 required_movement_angle，默认值为 0.5 rad。

initialize() 先调用父类初始化，再声明并读取角度阈值。父类动态回调负责 required_movement_radius 与 movement_time_allowance，子类动态回调负责 required_movement_angle。

3.2 check() 把平移和旋转组成逻辑或 ​

它的整体流程与 SimpleProgressChecker 相同，但 isRobotMovedEnough() 改为：

text
pose_distance(current, baseline) > required_movement_radius
or
poseAngleDistance(current, baseline) > required_movement_angle

只要平移或旋转任一条件成立，就刷新同一组基准位姿和基准时间。这样，执行 RotateToHeading、窄通道转向或原地调整航向时，机器人可以用角度变化证明控制过程仍在推进。

3.3 poseAngleDistance() 处理了正负 π 环绕 ​

函数调用 angles::shortest_angular_distance()，再取绝对值。机器人从接近 +π 转到接近 -π 时，实际只转过一个很小角度；直接相减会得到接近 2π 的错误结果，最短角距离则会返回真实的小角差。

3.4 选择 Pose 并不等于取消卡滞保护 ​

PoseProgressChecker 只是把有效进展条件从“只允许平移”扩展成“平移或旋转”，超时逻辑仍然存在。如果机器人只在阈值以内来回抖动，既没有累计足够 XY 位移，也没有累计足够最短角变化，时间窗结束后依然会失败。

四、三个 GoalChecker 到底差在哪里 ​

4.1 Position、Simple、Stopped 是三种不同终点契约 ​

三个插件都实现 nav2_core::GoalChecker，但判断维度不同：

  • PositionGoalChecker：检查 XY，忽略 Yaw，忽略速度。
  • SimpleGoalChecker：检查 XY 与 Yaw，忽略速度。
  • StoppedGoalChecker：继承 SimpleGoalChecker 的 XY 与 Yaw，再检查二维线速度和 Z 轴角速度。

StoppedGoalChecker 继承 SimpleGoalChecker；PositionGoalChecker 是独立实现，并不是 SimpleGoalChecker 的简化开关。它们都接收 Costmap 指针以满足接口，但当前三个实现都不依赖 Costmap 内容。

4.2 getTolerances() 报告的是插件实际使用字段 ​

GoalChecker 接口允许 Controller 或其他调用方查询位姿与速度容差。实现会把未参与判定的字段设为 std::numeric_limits<double>::lowest() 之类的无效哨兵值。

PositionGoalChecker 返回单位四元数，只是为了填充合法消息字段，不代表它会检查朝向。SimpleGoalChecker 返回 XY 和 Yaw 容差，但速度字段无效。StoppedGoalChecker 在父类结果上补充 linear.x、linear.y 和 angular.z 的停止阈值。

五、PositionGoalChecker：只要进入目标圆就算完成 ​

5.1 构造、析构与初始化 ​

构造函数把 xy_goal_tolerance_ 设为 0.25 m，同时建立 0.0625 的平方缓存，并初始化 stateful_=true 与 position_reached_=false。平方缓存让高频目标检查可以直接比较平方距离，避免每周期计算平方根。

析构函数使用默认实现。插件不拥有独立节点或 Costmap 资源，参数回调句柄等成员由对象生命周期自动释放。

initialize() 声明并读取 xy_goal_tolerance 与 stateful，同步计算平方容差并注册动态回调。传入的 costmap_ros 没有被使用，因为判定只需要当前和目标的 XY 坐标。

5.2 isGoalReached() 只比较一个容差圆 ​

核心条件为：

text
dx = current.x - goal.x
dy = current.y - goal.y

dx² + dy² <= xy_goal_tolerance²

它不读取两个 Pose 的 orientation，也不读取传入的 Twist。机器人高速穿过容差圆时，只要某个检查周期采样到位置在圆内，就可以返回 true。

5.3 stateful 锁存的是最终成功 ​

stateful=true 时，一旦位置条件成立，position_reached_ 就被置为 true，之后即使定位抖动让机器人暂时离开容差圆，插件仍返回成功，直到 Controller Server 为新路径调用 reset()。

stateful=false 时没有锁存，每个控制周期都会重新计算位置误差。setXYGoalTolerance() 和动态参数回调都会同步维护平方缓存，但不会清除已经锁存的成功状态。

5.4 它适合“到点即可”，不适合“到点停正” ​

巡检点只要求机器人经过某个区域、目标朝向没有业务含义时，PositionGoalChecker 可以减少无意义的末端旋转。如果任务要求机器人面向货架、充电桩或窄通道，它会过早结束；如果任务要求机器人真正停稳，它同样不够。

六、SimpleGoalChecker：位置与朝向之间还有一个状态机 ​

6.1 构造与初始化建立四类规则 ​

构造函数设置默认 xy_goal_tolerance=0.25 m、yaw_goal_tolerance=0.25 rad、stateful=true、check_xy=true 与 symmetric_yaw_tolerance=false。initialize() 声明并读取这些参数，计算 XY 平方缓存并注册动态回调。

6.2 isGoalReached() 先过位置门，再过朝向门 ​

当 check_xy_ 为 true 时，函数先比较 XY 平方距离。位置不满足就立即返回 false；位置满足后，如果 stateful=true，函数把 check_xy_ 改为 false，后续周期不再重复检查 XY。

随后函数从两个四元数提取 Yaw，并用最短角距离计算偏航误差。只有误差绝对值小于等于 yaw_goal_tolerance 才返回 true。

6.3 stateful 锁存的是位置阶段，不是整个结果 ​

这与 PositionGoalChecker 的锁存语义不同。SimpleGoalChecker 在位置首次满足后仍可能因为 Yaw 不满足而返回 false；stateful=true 只是允许机器人在后续调整朝向时稍微漂出 XY 容差，而不重新退回位置阶段。

reset() 把 check_xy_ 恢复为 true。动态修改 stateful 或 XY 容差不会自动调用 reset()，所以运行中把 stateful 从 true 改为 false，并不会自动把已经关闭的 check_xy_ 重新打开。

6.4 symmetric_yaw_tolerance 接受相反朝向 ​

默认情况下，只有目标 Yaw 附近的角度可接受。开启 symmetric_yaw_tolerance 后，代码还会计算当前 Yaw 到 goal_yaw + π 的最短角距离，两种朝向任一落入容差都算成功。

这个选项适合前后外形和任务语义等价的机器人，但不适合相机、机械臂、叉齿或充电触点有明确朝向要求的系统。它不是把 Yaw 检查关闭，而是把一个可接受方向扩展成两个相差 π 的方向。

6.5 getTolerances() 不会凭空加入速度条件 ​

函数报告 XY 与 Yaw 容差，并把所有速度字段设为无效。传入 isGoalReached() 的 Twist 也被明确忽略。因此“用了 SimpleGoalChecker，所以到点一定停稳”是错误结论。

七、StoppedGoalChecker：几何到点之后还必须停稳 ​

7.1 构造与初始化复用父类规则 ​

构造函数先建立 SimpleGoalChecker 的位置和偏航状态，再把 rot_stopped_velocity_ 与 trans_stopped_velocity_ 都设为 0.25。单位分别是 rad/s 和 m/s。

initialize() 先调用父类初始化，再声明并读取 rot_stopped_velocity 与 trans_stopped_velocity，最后注册子类动态回调。父类回调继续负责位姿参数，子类回调只负责速度参数。

7.2 isGoalReached() 是串联条件，不是替代条件 ​

函数先调用 SimpleGoalChecker::isGoalReached()。如果 XY 或 Yaw 不成立，立即返回 false；父类成立后，再检查：

text
hypot(velocity.linear.x, velocity.linear.y)
    <= trans_stopped_velocity

abs(velocity.angular.z)
    <= rot_stopped_velocity

线速度使用二维模长，而不是只看 linear.x。例如 vx 和 vy 单独都低于阈值，并不保证合速度低于阈值。角速度只读取平面导航使用的 angular.z。

7.3 速度来自阈值化里程计，不是刚发布的命令 ​

Controller Server 调用 GoalChecker 前，会读取里程计 Twist 并应用 min_x_velocity_threshold、min_y_velocity_threshold 与 min_theta_velocity_threshold。StoppedGoalChecker 看到的是这份处理后的反馈速度，不是局部控制器刚发布的速度命令。

这意味着停止判定同时受 Odom 数据质量和 Controller Server 最小速度阈值影响。最小阈值设得过大，真实的小速度可能先被归零，使 StoppedGoalChecker 更早成功；里程计噪声过大，则可能让机器人机械上已经停住但插件迟迟不通过。

7.4 getTolerances() 与动态回调补齐速度维度 ​

getTolerances() 先调用父类填充 XY 与 Yaw，再把平移阈值写入 linear.x、linear.y，把旋转阈值写入 angular.z。动态回调更新两个 double 阈值，同样不会重置父类的 check_xy_ 状态。

八、动态参数：改的是阈值，不是插件历史 ​

8.1 父类和子类回调各管一组参数 ​

PoseProgressChecker 与 StoppedGoalChecker 都先注册父类回调，再注册子类回调。参数更新请求到来时，多个回调分别检查参数类型和完整名称，只消费自己负责的字段。

  • SimpleProgressChecker：required_movement_radius、movement_time_allowance。
  • PoseProgressChecker：required_movement_angle。
  • PositionGoalChecker：xy_goal_tolerance、stateful。
  • SimpleGoalChecker：xy_goal_tolerance、yaw_goal_tolerance、stateful、symmetric_yaw_tolerance。
  • StoppedGoalChecker：trans_stopped_velocity、rot_stopped_velocity。

8.2 所有更新都不会自动 reset() ​

进展检查器会保留当前基准位姿和基准时间；PositionGoalChecker 会保留 position_reached_；SimpleGoalChecker 与 StoppedGoalChecker 会保留 check_xy_。因此动态调参改变的是从下一次检查开始使用的规则，不会自动清空任务历史。

8.3 当前回调没有额外拒绝负阈值 ​

源码按类型和名称更新成员，并返回 successful=true，没有在这些回调里额外拒绝负半径、负时间、负位置容差或负速度阈值。负容差通常会制造永远无法满足或立即超时的语义，参数管理侧不应依赖插件替你兜底。

九、怎样选插件，怎样排查误判 ​

9.1 包含原地转向的控制过程 ​

如果局部控制器会执行明显的原地旋转阶段，优先使用 PoseProgressChecker，让角度变化也能刷新进展时间窗。配置示例为：

yaml
controller_server:
  ros__parameters:
    progress_checker_plugin: "progress_checker"

    progress_checker:
      plugin: "nav2_controller::PoseProgressChecker"
      required_movement_radius: 0.50
      required_movement_angle: 0.50
      movement_time_allowance: 10.0

如果机器人只应通过平移证明任务推进，SimpleProgressChecker 更直接。不要只把 movement_time_allowance 无限调大来掩盖误判，那会同时削弱真实卡滞的发现能力。

9.2 只要求经过目标区域 ​

目标朝向无意义、任务只要求进入某个 XY 区域时，可以使用 PositionGoalChecker：

yaml
controller_server:
  ros__parameters:
    goal_checker_plugins: ["position_goal_checker"]

    position_goal_checker:
      plugin: "nav2_controller::PositionGoalChecker"
      xy_goal_tolerance: 0.25
      stateful: true

这份配置不会检查 Yaw 和速度，必须接受“进入容差圆就结束”的真实语义。

9.3 要求停在目标姿态 ​

任务要求位置、朝向和停稳同时成立时，使用 StoppedGoalChecker：

yaml
controller_server:
  ros__parameters:
    goal_checker_plugins: ["stopped_goal_checker"]

    stopped_goal_checker:
      plugin: "nav2_controller::StoppedGoalChecker"
      xy_goal_tolerance: 0.25
      yaw_goal_tolerance: 0.25
      stateful: true
      symmetric_yaw_tolerance: false
      trans_stopped_velocity: 0.05
      rot_stopped_velocity: 0.05

示例中的停止阈值只是语义演示，不能脱离底盘低速能力、里程计噪声和 Controller Server 的最小速度阈值直接照搬。

9.4 出现 Failed to make progress 时看什么 ​

  • 当前加载的是 SimpleProgressChecker 还是 PoseProgressChecker。
  • 控制器是否正在原地旋转，而插件只把 XY 位移视为进展。
  • 当前基准窗口内的累计位移、累计最短角变化和经过时间。
  • required_movement_radius、required_movement_angle 与定位噪声、机器人真实运动尺度是否匹配。
  • 运行期是否刚缩短 movement_time_allowance 或调大移动阈值，却没有重置当前窗口。

9.5 到点后 FollowPath 不结束时看什么 ​

  • 当前 Action 选中的 goal_checker_id 是否对应预期插件。
  • XY 距离、最短 Yaw 误差分别卡在哪个条件。
  • stateful 是否让 XY 阶段已经锁存，或者运行期改参后内部状态仍沿用旧任务历史。
  • StoppedGoalChecker 看到的阈值化 Odom Twist 是否仍超过二维线速度或角速度阈值。
  • symmetric_yaw_tolerance 是否符合任务方向语义，不能为了结束任务随意开启。

9.6 两组 GTest 钉住了哪些边界 ​

pctest 覆盖首次基准、重置、允许时间内与超时后的返回值、平移阈值、旋转阈值和动态修改允许时间。gctest 覆盖 Simple 与 Stopped 的差异、容差查询、动态参数、二维合速度、角速度、阈值附近浮点边界和对称偏航。

当前源码的既有本地验证记录为 pctest 与 gctest 全部通过，cppcheck、lint_cmake、xmllint 也通过。本文任务没有修改或重新构建插件源码，文章结论以当前 checkout 和既有测试证据为边界。

十、总结：把“过程健康”和“任务完成”分开调 ​

10.1 ProgressChecker 不负责到点 ​

SimpleProgressChecker 用 XY 位移刷新时间窗；PoseProgressChecker 额外接受最短角变化。它们的 false 表示过程在配置窗口内没有达到进展阈值，不表示目标一定不可达，也不表示控制器没有输出速度。

10.2 GoalChecker 不负责生成速度 ​

PositionGoalChecker 定义“到位置”；SimpleGoalChecker 定义“到位置并对齐朝向”；StoppedGoalChecker 定义“到位置、对齐朝向并满足反馈速度阈值”。选择插件，本质上是在选择任务完成契约。

10.3 状态与阈值必须一起看 ​

baseline_pose_set_、position_reached_ 和 check_xy_ 会跨越多个控制周期保存历史，而动态参数只改阈值、不自动重置。现场调试不能只截一帧参数或一帧 Pose，必须同时还原插件类型、当前内部阶段、位姿误差、速度反馈和时间窗口。

理解这 5 个插件后，再遇到“机器人明明在动却被判卡住”或“机器人明明到了却不结束”，就不必盲目放宽所有容差。先确认是哪一道检查在做决定，再对准它真正使用的数据和状态。

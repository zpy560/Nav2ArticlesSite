一个底盘，三种大脑：nav2_regulated_modules 如何用 Action 与 Service 串起整套 Nav2？ ​

同一台物流机器人，为什么既能让人用键盘接管，又能自主绕障规划，还能沿上游给定的固定路线巡迹？

关键不在于复制三套导航栈，而在于明确三件事：任务由谁接收，路径由谁生成，底盘命令最终归谁所有。nav2_regulated_modules 正是在这三条边界上重组 Nav2。它没有使用 Behavior Tree 编排任务，而是让一个 Lifecycle 状态机直接连接 Planner、Smoother 和 Controller 的标准 Action，并在 Launch 层把遥控、自主规划、固定路径做成互斥分支。

本文以 2026-07-28 的当前工作树为准。包内有 51 个生产入口，但这里不按函数机械排列，而是按照所有实际模块、Action、Service、Topic、TF 和回调接力关系，还原一条命令从入口到 /control_to_uart 的完整数据流。

一、这个包真正解决的是什么 ​

1.1 它不是新的规划器或控制器 ​

nav2_regulated_modules 不实现 A*、DWB、MPPI 或 Pure Pursuit。它保留标准 Nav2 服务器，把已有算法作为插件继续运行：

  • Planner Server 加载 NavFn、Smac2D、SmacHybrid、SmacLattice 和 ThetaStar。
  • Smoother Server 加载 simple_smoother。
  • Controller Server 同时加载 DWB、RPP、MPPI、Graceful Controller 和 Rotation Shim。
  • Velocity Smoother 对控制器输出做闭环速度限制。

本包新增的是“谁在什么时候调用谁”。regulated_navigator 取代 BT Navigator，成为导航任务的单一状态所有者。

1.2 三种模式共享一条安全边界 ​

启动参数 operation_mode 只允许三个值：

  • remote：人直接控制底盘。
  • autonomous：系统计算路径、平滑路径并闭环跟踪。
  • fixed_path：上游直接给出完整 Path，系统不做全局规划。

三种模式都必须满足同一条硬约束：任意时刻 /control_to_uart 只能有一个发布者。遥控模式由键盘节点发布；另外两种模式由 controlpub 发布。

1.3 源码边界必须先说清 ​

本文描述的是当前 navigation2 文件的真实行为，不依赖某个 Git 提交号作为阅读前提。

二、Launch 如何切开三条互斥链 ​

2.1 generate_launch_description() 是总路由器 ​

统一 Launch 读取 namespace、地图、参数文件、RViz、Composition、重启、日志、模式和键盘终端等参数。真正决定系统形态的是两个条件：

  • is_remote：operation_mode == remote。
  • is_navigation：operation_mode != remote。

因此遥控与导航组在进程层已经互斥，不需要等节点启动后再竞争控制权。

2.2 remote 只启动一个业务节点 ​

遥控分支只创建 myagv_keyboard_control。它不会启动 Map Server、Planner、Controller、Smoother、Velocity Smoother、regulated_navigator、Lifecycle Manager 或 controlpub。

这种设计的意义不是省资源，而是从 ROS 图上消除额外的底盘命令源。

2.3 两种导航模式共享同一组进程 ​

autonomous 和 fixed_path 都进入 navigation_group，共同启动：

  • RViz。
  • Map Server 与地图 Lifecycle Manager。
  • Planner Server。
  • Controller Server。
  • Smoother Server。
  • Velocity Smoother。
  • regulated_navigator。
  • controlpub。
  • 规控 Lifecycle Manager。

固定路径模式仍会启动 Planner 和 Smoother 进程，但 regulated_navigator 不向它们发送业务 Action Goal。这是“服务器存在”和“业务链调用”之间的重要区别。

2.4 进程模式与 Composition 模式 ​

use_composition=false 时，每个标准 Nav2 Server 都是独立进程。use_composition=true 时，Planner、Controller、Smoother、Velocity Smoother 和 Lifecycle Manager 被加载到指定容器，自定义 Navigator 与 controlpub 仍是独立进程。

当前 Launch 只执行 LoadComposableNodes，不会创建 Component Container。因此开启 Composition 前，外部必须已经启动名称匹配的容器。

三、十二类运行模块分别负责什么 ​

3.1 regulated_navigator：任务与状态所有者 ​

它对外是 NavigateToPose 和 NavigateThroughPoses 的 Action Server，对内是 ComputePath、SmoothPath 和 FollowPath 的 Action Client，同时还是双 Costmap 清图 Service 的客户端。

它保存任务类型、状态、目标、路径、反馈、恢复次数以及异步回调代次，是全链唯一可以决定“继续、抢占、恢复、成功或失败”的模块。

3.2 Planner Server 与 Global Costmap ​

Planner Server 接收 ComputePathToPose 或 ComputePathThroughPoses，读取 TF 和 Global Costmap，调用选中的规划插件并返回 nav_msgs/Path。

它还发布 /plan，并提供 is_path_valid Service。当前自研 Navigator 没有调用 is_path_valid，而是直接使用规划 Action 的 Result。

3.3 Smoother Server 与 Controller Server ​

Smoother Server 接收 SmoothPath，把原始 Path 交给 simple_smoother，输出平滑路径并发布 /plan_smoothed。

Controller Server 接收 FollowPath，结合 Local Costmap、TF、当前速度、Goal Checker 和 Progress Checker 计算 Twist。Launch 把它原本的 cmd_vel 输出重映射成 cmd_vel_nav。

3.4 Velocity Smoother 与 controlpub ​

Velocity Smoother 订阅 cmd_vel_nav，以 20 Hz 执行速度、加速度、减速度和超时约束。当前配置是 CLOSED_LOOP，每次平滑以 /odometry 的实测速度为起点，输出 Topic 被重映射为 /cmd_vel。

controlpub 订阅 /cmd_vel，把 linear.x 和 angular.z 写入 ControlRes.v 与 ControlRes.w，把升降和上肢旋转字段清零，再发布 /control_to_uart。

3.5 Map Server、Costmap 与 Lifecycle Manager ​

Map Server 从 YAML 和 PGM 加载静态地图，发布 /map。Global Costmap 把静态地图、雷达和 Inflation 合成为规划代价；Local Costmap 使用滚动窗口、实时雷达和 Footprint 支撑局部控制。

两个 Lifecycle Manager 分开管理地图链和规控链，避免 Planner 等待地图时出现无序激活。

3.6 键盘节点、RViz 与外部数据源 ​

键盘节点只属于 remote。RViz 只属于导航组，可展示地图、雷达、全局／局部代价地图和路径，也可通过 Goal Tool 或 Navigation 2 面板产生任务。

外部系统必须提供：

  • /c200_lidar_node/scan。
  • /odometry。
  • 可查询的 map → base_link TF。
  • 真正消费 /control_to_uart 的底盘通信节点。

四、Lifecycle 如何把接口从“存在”变成“可用” ​

4.1 构造阶段只声明参数 ​

RegulatedNavigator 构造函数声明坐标系、模式、Action 名称、插件 ID、超时、反馈频率、重规划、定位监控、恢复和停车 Topic 等参数。构造时不等待任何外部服务器，也不接收任务。

4.2 on_configure() 创建全部通信接口 ​

配置回调读取参数并完成四类动作：

  • 配置 PlanningModule 与 ControlModule。
  • 创建四个下游 Action Client。
  • 创建两个外层 Action Server、两个任务订阅和停车发布器。
  • 创建 TF Buffer、TF Listener、反馈 Timer 与监控 Timer。

固定路径订阅只在 operation_mode == fixed_path 时创建。goal_pose 订阅始终创建，但非自主模式的回调会明确忽略输入。

4.3 on_activate() 才开放任务 ​

激活回调设置 active_ = true 并创建 Lifecycle Bond。Goal 回调会检查 active_，因此配置完成但尚未激活的节点不会接收导航任务。

4.4 停用、清理与关闭 ​

on_deactivate() 先关闭业务入口，再取消任务、发布停车命令并销毁 Bond。

on_cleanup() 进一步释放 Action、Service、Topic、Timer 和 TF 对象，回到未配置状态。

on_shutdown() 在进程退出前再次调用任务取消逻辑，作为最后一道收口。

五、外层任务如何进入状态机 ​

5.1 NavigateToPose 的三个回调 ​

单点 Action Server 为每个 Goal 安装 Goal、Cancel 和 Accepted 回调：

  • Goal 回调检查必须处于自主模式、节点已激活、Pose 有效，并拒绝携带 Behavior Tree XML 的请求。
  • Cancel 回调只为当前活动句柄设置 cancel_requested_，真正取消由监控 Timer 统一执行。
  • Accepted 回调抢占旧任务，保存新终点，增加任务代次，再调用 startPlanning(false)。

5.2 NavigateThroughPoses 的区别 ​

多点 Goal 会逐个检查 Pose，并拒绝空数组。Accepted 回调保存完整目标序列，把最后一个 Pose 作为最终终点。

监控期间，机器人进入 passed_goal_radius 后，已通过的前置目标会从数组中移除。反馈里的 number_of_poses_remaining 因而会逐步减少。

5.3 goal_pose 是无 Action 句柄的兼容入口 ​

onTopicGoal() 接收 PoseStamped，同样要求自主模式、active 和有效 Pose。它会抢占旧任务并启动单点规划，但没有外层 Action Goal Handle，因此没有标准 Action Result 和 Feedback。

这条入口适合 RViz Goal Tool 或简单上游节点，不适合需要严格结果语义的任务调度器。

5.4 新任务如何隔离旧回调 ​

每个任务拥有 generation，每次规划和控制又各有独立 sequence。异步 Goal Response、Feedback 和 Result 只有同时匹配当前任务代次与当前请求序号，才允许修改状态。

旧 Goal 即使晚到，也不能用旧路径覆盖新任务。

六、自主模式的六个 Action 端点 ​

6.1 外层两个 Action 只负责表达任务 ​

navigate_to_pose 与 navigate_through_poses 是对上层任务系统的稳定接口。它们不直接计算路径，只负责接收目标、取消请求、反馈和最终结果。

6.2 Planner 的两个 Action 负责产生 Path ​

startPlanning() 根据任务类型选择：

  • 单点任务调用 compute_path_to_pose。
  • 多点任务调用 compute_path_through_poses。

两种 Goal 都设置 use_start=false，表示 Planner Server 通过 TF 获取当前机器人起点。规划插件 ID 来自 PlanningModule::plannerId()。

6.3 selected_planner 可能覆盖 Action 字段 ​

当前 Navigator 的 planner_id 与 Planner Server 的 selected_planner 都是 GridBasedAstar。

Planner Server 的 selected_planner 非空时，会覆盖 Action Goal 中的 planner_id。因此切换算法时不能只改 Navigator 参数，否则日志会提示 Action 请求与服务器强制选择不一致。

6.4 SmoothPath 是可选中间层 ​

规划成功后，onPathReady() 根据 use_smoother 分流。启用时构造 SmoothPath::Goal，写入原始 Path、平滑插件 ID、最长平滑时间和碰撞检查开关。

平滑成功则发送平滑 Path；Goal 被拒绝、Result 失败或返回空 Path 时，系统回退原始规划 Path，而不是直接让导航失败。

6.5 FollowPath 把 Path 变成控制闭环 ​

sendFollowPath() 写入 Path、controller_id 和 goal_checker_id。Controller Server 接收后设置当前全局路径，按控制频率生成速度。

FollowPath Feedback 中的 distance_to_goal 与 speed 被 Navigator 缓存，用于外层剩余距离和 ETA。Result 成功触发 succeedTask()；非取消状态下失败则进入恢复。

6.6 周期重规划不会停止控制 ​

控制状态下，监控 Timer 按 replan_frequency=1.0 Hz 再次调用 Planner。更新规划失败且旧 FollowPath 仍有效时，只要连续失败没有达到上限，Controller 会继续沿旧路径运动。

新 Path 成功后会提交新的 FollowPath Goal。Controller Server 接受 Pending Goal 后调用 setPlannerPath() 更新当前路径。

七、固定路径为什么不是“另一种规划” ​

7.1 输入是一条完整 Path ​

固定路径入口是 /fixed_path，消息类型为 nav_msgs/msg/Path，QoS 为可靠、深度一。每次消息都代表完整替换路径，不是增量补丁，也不是几个等待系统自动连线的稀疏航点。

7.2 prepareFixedPath() 只做契约处理 ​

它检查 Path 至少有两个 Pose、Path frame 不为空、位置为有限数、四元数范数有效。随后逐 Pose 使用 TF Buffer 变换到 global_frame，统一时间戳并生成新的 Path。

这里没有栅格搜索、绕障或路径拓扑修改。上游给出的线经过障碍时，系统不会调用 Planner 自动绕开。

7.3 首次 Path 创建任务 ​

首次收到有效 Path 时会创建 TaskType::FIXED_PATH，保存最后一个 Pose 作为终点，保存整条 Path 作为恢复数据，然后直接调用 FollowPath。

Planner Server 和 Smoother Server 虽然进程存在，但没有收到 Goal。

7.4 后续 Path 通过 FollowPath 抢占更新 ​

收到更新 Path 时，Navigator 不主动取消旧 FollowPath，而是提交新 Goal。Controller Server 接受 Pending Goal 后替换当前路径，控制进程不必重启。

这种方式保留 Local Costmap、碰撞检查、Progress Checker、Goal Checker 和速度平滑，只旁路全局路径生成。

7.5 定位丢失时只更新缓存 ​

状态为 LOCALIZATION_LOST 时，新 Path 会被校验并保存，但不会立即下发。定位连续稳定后，resumeCurrentTask() 重发最新完整 Path。

八、Controller 之后还有哪些数据变换 ​

8.1 Local Costmap 是控制器的实时环境 ​

Controller Server 内部拥有 Local Costmap，当前使用 Voxel Layer 和 Inflation Layer。活动传感器 Topic 是 /c200_lidar_node/scan，机器人 Footprint 参与碰撞语义。

固定 Path 不经过全局规划，并不等于无安全控制；局部控制器仍会根据 Local Costmap 拒绝危险速度。

8.2 控制器插件由 FollowPath Goal 选择 ​

当前 controller_id 为 DWB，Controller Server 同时加载 RPP、MPPI、Graceful Controller 和 Rotation Shim。Goal 中的 ID 决定本次跟踪使用哪个插件。

goal_checker_id 当前为 general_goal_checker，负责判断位置与航向是否到达。

8.3 两套 Progress Checker 同时存在 ​

Controller Server 内部的 SimpleProgressChecker 要求规定时间内移动规定距离。

Navigator 还用 map → base_link 自己做一层进展检查：累计平移达到 0.1 m 才刷新时间，连续 10 s 无进展则触发恢复。两层检查任何一层失败，都可能让 FollowPath 或外层任务进入失败链。

8.4 速度平滑是最终运动限幅 ​

Controller 的 cmd_vel 被重映射为 cmd_vel_nav。Velocity Smoother 使用 /odometry 闭环反馈，按三轴最大速度 [0.26, 0.0, 1.0]、加速度和减速度约束输出 /cmd_vel。

Navigator 的 stopRobot() 也向 cmd_vel_nav 发布三次零 Twist，因此停车命令仍会经过同一平滑和底盘转换链。

8.5 controlpub 只转换消息，不做控制 ​

controlpub 不计算速度，也不读取 Costmap。它只把 Twist.linear.x、Twist.angular.z 映射为 ControlRes.v、ControlRes.w，再发布 /control_to_uart。

九、遥控模式为什么完全旁路 Nav2 ​

9.1 Launch 先取得真实终端 ​

如果启动 Shell 有 TTY，Launch 使用 os.ttyname(sys.stdin.fileno()) 得到真实 /dev/pts/*；否则回退 /dev/tty。该路径通过 input_device 交给键盘节点。

这解决了 ROS 2 Launch 子进程仅有伪输出终端、却没有可读标准输入的问题。

9.2 Wall Timer 是遥控回调入口 ​

键盘节点以默认 50 Hz 执行 Timer 回调，单周期顺序是：

  • 非阻塞读取全部已到达字符。
  • 解析 WASD、方向键、Space、X 和 Q。
  • 判断方向键重复输入是否超时。
  • 用 steady clock 计算真实 dt。
  • 更新平滑速度并发布 ControlRes。

9.3 松键停车与紧急停车不同 ​

方向键一段时间没有重复字符后，目标速度归零，实际输出按减速度斜坡平滑下降。前后或左右换向会先减速到零，再向新方向加速。

Space 与 X 是正常平滑停车；Q 与节点安全收口会立即清零并发布停车。

9.4 遥控链没有 Service 或 Action ​

键盘节点没有业务 Action，也没有业务 Service。它的输入是终端字符，输出是 byd_custom_msgs/msg/ControlRes。

因此遥控模式不能返回“导航成功”，也没有目标、路径、Costmap 恢复或 ETA 概念。

十、所有业务 Service 如何连接 ​

10.1 Map Server 的两个地图 Service ​

map_server/map 返回当前 OccupancyGrid；map_server/load_map 在 active 状态下从新 YAML 加载地图，更新内部缓存并重新发布 /map。

统一 Launch 只启动 Map Server，不启动 Map Saver，因此没有本包运行链中的 save_map 服务端。

10.2 双 Costmap 的清理 Service ​

Local 与 Global Costmap 分别提供：

  • clear_entirely_*：清空非静态区域。
  • clear_around_*：清理机器人周边区域。
  • clear_except_*：保留指定区域，其余清理。
  • get_costmap：返回当前 Costmap。

Navigator 的恢复链只调用两个 clear_entirely_*。

10.3 Planner 的 is_path_valid ​

Planner Server 提供 is_path_valid，可根据当前 Costmap 检查 Path。当前 Navigator 不调用它；自主模式相信 Planner Result，固定路径则直接交给 Controller 与 Local Costmap 做运行期安全控制。

10.4 Lifecycle Manager 的管理 Service ​

两个 Lifecycle Manager 都提供：

  • <manager_name>/manage_nodes。
  • <manager_name>/is_active。

manage_nodes 支持 startup、reset、shutdown、pause 和 resume。地图 Manager 只管理 Map Server，规控 Manager 管理五个 Lifecycle 节点。

10.5 每个 Lifecycle 节点的标准 Service ​

Planner、Controller、Smoother、Velocity Smoother、Map Server 和 Navigator 都提供 change_state、get_state、可用状态、可用迁移和迁移图查询 Service。

这些 Service 决定接口是否处于 active，但不承载 Path、速度或导航反馈。

10.6 通用参数 Service ​

ROS 节点还会自动提供参数查询和设置 Service。它们属于统一控制面，不应与业务 Action 混淆。当前 Navigator 没有动态参数回调，构造和 configure 后修改部分参数并不会同步改变已缓存成员。

十一、两个定时器如何驱动“看不见的闭环” ​

11.1 publishFeedback() 以 5 Hz 运行 ​

反馈 Timer 查询当前 map → base_link，计算导航时间，再结合 FollowPath Feedback 中的剩余距离和速度估算 ETA。

单点与多点 Action 都会收到当前 Pose、导航时间、预计剩余时间、恢复次数和剩余距离；多点任务还会收到剩余 Pose 数。

11.2 monitorTask() 以 200 ms 运行 ​

监控 Timer 处理外层取消、恢复等待、TF 健康、定位跳变、控制进展、多点通过和周期重规划。它是没有行为树之后的主调度循环。

11.3 Cancel 不在 Action 回调中直接收口 ​

Cancel 回调只设置标志。下一次 monitorTask() 调用 cancelTask()，统一取消 Planner、Smoother、Controller 子 Goal，发布停车命令，并根据 Goal Handle 状态返回 canceled 或 aborted。

这样可以避免在 rclcpp_action 的取消状态迁移中重入复杂任务清理。

十二、定位与恢复链如何工作 ​

12.1 定位输入只有 TF ​

Navigator 通过 TF Buffer 查询 global_frame → robot_base_frame，当前即 map → base_link。它不订阅 AMCL Pose，也不依赖 odom → base_link TF。

Velocity Smoother 的 /odometry 是速度反馈，不能代替 Navigator 的全局定位 TF。

12.2 TF 超时会先停车 ​

超过 localization_timeout 无法取得 TF 时，系统取消全部子 Goal，发布三次零速度并进入 LOCALIZATION_LOST。

定位恢复后必须连续稳定 localization_stable_duration，才允许恢复运动；超过恢复总超时则结束任务。

12.3 定位跳变会废弃旧控制上下文 ​

相邻监控周期的平移或旋转跳变超过阈值时，Navigator 取消旧子 Goal、停车并恢复任务。

自主任务重新规划；固定路径任务重发保存的最新 Path。

12.4 恢复只保留清图与等待 ​

当前包不启动 Behavior Server，也不调用 Spin、BackUp 或 Wait Action。恢复流程是：

  • 取消在途 Planner、Smoother 和 Controller Goal。
  • 发布停车命令。
  • 异步请求清理 Local 与 Global Costmap。
  • 固定等待 Costmap 更新。
  • 按任务类型重新规划或重发路径。

达到最大恢复轮数后，外层 Action 失败。

十三、Topic 数据面如何从地图流到电机 ​

13.1 地图与雷达进入两张 Costmap ​

Map Server 发布 /map。Global Costmap 的 Static Layer 消费静态地图，Obstacle Layer 消费雷达；Local Costmap 的 Voxel Layer 消费同一个 LaserScan。两张 Costmap 再分别服务 Planner 与 Controller。

13.2 Path 有三种来源 ​

  • 自主单点 Planner Result。
  • 自主多点 Planner Result。
  • 固定路径 /fixed_path。

自主 Path 可经过 Smoother；固定 Path 不经过。最终都以 FollowPath Goal 进入 Controller。

13.3 Twist 有两个层级 ​

Controller 输出的是目标控制命令 cmd_vel_nav。Velocity Smoother 输出的是受实测速度、运动学约束和超时保护处理后的 /cmd_vel。

不要直接把 Controller 输出误认为底盘最终执行速度。

13.4 ControlRes 是底盘接口 ​

导航链通过 controlpub 产生 ControlRes；遥控链直接产生 ControlRes。两条链最终使用同一 /control_to_uart，但由 Launch 保证不会同时存在。

十四、当前源码中需要警惕的边界 ​

14.1 cancel_timeout 目前没有生效 ​

参数被声明并读取到成员，但 cancelSubGoals() 只异步调用 async_cancel_goal()，没有按 cancel_timeout_ 等待取消确认。

因此该参数当前不会改变取消耗时，也不能保证旧服务器在超时前已经停止输出。

14.2 部分参数缺少统一校验 ​

PlanningModule 校验重规划频率和连续失败上限，ControlModule 校验进展超时，但 feedback_frequency 没有正值检查。设为零会进入定时器周期除零。

恢复次数、定位超时和跳变阈值也没有在 on_configure() 中统一验证。

14.3 Action Server 等待不是一个总预算 ​

dependenciesReady() 对 Planner 单点、Planner 多点、可选 Smoother 和 Controller 依次使用完整 server_timeout。多个服务器都不可用时，总等待可能接近该参数的四倍。

14.4 固定 Path 校验失败只发零速 ​

已有固定路径正在 FollowPath 时，新 Path 若无效，回调只调用 stopRobot()，没有取消旧 FollowPath。Controller 后续周期仍可能重新发布速度，覆盖短暂的三帧零指令。

更严格的安全语义应明确选择“拒绝更新并继续旧路径”，或“取消旧控制并保持停车”，而不是两种状态同时存在。

14.5 failTask() 没有显式停车 ​

失败收口会取消子 Goal 并 abort 外层 Action，但没有直接调用 stopRobot()。最终停车依赖 Controller 对取消的处理，在异步链路中不如主动零速明确。

14.6 清图结果没有进入状态判断 ​

恢复流程只在 Service ready 时异步发送请求，不等待响应，也不检查清图是否成功。无论 Service 未就绪、请求失败还是成功，状态机都会在固定时间后继续恢复。

14.7 Pose 校验不等于四元数归一化 ​

validPose() 只要求四元数范数有限且大于极小值，不要求范数接近一，也不主动归一化自主 Action Goal。固定 Path 经过 TF 变换，自主 Goal 则直接进入 Planner。

14.8 RViz 与 Composition 都有启动前提 ​

默认 use_rviz=true，关闭 RViz 会触发整个关联 Launch 的 Shutdown。Composition 模式又要求外部容器预先存在。

这两个行为都不是算法错误，但会直接影响实车部署方式。

十五、把整套链路压缩成一句话 ​

nav2_regulated_modules 的核心不是“再造一个 Nav2”，而是把标准 Nav2 Server 重新组织成三个互斥运行模式：

  • 遥控模式让终端输入直接拥有底盘。
  • 自主模式用 Navigate Action 驱动 ComputePath、SmoothPath 和 FollowPath。
  • 固定路径模式保留局部安全控制，却把全局规划和平滑从业务链中移除。

Action 承载长任务、反馈与结果，Service 管理地图、Lifecycle 和恢复，Topic 传递地图、传感器、Path、速度与底盘命令，TF 则决定所有路径和状态能否落在同一个坐标世界里。

真正决定系统是否可靠的，不只是某个 Planner 或 Controller，而是这些接口之间是否保持单一所有权、可追踪回调和明确失败语义。

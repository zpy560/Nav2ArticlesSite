一张 PGM 地图怎样进入 Nav2？拆解 nav2_map_server 调用全数据流 ​

很多人第一次接触 Nav2，会把静态地图理解成一张黑白图片。

但规划器和定位器不能直接理解 PGM 或 PNG。它们需要知道每个像素对应多少米、地图原点位于哪里、黑白是否反转、什么灰度算障碍物，以及整张地图属于哪个坐标系。

nav2_map_server 的工作，就是把磁盘上的“图片和说明书”翻译成 ROS 2 可以传输的 nav_msgs/msg/OccupancyGrid，并在运行期提供读取、换图和保存能力。

本文从启动参数 yaml_filename 出发，完整追踪：

text
YAML 元数据
→ 图像像素
→ OccupancyGrid
→ /map
→ AMCL／Global Costmap／RViz2

同时再反向追踪 MapSaver 怎样把 /map 写回图片和 YAML。

一、先给结论：这个包里不只有 MapServer ​

nav2_map_server 包含三类 Lifecycle 节点和一套地图 I/O 库。

1.1 MapServer ​

读取静态地图，缓存 OccupancyGrid，发布地图 Topic，并提供 GetMap 和 LoadMap 服务。

1.2 MapSaver ​

临时订阅地图 Topic，把收到的 OccupancyGrid 写成图片和 YAML。

1.3 CostmapFilterInfoServer ​

发布代价地图过滤器元数据，告诉 Costmap Filter 去哪里订阅 mask，以及怎样把 mask 数值换算成过滤器参数。

1.4 map_io ​

map_io 是不依赖具体节点的转换库，完成 YAML、图片和 OccupancyGrid 之间的双向转换。

最核心的数据闭环是：

text
磁盘地图 → map_io → MapServer 缓存 → /map
   ↑                                  ↓
图片 + YAML ← map_io ← MapSaver ← OccupancyGrid

二、地图其实有三层 ​

理解 Map Server，首先要分清三种完全不同的数据形态。

2.1 YAML 元数据层 ​

典型地图 YAML 包含：

yaml
image: map.pgm
mode: trinary
resolution: 0.05
origin: [-10.0, -10.0, 0.0]
negate: 0
occupied_thresh: 0.65
free_thresh: 0.25

这里没有任何栅格数组。它只描述如何解释图片：

text
image              图片路径
resolution         每个像素对应的米数
origin             地图左下角在世界坐标中的 x、y、yaw
negate             是否翻转黑白的占用含义
occupied_thresh    判定占用的概率阈值
free_thresh        判定空闲的概率阈值
mode               trinary／scale／raw

相对 image 路径不是相对当前终端目录，而是相对 YAML 文件所在目录展开。YAML 路径本身以 ~/ 开头时，map_io 会尝试使用 HOME 环境变量展开。

2.2 图像像素层 ​

PGM、PNG 或 BMP 提供宽、高和每个像素的颜色。GraphicsMagick 负责解码图片，map_io 再把 RGB 和可选 Alpha 转成亮度与占用概率。

图像坐标原点通常在左上角，OccupancyGrid 的数据布局则按地图左下角语义组织。因此读写时都使用：

cpp
data[width * (height - y - 1) + x]

这个 Y 轴翻转是“图片看起来正确，但 RViz2 地图上下颠倒”问题的关键边界。

2.3 OccupancyGrid 消息层 ​

Nav2 真正消费的是：

text
header.frame_id／stamp
info.map_load_time
info.resolution
info.width／height
info.origin
data[]

data 中常见值为：

text
0    空闲
100  占用
-1   未知

从这一层开始，AMCL、StaticLayer、RViz2 和业务节点不再关心原始图片格式。

三、Lifecycle 决定“文件已读”和“地图可用”不是一回事 ​

Map Server 继承 nav2_util::LifecycleNode。它必须经过 configure 和 activate，才成为完整可用的地图服务。

3.1 构造阶段 ​

构造函数只声明三个参数：

text
yaml_filename
topic_name，默认 map
frame_id，默认 map

此时没有读取地图，没有创建 /map Publisher，也没有 GetMap／LoadMap 服务。

3.2 CONFIGURE 阶段 ​

on_configure() 读取参数。如果 yaml_filename 非空，就立即调用 loadMapFromYaml()，把结果写入成员缓存 msg_，并设置 map_available_=true。

加载失败不是“先启动再说”。配置回调会抛出异常，Lifecycle configure 失败，上层 Lifecycle Manager 也无法完成整组节点启动。

如果 yaml_filename 为空，configure 仍然可以成功。节点创建服务和 Publisher，但暂时没有地图，等待运行期通过 map_server/load_map 加载。

随后创建三项 ROS 接口：

text
<node_name>/map       nav_msgs/srv/GetMap
<node_name>/load_map  nav2_msgs/srv/LoadMap
topic_name            nav_msgs/msg/OccupancyGrid

3.3 ACTIVATE 阶段 ​

on_activate() 先激活 Lifecycle Publisher。如果已经有缓存地图，就立即发布一次；没有地图则只进入 active，继续等待 LoadMap。

之后调用 createBond()，让 Lifecycle Manager 可以监控 Map Server 存活状态。

3.4 DEACTIVATE 和 CLEANUP ​

deactivate 会停止 Publisher 并销毁 Bond。cleanup 会释放 Publisher、两个服务，清空 msg_ 并把 map_available_ 重置为 false。

所以，cleanup 后不是“地图仍在内存里但不发布”，而是整份运行时地图缓存已经被清掉。

四、加载主链：YAML 怎样变成 OccupancyGrid ​

loadMapFromYaml() 把错误分成元数据错误和图像数据错误，再串联两个核心步骤。

4.1 loadMapYaml：解析地图说明书 ​

这个函数读取 image、resolution、origin、两个阈值、mode 和 negate。

origin 必须恰好包含三个元素。mode 未填写时默认 trinary。negate 同时兼容整数和布尔写法。

YAML 文件无法打开、字段缺失、类型错误或 mode 非法，都会被归类为：

text
INVALID_MAP_METADATA

4.2 loadMapFromFile：逐像素生成地图 ​

GraphicsMagick 读出图片后，宽高直接成为 OccupancyGrid.info.width 和 height；分辨率与原点来自 YAML。

每个像素先计算 RGB 平均亮度 shade，范围为 0.0 到 1.0。然后根据 negate 计算占用程度：

text
negate = false：occ = 1.0 - shade
negate = true： occ = shade

默认 negate=false 时，黑色亮度低，因此占用程度高；白色亮度高，因此占用程度低。

图片无法读取或像素转换抛出异常，会被归类为：

text
INVALID_MAP_DATA

4.3 MapServer 再修正 Header ​

map_io 不是 ROS Node，只能用系统时钟临时填写时间，并默认使用 map frame。

加载回到 MapServer 后，updateMsgHeader() 会使用节点自己的 now() 更新 map_load_time 和消息时间戳，并用 frame_id 参数覆盖 frame。

这一步对仿真时间尤其重要：最终发布的地图 Header 由节点时钟决定，而不是保留 I/O 库最初写入的系统时间。

五、三种地图模式不是显示风格，而是数据语义 ​

同一个灰度像素，在 trinary、scale 和 raw 下可能得到完全不同的栅格值。

5.1 Trinary：三值地图 ​

这是默认模式：

text
occ > occupied_thresh → 100
occ < free_thresh     → 0
中间区域              → -1

它适合传统静态导航地图：明确分为空闲、障碍和未知三类。

Trinary 读取带透明通道的图片时，会把 Alpha 也加入颜色平均。源码特别提醒：GraphicsMagick 的 Alpha 数值语义与直觉相反，高值表示透明。

5.2 Scale：保留概率梯度 ​

Scale 在两个阈值之间按比例映射到 1～99，而不是全部变成 unknown。透明像素直接变为 -1。

这种模式需要图片格式支持透明通道，因此保存时默认选择 PNG。若强制使用 PGM 或 JPEG，代码会发出“Scale 需要透明度”的警告。

5.3 Raw：直接保留低范围像素值 ​

Raw 计算 round(shade × 255)。只有结果处于 0～100 时才直接写入；超过这个范围则标为 -1。

它不是“把黑色当 100”的概率转换，也不经过 free／occupied 阈值分类，因此不能按 Trinary 的直觉解释。

六、/map 为什么晚启动的订阅者仍能收到 ​

Map Server 的 OccupancyGrid Publisher 使用：

text
KeepLast(1)
transient_local
reliable

这相当于 ROS 1 的 latched Topic：发布者保留最近一份地图，之后加入且 QoS 兼容的订阅者仍能收到。

这一设计很适合静态地图。地图通常只在 activate 或换图后发布一次，不需要持续高频发送。

但 transient local 不是“所有订阅者无条件收到”。订阅端 QoS 必须兼容；发布者进程退出后，它保存的历史样本也随之消失。

七、GetMap：从缓存同步取图 ​

<node_name>/map 是 nav_msgs/srv/GetMap 服务。

回调不重新读磁盘，而是直接执行：

cpp
response->map = msg_;

因此 GetMap 返回的是当前缓存快照，速度快，但内容取决于最近一次 configure 预加载或 LoadMap 成功结果。

回调只在 Lifecycle 状态为 ACTIVE 时提供地图。非 active 状态会警告并直接返回，不把未准备好的缓存暴露给调用方。

需要注意：GetMap 服务名默认是 map_server/map，而 Topic 默认是 /map。两者消息类型和调用方式完全不同，排障时不能只看到名字里都有 map 就混为一谈。

八、LoadMap：运行中换图的原子主链 ​

<node_name>/load_map 接收 nav2_msgs/srv/LoadMap，请求核心字段是 map_url。

只有 ACTIVE 状态才允许加载。非 active 时返回：

text
RESULT_UNDEFINED_FAILURE

active 状态下重新执行完整的 YAML → image → OccupancyGrid 转换。成功后依次执行以下操作。

8.1 更新地图缓存 ​

更新 msg_ 缓存。

8.2 标记地图可用 ​

设置 map_available_=true。

8.3 写入 LoadMap Response ​

把地图写入 LoadMap Response。

8.4 返回成功结果 ​

返回 RESULT_SUCCESS。

8.5 发布新地图 ​

立即发布新的 /map。

失败状态被细分为：

text
RESULT_MAP_DOES_NOT_EXIST
RESULT_INVALID_MAP_METADATA
RESULT_INVALID_MAP_DATA

源码直接把新地图加载到成员 msg_。当前 loadMapFromFile() 只有在完整转换结束时才执行 map = msg，所以常见 YAML 或图片异常不会把半成品写入缓存；服务也不会发布失败地图。

换图后 AMCL 和 Global Costmap 是否立即形成一致状态，还取决于它们各自怎样处理新地图、定位状态和代价地图重建。LoadMap 成功只证明 Map Server 已完成缓存替换与发布，不等于机器人定位已经自动迁移到新地图。

九、MapSaver：为什么服务回调里还要单独开 Executor ​

MapSaver 提供 <node_name>/save_map 服务。默认节点名为 map_saver，所以常见服务路径是：

text
/map_saver/save_map

保存不是直接读取 Map Server 的成员缓存。MapSaver 与 MapServer 是两个独立节点，它只能订阅请求指定的地图 Topic。

9.1 补齐保存参数 ​

SaveMap Request 可以指定：

text
map_topic
map_url
image_format
map_mode
free_thresh
occupied_thresh

未指定 Topic 时使用 map。阈值为 0 时使用节点参数默认值 0.25 和 0.65。无法识别的 mode 会退回 trinary。

输出文件名前缀为空时，map_io 生成 map_<系统时间秒>。Scale 未指定格式时默认 PNG，其他模式默认 PGM。

9.2 临时订阅地图 ​

每次保存请求都会创建一个临时 OccupancyGrid 订阅器。默认启用 transient local、reliable、KeepLast(1)，因此即使 /map 很早以前只发布过一次，也能取得发布者保留的最近样本。

SaveMap 服务回调本身正在某个 executor 中运行。如果临时订阅仍放在同一个互斥执行上下文里，服务等待消息时可能阻塞订阅回调。

因此代码创建独立的 MutuallyExclusive callback group，再交给局部 SingleThreadedExecutor，调用 spin_until_future_complete()，等待地图到达或超过 save_map_timeout。

收到消息后立即释放临时订阅，后续只进行文件转换。

9.3 OccupancyGrid 反向生成图片 ​

保存参数必须满足：

text
阈值关系：0.0 ≤ free_thresh < occupied_thresh ≤ 1.0

图片格式不可写时回退到 PNG。推荐格式是 BMP、PGM 和 PNG。

随后逐栅格执行与加载方向对应的像素映射，并再次翻转 Y 轴。最终生成两个文件：

text
<map_url>.<image_format>
<map_url>.yaml

YAML 中写入图片文件名、模式、分辨率、原点 x／y／yaw、negate: 0 和两个阈值。

保存超时、订阅失败、参数非法或写盘异常，SaveMap Response 都返回 false。

十、MapSaver CLI 与 Server 是两条入口 ​

map_saver_server 是长期运行的 Lifecycle 服务节点，适合由 SLAM 或业务系统反复调用。

map_saver_cli 是一次性命令入口。它解析命令行参数，构造 MapSaver，手动调用 configure，然后直接执行 saveMapTopicToFile()；保存完成后退出。

两者最终复用相同的订阅和 map_io 写盘链，因此图片模式、阈值和超时规则一致。

十一、CostmapFilterInfoServer 在这个包里的位置 ​

这个节点不发布 OccupancyGrid，也不读取地图图片。

它发布 nav2_msgs/msg/CostmapFilterInfo，内容包括：

text
type
filter_mask_topic
base
multiplier

Publisher 同样使用 KeepLast(1)、transient local 和 reliable，并在 activate 时发布一次。

它告诉 Costmap Filter 如何解释另一个 mask Topic。mask 本身通常由独立 Map Server 以 OccupancyGrid 形式提供。因此过滤器场景常见两条并行数据流：

text
filter mask OccupancyGrid → 过滤区域数值
CostmapFilterInfo         → mask topic 名与换算参数

十二、地图发布后流向哪里 ​

12.1 AMCL ​

AMCL 使用静态地图构建似然场或距离场，并结合 LaserScan 和里程计估计 map → odom。

Map Server 只提供地图本体，不发布 map → odom TF。RViz2 出现 “No transform from map” 时，不能把 TF 缺失归因成 Map Server 没有发布坐标变换。

12.2 Global Costmap StaticLayer ​

StaticLayer 订阅 /map，把 OccupancyGrid 转成全局代价地图的静态层。之后 Planner Server 在融合后的 global costmap 上规划路径。

Map Server 的 free_thresh 和 occupied_thresh 决定最初的 OccupancyGrid 分类；StaticLayer 的参数又决定这些值怎样映射成 costmap 代价。两层阈值不能混为一组。

12.3 RViz2 和业务节点 ​

RViz2 的 Map Display 直接订阅 OccupancyGrid。业务程序可以订阅 /map，也可以调用 GetMap 获取缓存快照。

Topic 更适合监听换图；Service 更适合按需同步查询当前地图。

十三、最常见的七个排障边界 ​

13.1 yaml_filename 为空不等于配置失败 ​

yaml_filename 为空不代表 Map Server 配置失败，它可能在等待 LoadMap；但 active 后没有缓存时不会自动发布空地图。

13.2 YAML 可打开不等于地图有效 ​

图片路径、图片编码或像素读取错误属于 INVALID_MAP_DATA。

13.3 相对图片路径以 YAML 目录为基准 ​

相对图片路径以 YAML 所在目录为基准，不以 launch 文件或当前 shell 目录为基准。

13.4 /map 不持续刷新是正常现象 ​

/map 是 transient-local 静态数据，不是传感器流。

13.5 优先核对历史地图 QoS ​

订阅不到历史地图时先核对 QoS，而不是反复重启 Map Server。

13.6 Map Server Active 不等于定位 Active ​

AMCL、Lifecycle Manager、TF 和初始位姿仍是独立链路。

13.7 MapSaver 必须具备完整保存条件 ​

保存地图时 MapSaver 必须在超时前收到兼容 QoS 的 OccupancyGrid，并且进程具有目标目录写权限。

十四、建议的观测顺序 ​

遇到地图不显示或换图失败，可以按下面顺序检查。

14.1 检查 Map Server Lifecycle ​

确认 map_server Lifecycle 是否 active。

14.2 检查基础参数 ​

确认 yaml_filename、topic_name、frame_id 是否符合预期。

14.3 检查 YAML 与图片路径 ​

确认 YAML 的 image 相对路径和字段是否有效。

14.4 检查 /map 接口 ​

确认 /map 的类型、发布者数量和 QoS 是否正确。

14.5 检查 GetMap 结果 ​

确认 GetMap 是否返回有效 width／height／resolution。

14.6 检查 LoadMap 错误类型 ​

确认 LoadMap Response 的 result 具体是哪类错误。

14.7 检查下游地图接收 ​

确认 AMCL 与 StaticLayer 是否收到新地图。

14.8 检查 TF 链 ​

确认 map → odom → base_link TF 是否完整。

不要只看 RViz2 中“有没有一张图”。同样的空白界面，可能来自文件读取失败、Lifecycle 未激活、QoS 不兼容、固定坐标系错误或 TF 缺失。

十五、结语 ​

nav2_map_server 的本质，是地图数据格式和 ROS 运行时之间的边界层。

正向链路把静态文件变成可共享的地图状态：

text
YAML + image
→ 像素占用解释
→ OccupancyGrid 缓存
→ transient-local /map
→ 定位、代价地图和可视化

反向链路把运行时地图重新固化为文件：

text
OccupancyGrid Topic
→ MapSaver 临时订阅
→ 像素反向映射
→ image + YAML

理解这两条链，就能把“地图不显示”拆成具体的数据层、生命周期状态、ROS 接口和下游消费问题，而不是把所有故障都笼统归因给一张 PGM 图片。

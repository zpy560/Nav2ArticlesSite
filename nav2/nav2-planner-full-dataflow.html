目标点如何穿过障碍变成一条路？拆解 nav2_planner 的双 Action 与全局规划数据流 ​

机器人收到一个目标点后，第一件事并不是计算速度，而是回答一个更基础的问题：从当前位置到目标，究竟应该走哪条路？

在 Nav2 中，这个问题由 nav2_planner 回答。

它同时面对单目标、多途经点、不同坐标系、不同全局规划算法、动态障碍更新、路径失效和周期重规划。对上，它把这些复杂性收敛成两个 Action 和一个路径检查 Service；对下，它把 Global Costmap、TF 和不同 GlobalPlanner 插件组合成统一的路径计算运行时。

本文基于当前工程中的 nav2_planner 1.1.20 源码，完整整理本包的调用、状态和输入输出数据流，并单独标出当前 checkout 中与标准设计意图不完全一致的实现边界。

一、先给结论：Planner Server 负责“规划编排”，算法由插件完成 ​

nav2_planner 的核心节点是 PlannerServer。它本身不是 Dijkstra、A*、Hybrid-A* 或 Theta* 算法，而是全局规划任务服务器。

它主要负责：

  • 提供 /compute_path_to_pose 单目标规划 Action。
  • 提供 /compute_path_through_poses 多目标规划 Action。
  • 自己持有并运行 global_costmap。
  • 从 TF／Costmap 获取当前机器人位姿。
  • 把起点和目标统一转换到 Global Costmap Frame。
  • 按 Plugin ID 选择 GlobalPlanner，并调用 createPlan()。
  • 发布 plan Topic 用于可视化。
  • 提供 /is_path_valid Service 检查现有路径是否仍可通行。

上游调用者可以是：

  • 标准行为树中的 ComputePathToPose 和 ComputePathThroughPoses 节点。
  • 本项目取消行为树后的自研 RegulatedNavigator。
  • nav2_simple_commander 中直接请求路径的 API。

规划成功后，Path 可以继续流向 Smoother、Controller，也可以被行为树或自研规控节点缓存，用于周期重规划、路径有效性判断和恢复决策。

因此 Planner Server 的职责边界是：把“起点、目标、地图、规划器选择”变成一条全局 Path。它不负责跟踪路径，也不负责直接输出 cmd_vel。

二、第一层状态：Lifecycle 决定规划资源何时可用 ​

PlannerServer 继承 nav2_util::LifecycleNode。Global Costmap、规划插件、Action Server 和 Publisher 都跟随 Lifecycle 分阶段创建和激活。

2.1 UNCONFIGURED：声明插件清单，创建 Costmap 外壳 ​

构造函数声明三个服务器级参数：

  • planner_plugins：需要加载的 Planner Plugin ID 列表。
  • selected_planner：全局强制选择的 Planner ID。
  • expected_planner_frequency：规划耗时告警阈值的倒数。

随后创建名为 global_costmap 的 Costmap2DROS 对象，但还没有配置地图、加载插件或接受 Action。

当前源码默认声明六个 Plugin ID：

  • GridBased。
  • GridBasedAstar。
  • Smac2D。
  • SmacHybrid。
  • SmacLattice。
  • ThetaStar。

2.2 on_configure：把全局规划运行时装起来 ​

on_configure() 的核心调用顺序如下。

2.2.1 配置 Global Costmap ​

配置 global_costmap。

2.2.2 获取 Costmap 与 TF ​

获取底层 Costmap2D* 和 TF Buffer。

2.2.3 创建 Footprint 检查器 ​

如果机器人不是半径模型，创建 Footprint Collision Checker。

2.2.4 启动 Costmap 线程 ​

用独立 NodeThread 运行 Global Costmap。

2.2.5 创建规划插件 ​

根据 planner_plugins 逐个创建 GlobalPlanner 实例。

2.2.6 配置规划插件 ​

把父节点、Plugin ID、TF Buffer 和 Costmap 传入每个插件的 configure()。

2.2.7 检查强制规划器 ​

读取并检查 selected_planner。

2.2.8 计算期望耗时 ​

计算 expected_planner_frequency 对应的最大期望耗时。

2.2.9 创建 Plan Publisher ​

创建 Lifecycle plan Publisher。

2.2.10 创建规划 Action Server ​

创建两个规划 Action Server。

任一插件加载失败，on_configure() 会直接返回 FAILURE，避免节点在缺少规划算法的情况下进入 ACTIVE。

2.3 on_activate：开始接受规划任务 ​

激活阶段依次完成以下步骤。

2.3.1 激活 Plan Publisher ​

激活 plan Publisher。

2.3.2 激活规划 Action ​

激活两个规划 Action Server。

2.3.3 激活 Global Costmap ​

激活 Global Costmap。

2.3.4 激活规划插件 ​

激活所有 GlobalPlanner 插件。

2.3.5 创建路径检查 Service ​

创建 /is_path_valid Service。

2.3.6 注册动态参数回调 ​

注册动态参数回调。

2.3.7 建立 Bond ​

与 Lifecycle Manager 建立 Bond。

进入 ACTIVE 后，节点才真正具备规划和路径检查能力。

2.4 on_deactivate：停止对外规划能力 ​

停用阶段先停两个 Action Server，再停 plan Publisher、Global Costmap 和全部规划插件，最后移除动态参数回调并销毁 Bond。

2.5 on_cleanup：释放规划运行时 ​

Cleanup 会释放两个 Action Server、Publisher、TF Buffer，清理 Global Costmap 和全部规划插件，并释放 Costmap Thread 与底层 Costmap 指针。

on_shutdown() 在当前实现中只记录停机日志。

三、插件层：一个接口托管六种全局规划入口 ​

Planner Server 通过 Pluginlib 加载实现 nav2_core::GlobalPlanner 的外部插件。

这个接口只有五组核心能力：

  • configure()：接收节点、实例名、TF Buffer 和 Costmap。
  • activate()：激活插件资源。
  • createPlan(start, goal)：从起点计算到目标的 Path。
  • deactivate()：停用插件。
  • cleanup()：释放插件资源。

nav2_planner 自己是插件宿主，不实现具体搜索算法。当前工程配置加载六个 Plugin ID。

3.1 GridBased：NavFn Dijkstra ​

Plugin Type 为 nav2_navfn_planner/NavfnPlanner，参数 use_astar=false，使用 Dijkstra 势场搜索。

3.2 GridBasedAstar：NavFn A* ​

同样使用 NavfnPlanner Type，但 use_astar=true。这说明 Plugin ID 是“配置实例”，同一个 C++ Type 可以用不同参数加载为多个算法入口。

3.3 Smac2D：二维代价感知 A* ​

Plugin Type 为 nav2_smac_planner/SmacPlanner2D，在二维栅格上搜索，并把 Costmap 代价纳入路径代价。

3.4 SmacHybrid：考虑航向的 Hybrid-A* ​

Plugin Type 为 nav2_smac_planner/SmacPlannerHybrid。搜索状态包含位置和航向，可配置车辆运动模型、航向离散、最小转弯半径与解析扩展。

3.5 SmacLattice：运动基元状态格 ​

Plugin Type 为 nav2_smac_planner/SmacPlannerLattice。它使用预生成运动基元，把底盘可执行运动直接放进搜索空间。

3.6 ThetaStar：任意角度栅格规划 ​

Plugin Type 为 nav2_theta_star_planner/ThetaStarPlanner。它通过视线连接减少传统栅格搜索的折线约束。

3.7 Plugin ID 到底由谁决定 ​

Action Goal 带有 planner_id，但当前分支增加了 selected_planner 参数。

最终选择逻辑是：

text
selected_planner 非空
  -> 强制使用 selected_planner

selected_planner 为空
  -> 使用 Action Goal.planner_id

当前 regulated_modules.yaml 把 selected_planner 设置为 GridBasedAstar。因此即使 Action 请求另一个 planner_id，服务器仍会使用 GridBasedAstar，并只输出一次覆盖警告。

如果只加载一个插件，当前实现对空 ID 或无效 ID会回退到唯一插件；如果加载多个插件且最终 ID 无效，则返回空 Path，随后 Action 失败。

四、输入输出接口：两个 Action、一个 Service、一个 Topic ​

4.1 单目标 Action：/compute_path_to_pose ​

类型为 nav2_msgs/action/ComputePathToPose。

Goal 包含：

  • goal：最终目标位姿。
  • start：可选的显式起点。
  • planner_id：期望使用的 Planner Plugin ID。
  • use_start：是否使用请求中的 start。

Result 包含：

  • path：规划得到的 nav_msgs/Path。
  • planning_time：从 Action 回调开始到结果生成的总耗时。

该 Action 没有 Feedback 字段。规划过程不会像 FollowPath 那样周期发布剩余距离或进度。

4.2 多目标 Action：/compute_path_through_poses ​

类型为 nav2_msgs/action/ComputePathThroughPoses。

Goal 与单目标版本基本相同，只是 goal 变为 goals[]。Planner Server 会依次计算：

text
start -> goals[0]
goals[0] 附近实际路径末点 -> goals[1]
上一段实际路径末点 -> goals[2]
...

最后把所有分段 Path 的 poses 直接拼接成一条 Path。

这里特意使用“上一段实际路径末点”，而不是原始 Via Point。因为规划器可能使用 tolerance，实际路径末点不一定与请求点完全重合。下一段从真实末点继续，可以保持几何连续性。

不同插件通常会把每段起点也放入返回 Path，因此直接拼接时，分段交界处可能出现重复 Pose。当前 Planner Server 不负责去重。

4.3 起点输入：显式 Start 还是机器人当前位姿 ​

use_start=true 时，服务器使用 Goal 中的 start。

use_start=false 时，服务器调用 global_costmap 的 getRobotPose()，通过 TF 获取机器人当前位姿。

本项目的 RegulatedNavigator 在单点和多点请求中都设置 use_start=false，所以路径起点由自研定位提供的 map -> base_link 决定。

4.4 Service：/is_path_valid ​

请求为一条 nav_msgs/Path，响应包含：

  • is_valid：路径是否仍然有效。
  • invalid_pose_indices：无效路径点索引数组。

但当前 PlannerServer::isPathValid() 只设置 is_valid，没有填充 invalid_pose_indices。客户端不能依赖该数组定位具体碰撞点。

4.5 Topic：plan ​

规划成功后，服务器把 Path 发布到相对名称 plan，主要供 RViz 和调试工具可视化。

publishPlan() 只有在 Lifecycle Publisher 已激活且存在订阅者时才真正发布。但 Action Result 始终独立返回 Path，所以没有 plan 订阅者不会影响规划成功。

4.6 环境输入：Global Costmap 与 TF ​

规划插件共享 Planner Server 持有的 Global Costmap 和 TF Buffer。Global Costmap 汇总静态地图、障碍、膨胀层、Footprint 等信息，TF 则负责把起点和目标统一到 Costmap Global Frame。

规划请求不会直接订阅 /map 或 /scan。这些数据先进入 Global Costmap，再由 Planner Server 和插件通过共享指针读取。

五、单目标规划：从 Goal 到 Path 的完整调用链 ​

单目标 Action 的执行回调是 computePlan()。它在整个处理期间持有 dynamic_params_lock_。

完整顺序如下。

5.1 检查服务器和取消状态 ​

首先确认 Action Server 仍然 ACTIVE，然后检查客户端是否已经请求取消。

如果当前 Goal 正处于 canceling，terminate_all() 会把它收口为 CANCELED。

5.2 等待 Global Costmap 有效 ​

waitForCostmap() 以 100 Hz 轮询 costmap_ros_->isCurrent()。

这个等待没有超时。清图、传感器停止、TF 异常或 Costmap 无法恢复 Current 时，规划回调会一直阻塞。

5.3 处理 Pending Goal ​

Costmap 有效后，服务器检查是否出现抢占请求，并调用 accept_pending_goal() 让新 Goal 接管 Action。

当前源码的抢占实现存在一个后文会展开的按值传递边界。

5.4 获取并转换起点、目标 ​

服务器根据 use_start 选择显式起点或当前机器人位姿，再把起点与目标分别转换到 Global Costmap Frame。

任一变换失败都会终止当前 Action。

5.5 选择插件并计算 Path ​

getPlan() 先根据 selected_planner 与 Goal planner_id 得到最终 Plugin ID，再调用：

cpp
planners_[requested_planner_id]->createPlan(start, goal);

插件得到同一份 Global Costmap 和 TF 运行环境，返回 nav_msgs/Path。

5.6 验证、发布并成功收口 ​

Action 主链里的 validatePath() 只做一个检查：Path 是否为空。

Path 非空后执行以下步骤。

5.6.1 发布 Plan ​

发布 plan Topic。

5.6.2 计算规划时间 ​

计算 planning_time。

5.6.3 检查期望耗时 ​

如果超过期望耗时则输出告警。

5.6.4 返回成功 ​

把 Action 标记为 SUCCEEDED。

这里的“路径有效”只代表“插件返回了至少一个 Pose”，不代表服务器已经逐点做过碰撞检查。碰撞有效性是 /is_path_valid Service 的另一套逻辑。

六、多目标规划：逐段计算，再拼成一条路 ​

computePlanThroughPoses() 与单目标主链共用大部分辅助函数，但中间增加了分段循环。

处理过程如下。

6.1 获取初始 Start ​

获取初始 Start。

6.2 选择当前 Goal ​

取第一个 Via Point 作为当前 Goal。

6.3 转换规划坐标系 ​

把当前 Start 和 Goal 转换到 Global Costmap Frame。

6.4 计算分段 Path ​

调用同一个 GlobalPlanner 插件生成当前分段 Path。

6.5 检查分段结果 ​

检查当前分段 Path 非空。

6.6 拼接分段 Path ​

把当前分段全部 Pose 追加到 concat_path。

6.7 更新下一段 Start ​

使用 concat_path 的最后一个 Pose 作为下一段 Start。

6.8 发布完整 Path ​

所有分段成功后发布并返回完整 Path。

只要任意一段返回空 Path、TF 转换失败或插件抛异常，整个多目标 Action 都会失败，不会返回“成功规划的前半段”。

planning_time 统计整个多点任务，从进入回调、等待 Costmap、逐段转换和逐段搜索，一直到最终拼接完成。

当前实现对空 goals[] 会先终止当前 Goal，但没有立即 return，后续仍会执行空路径发布和成功收口调用；因为 Goal Handle 已被终止，最终终态仍不会变成成功，但这属于不必要的后续执行。

七、路径有效性 Service：为什么只检查“机器人前方” ​

isPathValid() 不会从 Path 第一个点开始盲目检查，而是先获取机器人当前位姿，找到路径中距离机器人最近的 Pose，然后只检查该点之后的剩余路径。

原因很实际：机器人已经走过的 Path 可能被新障碍占用，但它不应该导致前方仍安全的路径被判无效。

7.1 半径机器人模型 ​

当 Costmap 使用机器人半径时，每个路径点转换为地图栅格：

  • 超出 Costmap 范围，按 LETHAL 处理。
  • 栅格为 LETHAL_OBSTACLE，路径无效。
  • 栅格为 INSCRIBED_INFLATED_OBSTACLE，路径无效。

7.2 Footprint 机器人模型 ​

当 Costmap 使用多边形 Footprint 时，服务器根据每个路径点的位置和 Yaw，把机器人轮廓放到地图中，通过 FootprintCollisionChecker 计算碰撞代价。

检测到 LETHAL 碰撞时返回无效。

7.3 当前实现的两个接口边界 ​

7.3.1 不填充 invalid_pose_indices ​

虽然 Service 定义包含该字段，但当前代码只在遇到第一个无效点时把 is_valid 设为 false，并立即退出，没有记录索引。

7.3.2 机器人位姿获取失败时保持 true ​

函数一开始把 is_valid 设为 true。只有成功获取机器人位姿后才执行碰撞检查；如果当前位姿获取失败，没有显式失败分支，响应会保持 true。

因此在定位或 TF 不可靠的场景，不能把 is_path_valid=true 单独当作路径安全的充分证据，还应同时确认定位链路可用。

八、第二层状态：Action 成功、取消、抢占与失败 ​

Lifecycle ACTIVE 只说明 Planner Server 能接受请求。每个规划 Goal 还有自己的 Action 状态。

8.1 SUCCEEDED ​

插件返回非空 Path，坐标转换成功，服务器发布结果并调用 succeeded_current()。

8.2 CANCELED ​

规划回调刚开始时，如果发现客户端已请求取消，调用 terminate_all()。SimpleActionServer 会把 canceling 状态的 Goal 标记为 CANCELED。

8.3 ABORTED ​

主要失败入口包括：

  • use_start=false 时无法获取机器人当前位姿。
  • 起点或目标无法转换到 Global Costmap Frame。
  • 多插件配置下 planner_id 无效。
  • Planner 插件返回空 Path。
  • Planner 插件抛出异常。
  • 多目标任务的任意分段失败。

8.4 规划过程不是可抢占计算内核 ​

nav2_core::GlobalPlanner::createPlan() 接口没有取消 Token。插件一旦进入搜索，Planner Server 无法从外部中断本次算法，只能等 createPlan() 返回。

同样，取消检查只发生在 waitForCostmap() 之前。等待 Costmap 期间没有再次检查取消，插件计算期间也没有服务器级中断点。因此当前实现的取消响应不是全流程即时的。

九、当前 checkout 的抢占边界：新 Goal 接管了句柄，旧请求仍可能参与计算 ​

当前头文件中，抢占辅助函数签名为：

cpp
template<typename T>
void getPreemptedGoalIfRequested(
  std::unique_ptr<nav2_util::SimpleActionServer<T>> & action_server,
  typename std::shared_ptr<const typename T::Goal> goal);

第二个参数 goal 按值传递。

函数内部执行：

cpp
goal = action_server->accept_pending_goal();

这只修改辅助函数内部的 shared pointer 副本，不会更新 computePlan() 或 computePlanThroughPoses() 中的外层 goal 变量。

结果可能是：

  • SimpleActionServer 已经把 Pending Goal 设为新的 Current Goal。
  • 旧 Goal Handle 被 ABORTED。
  • 但本轮起点、目标和 planner_id 仍从外层旧 Goal 读取。
  • 最终结果可能发送给新 Goal Handle，却是按旧请求计算的 Path。

这是当前工程源码的静态审计结论，不是 Global Planner 插件的算法问题，也不应推广成所有 Nav2 版本的行为。

更符合预期的接口应让 Goal 指针按引用传入，或直接在调用者中接收 accept_pending_goal() 的返回值。

本文只记录问题，不修改源码。

十、动态参数：expected_planner_frequency 不会触发周期规划 ​

Planner Server 动态处理两个参数。

10.1 expected_planner_frequency ​

服务器把它转换为：

text
max_planner_duration = 1 / expected_planner_frequency

规划总耗时超过该值时只输出警告。它不会创建 Timer，也不会让 Planner Server 自动按该频率重规划。

真正的重规划频率由上层决定：

  • 行为树的 RateController。
  • 自研 RegulatedNavigator 的 replan_frequency。
  • 外部 Action Client 的调用频率。

而且 planning_time 从 Action 回调开始计时，包含等待 Global Costmap、起终点转换和插件计算，不只是搜索算法耗时。

10.2 selected_planner ​

动态修改为非空 ID 时，服务器会先检查该 ID 是否已经加载；无效值会拒绝参数更新。设置为空字符串后，重新允许 Action Goal 的 planner_id 决定算法。

computePlan() 和 computePlanThroughPoses() 在整个任务期间持有 dynamic_params_lock_，动态参数回调会等待规划结束。若任务阻塞在无超时的 waitForCostmap()，参数更新也会同时被阻塞。

十一、源码函数地图：从入口到结果分别在哪里 ​

11.1 节点入口 ​

  • src/main.cpp：初始化 ROS 2 和日志，创建 PlannerServer 并 Spin。

11.2 Lifecycle 与资源管理 ​

  • PlannerServer::PlannerServer()：声明插件参数并创建 Global Costmap 对象。
  • on_configure()：配置 Costmap、加载插件、创建 Publisher 与双 Action。
  • on_activate()：激活资源、创建路径检查 Service 和 Bond。
  • on_deactivate()：停 Action、Publisher、Costmap 和插件。
  • on_cleanup()：释放规划运行时。

11.3 Action 主链 ​

  • computePlan()：单目标规划。
  • computePlanThroughPoses()：多目标逐段规划与拼接。
  • getStartPose()：选择请求 Start 或当前机器人位姿。
  • transformPosesToGlobalFrame()：统一规划坐标系。
  • getPlan()：选择插件并调用 createPlan()。
  • validatePath()：检查返回 Path 非空。
  • publishPlan()：发布可视化 Path。

11.4 状态辅助 ​

  • isServerInactive()：检查 Action Server 是否可用。
  • isCancelRequested()：处理取消请求。
  • waitForCostmap()：等待 Global Costmap Current。
  • getPreemptedGoalIfRequested()：接受 Pending Goal。

11.5 路径检查与参数 ​

  • isPathValid()：检查当前 Path 剩余段是否与 Costmap 冲突。
  • dynamicParametersCallback()：更新耗时告警阈值和强制 Planner ID。

十二、排查规划问题时，优先看这九个点 ​

12.1 Action Server 找不到 ​

确认 planner_server 已进入 ACTIVE。仅启动节点进程而没有完成 Lifecycle 激活，两个规划 Action 不会工作。

12.2 请求一直不返回 ​

检查 global_costmap 是否 Current。waitForCostmap() 没有超时，是最需要优先排查的等待点。

12.3 明明请求 Smac，却总在运行 NavFn A* ​

检查 selected_planner。非空时它会覆盖 Action 中的 planner_id。

12.4 TF 报错或起点获取失败 ​

确认 Robot Base Frame、目标 Frame 和 Global Costmap Frame 之间的变换完整。use_start=false 也依赖机器人当前位姿 TF。

12.5 Action 成功但 RViz 没有 plan ​

检查 Topic 名称、命名空间和订阅者数量。Publisher 没有订阅者时不会发送 Topic，但 Action Result 仍可能成功返回 Path。

12.6 planning_time 比插件日志中的搜索时间长 ​

这是正常现象。Action 统计包含 Costmap 等待、TF 转换、分段循环和结果处理。

12.7 多点路径交界处有重复 Pose ​

当前实现直接拼接各分段全部 Pose，没有去除相邻分段共享的起终点。

12.8 is_path_valid=true 但定位已经丢失 ​

当前函数在机器人位姿获取失败时保持默认 true，需要额外检查 TF 和定位状态。

12.9 抢占后路径仍指向旧目标 ​

检查当前分支按值传递 Goal 的抢占辅助函数。这是服务器编排层问题，不要先归因于规划算法。

十三、把整个包压缩成一句话 ​

nav2_planner 可以概括为：

用 Lifecycle 管理 Global Costmap、TF、双规划 Action 和 GlobalPlanner 插件，把单点或多点目标统一转换到全局坐标系，选择规划算法生成 Path，并通过 Result、plan Topic 和 is_path_valid Service 把路径交给上层导航系统。

目标点只是“想去哪里”，Global Costmap 描述“哪里能走”，Planner 插件决定“怎样搜索”。

而 PlannerServer 的价值，是把这三者变成一条稳定、可切换、可被上层编排的全局路径生产线。

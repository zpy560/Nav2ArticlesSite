一条 SpeedLimit，如何把整套局部控制器限速？拆解 Nav2 的消息、Costmap 与控制闭环 ​

机器人进入危险区域后为什么会自动变慢？为什么一条看起来只有三个字段的 nav2_msgs/msg/SpeedLimit，最终能够改变 DWB、RPP、MPPI 甚至 TEB 的速度约束？更容易误判的是：SpeedLimit 不是速度指令，也不是停车指令，它是一条异步到达的“控制器约束事件”。本文沿着当前项目源码，把它从消息定义、两类生产者、Topic 传输、ControllerServer 分发、局部控制器内部参数更新，一直追到 /cmd_vel 和 /control_to_uart。

本文审计的是当前 checkout 中的实现，重点涉及 nav2_msgs、nav2_costmap_2d、nav2_route、nav2_controller、DWB、RPP、MPPI、Graceful、RotationShim、TEB 和项目自定义的 nav2_regulated_modules。文章中的行号指向当前源码，而不是泛化后的伪实现。

一、先给结论：SpeedLimit 是约束消息，不是速度消息 ​

1.1 消息真正携带了什么 ​

navigation2/nav2_msgs/msg/SpeedLimit.msg 的定义非常短：

text
std_msgs/Header header
bool percentage
float64 speed_limit

消息被 navigation2/nav2_msgs/CMakeLists.txt:15-20 加入 rosidl_generate_interfaces()，因此 nav2_msgs 只负责生成类型，不负责决定谁发布、谁订阅以及速度如何应用。

三个字段的职责并不对称：

  • header 携带时间戳和坐标系信息。当前 ControllerServer 的回调不读取它，因此它目前没有参与限速有效性判断。
  • percentage 是单位模式开关。true 表示百分比，false 表示绝对速度。
  • speed_limit 是数值本身。它不能脱离 percentage 单独解释。

这意味着下面两条消息的物理意义完全不同：

yaml
# 基础速度为 0.26 m/s 时，实际约束为 0.13 m/s
percentage: true
speed_limit: 50.0
yaml
# 实际约束为 0.10 m/s
percentage: false
speed_limit: 0.10

1.2 0.0 为什么不是停车 ​

nav2_costmap_2d/costmap_filters/filter_values.hpp:56-59 把 NO_SPEED_LIMIT 定义为 0.0。各控制器收到这个值后，通常会恢复配置阶段保存的基础速度上限。

所以：

text
speed_limit = 0.0  -> 解除动态限速，恢复控制器默认约束
speed_limit 很小   -> 真正降低速度
cmd_vel = 0.0      -> 才是速度指令层面的停车

如果把 0.0 当成停车命令，排查结果会完全反过来。SpeedLimit 只改变“控制器允许生成多大的速度”，不直接写入 cmd_vel。

二、两条生产链：语义地图和路线边都能产生限速 ​

2.1 两类生产者汇入同一个 Topic ​

当前仓库中，真正构造并发布 nav2_msgs::msg::SpeedLimit 的生产分支主要有两条：

  • nav2_costmap_2d::SpeedFilter：根据机器人当前所在语义栅格区域计算限速。
  • nav2_route::AdjustSpeedLimit：根据路线图当前进入边的 metadata 计算限速。

它们都可以发布到默认的 speed_limit Topic，最终汇入 ControllerServer。

这是一种“多生产者、单消费入口”的架构。它的好处是控制器不需要知道限速来自语义地图还是路线图；代价是当前实现没有消息来源、优先级和冲突仲裁字段。

2.2 Costmap SpeedFilter：从当前位置栅格读出速度 ​

SpeedFilter 是 Costmap Filter 的一个插件。它不像普通障碍层那样把雷达或静态地图合成到 master Costmap，而是把 filter_mask 看成一张语义规则地图。

完整输入可以写成：

text
CostmapFilterInfo
        +
filter_mask：nav_msgs/msg/OccupancyGrid
        +
机器人在 global frame 下的当前位姿
        ↓
SpeedFilter
        ↓
nav2_msgs/msg/SpeedLimit

CostmapFilterInfo.msg 的 type、filter_mask_topic、base 和 multiplier 共同解释掩码。当前定义中，type=1 表示百分比限速，type=2 表示绝对速度限速；转换公式是：

text
target_value = mask_cell_value * multiplier + base

例如：

text
mask_cell_value = 85
base = 100
multiplier = -1
percentage = true

target_value = 85 * (-1) + 100 = 15

这就是“栅格值 85 代表速度百分之十五”的来源。地图文件只保存栅格整数，具体数值空间由 CostmapFilterInfo 决定。

2.3 SpeedFilter 的位置查询和发布门控 ​

SpeedFilter::process() 位于 navigation2/nav2_costmap_2d/plugins/costmap_filters/speed_filter.cpp:137-203，核心过程可以拆成几个连续阶段：

2.3.1 读取当前机器人位姿 ​

基础 CostmapFilter 在 updateBounds() 阶段保存机器人当前的 x、y、yaw，随后在 updateCosts() 中调用插件的 process()。

如果掩码和当前 Costmap 不在同一个坐标系，过滤器先通过 TF 把机器人位置转换到掩码坐标系；转换失败时直接返回。

2.3.2 把世界坐标映射成掩码索引 ​

worldToMask() 根据掩码的原点、分辨率、宽度和高度计算整数索引。它本质上是：

text
mx = (world_x - origin_x) / resolution
my = (world_y - origin_y) / resolution

因此限速区域边界是离散栅格边界。机器人跨过相邻栅格后，限制值可能突然切换。

2.3.3 把特殊栅格转换成控制语义 ​

  • 栅格值为 0：设置 NO_SPEED_LIMIT=0.0。
  • 栅格值为 -1：视为未知，记录错误并返回。
  • 栅格值为 1～100：套用 data * multiplier + base。
  • 百分比模式：结果必须在 0～100 之间。
  • 绝对模式：结果不能小于 0 m/s。

2.3.4 只有值变化才发布 ​

SpeedFilter 保存 speed_limit_prev_。如果当前限制与上一次相同，它不会重复发布。这能减少控制面上的无效消息，但也意味着 /speed_limit 不是周期性心跳。

当前实现还存在一个安全边界：TF 失败、掩码越界或未知栅格时，process() 直接返回，不主动发布恢复消息。如果控制器此前已经收到低速限制，旧限制可能继续留在控制器内部，直到下一条有效的 SpeedLimit 改变它。

2.4 Route AdjustSpeedLimit：从路线边 metadata 读出速度 ​

Route 分支的调用时机不是 Costmap 的每次更新，而是路线状态变化。

RouteTracker 发现机器人到达当前节点并切换到下一条边后，将 status_change 置为真，再调用 OperationsManager::process()。OperationsManager 随后执行图操作和状态变化操作，AdjustSpeedLimit 就在这个阶段读取进入边的 metadata。

默认操作列表在 navigation2/nav2_route/src/operations_manager.cpp:34-38 中包含 AdjustSpeedLimit。插件的 perform() 位于 navigation2/nav2_route/src/plugins/route_operations/adjust_speed_limit.cpp:45-66，它的行为是：

  • 没有进入边时直接返回。
  • 从边 metadata 读取 speed_tag，默认键为 speed_limit。
  • 找不到键时使用 100.0。
  • 固定设置 percentage=true。
  • 发布 SpeedLimit。

因此当前实现把路线边上的 speed_limit 统一解释为百分比。仓库示例图 navigation2/nav2_route/graphs/sample_graph.geojson:63 中的 0.85，按当前代码就是百分之零点八五，而不是百分之八十五。

假设 DWB 的基础最大速度为 0.26 m/s：

text
0.26 * 0.85 / 100 = 0.00221 m/s

这足以让机器人看起来“有控制反馈，但几乎不走”。如果业务数据实际想表达百分之八十五，应写成 85.0；如果想表达 0.85 m/s，则不能直接使用当前这个固定百分比的 AdjustSpeedLimit 语义。

这里还有一个源码级参数问题：插件声明了 AdjustSpeedLimit.speed_limit_topic，但实际读取的是 AdjustSpeedLimit.speed_tag。当用户试图通过参数改变输出 Topic 时，配置可能不会按预期生效。

三、统一入口：ControllerServer 如何接住这条消息 ​

3.1 Topic 名称和订阅时机 ​

ControllerServer 在构造阶段声明：

cpp
declare_parameter("speed_limit_topic", "speed_limit");

配置阶段读取参数，并在创建 FollowPath Action Server 后建立订阅：

cpp
speed_limit_sub_ = create_subscription<nav2_msgs::msg::SpeedLimit>(
  speed_limit_topic, rclcpp::QoS(10),
  std::bind(&ControllerServer::speedLimitCallback, this, std::placeholders::_1));

对应源码位置是 navigation2/nav2_controller/src/controller_server.cpp:53、105-106、175-181。

当前 nav2_regulated_modules/params/regulated_modules.yaml 没有显式设置 speed_limit_topic，因此默认使用相对 Topic speed_limit；在当前无命名空间启动方式下，实际通常表现为 /speed_limit。

3.2 回调不保存消息，而是立即广播约束 ​

回调的实现只有一个关键动作：遍历 controllers_，对每个已加载控制器调用：

cpp
controller->setSpeedLimit(msg->speed_limit, msg->percentage);

源码位于 navigation2/nav2_controller/src/controller_server.cpp:549-553。

这里有三个容易忽略的事实：

  • 它更新的是所有已加载控制器，不只是当前执行 FollowPath 的那个控制器。
  • 它不读取 header.frame_id，因此不会根据坐标系拒绝消息。
  • 它不读取 header.stamp，因此不会判断消息是否过期。

当前项目的 Controller Server 一次加载 DWB、RPP、MPPI、GracefulController 和 RotationShimController，但 regulated_navigator 的 controller_id 设置为 DWB。所以限速消息会同步写入五个控制器的内部状态，实际当前周期主要由 DWB 使用。

3.3 为什么没有“速度限制栈” ​

从当前实现看，ControllerServer 没有维护这样的结构：

text
地图限速
路线限速
人工限速
安全限速
取最小值

它只有一个回调入口，收到哪条消息，就把哪条消息直接传给控制器。多个节点发布同一 Topic 时，ROS 2 会把多条消息交给订阅者，但消息内部没有来源标识和优先级，最终状态由到达顺序决定。

因此，如果未来同时启用 Costmap SpeedFilter、Route AdjustSpeedLimit 和外部人工限速节点，应该在系统设计层提前决定：

  • 是否只允许一个节点发布 /speed_limit。
  • 是否由单独仲裁器取所有限制的最小值。
  • 是否把不同来源拆到不同 Topic，再由一个安全节点统一输出。

四、控制器收到限制后，内部到底改了什么 ​

nav2_core::Controller 把统一接口定义为：

cpp
virtual void setSpeedLimit(
  const double & speed_limit,
  const bool & percentage) = 0;

接口注释明确规定：percentage=true 按最大速度百分比解释，false 按 m/s 绝对值解释；插件应在后续控制周期使用最新限制。不同控制器对“速度”的内部定义并不一样，因此同一条消息不会产生完全相同的参数变化。

4.1 DWB：同时缩放线速度和角速度采样边界 ​

DWB 的调用链是：

text
ControllerServer
  -> DWBLocalPlanner::setSpeedLimit()
  -> StandardTrajectoryGenerator::setSpeedLimit()
  -> KinematicsHandler::setSpeedLimit()

KinematicsHandler 在百分比模式下缩放：

text
max_speed_xy
max_vel_x
max_vel_y
max_vel_theta

如果基础最大速度是 0.26 m/s，收到百分之五十后，DWB 的前向速度上限约为 0.13 m/s。角速度也会按相同比例缩放，这会改变 DWB 后续轨迹采样窗口。

绝对值模式存在一个重要边界：只有当绝对速度小于基础最大速度时，DWB 才降低约束；如果收到的绝对值大于基础值，当前实现不会自动恢复此前的低速状态。最稳妥的恢复方式仍然是发送 speed_limit=0.0。

实现位于 navigation2/nav2_dwb_controller/dwb_plugins/src/kinematic_parameters.cpp:127-164。

4.2 RPP：直接改变期望线速度 ​

RPP 在配置时保存 base_desired_linear_vel_。收到百分比限制时：

text
desired_linear_vel = base_desired_linear_vel * limit / 100

收到绝对值限制时，则直接把 desired_linear_vel_ 设置成消息中的数值。取消限制时恢复配置阶段保存的基础值。

这意味着同一个百分比消息在 RPP 中主要影响前向期望速度，而不是像 DWB 那样完整改写采样器的线速度、横向速度和角速度边界。源码位于 navigation2/nav2_regulated_pure_pursuit_controller/src/regulated_pure_pursuit_controller.cpp:121-122、680-696。

4.3 MPPI：缩放优化器的运动约束 ​

MPPI 先由 MPPIController::setSpeedLimit() 转发给 Optimizer::setSpeedLimit()，再修改：

text
vx_max
vx_min
vy
wz

百分比模式直接使用 limit / 100。绝对值模式使用 speed_limit / base_constraints.vx_max 作为比例，再同步缩放各个约束。

因此，MPPI 的限速不仅会影响最大前进速度，也会改变横向和角速度约束。源码位于 navigation2/nav2_mppi_controller/src/controller.cpp:128-131 和 navigation2/nav2_mppi_controller/src/optimizer.cpp:422-447。

4.4 Graceful、RotationShim 和 TEB 的差异 ​

GracefulController 会同时改变线速度和角速度上限，并在百分比模式下使用 v_linear_min 保护线速度下限；绝对模式下，角速度按绝对线速度与基础线速度的比例调整。实现位于 navigation2/nav2_graceful_controller/src/graceful_controller.cpp:219-241。

RotationShimController 不重新解释消息，而是把限制转发给 primary_controller_。当前项目的主控制器是 DWB，源码位于 navigation2/nav2_rotation_shim_controller/src/nav2_rotation_shim_controller.cpp:363-366。

TEB 也实现了 setSpeedLimit()，会修改自身的机器人速度配置；它属于当前仓库的通用消费者，但没有加入当前 regulated_modules 的控制器列表。

五、从 FollowFixedPath 到底盘：SpeedLimit 在哪里插入 ​

5.1 固定路径 Action 和限速消息是两条并行输入 ​

当前项目的固定路径请求大致沿着下面的控制链进入：

text
FollowFixedPath
      ↓
regulated_navigator
      ↓ 发送 FollowPath
ControllerServer
      ↓ 选中 DWB
DWB::computeVelocityCommands()
      ↓
/cmd_vel_nav
      ↓
velocity_smoother
      ↓
/cmd_vel
      ↓
controlpub
      ↓
/control_to_uart

SpeedLimit 不在这条路径上携带一个新的速度值，而是在 ControllerServer 旁路进入：

text
/speed_limit
      ↓
ControllerServer::speedLimitCallback()
      ↓
DWB 内部速度约束
      ↓
下一次 computeVelocityCommands()

所以它的作用时序是：限速消息先改变控制器状态，随后控制器在下一个控制周期生成受约束的 Twist。

5.2 velocity_smoother 和 controlpub 不知道 SpeedLimit ​

当前 Launch 将 Controller Server 的输出重映射为 cmd_vel_nav，再将 velocity_smoother 的输入接到这个 Topic，并把平滑输出重映射为 /cmd_vel。对应配置位于 navigation2/nav2_regulated_modules/launch/regulated_modules.launch.py:200-231。

controlpub 的输入参数是 /cmd_vel，输出是 /control_to_uart，对应 Launch 文件的 242-248 行。它接收的是已经经过控制器和速度平滑器处理后的速度消息，不会读取 nav2_msgs/msg/SpeedLimit。

这条边界非常重要：如果 /speed_limit 正确到达 ControllerServer，但 /cmd_vel 仍然为零，问题就已经不在 SpeedLimit 消息本身，而要继续检查 DWB 是否生成轨迹、Costmap 是否阻塞、速度平滑器是否限幅，以及 controlpub 是否继续发布到底盘。

六、当前项目配置下，哪些分支实际会运行 ​

6.1 regulated_modules 当前没有 Costmap SpeedFilter ​

当前 navigation2/nav2_regulated_modules/params/regulated_modules.yaml:405-418 的局部 Costmap 插件只有：

yaml
plugins: ["voxel_layer", "inflation_layer"]

没有：

yaml
filters: ["speed_filter"]

因此，使用当前 fixed_path Launch 时，局部 Costmap 不会自己根据 filter_mask 发布 /speed_limit。仓库的 Costmap Filter 系统测试配置则明确加载了 SpeedFilter，例如 navigation2/nav2_system_tests/src/costmap_filters/speed_global_params.yaml:218-243。

当前 fixed_path 运行中，如果观察到 /speed_limit 有 publisher，优先确认它是不是：

  • 外部自定义限速节点。
  • 独立启动的 Costmap SpeedFilter。
  • Route Server 加载的 AdjustSpeedLimit。

6.2 为什么百分之零点五会制造“车不走”假象 ​

当前 DWB 配置的最大前向速度为 0.26 m/s。如果收到：

yaml
percentage: true
speed_limit: 0.5

则 DWB 的前向上限约为：

text
0.26 * 0.5 / 100 = 0.0013 m/s

这不是零，但已经低到很难在真实底盘上观察到运动。Route 示例中的 0.85 甚至只对应约 0.00221 m/s。

排查时不要只看反馈里的 distance_remaining 是否变化，还要同时观察：

text
/speed_limit
/cmd_vel_nav
/cmd_vel
/control_to_uart

如果 /cmd_vel_nav 只有极小的非零线速度，SpeedLimit 的单位解释就是首要嫌疑；如果 /cmd_vel_nav 已经正常而 /cmd_vel 变为零，则问题在 Velocity Smoother 或其下游。

6.3 SpeedLimit 的恢复路径 ​

语义地图驶出限速区域时，SpeedFilter 会在栅格值为 0 时生成 speed_limit=0.0，控制器随后恢复默认约束。

Route AdjustSpeedLimit 在进入缺少 speed_limit metadata 的边时，当前实现默认发送 100.0%，这对百分比模式控制器通常等价于恢复基础速度，但它不是统一的 NO_SPEED_LIMIT 哨兵。

如果消息生产者停止发布，ControllerServer 不会自行恢复；恢复动作必须由生产者显式发送。

七、设计优点与当前实现边界 ​

7.1 为什么不用一个 Topic 直接发最终 cmd_vel ​

把限速做成独立消息，有几个结构性优势：

  • 语义地图、路线图和外部规则都能成为限速生产者，控制器不需要知道来源。
  • 控制器可以在内部保留自己的基础参数，并把动态限制叠加到这些基础参数上。
  • DWB、RPP、MPPI 等算法可以根据自己的运动模型解释同一份限制，而不是被迫共用一套速度公式。
  • 限速不会绕过 Costmap、控制器、速度平滑器和底盘接口之间已有的安全边界。
  • SpeedLimit 与 cmd_vel 分离后，调试时可以分别回答“约束有没有到”和“控制器最终发了什么”。

这就是它比“另起一个节点强行覆盖 /cmd_vel”更适合 Nav2 的地方：它改变的是控制器决策空间，不是从链路末端粗暴截断结果。

7.2 当前实现还缺少哪些安全能力 ​

从当前源码看，SpeedLimit 还不是一个完整的安全仲裁协议：

  • 消息没有来源 ID，无法区分地图限速、路线限速和人工限速。
  • ControllerServer 不校验 header.stamp，没有统一超时恢复。
  • 多发布者共享同一 Topic 时没有取最小值或优先级规则。
  • percentage 只是布尔模式，缺少范围和单位版本校验；Route 分支当前也没有主动验证百分比是否在 0～100。
  • 不同控制器对绝对速度超过基础上限的处理不一致，不能假设所有插件都只会“降低”速度。
  • SpeedFilter 在 TF 失败、越界和未知栅格时直接返回，未必能把已经生效的旧限速恢复掉。

如果要把它用于真实车辆，建议把“来源、优先级、有效期、恢复策略”放到上层限速仲裁器中，而不是继续让多个节点直接竞争 /speed_limit。

八、现场调试时应沿着数据流逐段确认 ​

可以用下面的命令先确认消息生产和控制传播：

bash
ros2 interface show nav2_msgs/msg/SpeedLimit
ros2 topic info /speed_limit --verbose
ros2 topic echo /speed_limit
ros2 topic echo /cmd_vel_nav
ros2 topic echo /cmd_vel

观察顺序应当是：

  • /speed_limit 是否存在 publisher。
  • percentage 是否符合生产者约定。
  • speed_limit 是否误写成 0.5、0.85 这类极小百分比。
  • ControllerServer 是否加载并激活了预期控制器。
  • /cmd_vel_nav 是否已经产生合理速度。
  • /cmd_vel 是否被速度平滑器继续限幅或置零。
  • controlpub 是否收到 /cmd_vel 并发布 /control_to_uart。

最终可以把整条链压缩成一句话：

text
语义区域或路线边
  -> 生成 SpeedLimit
  -> ControllerServer 广播约束
  -> 局部控制器更新内部速度边界
  -> computeVelocityCommands 生成受限 Twist
  -> velocity_smoother
  -> controlpub
  -> 底盘

SpeedLimit 真正改变的是“控制器允许怎么走”，而不是“底盘直接收到什么”。理解这条边界，才能把“消息没到”“控制器限得太低”“速度平滑器置零”和“底盘输出失败”从同一个表象中区分开。

Nav2 为什么不会“一窝蜂启动”？拆解 nav2_lifecycle_manager 全数据流 ​

Nav2 里有 map_server、AMCL、planner_server、controller_server、bt_navigator 等一批服务器。进程启动，只代表它们进入了 ROS graph；参数是否加载成功、插件是否创建完成、Action 是否可以接单，仍然是另一回事。

nav2_lifecycle_manager 解决的正是这个问题：它把一组 Lifecycle 节点当成一个系统，统一控制启动、暂停、恢复、重置和关闭，并用 Bond 心跳监控节点是否仍然存活。

这篇文章不逐行翻译源码，而是沿着请求、状态迁移、心跳和故障恢复四条数据流，把它的完整工作过程拆开。

一、它管理的不是进程，而是“可用状态” ​

普通 ROS 2 节点启动后通常立即开始工作。Lifecycle 节点不同，它需要经过明确的主状态：

text
unconfigured → inactive → active → finalized

unconfigured 表示进程存在，但业务资源尚未配置；inactive 表示参数、插件和通信资源已经准备好，但还不对外工作；active 才表示 Publisher、Action Server 和控制循环真正可用。

Lifecycle Manager 位于调用方和所有托管节点之间。外部只向管理器发送一条命令，管理器再逐个调用每个节点的 lifecycle 服务。

它对外暴露两个核心服务：

  • /<manager>/manage_nodes：类型为 nav2_msgs/srv/ManageLifecycleNodes，接收 STARTUP、RESET、SHUTDOWN、PAUSE、RESUME。
  • /<manager>/is_active：类型为 std_srvs/srv/Trigger，返回内部的 system_active_。

注意，is_active 并不会临时遍历所有节点重新查询状态，它返回的是管理器维护的系统标志。因此这个标志是否可靠，取决于所有状态迁移和 Bond 故障处理是否完整执行。

二、构造阶段已经搭起三条执行链 ​

LifecycleManager 本身是普通 rclcpp::Node，既可以作为独立可执行文件运行，也注册成 rclcpp_components 组件。

构造函数首先读取五个关键参数：

  • node_names：托管节点列表，也是启动顺序。
  • autostart：是否创建完客户端后自动执行 STARTUP。
  • bond_timeout：Bond 心跳超时时间，默认 4 秒；设为 0 会关闭 Bond 监控。
  • bond_respawn_max_duration：等待崩溃节点恢复的最大窗口，默认 10 秒。
  • attempt_respawn_reconnection：是否尝试在节点重生后自动拉起整组系统。

这里形成三条链：

2.1 命令链 ​

manage_nodes 收到请求后进入 managerCallback()，再分派给 startup()、reset()、shutdown()、pause() 或 resume()。

2.2 节点控制链 ​

一个 0 秒 wall timer 延迟创建 LifecycleServiceClient，每个 node_names 元素对应一个客户端，负责调用该节点的 change_state 和 get_state。

2.3 健康链 ​

DiagnosticUpdater 持续发布 Nav2 Health，Bond timer 在系统 active 后检查各节点心跳。

两个管理服务被放入 MutuallyExclusive callback group，并由独立的 SingleThreadedExecutor 和 NodeThread 执行。这意味着同一个管理器不会同时处理两条状态命令，避免 STARTUP 与 RESET 之类的操作交叉执行。

三、STARTUP 不是逐节点“配置后立刻激活” ​

STARTUP 的真实顺序很重要。源码不是让 N1 configure、N1 activate，然后处理 N2；而是分成两个完整阶段。

3.1 全量 Configure ​

N1 configure → N2 configure → … → Nn configure。

3.2 全量 Activate ​

N1 activate → N2 activate → … → Nn activate。

3.3 核验单次状态迁移 ​

每次迁移都包含两次判断。

3.3.1 调用状态变更服务 ​

调用 change_state(transition) 并检查服务返回。

3.3.2 核验最终主状态 ​

调用 get_state()，确认节点确实到达 transition_state_map_ 记录的目标主状态。服务调用成功但最终状态不对，同样会被判为失败。

3.4 建立 Bond 与系统状态 ​

当节点进入 active，管理器会为它创建 Bond：

text
topic：bond
heartbeat period：0.10 s
heartbeat timeout：bond_timeout
首次建链等待上限：bond_timeout / 2

只有全部节点 configure、activate 且 Bond 建立成功，管理器才执行：

text
system_active_ = true
createBondTimer()

任意一步失败，STARTUP 立即返回 false，并打印 Failed to bring up all requested nodes。它不会把“部分节点 active”包装成成功。

四、为什么启动正序，停机必须逆序 ​

node_names 不只是名单，它隐含依赖顺序。典型导航链可以写成：

text
controller_server → planner_server → behavior_server → bt_navigator

启动时按正序处理，使基础服务器先准备；停机时按逆序处理，让上层调用者先停止接单，再关闭下层能力。

五类命令的语义分别是：

4.1 STARTUP ​

正序 CONFIGURE，再正序 ACTIVATE，最后建立系统健康监控。

4.2 PAUSE ​

逆序 DEACTIVATE，节点保留已配置资源，系统可以快速恢复。

4.3 RESUME ​

正序 ACTIVATE，重新建立每个节点的 Bond。

4.4 RESET ​

逆序 DEACTIVATE，再逆序 CLEANUP，最终回到 unconfigured，但进程仍在。

4.5 SHUTDOWN ​

逆序 DEACTIVATE、CLEANUP、UNCONFIGURED_SHUTDOWN，最终进入 finalized，并销毁 lifecycle 客户端。

因此 PAUSE 和 RESET 不是一回事：PAUSE 保留配置结果，RESET 会释放插件、地图、代价地图等在 configure 阶段创建的业务资源。SHUTDOWN 更进一步，使 Lifecycle 节点到达终态，不能再从 finalized 重新 configure。

五、Bond 不是“在线状态图标”，而是故障触发器 ​

系统 active 后，管理器每 200 毫秒遍历 bond_map_。只要一个 Bond 的 isBroken() 返回 true，就认为整套 Nav2 已经失去一致性。

故障处理不是只重启掉线节点，而是：

text
单节点 Bond 断裂
→ system_active_ = false
→ reset(true)
→ 整组节点逆序 deactivate + cleanup
→ 清空 bond_map_

这里的 hard_reset=true 很关键。普通 RESET 遇到一个节点迁移失败会立即中止；硬重置会继续处理其余仍存活节点。因为崩溃节点已经无法响应 lifecycle 服务，如果仍采用普通模式，系统会卡在第一个失败点，其他节点继续 active，留下更危险的半工作状态。

这体现了 Lifecycle Manager 的核心取舍：一致性优先于局部可用性。规划器崩溃后，即使 controller_server 还活着，也不再把整套导航标记为 active。

六、节点重生后，管理器如何自动恢复 ​

6.1 启动 Respawn Timer ​

如果 attempt_respawn_reconnection=true，Bond 故障后会启动一个 1 秒周期的 respawn timer。

6.2 检查 Lifecycle 服务 ​

每轮检查依次对所有 node_names 调用 get_state()。这里关心的不是节点当前处于 active 还是 unconfigured，而是 lifecycle 服务是否重新可访问。

6.3 重新启动整组节点 ​

当所有服务都恢复，管理器停止 respawn timer，清零恢复起始时间，并重新调用 startup()。整组节点再次走完 configure、activate 和 Bond 建链流程。

6.4 超时后停止自动恢复 ​

如果超过 bond_respawn_max_duration 仍未全部恢复，自动恢复停止，系统保持 inactive，等待外部运维处理。

6.5 避免并发恢复 ​

如果外部已经把系统重新激活、ROS 正在退出，或 node_names 已清空，自动恢复会立即取消，避免与外部命令争抢状态机。

七、LifecycleManagerClient 做了什么 ​

LifecycleManagerClient 是 RViz2 或业务程序使用的轻量封装。构造时只需要管理器名称，例如：

cpp
LifecycleManagerClient client(
  "lifecycle_manager_navigation", parent_node);

它会拼出两个服务名：

text
lifecycle_manager_navigation/manage_nodes
lifecycle_manager_navigation/is_active

startup()、shutdown()、pause()、resume() 和 reset() 最终都进入同一个 callService()，区别只是请求中的 command 数值。

is_active() 有三种结果：ACTIVE、INACTIVE、TIMEOUT。服务不存在、等待超时或调用抛出运行时异常都会归为 TIMEOUT；服务正常返回后，再根据 response.success 区分 ACTIVE 与 INACTIVE。

八、结合真实报错，应该怎样定位 ​

看到下面的日志：

text
Failed to change state for node: map_server
Failed to bring up all requested nodes. Aborting bringup.

第二行只是汇总结论，第一行也不是最底层原因。真正应该向前找的是目标节点自己的 configure／activate 日志，以及它当时的 lifecycle 主状态。

常见根因有四类：

  • 参数、地图或插件在 on_configure() 中加载失败。
  • 节点当前状态不允许目标 transition，例如对 finalized 节点再次 configure。
  • 服务同名冲突，请求命中了旧实例。
  • 节点 active 后没有正确创建 Bond，管理器等待建链失败。

排障时先执行：

bash
ros2 lifecycle get /map_server
ros2 service list | grep manage_nodes
ros2 node list

如果使用仿真，还要确认 /clock 只有一个发布者。多个时钟源会让 TF buffer 和 RViz2 反复检测到时间倒退，看起来像 lifecycle 或显示故障，实际是系统时间基准已经不一致。

九、读完源码后最值得记住的六点 ​

9.1 管理整组节点的可用状态 ​

Lifecycle Manager 管的是整组节点的“可用状态”，不是简单拉起进程。

9.2 STARTUP 分为两个完整阶段 ​

STARTUP 是先全量 configure，再全量 activate，不是逐节点一步到位。

9.3 启停顺序表达依赖关系 ​

启动按 node_names 正序，停止和清理按逆序，列表顺序就是依赖设计。

9.4 同时检查服务与最终状态 ​

每次迁移既检查服务返回，也核验最终主状态。

9.5 Bond 故障触发整组硬重置 ​

任何 Bond 故障都会让整组系统硬重置，以一致性换取安全。

9.6 全部服务恢复后才重新 STARTUP ​

respawn 恢复只有在全部 lifecycle 服务重新出现后才会重新 STARTUP。

nav2_lifecycle_manager 的代码量不算大，但它决定了 Nav2 是一堆“进程都在”的节点，还是一套状态一致、可监控、可恢复的导航系统。

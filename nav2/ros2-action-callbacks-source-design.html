三个回调为什么到了规划器只剩两个？从 Nav2 源码拆透 ROS 2 Action ​

同样是 rclcpp_action::Client<ActionT>::SendGoalOptions，为什么 navigator_control.cpp 同时设置 goal_response_callback、feedback_callback 和 result_callback，到了 navigator_planning.cpp 却只剩下两个？

答案不是少写了一段代码，也不是 Planner Server 不支持 Action，而是两类任务对“中间过程”的需求不同。

FollowPath 是持续执行型任务。机器人可能沿路径运行数十秒，调用方需要知道 Goal 是否被接收、当前还剩多远、机器人速度是多少，以及最终成功还是失败。因此，三个回调都有明确的数据。

ComputePathToPose、ComputePathThroughPoses 和 SmoothPath 是有界计算型任务。调用方关心请求有没有被接受，以及最终返回哪条 Path。它们当前的 Action 接口没有定义有效的 Feedback 字段，所以不注册 feedback_callback 才是更准确的设计。

本文以当前 navigation2 源码和本机 ROS 2 Humble 的 rclcpp_action 头文件为依据，从这个小差异出发，完整拆开 ROS 2 Action 的客户端函数、服务端函数、五条底层通道、取消语义和异步回调防护。

一、回调数量不同的直接答案 ​

1.1 控制模块注册了三个回调 ​

navigator_control.cpp 的 sendFollowPath() 构造 FollowPath::Goal 后，给 SendGoalOptions 安装三个客户端回调：

  • goal_response_callback：判断 Controller Server 是否接受 Goal，并保存活动 Goal Handle。
  • feedback_callback：接收剩余距离和当前速度。
  • result_callback：处理成功、失败和取消后的最终收口。

控制任务不是“一次输入、立即输出”的计算，而是一段持续占用机器人的物理执行过程。中间反馈可以直接服务上层调度、界面显示、超时判断和固定路径 Action 的反馈转发。

1.2 规划模块只注册了两个回调 ​

navigator_planning.cpp 会向三个 Action 发送 Goal：

  • ComputePathToPose：计算当前位置到单个目标的路径。
  • ComputePathThroughPoses：计算经过多个目标点的路径。
  • SmoothPath：对原始 Path 做平滑处理。

三个 Action 都设置 goal_response_callback 和 result_callback，但都没有设置 feedback_callback。原因就在对应 .action 文件的 Feedback 区：它们只有注释，没有任何业务字段。

1.3 判断依据是数据语义 ​

SendGoalOptions 提供三个回调槽，不代表三个槽必须全部填写。ROS 2 Humble 中，这三个成员默认都是 nullptr，客户端可以按需使用。

回调数量应由以下事实决定：

  • .action 是否定义了有效字段。
  • 服务端是否真的发布对应数据。
  • 中间过程对调用方是否有决策价值。
  • 回调是否会改变上层状态、监控或人机界面。

为了让两个文件看起来对称而注册一个空 Feedback 回调，只会制造没有业务价值的调度和日志。

二、Action 为什么不能简单理解成 Service ​

2.1 .action 文件定义三类数据 ​

一个 Action 接口由 Goal、Result 和 Feedback 三个区域组成。

yaml
# Goal
任务输入
---
# Result
最终输出
---
# Feedback
执行过程数据

Goal 表达“要做什么”，Result 表达“最终做成什么样”，Feedback 表达“现在进行到哪里”。

Feedback 区可以为空。空 Feedback 仍会生成 C++ 消息类型，这是模板化代码生成的结果，但生成出类型不等于存在可用的业务数据。

2.2 传输层由五条通信通道组成 ​

ROS 2 Action 在底层不是一个独立的 DDS 原语，而是 Service 与 Topic 的组合：

  • send_goal Service：提交 Goal，并获得接受或拒绝响应。
  • get_result Service：请求某个 Goal 的最终状态和 Result。
  • cancel_goal Service：请求取消一个或一组 Goal。
  • feedback Topic：服务端向客户端发布过程反馈。
  • status Topic：服务端发布 Goal 状态数组。

这个结构解释了 Action 为什么既像 Service，又能持续反馈和取消。Goal 提交与 Result 获取是分开的，Feedback 也有独立的 Topic 数据流。

2.3 Action 适合持续任务 ​

Action 通常用于以下任务：

  • 机器人导航到目标点。
  • 机械臂执行一段轨迹。
  • 底盘跟随一条路径。
  • 长时间感知或计算任务。
  • 支持取消、抢占和进度显示的业务任务。

普通 Service 更适合耗时短、无需过程反馈、无需取消的请求—响应操作。把持续执行任务放进 Service，会让超时、取消和状态观察都变得笨重。

三、FollowPath 的三个客户端回调怎样接力 ​

3.1 sendFollowPath() 负责组装请求 ​

sendFollowPath(const nav_msgs::msg::Path & path) 是控制链的入口。它先拒绝空路径和空任务，再保存 task_.active_path，把任务状态改为 CONTROLLING。

随后，它捕获当前任务的 generation，递增 follow_sequence_，并构造：

cpp
FollowPath::Goal goal;
goal.path = path;
goal.controller_id = control_module_.controllerId();
goal.goal_checker_id = control_module_.goalCheckerId();

这里的输入是待跟踪 Path，输出不是函数返回值，而是一条异步 Action 数据流。真正的响应会在未来通过三个回调到达。

3.2 goal_response_callback 处理接受与拒绝 ​

Goal Response 回调拿到 ClientGoalHandle<FollowPath>::SharedPtr。

Handle 非空表示 Controller Server 接受了 Goal。代码把它保存到 active_follow_goal_，后续取消、抢占和状态判断都需要这个句柄。

Handle 为空表示 Goal 被拒绝。此时任务并没有进入正常执行流程，代码直接调用 startRecovery("控制 Goal 被拒绝")。

这个回调只回答“服务端收不收”，不能回答“机器人最终到没到”。

3.3 feedback_callback 接收连续运行数据 ​

FollowPath.action 的 Feedback 定义了两个字段：

yaml
float32 distance_to_goal
float32 speed

回调把它们写入当前任务：

cpp
task_.distance_remaining = static_cast<double>(controller_feedback->distance_to_goal);
current_speed_ = controller_feedback->speed;

当外层正在执行 FollowFixedPath 时，代码还会新建 FollowFixedPath::Feedback，把剩余距离发布给外部调用者。于是内部 Controller Feedback 被转换成了业务级固定路径 Feedback。

这说明 Feedback 不是装饰信息。它跨过了两层 Action，成为上游任务系统能够观察的实时进度。

3.4 result_callback 负责唯一的最终收口 ​

Result 回调先清理 active_follow_goal_，再检查 WrappedResult.code。

状态为 SUCCEEDED 时调用 succeedTask()；非成功状态且任务没有处于主动取消流程时，调用 startRecovery()。

FollowPath.action 的 Result 载荷是 std_msgs/Empty。因此，执行是否成功主要由 WrappedResult.code 表达，不能指望从空 Result 消息中读取一个 success 字段。

四、规划与平滑为什么不需要 Feedback 回调 ​

4.1 ComputePathToPose 返回最终 Path ​

单点规划 Goal 包含终点、可选起点、规划器 ID 和 use_start。当前 Navigator 设置 use_start=false，让 Planner Server 通过 TF 获取机器人当前位置。

Result 包含：

yaml
nav_msgs/Path path
builtin_interfaces/Duration planning_time

调用方真正需要的产物是完整 Path。Goal 被接受后，等待一次 Result 就能推进状态机。

4.2 ComputePathThroughPoses 语义相同 ​

多点规划把单个目标换成目标数组，Result 仍然是 Path 与规划耗时。当前接口没有定义“已经处理了几个目标”或“搜索完成比例”，所以没有可以消费的中间反馈。

4.3 SmoothPath 也是结果驱动 ​

平滑 Goal 输入原始 Path、平滑器 ID、最长平滑时间和碰撞检查开关。Result 返回：

  • 平滑后的 Path。
  • 实际平滑耗时。
  • was_completed 完成标志。

当前 Navigator 在成功且 Path 非空时调用 sendFollowPath()；失败时回退 pending_raw_path_。这同样是“请求一个最终产物”的流水线。

4.4 空 Feedback 类型不等于需要空回调 ​

三个 .action 文件都保留 Feedback 分隔区，但区内没有字段。ROS 2 仍会生成 ActionT::Feedback，客户端也仍然可以写一个类型正确的 feedback_callback。

但服务端没有业务数据可以填充，当前 Planner Server 和 Smoother Server 也不需要周期发布空消息。所以不注册回调更清楚地表达了接口事实：这个 Action 的中间过程不是公共协议的一部分。

五、常规 Action Client 会用到哪些函数 ​

5.1 rclcpp_action::create_client() ​

创建并把 Action Client 加入节点：

cpp
client_ = rclcpp_action::create_client<ActionType>(node, "action_name");

客户端创建成功不代表服务端已经启动。Action 名称和 Action 类型必须与服务端一致。

5.2 wait_for_action_server() ​

在发送 Goal 前等待服务端可用：

cpp
if (!client_->wait_for_action_server(timeout)) {
  return;
}

它只检查 Action Server 的通信端点是否就绪，不会验证某个 Goal 一定会被接受。

5.3 SendGoalOptions ​

SendGoalOptions 是发送 Goal 时的回调配置：

cpp
typename rclcpp_action::Client<ActionType>::SendGoalOptions options;
options.goal_response_callback = ...;
options.feedback_callback = ...;
options.result_callback = ...;

三个成员默认都是 nullptr。是否设置，取决于调用方准备怎样消费异步结果。

5.4 async_send_goal() ​

发送 Goal：

cpp
auto future = client_->async_send_goal(goal, options);

函数返回一个共享 Future。服务端接受 Goal 时，Future 得到有效 Goal Handle；拒绝时得到空 Handle。如果配置了 Goal Response 回调，同样的接受／拒绝结果会通过回调通知调用方。

async_send_goal() 不会等任务执行完才返回。它只启动异步交互。

5.5 async_get_result() ​

调用方可以通过 Goal Handle 主动请求最终结果：

cpp
auto result_future = client_->async_get_result(goal_handle);

如果发送 Goal 时已经设置 result_callback，通常不需要再额外组织一条等待 Future 的业务链。两种风格应当按状态机结构选择，避免同一任务出现两套终态处理逻辑。

5.6 async_cancel_goal() ​

取消指定 Goal：

cpp
client_->async_cancel_goal(goal_handle);

返回的 Cancel Response 只表示服务端是否接受“尝试取消”的请求，不表示任务已经停止，也不表示客户端已经收到 CANCELED Result。

5.7 批量取消函数 ​

客户端还提供：

cpp
client_->async_cancel_all_goals();
client_->async_cancel_goals_before(stamp);

前者请求取消当前 Action Server 的全部 Goal，后者按时间戳取消一组 Goal。导航系统通常更适合持有明确 Goal Handle 并定点取消，避免影响不属于当前任务的 Goal。

5.8 Client Goal Handle ​

客户端 Goal Handle 表示一个已经被服务端接受的具体 Goal。常见用途包括：

  • 取得 Goal UUID。
  • 查询本地已知状态。
  • 请求最终 Result。
  • 发起取消。
  • 把 Feedback 和 Result 与特定 Goal 对齐。

Handle 是后续控制权的凭证，所以当前代码会在 Goal Response 回调中保存它，在 Result 回调中释放它。

六、三个客户端回调的准确语义 ​

6.1 Goal Response Callback ​

典型签名为：

cpp
void callback(GoalHandle::SharedPtr goal_handle);

它可能只调用一次。Handle 非空表示接受，空 Handle 表示拒绝。

Goal 被拒绝后不会进入正常执行状态，调用方必须在这里完成拒绝处理，不能假设未来还会收到一个普通 Result 回调来兜底。

6.2 Feedback Callback ​

典型签名为：

cpp
void callback(GoalHandle::SharedPtr goal_handle, std::shared_ptr<const ActionType::Feedback> feedback);

它可能一次都不调用，也可能调用很多次。回调适合更新进度、速度、剩余时间和 UI，不适合决定任务的最终成功。

Feedback 与取消、Result 可能在多线程执行器中靠得很近。回调需要确认 Goal 身份和任务当前性。

6.3 Result Callback ​

典型签名为：

cpp
void callback(const GoalHandle::WrappedResult & result);

WrappedResult 同时携带 Goal ID、结果码和 .action 定义的 Result 载荷。常见结果码包括：

  • SUCCEEDED：正常成功。
  • ABORTED：服务端执行失败。
  • CANCELED：任务完成取消收口。
  • UNKNOWN：客户端无法识别终态。

代码需要同时核对结果码、Result 指针和业务字段。仅检查其中一项，容易把传输状态和业务状态混在一起。

七、常规 Action Server 会用到哪些函数 ​

7.1 rclcpp_action::create_server() ​

创建 Action Server 时必须提供三个入口：

cpp
server_ = rclcpp_action::create_server<ActionType>(
  node,
  "action_name",
  handle_goal,
  handle_cancel,
  handle_accepted);

这里的三个服务端入口与客户端的三个回调不是一一对应关系。

客户端回调描述“客户端准备消费哪些返回数据”；服务端入口描述“服务端怎样接收 Goal、处理取消并启动执行”。

7.2 handle_goal ​

Goal 回调的典型签名为：

cpp
rclcpp_action::GoalResponse callback(
  const rclcpp_action::GoalUUID & uuid,
  std::shared_ptr<const ActionType::Goal> goal);

它适合执行快速校验：

  • 节点是否激活。
  • 当前模式是否允许此 Action。
  • Goal 字段是否完整。
  • 数值、坐标系和枚举是否合法。
  • 当前资源是否允许接受新任务。

返回值包括 REJECT、ACCEPT_AND_EXECUTE 和 ACCEPT_AND_DEFER。

ACCEPT_AND_EXECUTE 表示接受后立即进入执行态；ACCEPT_AND_DEFER 表示先接受，稍后由代码调用 Goal Handle 的 execute()。

7.3 handle_cancel ​

Cancel 回调的典型签名为：

cpp
rclcpp_action::CancelResponse callback(std::shared_ptr<ServerGoalHandle> goal_handle);

它返回 ACCEPT 或 REJECT。ACCEPT 的准确含义是“服务端愿意尝试取消”，真正停止控制、释放资源和生成取消 Result 仍由执行逻辑完成。

当前固定路径实现只设置 cancel_requested_，由统一监控逻辑执行下游取消和任务复位。这避免了在 Cancel 回调中重入复杂状态机。

7.4 handle_accepted ​

Accepted 回调在 Goal 被接受后获得 ServerGoalHandle。它应该快速保存句柄，并把耗时工作派发到工作线程、定时器或状态机。

ROS 2 Humble 的 rclcpp_action::Server 头文件明确要求 Goal、Cancel 和 Accepted 回调保持非阻塞。原因是这些入口由 Executor 调度，长时间等待会占用执行器线程，并延迟其他 Topic、Service、Timer 和 Action 回调。

7.5 publish_feedback() ​

服务端在 Goal 执行期间发布反馈：

cpp
auto feedback = std::make_shared<ActionType::Feedback>();
goal_handle->publish_feedback(feedback);

反馈应该有稳定语义，并控制发布频率。高频发布不等于信息更多，反而可能增加 DDS、Executor 和日志压力。

7.6 succeed()、abort() 与 canceled() ​

服务端通过 Goal Handle 的终态函数结束任务：

cpp
goal_handle->succeed(result);
goal_handle->abort(result);
goal_handle->canceled(result);

三者分别表示成功、执行失败和取消完成。一个 Goal 进入终态后，不应继续发布 Feedback，也不应再次调用其他终态函数。

7.7 execute() ​

Goal 通过 ACCEPT_AND_DEFER 接受时，可以在资源就绪后调用：

cpp
goal_handle->execute();

这适合需要排队、串行化资源或等待调度窗口的服务端。直接使用 ACCEPT_AND_EXECUTE 时不需要额外调用。

八、当前固定路径 Action 展示了怎样的服务端设计 ​

8.1 handleFixedPathGoal() 做快速结构校验 ​

它检查运行模式、Lifecycle 激活状态、路径点数量、顶层坐标系、有限坐标和四元数有效性。结构错误直接返回 REJECT。

这类检查适合放在 Goal 回调，因为它们不需要等待外部系统。

8.2 handleFixedPathCancel() 只设置取消请求 ​

当前代码确认 Goal 是否为活动固定路径 Goal，然后设置 cancel_requested_，最后返回 CancelResponse::ACCEPT。

它没有在 Action 回调里同步取消下游 FollowPath、清理 Costmap 或发布终态。这种分层避免 Cancel 回调承担过多职责。

8.3 handleFixedPathAccepted() 启动内部 FollowPath ​

Accepted 回调会完成 Path 坐标转换、等待 FollowPath Server、抢占旧任务、建立新任务状态并调用 sendFollowPath()。

业务上，这形成了外层 FollowFixedPath Server 到内层 FollowPath Client 的桥接。

工程上需要看到一个边界：TF 转换会遍历路径，wait_for_action_server() 也可能等待 server_timeout_。它们让 Accepted 回调比“保存句柄并立即派发”更重。

多线程 Executor 可以降低单个线程阻塞的影响，但不能把阻塞本身变成无成本。如果固定路径点很多，或下游 Server 经常未就绪，更稳妥的结构是把准备和等待逻辑交给任务状态机，再由 Accepted 回调快速返回。

九、异步 Action 为什么必须过滤旧回调 ​

9.1 回调到达顺序不等于任务创建顺序 ​

导航系统会重规划、抢占、取消和恢复。Goal A 发出后，Goal B 可能已经替代它，但 Goal A 的 Feedback 或 Result 仍可能晚到。

如果旧 Result 不经检查直接调用 succeedTask()，新任务可能被错误结束；如果旧规划结果直接覆盖当前 Path，机器人可能沿上一条任务路径运动。

9.2 generation 隔离不同外层任务 ​

每次外层任务变化，task_.generation 都会更新。回调捕获发送 Goal 时的 generation，并与当前任务比较。

它回答的是：

这个回调还属于当前导航任务吗？

9.3 sequence 隔离同一任务的多次请求 ​

同一个外层任务可能周期重规划，也可能多次更新 FollowPath。

plan_sequence_ 区分同一任务内的多次规划；follow_sequence_ 区分多次控制 Goal。它回答的是：

这个回调还是当前任务里最新的一次下游请求吗？

9.4 两层标识共同构成当前性门禁 ​

isCurrentPlan() 和 isCurrentFollow() 同时比较任务代次与请求序号。只有两个值都匹配，回调才能修改共享状态。

这是一种轻量的逻辑失效机制。它不要求旧网络消息立即消失，而是保证旧消息到达后没有写权限。

十、怎样决定一个 Action 是否需要 Feedback ​

10.1 适合定义 Feedback 的任务 ​

Feedback 值得进入公共接口时，通常满足以下条件：

  • 任务持续时间足以让调用方感知等待。
  • 中间状态对上层调度或用户有价值。
  • 数据可以稳定解释，而不是插件私有调试变量。
  • 服务端能够以合理频率持续产生数据。
  • 调用方会用它做展示、监控、估时或控制决策。

FollowPath 的剩余距离与速度符合这些条件。

10.2 不适合为了对称增加 Feedback ​

以下情况通常不需要 Feedback：

  • 任务很短，Result 很快到达。
  • 中间值不稳定，容易被误解成完成比例。
  • 不同插件无法提供一致语义。
  • 调用方收到后不会采取任何动作。
  • 只能发布空消息或重复陈旧数据。

当前 ComputePath 和 SmoothPath 的接口选择就是结果驱动，而不是过程驱动。

10.3 新增 Feedback 应从协议开始 ​

如果未来希望规划过程可观测，应先修改 .action，定义真正可消费的数据，例如：

  • 已展开搜索节点数。
  • 当前最优路径代价。
  • 搜索或平滑迭代次数。
  • 已消耗时间。
  • 可解释的阶段状态。

随后由服务端实际调用 publish_feedback()，客户端再注册 feedback_callback。只改单侧客户端没有意义。

10.4 Feedback 应限频且不拥有终态 ​

Feedback 可以帮助估计任务进度，但不应替代 Result。即使剩余距离显示为零，也可能仍需满足 Goal Checker、姿态误差或停止条件。

最终状态只能由 succeed()、abort() 或 canceled() 产生，并在客户端 Result 回调中统一处理。

十一、最容易混淆的 Action 语义 ​

11.1 Goal 被接受不等于任务成功 ​

Goal Response 只表示服务端愿意执行。路径可能在后续跟踪中遇到障碍、控制失败或被主动取消。

11.2 接受取消不等于已经取消 ​

Cancel 回调返回 ACCEPT 后，执行逻辑仍需真正停止任务，并调用 canceled(result)。客户端应以最终 CANCELED Result 作为取消完成依据。

11.3 有 Feedback 类型不等于有反馈字段 ​

空 Feedback 仍有生成类型，但没有可传递的业务数据。接口定义、服务端发布行为和客户端消费逻辑必须同时成立，Feedback 链路才有意义。

11.4 Result 载荷不等于 ResultCode ​

.action 的 Result 是业务载荷，WrappedResult.code 是 Action 终态。FollowPath 的载荷为空，但仍能通过 SUCCEEDED、ABORTED 和 CANCELED 清楚表达结果。

11.5 客户端三个回调不等于服务端三个入口 ​

客户端的 Goal Response、Feedback、Result 是返回数据消费点。

服务端的 Goal、Cancel、Accepted 是请求接收和执行控制点。两边都恰好出现“三个”，但职责完全不同，不能按名称或数量机械对应。

十二、回到最初问题 ​

12.1 navigator_control.cpp 的三个回调都不可替代 ​

它需要处理 Goal 接收、持续控制反馈和最终终态，还要把内部 FollowPath Feedback 转成外层 FollowFixedPath Feedback。

12.2 navigator_planning.cpp 的两个回调已经完整 ​

规划和平滑 Action 的公共协议只承诺 Goal Response 与最终 Path，没有定义中间反馈字段。省略 feedback_callback 不是缺失，而是忠实反映接口。

12.3 最终设计原则 ​

ROS 2 Action 的回调设计可以归结为一句话：

按任务语义和真实数据流注册回调，不按结构体提供了多少槽位追求形式对称。

持续执行的任务需要可观察、可取消和可收口；有界计算任务如果只产生最终产物，就让 Result 承担结果语义。当异步 Goal 可能重叠时，再用 Goal Handle、任务代次和请求序号守住共享状态边界。

理解这条原则后，Action 就不再是“比 Service 多一个 Feedback”的接口，而是一套围绕长任务生命周期设计的完整通信协议。

nav2 ~二 · 全局规划与路径搜索2026-07-209 min read

栅格只能横平竖直？拆解 Theta* 如何用视线检查走出任意角全局路径 ​

本文基于当前项目中的 nav2_theta_star_planner 源码，逐层拆解它在 Nav2 中的真实调用位置、生命周期状态、输入输出和 Lazy Theta* 搜索数据流。文中同时区分算法设计与当前仓库实现边界。

一、先给结论：它不是节点，而是一段被调用的规划能力 ​

nav2_theta_star_planner 不启动独立 ROS 2 节点，也不自己订阅地图、目标点或 TF。它被编译成共享库，并以 nav2_core::GlobalPlanner 插件的身份装入 planner_server。

对外只有六个关键入口：

  • configure()：接收父节点、插件名、TF Buffer 和全局 Costmap。
  • activate()：注册动态参数回调。
  • deactivate()：进入非活动状态。
  • cleanup()：释放搜索器。
  • createPlan()：接收已变换到全局地图坐标系的起点和终点，返回 nav_msgs::msg::Path。
  • 动态参数回调：更新搜索方向数、未知区域策略和代价权重。

所以，用户在导航时看到的规划 Action、服务端状态和路径话题，属于 nav2_planner；Theta* 只负责其中“根据一张代价地图算出一条路”的核心步骤。

二、插件是怎样被调用的 ​

插件 XML 将 nav2_theta_star_planner/ThetaStarPlanner 映射到 C++ 类型 nav2_theta_star_planner::ThetaStarPlanner。PlannerServer 根据参数中的插件 ID 创建实例，随后由生命周期管理器推动配置、激活、停用和清理。

一次典型调用沿着下面的链路发生。

2.1 上层导航器发送目标 ​

上层导航器向 ComputePathToPose 或 ComputePathThroughPoses Action 发送目标。

2.2 PlannerServer 获取并变换位姿 ​

PlannerServer 获得机器人当前位姿，并把起点、终点变换到全局 Costmap 的坐标系。

2.3 PlannerServer 选择插件 ​

PlannerServer 根据 planner ID 选择 Theta* 插件。

2.4 进程内调用规划器 ​

PlannerServer 在进程内直接调用 createPlan(start, goal)，不是通过 ROS 话题或服务调用。

2.5 Theta* 执行搜索 ​

Theta* 锁住 Costmap，完成坐标转换、搜索、回溯和插值。

2.6 返回路径 ​

返回的 Path 再由 PlannerServer 交给上层导航流程和控制器。

当前 nav2_regulated_modules 参数确实加载了名为 ThetaStar 的插件，但 selected_planner 仍是 GridBasedAstar。这意味着 Theta* 已可被显式选择，却不是该配置下的默认规划器。

三、生命周期：资源在什么时候出现 ​

configure() 创建内部 ThetaStar 搜索对象，保存 Costmap 指针与全局坐标系，并读取六类规划参数。activate() 才添加动态参数回调；cleanup() 将搜索对象置空。

从状态角度看，它依附于 planner_server。

3.1 未配置 ​

只有插件对象，没有可用搜索器。

3.2 非活动 ​

搜索器已创建，但服务端不对外执行规划任务。

3.3 活动 ​

允许 createPlan()，动态参数也可以生效。

3.4 已清理 ​

搜索器被释放，等待下一次配置。

当前实现有一个生命周期边界：deactivate() 没有注销动态参数回调，cleanup() 也只释放搜索器。如果清理后仍触发参数更新，回调可能访问已经为空的搜索器。工程上更稳妥的做法，是在停用或清理阶段显式重置回调句柄。

四、输入输出接口：ROS 外壳与算法内核要分开看 ​

Theta* 的直接输入不是 ROS 话题，而是四组进程内数据：

  • 起点 geometry_msgs::msg::PoseStamped。
  • 终点 geometry_msgs::msg::PoseStamped。
  • Costmap2D 指针，提供分辨率、原点、栅格代价和坐标转换。
  • 参数快照，控制邻接方向、未知区域和代价模型。

直接输出只有 nav_msgs::msg::Path。失败不是单独的错误码，而通常表现为空路径，之后由 PlannerServer 转成规划 Action 的失败结果。

它保存了 TF Buffer，但当前 createPlan() 不调用 TF。也就是说，坐标系一致性由 PlannerServer 在进入插件前保证。

它没有自己的订阅者、发布者、Service 或 Action；地图更新也不是消息回调进入插件，而是通过共享的 Costmap 对象被读取。

五、createPlan()：一条路径从哪里开始长出来 ​

createPlan() 先锁住 Costmap 的互斥量，这把锁覆盖整个搜索和路径生成过程。随后依次执行以下步骤。

5.1 转换栅格坐标 ​

将世界坐标的起点、终点转换成地图栅格坐标。

5.2 检查地图边界 ​

如果任一点超出地图边界，立即返回空路径。

5.3 处理起终点同栅格 ​

如果起终点落在同一栅格，检查该栅格是否可通行；可通行时只返回一个点。

5.4 执行端点检查与搜索 ​

普通情况先检查起点和终点安全性，再运行 Theta* 搜索。

5.5 回溯路径 ​

从终点沿父指针回溯到起点，转换成世界坐标。

5.6 插值路径 ​

按 Costmap 分辨率做线性插值，形成输出路径。

5.7 设置末端方向 ​

根据参数决定末端方向使用目标姿态，还是使用最后一段路径的切线方向。

这里没有“目标容差”逻辑。目标栅格不可通行或完全不可达时，插件直接返回空路径。

六、代价函数：短、远离障碍、靠近目标之间怎样权衡 ​

当前实现把搜索代价拆为三部分：

  • 欧氏距离代价：鼓励路径更短。
  • 穿越代价：由 Costmap 栅格代价转换，并以平方项放大靠近障碍的代价。
  • 启发代价：用当前位置到目标的欧氏距离引导搜索。

可以概括为：

f(n) = g(n) + w_heuristic × h(n)

其中 g(n) 累积路径长度与穿越代价；h(n) 是到目标的直线距离。源码还给栅格代价加上固定偏置，使自由空间也有稳定的穿越成本。

关键参数包括：

  • how_many_corners：配置阶段只接受 4 或 8，决定四邻域或八邻域扩展。
  • allow_unknown：是否允许进入 NO_INFORMATION 栅格。
  • w_euc_cost：欧氏距离项权重。
  • w_traversal_cost：Costmap 穿越代价权重。
  • w_heuristic_cost：内部取 min(w_euc_cost, 1.0)。
  • use_final_approach_orientation：末点方向是否沿用最终接近方向。

动态更新还有两个当前实现边界。

6.1 how_many_corners 动态更新边界 ​

运行期修改 how_many_corners 时没有再次限制为 4 或 8，大于 8 可能越过固定邻接数组。

6.2 w_euc_cost 动态更新边界 ​

运行期修改 w_euc_cost 不会重新计算启发权重，因此搜索启发项仍保持配置阶段的值。

七、Lazy Theta* 的核心：能看见祖父节点，就把弯拐直 ​

普通 A* 的父节点只能来自直接相邻栅格，所以路径天然带有栅格折线。Theta* 的关键是“视线检查”：当前节点准备扩展邻居时，会尝试让邻居绕过当前节点，直接连接当前节点的父节点。

当前源码采用 Lazy Theta* 风格。

7.1 取出最小代价节点 ​

从优先队列取出总代价最小的节点。

7.2 执行视线检查 ​

在正式扩展前，用改造过的 Bresenham 算法检查它与祖父节点之间是否无遮挡。

7.3 重连父节点 ​

若直连安全且累计代价更低，就把父指针改到祖父节点。

7.4 扩展邻域节点 ​

再扩展四邻域或八邻域节点，更新它们的 g、h、f 与父指针。

7.5 判断搜索结束 ​

直到目标被取出，或开放队列耗尽。

视线检查不仅判断致命障碍，还会累积沿线的穿越代价，并阻止从障碍角点间斜穿。未知栅格在允许未知区域时可以通过，但会按高代价参与计算。

八、路径回溯、插值和朝向 ​

搜索成功后，父指针形成一棵从目标通向起点的树。backtrace() 先逆序收集节点，再反转成起点到终点的原始路径。随后 linearInterpolation() 按地图分辨率在每段之间插点，让控制器收到更密集的轨迹。

当前插值实现有三个值得注意的事实：

  • 每段会插入段首和若干中间点，但没有显式追加原始路径最后一个点，所以输出末点可能停在目标前一个分辨率以内。
  • Path.header 会写入全局坐标系和时间戳，但每个插值 PoseStamped 的 header 没有同步填充。
  • 中间点方向保持默认值，只有最后一个输出点会设置目标方向或最终接近方向。

因此，下游真正应该依赖的是 Path.header.frame_id 和路径几何；若控制器需要每个点都有合法四元数与独立 header，应先修正这里的输出封装。

九、状态与失败结果全景 ​

一次规划请求内部会经历以下运行状态。

9.1 接收请求 ​

保存起点、终点并锁定 Costmap。

9.2 坐标校验 ​

将世界坐标转换为地图索引。

9.3 端点校验 ​

确认起终点可进入。

9.4 搜索中 ​

开放队列驱动节点扩展和视线重连。

9.5 回溯中 ​

父指针转换为世界坐标折线。

9.6 插值中 ​

按分辨率加密路径并设置末端方向。

9.7 成功 ​

返回非空 Path。

9.8 失败 ​

越界、端点不安全或开放队列耗尽，返回空 Path。

此外，当前搜索循环先扩展源点再进入弹出循环，源点可能被重复展开；循环退出条件又与“目标是否最后一个出队”耦合。这类边界应通过最小地图回归测试确认，不能只靠正常场景判断算法正确。

十、落地时最容易踩的坑 ​

10.1 插件名有两层 ​

参数中的 ID 可以叫 ThetaStar，但 plugin 字段必须匹配 XML 导出的类型名。

10.2 allow_unknown=true 不代表未知区没有代价 ​

它只是允许搜索进入，未知栅格仍会形成很高的穿越成本。

10.3 权重不是越大越好 ​

w_traversal_cost 太大会让路径过度远离障碍，w_euc_cost 太大会缩短路径但可能贴近障碍；调整时应同时观察路径长度、最小障碍距离和搜索耗时。

10.4 规划期间 Costmap 被长时间加锁 ​

大地图、复杂障碍或弱算力平台上，搜索耗时也会变成地图更新阻塞时间。

10.5 动态参数并非全部安全 ​

当前实现缺少部分范围校验、并发保护与派生参数重算，实车更适合在非活动状态修改关键搜索参数。

十一、结语 ​

Theta* 真正解决的不是“能不能找到路”，而是“如何在栅格地图上少受栅格方向限制”。它通过视线检查重连父节点，让路径更接近连续空间中的直线，同时继续复用 Nav2 的 Costmap、插件体系和 PlannerServer 调度。

读懂这条数据流后，调参就不再是盲目修改几个权重：先确认调用方和坐标系，再检查端点安全与未知区策略，最后才是欧氏距离、穿越代价和启发权重之间的取舍。

Costmap Filters 如何把地图语义变成导航约束？拆解 Nav2 的掩膜、插件与限速数据流 ​

机器人进入施工区后为什么必须绕开，进入限速区却只需要减速？这两个规则都来自一张带有空间语义的地图，但在 Nav2 中不能用同一种方式处理。Costmap Filters 的核心价值，就是把“这里有什么”和“机器人在这里应该怎么做”分离：KeepoutFilter 将禁行语义变成 Costmap 代价，SpeedFilter 将限速语义变成 nav2_msgs/msg/SpeedLimit，Planner 和 Controller 继续使用各自熟悉的标准接口。

本文以 navigation2/doc/design/CostmapFilters_design.pdf 的 v1.1 高层设计为主线，结合当前 checkout 中的 nav2_costmap_2d、nav2_msgs、nav2_controller、nav2_core 和 Costmap Filter 测试代码，完整解释语义掩膜、元数据、插件生命周期、坐标转换、代价合并、速度广播和工程边界。PDF 是设计草图，当前源码已经增加了 BinaryFilter、TF 处理、更新窗口和动态启停等实现细节，文中会明确区分两者。

一、先给结论：Costmap Filter 是空间策略层 ​

1.1 普通 Costmap 解决环境问题 ​

普通 Costmap 主要回答“环境中哪里存在碰撞风险”。Static Layer 可以接收静态地图，Obstacle Layer 和 Voxel Layer 可以接收传感器观测，Inflation Layer 可以把障碍物扩展为安全边界。它们描述的是墙、设备、人员和传感器观测到的物理环境。

但机器人系统还会遇到一类不等于物理障碍物的规则：某条通道只允许特定车辆通行，某个区域允许经过但必须低速，某片地面因为施工暂时禁止进入，某个仓库车道需要优先使用。这些规则是运行策略，不是传感器直接观察到的障碍物。

1.2 Filter 把空间规则转换成导航行为 ​

Costmap Filter 把一张语义掩膜解释成具体的导航动作。典型映射如下：

空间语义主要输出下游处理者
禁行区高代价或 LETHAL_OBSTACLEGlobal Costmap、Local Costmap、Planner、Controller
限速区nav2_msgs/msg/SpeedLimitController Server、Controller Plugin
二值触发区布尔状态外部行为或任务节点
优选车道代价偏好或禁行表达Planner 或 Costmap Filter

因此，Costmap Filter 不是简单的“过滤噪声”，而是一层位于基础环境模型和导航执行器之间的空间策略适配层。

二、PDF 描绘的总体架构 ​

2.1 Map Server 与 Semantic Map Server 分工 ​

PDF 第 2 页同时放置了 Map Server 和 Semantic Map Server。前者负责普通地图，后者负责带有禁行、限速、车道或其他规则的语义地图。

两者的职责可以拆开理解：

  • Map Server 提供基础环境几何。
  • Semantic Map Server 提供某一类空间规则。
  • Global Costmap 和 Local Costmap 接收过滤器处理后的结果。
  • Planner Server 使用全局代价选择路线。
  • Controller Server 使用局部代价生成速度，并接收速度限制。

这里的 Semantic Map Server 是一种架构角色，不要求必须由某个固定 Nav2 节点实现。任何能够发布约定消息的地图、调度或业务节点，都可以充当语义地图生产者。

2.2 Global Costmap 与 Local Costmap 可以承担不同约束 ​

同一个过滤器可以加载到 Global Costmap，也可以加载到 Local Costmap。两者的影响范围不同：

  • Global Costmap 加载 KeepoutFilter，规划器会在全局路径层面避开禁行区。
  • Local Costmap 加载 KeepoutFilter，控制器在局部跟踪层面也会把禁行区当成碰撞风险。
  • Local Costmap 加载 SpeedFilter，机器人进入区域后可以实时改变控制器的速度上限。

这让系统可以把约束放在不同阶段。需要全局绕开时，约束必须进入 Planner 能够看到的全局代价；只需要接近区域时进行局部安全控制，则可以只放在 Local Costmap。

2.3 为什么限速不直接改成障碍物 ​

如果把限速区直接写成致命障碍，Planner 会把它理解成“不能走”，最终得到绕行路径。但很多业务规则真正想表达的是“可以走，但必须慢”。

Costmap Filters 因此把两种语义分成两条输出路径：

text
禁行语义 -> Costmap 代价 -> Planner / Controller 避开
限速语义 -> SpeedLimit -> Controller 限制速度

这个分叉是整份设计最重要的取舍。它避免用一个代价值同时表达通行权和速度权。

三、两个输入 Topic：解释元数据与空间数据分离 ​

3.1 CostmapFilterInfo 是解释元数据 ​

nav2_msgs/msg/CostmapFilterInfo 定义在 navigation2/nav2_msgs/msg/CostmapFilterInfo.msg，字段包括：

text
std_msgs/Header header
uint8 type
string filter_mask_topic
float32 base
float32 multiplier

这些字段并不是每个栅格的内容，而是告诉过滤器“应该订阅哪张掩膜，以及如何解释掩膜中的数字”。

  • type 决定插件和数值语义。
  • filter_mask_topic 指向真正的 OccupancyGrid Topic。
  • base 是数值偏移。
  • multiplier 是数值比例。

过滤器不需要把掩膜 Topic 写死在插件代码里，语义地图服务器可以通过 Info 把实际数据源告诉它。

3.2 OccupancyGrid 是空间数据 ​

filter_mask 使用 nav_msgs/msg/OccupancyGrid，其中包含：

  • resolution：栅格分辨率。
  • origin：地图原点。
  • width 和 height：地图尺寸。
  • header.frame_id：掩膜坐标系。
  • data：每个栅格的整数值。

这意味着语义地图可以复用 ROS 2 现有的地图工具链。地图生产者只需要生成一张带有语义数值的栅格图，不需要直接访问 Costmap2D 内部内存。

3.3 base、multiplier 与 type 共同定义数值空间 ​

PDF 给出的转换公式是：

text
semantic_value = mask_data * multiplier + base

例如，SpeedFilter 可以把掩膜值 50 转换为绝对速度：

text
mask_data = 50
multiplier = 0.02
base = 0
type = SPEED_FILTER_ABSOLUTE

speed_limit = 50 * 0.02 + 0 = 1.0 m/s

也可以把掩膜值 30 转换成最大速度百分之三十：

text
mask_data = 30
multiplier = 1
base = 0
type = SPEED_FILTER_PERCENT

speed_limit = 30%

当前 filter_values.hpp 中的类型约定是：0 表示 Keepout，1 表示百分比限速，2 表示绝对限速，3 表示当前实现增加的 BinaryFilter。KeepoutFilter 要求 base=0、multiplier=1，而 SpeedFilter 使用这两个参数进行转换。

四、统一基类：过滤器如何接入 Costmap 更新循环 ​

4.1 CostmapFilter 的三个核心扩展点 ​

当前 CostmapFilter 位于 navigation2/nav2_costmap_2d/include/nav2_costmap_2d/costmap_filters/costmap_filter.hpp，继承的是 nav2_costmap_2d::Layer。PDF 的示意图使用了 CostmapLayer 名称，但它表达的是同一类设计意图：过滤器复用 Costmap Layer 的生命周期和更新入口。

公共接口可以概括为：

text
initializeFilter(filter_info_topic)
process(master_grid, bounds, robot_pose)
resetFilter()

具体职责如下：

  • initializeFilter()：建立 Info、掩膜和特有输出的连接。
  • process()：执行当前插件的空间语义算法。
  • resetFilter()：清理订阅、发布器和缓存状态。

KeepoutFilter 通过 process() 修改主 Costmap，SpeedFilter 通过 process() 查询机器人当前位置并发布 SpeedLimit。同一个基类因此可以承载“改地图”和“发策略消息”两种输出类型。

4.2 activate、deactivate 与 reset 管理连接 ​

PDF 给出的生命周期思路是：

text
activate   -> initializeFilter()
deactivate -> resetFilter()
reset      -> resetFilter() + initializeFilter()

当前代码在 activate() 时建立订阅，在 deactivate() 时清理订阅，在 reset() 时先清理旧连接再重新初始化。这样做的目的不是简单重置变量，而是允许语义地图 Topic、掩膜和输出发布器被整体替换。

当前实现还为每个过滤器声明了 enabled、filter_info_topic 和 transform_tolerance 参数，并提供 toggle_filter 服务。过滤器关闭后不会继续执行 updateBounds() 和 updateCosts()。

4.3 Costmap 更新窗口决定计算范围 ​

Costmap Layer 通常不会每次更新都重新处理整张地图，而是通过 updateBounds() 汇总变化区域，再在 updateCosts() 阶段处理对应窗口。

Costmap Filter 复用了这个机制：

  • 基类在 updateBounds() 中保存最新机器人位置。
  • KeepoutFilter 在收到新的掩膜后扩大更新边界，确保变化区域能够被重新写入。
  • updateCosts() 只把窗口和最新 Pose 交给具体 process()。

这让 KeepoutFilter 既能处理静态语义地图，也能处理运行期更新的掩膜。

4.4 Filter 是基础 Layer 后处理层 ​

当前 LayeredCostmap 在启用过滤器时采用：

text
普通 Plugins
    -> primary_costmap
    -> combined_costmap
    -> Costmap Filters
    -> 最终输出

普通插件先把传感器和基础地图融合到 primary_costmap，再复制到 combined_costmap，最后由过滤器做后处理。过滤器的结果不会反过来成为普通插件下一轮的输入。

五、KeepoutFilter：把空间禁行规则变成代价 ​

5.1 通过 Info 找到掩膜 ​

KeepoutFilter 激活后首先订阅 CostmapFilterInfo。收到 Info 后，它会读取 filter_mask_topic，再创建对 nav_msgs/msg/OccupancyGrid 的订阅。

这形成了一个两阶段发现过程：

text
filter_info_topic
    -> CostmapFilterInfo
    -> filter_mask_topic
    -> OccupancyGrid filter_mask

Info 的 QoS 在当前实现中使用 KeepLast(1)、transient_local() 和 reliable()。这符合地图元数据的特点：后来加入的过滤器也应该能够拿到最近一次有效配置。

KeepoutFilter 收到掩膜后，会把 OccupancyGrid 构造成内部 Costmap2D，并记录掩膜的 frame_id、宽度和高度。

5.2 坐标系不一致时先做 TF 转换 ​

主 Costmap 和语义掩膜不一定处于同一个坐标系。当前 KeepoutFilter 在处理前会检查：

text
mask_frame == global_frame

如果不相同，就查询从主 Costmap 坐标系到掩膜坐标系的 TF，并把主 Costmap 栅格中心转换到掩膜坐标系，再查询对应掩膜栅格。

如果两者处于同一坐标系，代码会利用地图边界直接计算重叠窗口，只遍历真正相交的区域。没有交集时直接返回，不会扫描整张主地图。

5.3 栅格代价通过最大值合并 ​

KeepoutFilter 的主处理循环可以概括为：

text
主 Costmap 栅格
        -> 转换到世界坐标
        -> 必要时转换到掩膜坐标系
        -> 查询掩膜栅格
        -> 读取掩膜代价
        -> 与原代价比较
        -> 写入更高代价

当前实现会跳过掩膜中的未知值，并在掩膜代价高于原代价，或原代价为未知时写入。因此其核心合并关系是：

text
new_cost = max(old_cost, filter_cost)

这种合并方式有一个直接的安全意义：过滤器不会因为自身数据较低而降低原有障碍物代价。障碍物层已经标记为致命障碍的区域，KeepoutFilter 不能把它重新变成可通行区域。

5.4 为什么 Planner 不需要认识 KeepoutFilter ​

KeepoutFilter 把禁行区域编码为 Costmap 代价后，Planner 看到的仍然是普通 Costmap。它不需要知道：

  • 这个代价来自墙体还是语义禁行区。
  • 掩膜由哪个 Semantic Map Server 发布。
  • 这个区域是否来自施工系统或仓库调度系统。

这就是插件层的解耦价值：空间规则在进入规划器之前完成转换，规划器继续复用已有碰撞检查和代价评估逻辑。

六、SpeedFilter：把当前位置语义变成 SpeedLimit ​

6.1 为什么 SpeedFilter 只查询机器人当前位置 ​

SpeedFilter 的目标不是重新生成一张代价地图，而是回答：

text
机器人当前所在区域允许的最大速度是多少

因此它不需要遍历整张掩膜，也不需要把所有栅格的限速值发送给 Controller。它只需要在每次 Costmap 更新时：

  • 读取当前机器人 Pose。
  • 将 Pose 转换到掩膜坐标系。
  • 根据掩膜原点和分辨率计算索引。
  • 查询机器人所在的一个栅格。

这使得 SpeedFilter 的核心开销与掩膜总面积无关，更像一个“空间状态查询器”，而不是一个 Costmap 写入层。

6.2 栅格值如何变成速度数值 ​

当前实现对机器人所在栅格的处理可以概括为：

text
mask_data = 0
    -> speed_limit = 0.0
    -> 解除限速

mask_data = -1
    -> 未知
    -> 记录错误并返回

mask_data = 1..100
    -> speed_limit = mask_data * multiplier + base

当 type=1 时，结果被解释成最大速度百分比，并限制在 0～100；当 type=2 时，结果被解释成绝对速度，单位是 m/s，不能小于零。

例如控制器基础速度为 0.26 m/s，语义地图希望机器人在某区域只能使用百分之五十的速度：

text
percentage = true
speed_limit = 50
实际上限 = 0.26 * 50 / 100 = 0.13 m/s

如果语义地图直接表达 0.10 m/s，则消息应该使用：

text
percentage = false
speed_limit = 0.10

SpeedLimit 不是 cmd_vel，speed_limit=0.0 也不是停车命令，而是恢复控制器默认速度约束。

6.3 只有限速变化时才发布 ​

SpeedFilter 保存上一次发布的速度限制。机器人停留在同一个限速栅格时，不会每个 Costmap 周期重复发布同一条消息；当机器人进入新的限速区域，或者离开限速区域恢复无上限时，才发布新的 SpeedLimit。

这个门控减少了无效 Topic 流量，但也带来一个工程含义：speed_limit 更像状态变化消息，不是周期性心跳。控制器启动顺序、发布器 QoS、限速状态超时和故障恢复策略需要由系统整体设计。

6.4 ControllerServer 统一广播给控制器 ​

ControllerServer 通过 speed_limit_topic 参数订阅 nav2_msgs/msg/SpeedLimit。收到消息后，它不会自己计算速度，也不会只更新当前控制器，而是遍历已经加载的控制器，调用统一接口：

text
ControllerServer
    -> Controller::setSpeedLimit(speed_limit, percentage)
    -> DWB、RPP、MPPI、其他 Controller Plugin

nav2_core::Controller 的接口约定了两种单位模式。真正如何修改速度边界，由各控制器实现：

  • DWB 可以缩放速度采样边界。
  • RPP 可以调整期望线速度。
  • MPPI 可以缩放运动约束。
  • 自定义控制器必须自行实现同样的约束语义。

这条链路体现了“消息契约稳定、算法内部自由”的设计原则。

七、PDF 与当前源码的对应关系 ​

7.1 基类关系已经发生工程化演进 ​

PDF 第 3 页把 CostmapFilter 画成继承自 CostmapLayer，而当前代码实际声明为：

text
class CostmapFilter : public Layer

这不是设计思想失效，而是实现层对共享 Costmap 资源和 Layer 生命周期的具体取舍。当前源码注释明确说明，直接继承 Layer 是为了避免共享资源处理中的隐藏问题。

7.2 LanesFilter 被合并，BinaryFilter 成为新增扩展 ​

PDF 右侧列出 KeepoutFilter、SpeedFilter 和 LanesFilter，并标注 LanesFilter 由 KeepoutFilter 覆盖。当前 costmap_plugins.xml 注册的是：

当前插件主要输出当前作用
KeepoutFilterCostmap 代价禁行或车道语义
SpeedFilterSpeedLimit百分比或绝对限速
BinaryFilterstd_msgs/msg/Bool区域触发二值状态

因此，PDF 中的 LanesFilter 更适合作为设计方向理解，而不是当前源码中一定存在的独立类。

7.3 测试把设计契约落到了可验证行为 ​

当前包内测试覆盖了：

  • worldToMask() 的世界坐标到掩膜索引转换。
  • KeepoutFilter 的掩膜加载、坐标系转换、更新区域和代价合并。
  • SpeedFilter 的百分比模式、绝对模式、边界值、离开区域和重复值抑制。
  • BinaryFilter 的默认状态、阈值翻转和区域越界。
  • 系统测试中的掩膜服务器、Info 服务器、Global／Local 参数和 SpeedLimit 订阅。

这说明 Costmap Filters 并不是只停留在 PDF 中的架构概念，而是已经形成了消息、插件、参数和测试组合起来的运行契约。

八、这套设计为什么有价值 ​

8.1 语义地图生产者与导航算法解耦 ​

语义地图服务器只负责表达空间规则，Planner 和 Controller 只负责执行已经转换好的约束。两者通过 ROS 2 Topic 和消息连接，不需要共享 C++ 类，也不需要把业务系统直接编译进导航算法。

这使得施工系统、仓库调度系统、GIS 服务和 Nav2 可以独立演进。

8.2 Keepout 和 Speed 复用不同的既有契约 ​

禁行区进入 Costmap，因为 Planner 和 Controller 已经理解 Costmap 中的碰撞代价；限速区进入 SpeedLimit，因为速度上限属于 Controller 的控制约束。

如果把两者都强行写成 Costmap 代价，就会丢失“可以通行但必须慢速”的重要语义。当前设计把输出接到了最合适的下游接口上。

8.3 多层 Costmap 带来不同约束等级 ​

同一个系统可以把过滤器放在不同 Costmap：

  • 放在 Global Costmap，影响全局路径。
  • 放在 Local Costmap，影响局部避障和速度控制。
  • 两边都放，形成规划和控制的双重约束。

这种部署粒度比修改某一个 Planner 或 Controller 更灵活。

8.4 运行期更新和计算范围可控 ​

通过 CostmapFilterInfo 动态发现掩膜 Topic，通过 Lifecycle 管理订阅，通过 TF 处理地图坐标，通过更新窗口限制 Keepout 的遍历范围，通过当前位置采样限制 SpeedFilter 的计算量。

这些机制共同支持了临时封路、动态限速和运行期语义地图更新。

九、工程边界：设计好用，但不能掩盖这些风险 ​

9.1 坐标系、分辨率和边界对齐 ​

过滤器依赖 OccupancyGrid 的原点、分辨率、尺寸和 frame_id。TF 正确只能解决坐标系变换，不能自动修复两张栅格地图之间的分辨率、原点和边界错位。

错位可能表现为：

  • 禁行区向旁边偏移。
  • 机器人进入限速区后延迟触发。
  • 区域边缘来回切换。
  • 小于一个栅格的通道无法稳定表达。

因此语义掩膜制作和 Costmap 配置必须把栅格对齐当成接口契约，而不是可选优化。

9.2 当前栅格查询不等于机器人足迹查询 ​

SpeedFilter 当前查询的是机器人 Pose 对应的一个掩膜栅格，不是整个机器人足迹，也不是机器人未来轨迹。如果机器人尺寸较大，中心点还没有进入限速区时，外轮廓可能已经进入区域。

对于窄限速区、窄禁行区和高速机器人，通常需要：

  • 在语义地图中向外扩展安全边界。
  • 使用足迹覆盖范围生成掩膜。
  • 添加前视或预测式自定义过滤器。

9.3 SpeedLimit 不会自动改变 Planner 的路线 ​

SpeedFilter 只向 Controller 发布速度限制，不会告诉 Planner“这条路线虽然能走但代价更高”。如果业务要求机器人优先避开限速区，应额外使用 Keepout 或非致命代价表达。

可以用下面的判断选择机制：

业务目标更合适的表达
绝对不能进入KeepoutFilter
可以进入但必须慢SpeedFilter
尽量少走但不是禁止非致命代价或自定义评分
进入区域触发业务动作BinaryFilter 或外部任务节点

9.4 Unknown、消息过期和多来源限速需要系统策略 ​

当前 SpeedFilter 遇到未知栅格、TF 失败或掩膜越界时可能直接返回，不主动发布恢复消息；ControllerServer 也不会校验 SpeedLimit.header 的时间戳、坐标系和有效期。

另外，Costmap SpeedFilter、Route 操作和外部人工限速节点都可能成为 SpeedLimit 生产者，但消息本身没有来源 ID、优先级和仲裁字段。如果多个来源同时发布同一个 Topic，最后到达的消息可能覆盖之前的限制。

安全系统应在更高层增加：

  • 单一限速仲裁器。
  • 多来源取最小值策略。
  • 限速有效期和超时恢复。
  • 失去语义地图时的安全默认值。

十、总结：把空间语义接入导航行为 ​

10.1 一句话理解 Costmap Filters ​

Costmap Filters 的核心不是增加一张地图，而是建立一条标准转换链：

text
Semantic Map
    -> CostmapFilterInfo 解释元数据
    -> OccupancyGrid 空间掩膜
    -> Costmap Filter 插件
    -> Costmap 代价或 SpeedLimit
    -> Planner / Controller 行为

KeepoutFilter 让规划和控制理解“这里不能进入”，SpeedFilter 让控制器理解“这里允许经过但必须降速”，BinaryFilter 则把进入区域转换成可供任务系统消费的状态。

它的最大优点，是把环境建模、空间语义和导航算法解耦，同时复用 Nav2 已经稳定的 Costmap、Pluginlib、Lifecycle、TF、Topic 和 Controller 接口。它的最大边界，则是语义地图的坐标与时间一致性、当前位置采样的安全覆盖范围、限速来源仲裁和自定义控制器的契约实现。

从系统设计角度看，Costmap Filters 把一张栅格地图从“障碍物描述”扩展成了“机器人在不同空间区域应该如何行动的规则载体”。这正是它能够支持仓储车道、施工封路、区域限速和动态安全策略的根本原因。

一条参数命令，如何让 Nav2 当场“换脑”？逐行拆解 PlannerServer 动态回调 ​

Nav2 正在运行，能不能不重启节点，就把全局规划器从 GridBasedAstar 切换成 Smac2D？

当前工程确实支持这种热切换。入口不是新的 Action，也不是参数事件订阅者，而是 PlannerServer::dynamicParametersCallback(std::vector<rclcpp::Parameter> parameters)。它站在 ROS 2 参数真正提交之前：读取一批候选值、修改 Planner Server 的运行时成员，再用 rcl_interfaces::msg::SetParametersResult 投出“接受”或“拒绝”票。

这个函数只有三十多行，但同时连接参数服务、Lifecycle、插件表、两个规划 Action 和运行时互斥锁。它既能让机器人当场切换规划算法，也藏着一个容易被忽视的原子批量副作用。

本文基于当前本地 nav2_planner 1.1.20、planner_server.cpp、头文件、单元测试、ROS 2 Humble 参数接口和现用 YAML，只解析这一个回调的详细用法与实现边界。

一、先读懂函数签名 ​

1.1 返回值不是新参数，而是一张表决票 ​

函数返回：

cpp
rcl_interfaces::msg::SetParametersResult

这个消息只有两个核心字段：

  • successful：本回调是否接受整批候选参数。
  • reason：接受或拒绝的解释，供命令行、日志和界面显示。

生成消息的默认值是 successful=false、reason=""。因此源码不能只构造 result 后直接返回，而是在全部候选值检查完毕后显式写入：

cpp
result.successful = true;
return result;

一旦发现非法 selected_planner，函数会写入拒绝原因并提前返回。这里的返回值控制参数能否提交，不是 Planner Action 的执行结果，也不携带 Path。

1.2 输入是一次设置请求的候选参数向量 ​

输入类型是：

cpp
std::vector<rclcpp::Parameter> parameters

使用单参数接口时，向量通常只有一个元素；使用原子批量接口时，它可以包含多个候选参数。每个 rclcpp::Parameter 同时保存名称、类型和值，回调通过：

cpp
parameter.get_type();
parameter.get_name();
parameter.as_double();
parameter.as_string();

识别自己关心的内容。当前签名按值接收向量，循环又写成 for (auto parameter : parameters)，因此会再次复制每个参数对象。把它改成常量引用可以减少复制，但不改变回调语义。

二、一条命令如何进入这个回调 ​

2.1 参数服务先接收候选值 ​

执行：

bash
ros2 param set /planner_server selected_planner Smac2D

命令不会直接调用 dynamicParametersCallback()。请求先进入 Planner Server 的 ROS 2 参数服务，rclcpp 检查参数声明和静态类型，再调用已注册的 On Set Parameters Callback。此时传进函数的值仍是候选值，尚未写入节点参数存储。

2.2 回调在提交之前同步表决 ​

函数返回 successful=true 后，rclcpp 才允许参数进入存储，并发布 Parameter Event。返回 successful=false 时，请求方会收到 reason，候选值不提交。

所以它不是“参数变化后的通知”，而是“参数提交前的守门人”。这个时序非常重要：ROS 2 可以撤销尚未提交的参数存储，却不会自动撤销回调已经写入的普通 C++ 成员。

2.3 其他参数并不由这个函数负责 ​

当前回调只处理两种“类型＋名称”组合：

  • double + expected_planner_frequency。
  • string + selected_planner。

其他名称会被本函数忽略，并在循环结束时得到一张成功票。它们是否最终成功，还取决于参数是否已声明、类型是否匹配，以及同一节点上其他参数回调是否接受。特别是 planner_plugins 即使参数存储发生变化，本函数也不会创建、配置或激活新插件。

三、Lifecycle 决定回调是否存在 ​

3.1 构造阶段只声明参数 ​

PlannerServer() 声明：

text
selected_planner = ""
expected_planner_frequency = 1.0

此时 planners_ 还没有加载完成，动态回调也没有注册。

3.2 configure 读取初值并建立插件表 ​

on_configure() 根据 planner_plugins 创建全部 Global Planner 实例，再读取 selected_planner 和 expected_planner_frequency。现用主要配置把频率设为 20.0 Hz，并预加载 GridBased、GridBasedAstar、Smac2D、SmacHybrid、SmacLattice 和 ThetaStar。

如果启动 YAML 中的 selected_planner 不在 planners_，configure 只打印警告，不会清空非法值，也不会让 Lifecycle 配置失败。这比运行期回调宽松。

3.3 active 阶段才注册回调 ​

on_activate() 先激活 Action Server、Costmap 和全部 Planner 插件，随后调用：

cpp
dyn_params_handler_ = node->add_on_set_parameters_callback(
  std::bind(&PlannerServer::dynamicParametersCallback, this, _1));

返回的句柄必须保存在 dyn_params_handler_。句柄生命周期就是回调生命周期；如果不保存，共享指针释放后，回调也会失效。

3.4 deactivate 会注销回调 ​

on_deactivate() 执行 dyn_params_handler_.reset()。节点基础参数服务仍然存在，因此 inactive 期间参数存储仍可能被修改，但 selected_planner_id_ 和 max_planner_duration_ 不会经过本函数同步。

单纯重新 activate 只会重新注册回调，不会补读 inactive 期间的参数。要重新按参数存储建立运行时状态，需要让节点重新经过 cleanup 和 configure。

运行期修改前应先检查：

bash
ros2 lifecycle get /planner_server
ros2 param get /planner_server selected_planner
ros2 param get /planner_server expected_planner_frequency

四、互斥锁保证一次规划不会中途换算法 ​

4.1 回调入口先锁住 Server 级状态 ​

函数开头立即创建：

cpp
std::lock_guard<std::mutex> lock(dynamic_params_lock_);

这把锁保护的不是 ROS 2 参数存储，而是 Planner Server 自己的运行时成员和规划过程。

4.2 两个规划 Action 使用同一把锁 ​

computePlan() 与 computePlanThroughPoses() 入口也持有 dynamic_params_lock_，并一直覆盖 Costmap 等待、TF 变换、插件 createPlan()、路径校验和 Action 结束。

因此当前规划执行时，参数更新会等待；参数回调执行时，新的规划请求也会等待。一次规划不会在 createPlan() 中途突然切换 Planner，也不会在结束前改变耗时告警阈值。

代价是参数服务延迟与规划耗时直接相关。若插件规划很慢，ros2 param set 看起来也会“卡住”，这不是参数服务失效，而是在等待同一把锁。

五、expected_planner_frequency 实际只控制告警 ​

5.1 正值会换算成最大规划时长 ​

正值采用：

text
max_planner_duration = 1 / expected_planner_frequency

例如：

text
20.0 Hz → 0.05 s
5.0 Hz  → 0.20 s

两个规划 Action 完成后都会比较 planning_time 与该阈值。超时只打印 Planner loop missed its desired rate，不会取消 Path，也不会自动重试。

5.2 它不会改变重规划周期 ​

这个参数不会创建 Wall Timer，不会改变 Behavior Tree 的 RateController，也不会主动发起新的 ComputePath Action。全局规划多久调用一次，仍由 BT 或其他 Action Client 决定。

名字中的 frequency 表示期望性能基线，不是 Planner Server 内部执行频率。

5.3 非正值会关闭告警但仍然成功 ​

当候选值小于或等于零时，函数打印警告，把 max_planner_duration_ 设为 0.0，最后仍返回 successful=true。因为后续判断写成：

cpp
if (max_planner_duration_ && cycle_duration.seconds() > max_planner_duration_)

零值会直接关闭耗时越界告警。

实际使用：

bash
ros2 param set /planner_server expected_planner_frequency 5.0
ros2 param get /planner_server expected_planner_frequency

参数已声明为 double，命令中使用 5.0，不要写成整数 5。

六、selected_planner 如何让 Nav2 在线换脑 ​

6.1 候选值必须是已加载的插件 ID ​

非空候选值会在 planners_ 中查找。这里需要的是插件 ID，例如 Smac2D，不是 pluginlib 类型名 nav2_smac_planner/SmacPlanner2D。

现用配置已加载六个 ID：

  • GridBased。
  • GridBasedAstar。
  • Smac2D。
  • SmacHybrid。
  • SmacLattice。
  • ThetaStar。

切换命令：

bash
ros2 param set /planner_server selected_planner Smac2D
ros2 param get /planner_server selected_planner

成功后，下一次规划请求读取新的 selected_planner_id_。

6.2 非空 Server 参数覆盖 Action Goal ​

getPlan() 的实际选择公式是：

cpp
requested_planner_id = selected_planner_id_.empty() ?
  planner_id : selected_planner_id_;

只要 Server 参数非空，即使 Action Goal 明确请求 ThetaStar，也会使用 Server 选择的 Smac2D。源码会输出一次警告，说明 Action 请求被配置值覆盖。

6.3 空字符串把选择权还给 Action ​

恢复每个 Action Goal 自己选择 Planner：

bash
ros2 param set /planner_server selected_planner "''"
ros2 param get /planner_server selected_planner

空字符串会合法写入 selected_planner_id_。后续 getPlan() 重新读取 Goal 的 planner_id；如果 Server 只加载一个插件，还保留单插件回退逻辑。

6.4 不存在的 ID 会被拒绝 ​

bash
ros2 param set /planner_server selected_planner NotLoaded

回调返回：

text
successful = false
reason = "selected_planner is not configured"

参数存储保持原值，运行时成员也不会在这个拒绝分支被覆盖。这个检查只能切换已存在于 planners_ 的实例，不能热加载新插件。

七、为什么修改 planner_plugins 不会热加载 ​

7.1 插件实例只在 configure 创建 ​

planner_plugins 决定插件 ID 列表，<id>.plugin 决定 pluginlib 类型。它们在构造和 configure 阶段被读取，插件随后经过 create、configure 和 activate。

动态回调没有处理这两类参数，也没有调用 ClassLoader。因此运行期执行：

bash
ros2 param set /planner_server planner_plugins "['Smac2D']"

即使参数服务接受了存储变化，planners_ 也不会随之重建。可靠做法是修改配置后重新执行完整 Lifecycle 配置流程。

7.2 Server 选择与插件装载必须分开理解 ​

selected_planner 是“从已加载实例里选谁”，planner_plugins 是“configure 时要创建谁”。前者适合热更新，后者属于资源结构变化，不能由这一个回调完成。

八、原子批量提交仍可能留下成员副作用 ​

8.1 参数存储的原子性不覆盖普通成员 ​

假设原子请求按如下顺序传入：

text
expected_planner_frequency = 5.0
selected_planner = NotLoaded

循环先把 max_planner_duration_ 改成 0.2 s，随后发现 Planner ID 非法并返回失败。ROS 2 参数存储会拒绝整批候选值，但不会把普通 C++ 成员恢复成旧阈值。

于是可能出现：

text
参数存储仍是 20.0 Hz
运行时阈值却已经是 0.2 s

如果其他参数回调在本函数返回成功后拒绝整批请求，也可能留下相同类型的副作用。

8.2 安全使用应采用单参数更新 ​

当前实现下，Server 级参数宜一次修改一个，并立即读取验证：

bash
ros2 param set /planner_server selected_planner Smac2D
ros2 param get /planner_server selected_planner

随后触发一次规划，通过日志、Path 形态或插件调试信息确认实际 Planner。

8.3 源码修复应采用两阶段提交 ​

更稳妥的实现方式是先把候选频率和 Planner ID 放入局部变量，完成整批类型与合法性检查；只有所有候选值都通过，才一次性更新 max_planner_duration_ 和 selected_planner_id_。

这样 SetParametersResult 的成功与成员提交形成同一个事务边界。

九、现有单元测试覆盖了什么 ​

9.1 已覆盖正频率与负频率写入 ​

test_dynamic_parameters.cpp 通过 AsyncParametersClient::set_parameters_atomically() 写入 100.0 和 -1.0，随后读取参数存储，确认两者都能提交。这与“非正值关闭告警但仍返回成功”的实现一致。

9.2 Shim 丢弃了真实回调结果 ​

测试中的 dynamicParamsShim() 先把自己的 result.successful 设为 true，再调用 dynamicParametersCallback(parameters)，但没有接住并返回真实结果：

cpp
dynamicParametersCallback(parameters);
return result;

因此即使未来加入非法 Planner 用例，这个 Shim 也会把真实拒绝覆盖成成功。测试还没有断言 max_planner_duration_，所以只证明参数存储变化，没有证明运行时阈值同步。

9.3 仍缺少四类关键回归 ​

  • 非法 selected_planner 必须返回失败和明确原因。
  • 空字符串必须恢复 Action Goal 选择权。
  • inactive 阶段写参数后重新 activate 的成员漂移。
  • 原子批量失败时成员不得保留局部副作用。

这些用例比继续增加普通成功值更能守住回调的事务边界。

十、运行时怎么安全使用 ​

10.1 切换前确认 Lifecycle 与可用 ID ​

bash
ros2 lifecycle get /planner_server
ros2 param get /planner_server planner_plugins
ros2 param get /planner_server selected_planner

只有 active 状态下，本回调才会同步运行时成员。目标 ID 必须已经出现在 planner_plugins 对应的加载集合中。

10.2 切换后同时检查存储与行为 ​

bash
ros2 param set /planner_server selected_planner Smac2D
ros2 param get /planner_server selected_planner

参数读取相等，只能证明 ROS 2 存储已提交；还应触发一次 ComputePath 请求，确认新插件真实执行。

10.3 排障时先区分三种失败 ​

  • 命令立即报类型错误：候选值没有通过参数类型检查。
  • 返回 selected_planner is not configured：ID 未加载。
  • 命令长时间等待：规划 Action 可能正持有 dynamic_params_lock_。

这三种现象分别属于参数层、插件表和并发互斥，处理方向完全不同。

十一、这个回调真正控制了什么 ​

11.1 它控制两项 Server 级运行时策略 ​

selected_planner_id_ 决定下一次规划优先使用哪个已加载插件；max_planner_duration_ 决定何时打印规划耗时越界告警。

11.2 它不控制四类结构行为 ​

  • 不加载或卸载 Planner 插件。
  • 不改变 Behavior Tree 的重规划周期。
  • 不让正在执行的规划中途换算法。
  • 不自动回滚已经写入的 C++ 成员副作用。

十二、结语 ​

dynamicParametersCallback() 的本质不是“收到参数后改两个变量”，而是 Planner Server 的运行时事务入口。

它用 SetParametersResult 决定参数存储是否提交，用 Lifecycle 句柄限定热更新有效期，用 dynamic_params_lock_ 保证规划与更新串行，再用 selected_planner_id_ 和 max_planner_duration_ 改变下一次规划的插件选择与耗时告警。

真正安全的使用方式也由此变得清晰：只在 active 状态修改，一次更新一个 Server 参数，只选择已经加载的插件，设置后同时检查参数存储和规划行为。若要从源码消除批量副作用，则必须把“校验候选值”和“提交运行时成员”拆成两个阶段。

每 50 毫秒“试跑”420 条未来，机器人为什么只执行这一条？拆解 Nav2 DWB 全调用、状态与数据流 ​

DWB 每个控制周期生成一批速度，推演未来约 1.7 s 的轨迹，再让多个 Critic 评分。违法轨迹淘汰，合法轨迹中总分最低者成为本周期控制指令。

一、DWB 到底负责什么 ​

1.1 它是 Controller 插件 ​

DWBLocalPlanner 实现 nav2_core::Controller，由 controller_server 动态加载，不是独立节点。它接收全局路径、机器人位姿、里程计速度和局部 Costmap，返回 TwistStamped。

Action 管理、进度检查、到达判定以及最终速度 Topic 发布都属于 Controller Server。DWB 只负责局部速度搜索。

1.2 八个包组成一条算法链 ​

  • dwb_core：主循环、轨迹生成与评分协议。
  • dwb_plugins：两类轨迹生成器。
  • dwb_critics：路径、目标、障碍物等评分器。
  • costmap_queue：栅格距离传播队列。
  • dwb_msgs、nav_2d_msgs：轨迹、速度与评估消息。
  • nav_2d_utils：Path、Pose、Twist 的二维转换工具。
  • nav2_dwb_controller：聚合包与插件导出入口。

二、调用与状态如何流动 ​

2.1 Lifecycle 建立运行环境 ​

configure() 读取运动学参数，加载 TrajectoryGenerator、Critic 和调试发布器。activate()、deactivate() 控制 Publisher，cleanup() 释放资源。

setPlan() 将 nav_msgs/Path 转成 global_plan_，同时重置生成器和 Critic。速度上限通过 setSpeedLimit() 注入。

2.2 状态跨周期保留 ​

DWB 并非每个周期完全从零开始。以下状态会影响下一轮搜索：

  • 已裁剪的 global_plan_。
  • OscillationCritic 记录的振荡方向限制。
  • RotateToGoalCritic 的接近目标与旋转阶段状态。
  • 当前速度上限、加速度和减速度约束。

三、Path 如何变成评分基准 ​

3.1 路径先裁剪再变换 ​

每个周期，DWB 把机器人位姿变换到 Path 坐标系，在 prune_distance 内找到有效起点，截取局部 Costmap 可覆盖的前向路径，再变换到 Costmap 的 global_frame。已走过的前缀会被删除，最终目标位姿单独保留。

这一步决定 Critic 看到的不是整条全局路径，而是与当前位置和局部地图匹配的一段参考走廊。

3.2 MapGrid 把几何关系变成距离场 ​

PathDist、GoalDist、PathAlign 和 GoalAlign 会在 Costmap 栅格上建立距离场。路径或目标附近的栅格距离较小，向外通过队列传播，最终得到近似曼哈顿距离。

候选轨迹只需查询端点或前向点所在栅格的距离值，适合高频批量评分。

四、约 420 条候选轨迹从哪里来 ​

4.1 速度采样窗口 ​

当前配置中，Controller Server 以 20 Hz 运行，也就是每 50 ms 计算一次控制。差速底盘对 vx 采样 20 份，vy 被限制为零，只剩 1 份；vtheta 采样 20 份，并可能补入零角速度。因此候选规模约为：

text
20 × 1 × 21 ≈ 420

全零组合和不满足约束的速度会被过滤，实际数量可能略少。

4.2 两类生成器代表两种窗口 ​

StandardTrajectoryGenerator 用完整 sim_time 判断未来可达速度，并按加速度限制逐步积分位姿。它允许机器人在推演过程中继续加速或减速。

LimitedAccelGenerator 使用一个控制周期 sim_period 形成经典 Dynamic Window，只在当前速度附近采样短时可达速度，随后用该候选速度推演整条轨迹。

两者评分接口相同，但速度窗口含义不同。

五、Critic 如何选出赢家 ​

5.1 评分协议 ​

每周期各 Critic 的 prepare() 执行一次。每个候选速度生成 Trajectory2D，按配置顺序评分。

Critic 抛出非法轨迹异常时，候选立即淘汰。合法轨迹总分是各项原始分数乘权重后的和。累计分数高于当前最优值时可短路，最终最低分轨迹胜出。

5.2 十个 Critic 的职责 ​

  • 导航方向：PathDist、GoalDist、PathAlign、GoalAlign。
  • 碰撞安全：BaseObstacle、ObstacleFootprint。
  • 动作约束：RotateToGoal、Oscillation、PreferForward、Twirling。

当前配置启用了其中七个：RotateToGoal、Oscillation、BaseObstacle、GoalAlign、PathAlign、PathDist 和 GoalDist。

5.3 权重决定行为偏好 ​

现有参数中，PathAlign 与 PathDist 的 scale 为 32，GoalAlign 与 GoalDist 为 24，RotateToGoal 为 32，BaseObstacle 为 0.02。

scale 不能脱离原始分数量纲比较。判断谁主导行为，应查看 evaluation 或 cost cloud 的实际分项。

六、输出、失败与观测 ​

6.1 成功输出链 ​

最优轨迹的初始速度被转换成 TwistStamped 返回 Controller Server。当前系统中的主链为：

text
FollowPath
  → controller_server
  → DWBLocalPlanner::computeVelocityCommands()
  → cmd_vel_nav
  → velocity_smoother
  → cmd_vel
  → 底盘适配节点

DWB 限制的是建议速度；最终速度还受 velocity_smoother 的速度、加速度与死区约束。

6.2 失败与调试输出 ​

如果全部候选非法，DWB 抛出无合法轨迹异常。Controller Server 可在 failure_tolerance 内容忍短暂失败，持续失败才终止 FollowPath。

常用观测包括 evaluation、Marker、接收路径、变换后路径、局部轨迹和 cost cloud。Rotation Shim 内部也加载 DWB 时，要检查 Topic 是否重叠。

七、源码边界与排障重点 ​

7.1 容易误判的边界 ​

  • computeVelocityCommands() 收到的 GoalChecker 不直接参与 DWB 评分；RotateToGoal 的容差是独立参数。
  • Path 裁剪与部分 TF 处理发生在 DWB 持有 Costmap 互斥锁之前。
  • 个别 Pose 变换返回值未被逐项检查，TF 边缘故障可能表现为后续评分异常。
  • Critic 的 prepare() 返回失败时主要记录警告，不一定中止本轮。
  • 动态速度限制变化时，要同时核对线速度上限及其平方缓存是否一致。
  • 默认调试配置可能仍构造完整 evaluation，关闭发布并不等于没有计算开销。
  • DWB 命名空间下的 stateful 不是 DWB 自身读取的核心参数，不要与 GoalChecker 的同名参数混淆。

7.2 按数据链定位问题 ​

  • 没有候选：查当前速度、采样数、速度上下限与加速度窗口。
  • 全部非法：查 footprint、局部 Costmap、TF、Obstacle Critic 和膨胀层。
  • 轨迹贴不住路径：查变换后路径、MapGrid 距离场和 Align／Dist 权重。
  • 终点抖动：查 RotateToGoal、GoalChecker 容差及 Oscillation 状态。
  • DWB 输出正常但底盘速度异常：继续查 velocity_smoother 与底盘适配节点。

八、完整数据流总结 ​

8.1 一条主线看懂 DWB ​

text
Path + Pose + Odom + Local Costmap + SpeedLimit
  → Path 裁剪与 TF 变换
  → 速度窗口采样
  → 加速度约束轨迹推演
  → Critic prepare
  → 非法轨迹淘汰
  → 分项加权与短路
  → 最低总分轨迹
  → TwistStamped
  → Controller Server
  → Velocity Smoother
  → 底盘

DWB 的本质不是“直接跟踪路径”，而是在当前局部地图、运动学约束和路径目标之间，持续做有限时域的离散优化。理解候选速度、未来轨迹和 Critic 分数这三层数据，就能把大多数“走不动、贴障碍、终点抖动、速度不对”的问题定位到具体环节。

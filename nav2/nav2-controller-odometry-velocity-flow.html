nav2 ~三 · 局部控制与速度生成2026-07-226 min read

机器人明明在动，Nav2 为什么还要追问速度？拆解 Odometry 如何驱动控制闭环 ​

路径告诉机器人去哪里，Costmap 告诉它哪里不能走，但真正决定“下一帧速度能改多快”的，是机器人此刻到底跑多快。这个当前速度主要来自 /odom。

本文沿当前仓库源码拆开 Controller Server、五类控制器与 Velocity Smoother，讲清 Odometry 的速度从哪里进入、在哪里被使用，以及为什么命令速度不等于实测速度。

一、控制模块的输入输出边界 ​

1.1 FollowPath 只是任务入口 ​

Controller Server 暴露 FollowPath Action。Goal 带来 Path、controller_id、goal_checker_id 和 progress_checker_id。真正计算速度时，还要汇合四类运行时输入：

  • Local Costmap 与 footprint 碰撞代价。
  • TF 提供的机器人当前 Pose。
  • /odom 提供的当前 vx、vy、wz。
  • speed_limit 提供的绝对或百分比限速。

Controller 插件返回 TwistStamped，Controller Server 再发布 cmd_vel。当前 Nav2 Launch 将它重映射为 cmd_vel_nav，交给 Velocity Smoother，平滑后再发布最终 cmd_vel。

二、Odometry 速度怎样进入 Controller Server ​

2.1 OdomSubscriber 只保存最新速度 ​

当前源码创建 nav_2d_utils::OdomSubscriber，订阅 Controller Server 的 odom_topic。回调从 nav_msgs/Odometry.twist.twist 中提取 linear.x、linear.y 和 angular.z，写入互斥保护的 Twist2DStamped 缓存。

这里没有滑动平均，也没有使用 Pose 和 covariance。控制位姿来自 Local Costmap 的 TF 查询，不是 Odometry 消息里的 Pose。

2.2 小速度先被归零 ​

每个控制周期读取最新 Twist 后，getThresholdedTwist() 会应用 min_x_velocity_threshold、min_y_velocity_threshold 和 min_theta_velocity_threshold。绝对值不超过阈值的分量直接变成零。

阈值能压掉静止噪声，但过大也会让低速爬行被控制器误认为静止。当前实车配置为 0.001 m/s、0.5 m/s 和 0.001 rad/s；差速底盘不使用横移，因此 vy 的大阈值不会影响正常运动。

三、20 Hz 控制周期怎样汇合数据 ​

3.1 Pose、进展和速度依次就位 ​

当前 controller_frequency 为 20 Hz。每轮先从 Costmap／TF 取得 Pose，再由 ProgressChecker 判断机器人是否持续取得位移进展，随后读取并阈值化 Odometry Twist。

Controller Server 调用：

cpp
computeVelocityCommands(pose, current_twist, goal_checker)

插件内部再读取已缓存的 Path、Costmap 和 TF，输出本周期建议速度。异常在 failure_tolerance 内会暂时转换为零速度，持续超时才让 FollowPath 失败。

3.2 命令反馈不是实测反馈 ​

FollowPath Feedback 中的 speed 来自本周期 cmd_vel 的线速度模长，distance_to_goal 来自当前 Pose 到剩余 Path 的长度。它们用于任务反馈，但 speed 不是 /odom 实测速度。

四、五类控制器如何使用当前速度 ​

4.1 DWB 把速度当作动态窗口起点 ​

DWB 用当前 Twist 计算加减速度约束下的可达速度窗口，并把它作为候选轨迹积分的初始速度。Odom 延迟会让动态窗口落后，表现为起步、刹车或转向预测不准。

4.2 MPPI 把速度写入预测状态 ​

MPPI 将 vx、vy、wz 写入批量状态张量的首列，再从这个初始状态向未来 rollout。错误的速度符号会直接污染全部候选轨迹的起点。

4.3 RPP 用于前视和旋转约束 ​

启用速度缩放前视后，RPP 用 |vx| × lookahead_time 计算前视距离；原地转向时，又以当前 wz 和 max_angular_accel × dt 限制下一帧角速度。

4.4 Rotation Shim 可选择闭环角速度 ​

closed_loop=true 时，Rotation Shim 使用 Odometry 的 wz 作为旋转加速度窗口起点；关闭后使用上一帧命令角速度。当前实车配置开启了该闭环。

4.5 Graceful 当前忽略速度参数 ​

Controller 接口统一传入 Twist，不代表每个插件都使用它。当前 Graceful Controller 的实现显式忽略 velocity 参数。

五、Odometry 还会影响到达判定吗 ​

5.1 取决于 GoalChecker 类型 ​

Controller Server 会再次读取阈值化 Odom Twist，并与当前 Pose、目标 Pose 一起传入 GoalChecker。

SimpleGoalChecker 和 PositionGoalChecker 只判断位置与朝向，不使用速度。StoppedGoalChecker 才会额外检查平移和旋转速度是否低于停止阈值。因此“进入目标容差”和“机器人已经停稳”不是同一个条件。

六、Velocity Smoother 的两种反馈模式 ​

6.1 OPEN_LOOP 使用上一帧输出 ​

OPEN_LOOP 下，平滑器把自己的 last_cmd 当作当前速度，再执行绝对速度 clamp、加减速度限制、死区和超时减速。此时 /odom 仍进入 Controller Server，但不进入 Velocity Smoother。

6.2 CLOSED_LOOP 使用平均 Odometry ​

CLOSED_LOOP 下，平滑器独立创建 nav2_util::OdomSmoother。它保留 odom_duration 时间窗内的 Odometry，并对各 Twist 分量做算术平均，以这个实测均值作为加减速度约束的起点。

闭环更贴近真实底盘，但要求 Odometry 高频、低延迟。平滑频率高于 Odom 更新频率，或窗口过长时，反馈会滞后，机器人可能加速慢、振荡或过冲。

七、当前项目真正采用哪条链 ​

7.1 Controller 是速度闭环，末端平滑仍是开环 ​

myagv_test_bringup 与 nav2_regulated_modules 都把 velocity_smoother.feedback 配置为 OPEN_LOOP。因此当前链路是：

text
/odom → Controller Server → Controller 插件
cmd_vel_nav → Velocity Smoother(last_cmd) → cmd_vel → 底盘

若将平滑器改为 CLOSED_LOOP，同一 /odom 会被两个节点分别订阅：Controller Server 使用最新一帧，Velocity Smoother 使用时间窗均值。两者参数和延迟必须分别检查。

八、实车排障抓住三层 ​

8.1 源头层 ​

检查 /odom 频率、时间戳、vx／vy／wz 符号、静止噪声和响应延迟。TF 正常不代表 Twist 正确。

8.2 参数层 ​

核对两个节点各自的 odom_topic，再检查 Controller 阈值、平滑器 feedback、odom_duration 和 smoothing_frequency。当前本地 Controller 源码使用最新 Odom，不读取官方新版本文档中的 Controller odom_duration，不能跨版本照抄参数。

8.3 现象层 ​

  • 起步慢或转向迟钝：检查阈值、Odom 延迟和闭环窗口。
  • 旋转抖动或过冲：检查 wz 噪声、符号和频率。
  • Nav2 命令正常但底盘异常：继续沿 Velocity Smoother、底盘适配和执行器反馈排查。

九、一句话看懂这条闭环 ​

9.1 Odometry 不是附属显示数据 ​

Path 决定方向，Costmap 决定安全边界，Odometry 速度决定控制器从什么运动状态继续计算。它既能改变 DWB／MPPI 的未来预测，也能改变 RPP／Rotation Shim 的即时约束；在 Velocity Smoother 闭环模式下，还会再次决定最终速度每周期允许变化多少。

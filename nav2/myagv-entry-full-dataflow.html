没有 AMCL，Nav2 怎么跑？拆解 map→base_link 自研定位的实车全数据流 ​

第一篇文章从 myworld_bringup/entry.launch.py 出发，分析了 Ignition、bridge、AMCL、TEB 和仿真底盘组成的完整闭环。但机器人真正上车后，系统边界完全不同：Gazebo 不再提供传感器和里程计，AMCL 也不再负责定位，所有关键状态都来自车上的真实系统。

myagv_test_bringup/launch/entry.launch.py 正是这个实车入口。它默认隐藏 Gazebo 和 AMCL 接口，由自研定位实时发布 map→base_link，真实 C200 雷达发布 LaserScan，Nav2 负责规划与控制，最后通过 controlpub 把 /cmd_vel 转换成底盘通信消息。

本文沿数据流方向拆解这套架构：外部系统需要提供什么，Nav2 内部如何消费，速度命令又如何走到串口与电机。

一、实车入口真正启动了什么 ​

entry.launch.py 默认参数面向板端实车：use_sim_time=False、use_simulator=False、autostart=true。实际启动的核心组件只有五组：

1.1 RViz 子 Launch ​

由 use_rviz 控制，板端无图形界面时可以关闭。

1.2 map_server ​

读取 maps/out.yaml 和栅格地图，发布 /map。

1.3 lifecycle_manager_localization ​

名字虽然带 localization，但当前只管理 map_server，不管理 AMCL。

1.4 navigation_launch.py ​

启动 planner、controller、smoother、behavior、bt_navigator、waypoint_follower、velocity_smoother 和生命周期管理器。

1.5 controlpub ​

把 Nav2 的 /cmd_vel 转换为 /control_to_uart。

Gazebo 服务端和客户端仍保留条件代码，但默认 use_simulator=False，不会创建进程。locationpub、laserpub、map2base_tf、静态 odom→base_link、robot_state_publisher 和 joint_state_publisher 都被注释，没有加入 LaunchDescription。

这意味着入口只负责 Nav2 和地图，不再伪造任何真实车辆状态。

二、为什么可以不启动 AMCL ​

Nav2 并不强制要求使用 AMCL。它真正要求的是：在传感器消息对应的时间点，TF Buffer 能查询机器人从全局坐标系到本体坐标系的位姿。

当前系统由自研定位直接发布动态：

text
map → base_link

自研定位可以融合 GNSS、IMU、轮速、激光匹配或其他定位结果，但输出必须满足四项约束：

2.1 固定父子坐标系 ​

父坐标系是 map，子坐标系是 base_link。

2.2 实时更新动态变换 ​

变换必须实时更新，不能用一次性静态 TF 代替运动位姿。

2.3 统一时间基准 ​

时间戳要与雷达、里程计和 Nav2 使用同一时间基准。当前实车默认使用系统时间，不是 /clock。

2.4 保持唯一权威发布者 ​

只能有一个权威发布者。不能同时发布另一条 map→base_link，也不能再拼出一条与其竞争的 map→odom→base_link。

当前 local costmap 和 global costmap 的 global_frame 都配置为 map，robot_base_frame 都是 base_link。因此它们会直接查询 map→base_link，不依赖 AMCL 生成 map→odom。

三、外部系统必须提供哪些数据 ​

去掉仿真和 AMCL 后，Nav2 仍然需要地图、位姿、障碍物和速度反馈。

地图来自本包：map_server 读取 maps/out.yaml，以 transient local 方式发布 /map。新启动的 global costmap 可以立即收到最近一帧静态地图。

机器人位姿来自外部自研定位发布的 map→base_link。

真实 C200 雷达必须发布：

text
topic: /c200_lidar_node1/scan
type:  sensor_msgs/msg/LaserScan

LaserScan 的 frame_id 必须能通过 TF 连接到 base_link。由于入口没有启动 robot_state_publisher，如果雷达坐标系不是 base_link，外部驱动或专门 TF 节点还必须提供 base_link→lidar_frame。

底盘或状态融合系统还需要发布 /odom。它在当前架构中主要提供速度反馈：bt_navigator 和 controller_server 使用当前运动状态，velocity_smoother 虽然配置了 odom_topic，但当前 feedback=OPEN_LOOP，速度平滑主要依据上一周期命令估算。

四、两张代价地图为何都使用 map ​

global costmap 组合 StaticLayer、ObstacleLayer 和 InflationLayer。它使用 /map 建立全局环境，用 C200 LaserScan 标记和清除临时障碍，再扩张机器人安全半径。

local costmap 是 3 m × 3 m 的 rolling window，使用 VoxelLayer 和 InflationLayer，更新频率 5 Hz。虽然窗口会随机器人移动，但它的全局坐标系同样是 map，移动中心直接由 map→base_link 决定。

这种配置与标准的 map→odom→base_link 不同：它省掉 odom 坐标层，接口更直接；代价是定位输出的短时连续性会直接影响 local costmap 和 controller。如果 map→base_link 出现跳变，局部窗口和控制误差也会同步跳变。

因此自研定位不仅要“全局准确”，还要满足局部控制需要的连续、低延迟和高更新率。

五、目标如何变成全局路径 ​

RViz 或上层调度系统发送 NavigateToPose 后，bt_navigator 接收目标并运行行为树。

行为树从 TF 获取当前 base_link 在 map 中的位姿，然后调用 planner_server。当前参数虽然加载了 Navfn、Smac 和 Theta* 等多个插件，但自定义 selected_planner=GridBasedAstar 固定选择 NavfnPlanner，并启用 A* 搜索。

planner 的核心输入是当前位姿、目标位姿和 global costmap，输出为 map 坐标系的 nav_msgs/msg/Path。路径可以经过 SimpleSmoother 平滑，再由 FollowPath Action 送入 controller。

规划或控制失败时，行为树可以调用 Spin、BackUp、DriveOnHeading、Wait 等行为，完成恢复后重新规划。所有这些节点都由 lifecycle_manager_navigation 统一配置和激活。

六、DWB 如何生成局部速度 ​

与第一篇使用 TEB 不同，当前实车参数选择：

text
bt_navigator.selected_controller = DWB

因此 controller_server 调用 dwb_core::DWBLocalPlanner。

DWB 的输入包括全局 Path、map→base_link 当前位姿、/odom 当前速度和 local costmap 障碍物。每个控制周期可以概括为：

6.1 采样候选速度 ​

在允许的线速度和角速度范围内采样候选速度。

6.2 模拟短时轨迹 ​

对每组速度向前模拟短时轨迹。

6.3 检查碰撞并评分 ​

检查轨迹是否碰撞，并由多个 Critic 评分。

6.4 综合 Critic 代价 ​

综合 PathAlign、PathDist、GoalAlign、GoalDist、BaseObstacle、Oscillation 和 RotateToGoal 等代价。

6.5 选择轨迹并输出 Twist ​

选择合法且总代价最低的轨迹，输出对应 Twist。

controller_server 运行频率为 20 Hz，内部 cmd_vel 被 remap 为 /cmd_vel_nav，避免未经平滑的速度直接进入底盘。

七、从 /cmd_vel 到 /control_to_uart ​

velocity_smoother 订阅 /cmd_vel_nav，按照最大速度、加速度、减速度和超时约束生成最终 /cmd_vel。当前平滑频率为 20 Hz，最大线速度 0.26 m/s，最大角速度 1.0 rad/s。

controlpub 是 Nav2 与自研底盘协议之间的适配层。它订阅 geometry_msgs/msg/Twist，发布 byd_custom_msgs/msg/ControlRes：

text
ControlRes.v          = Twist.linear.x
ControlRes.w          = Twist.angular.z
ControlRes.v_lift     = 0.0
ControlRes.w_rotation = 0.0

输出 topic 为 /control_to_uart，后续串口或 CAN 节点把消息发送给底盘控制器。电机执行后，底盘产生新的 /odom，自研定位产生新的 map→base_link，真实雷达产生新的扫描，这些反馈再进入 Nav2 的下一控制周期。

完整实车闭环是：

text
导航目标
  → bt_navigator
  → GridBasedAstar 全局路径
  → DWB 局部速度
  → /cmd_vel_nav
  → velocity_smoother
  → /cmd_vel
  → controlpub
  → /control_to_uart
  → 串口/CAN与底盘
  → /odom + map→base_link + LaserScan
  → Nav2 下一周期

八、实车联调最容易忽略的检查项 ​

8.1 检查 use_sim_time 的运行期值 ​

虽然 YAML 中多个节点写着 True，但入口通过 RewrittenYaml 统一覆盖为 launch 参数；默认实车运行时最终值是 False。

8.2 检查 TF 唯一性 ​

map→base_link 必须只有一个发布者，入口中被停用的 map2base_tf 和静态 TF 不能重新启用。

8.3 检查雷达时间和坐标 ​

LaserScan 时间戳要与定位一致，frame_id 必须能连到 base_link，否则 costmap 会丢弃数据。

8.4 检查定位连续性 ​

全局位置正确但帧间跳变明显，依然会造成 local costmap 抖动、DWB 评分突变和速度不稳定。

8.5 检查控制接口链 ​

排查机器人不动时要依次检查以下接口，不能只看 controller 是否 active。

8.5.1 检查 /cmd_vel_nav ​

确认 Controller Server 是否输出未经平滑的导航速度。

8.5.2 检查 /cmd_vel ​

确认 Velocity Smoother 是否输出最终速度。

8.5.3 检查 /control_to_uart ​

确认 controlpub 是否完成底盘协议转换与发布。

九、核心结论 ​

没有 AMCL 并不意味着没有定位链。当前架构把定位责任完整交给自研系统，并把接口压缩成一条动态 map→base_link。Nav2 不关心这条 TF 是由粒子滤波、组合导航还是地图匹配生成，只关心它是否实时、连续、唯一且与传感器时间一致。

与第一篇仿真链路相比，这套实车系统少了 Gazebo 和 bridge，多了三个真正的工程边界：自研定位 TF、真实 C200 雷达，以及 /cmd_vel→ControlRes→串口底盘 的协议适配。实车 Nav2 的稳定性，最终取决于这些边界是否被清晰定义并逐段验证。

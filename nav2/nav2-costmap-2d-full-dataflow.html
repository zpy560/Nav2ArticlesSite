nav2 ~四 · 代价地图与安全2026-07-1514 min read

一束激光怎样变成避障代价？拆解 nav2_costmap_2d 调用全数据流 ​

地图告诉机器人哪里有墙，激光雷达告诉机器人眼前出现了什么，Footprint 告诉系统机器人到底有多大。

但 Planner 和 Controller 最终不能直接拿着这三份数据做决策。它们需要一张统一的二维栅格：每个格子都用一个代价值表达“从这里通过有多危险”。

这张图就是 Costmap。

nav2_costmap_2d 不只是“把障碍物画进地图”。它同时处理 Lifecycle、TF、静态地图、LaserScan、PointCloud2、机器人几何、滚动窗口、多插件融合、膨胀、安全区、过滤器、增量发布、清图服务和碰撞检查。

本文从一帧 /scan 出发，完整追踪它怎样进入 ObservationBuffer，怎样标记和清除栅格，怎样与静态层融合，再怎样经过 Inflation Layer 变成 Planner 和 Controller 使用的安全代价。

一、先给结论：Costmap 是“环境数据融合器”，不是地图副本 ​

静态地图通常只有 free、occupied 和 unknown。Costmap 内部却使用 0～255 的 unsigned char 代价值：

text
0    FREE_SPACE
1～252 渐变代价
253  INSCRIBED_INFLATED_OBSTACLE
254  LETHAL_OBSTACLE
255  NO_INFORMATION

它融合的输入至少包括：

text
/map                     静态 OccupancyGrid
LaserScan／PointCloud2    动态障碍观测
Range                    距离传感器观测
TF                       机器人和传感器坐标转换
robot_radius／footprint   机器人几何
Costmap Filter mask/info 禁行区、限速区等语义约束

输出则流向：

text
Planner Server     评估全局路径是否穿过高代价区域
Controller Server  评估局部轨迹、速度和碰撞风险
Behavior Server    预测恢复动作是否会碰撞
RViz2／工具节点     显示、查询和调试代价地图

所以 Costmap 不是 Map Server 的复制品，而是随机器人、传感器和插件状态不断变化的导航风险场。

二、一个 Costmap 由三层对象组成 ​

2.1 Costmap2DROS：ROS 与 Lifecycle 外壳 ​

Costmap2DROS 负责：

text
读取参数
创建 TF Buffer
动态加载插件和 Filter
管理 Lifecycle
启动更新线程
创建发布器、Footprint 接口和清图服务

它本身不实现静态地图、障碍物或膨胀算法。

2.2 LayeredCostmap：融合调度器 ​

LayeredCostmap 保存两个或一个主栅格，以及有序插件列表：

text
plugins_  Static／Obstacle／Voxel／Inflation／Denoise 等
filters_  Keepout／Speed／Binary 等后处理层

每轮更新由它计算更新窗口，再按配置顺序调用各层。

2.3 Costmap2D：真正的二维数组 ​

Costmap2D 保存：

text
size_x／size_y
resolution
origin_x／origin_y
unsigned char costmap_[]
mutex

它提供 worldToMap、mapToWorld、resizeMap、updateOrigin、resetMap、raytraceLine、copyWindow 等底层操作。

三、Lifecycle 与两类线程怎样配合 ​

Costmap 通常以内嵌节点形式存在于 Planner Server 或 Controller Server 中，但它自己仍是 LifecycleNode。

3.1 CONFIGURE：搭好全部数据通道 ​

configure 阶段读取：

text
global_frame／robot_base_frame
width／height／resolution／origin
rolling_window／track_unknown_space
update_frequency／publish_frequency
plugins／filters
robot_radius／footprint／footprint_padding

随后创建 LayeredCostmap，按米制尺寸和分辨率分配栅格；创建 TF Buffer 和 Listener；通过 pluginlib 依次加载 Layer 与 Filter。

默认插件为：

text
static_layer
obstacle_layer
inflation_layer

插件顺序不是展示顺序，而是写入 Master Costmap 的执行顺序。通常静态和动态障碍层先写，Inflation 最后根据已存在的致命障碍生成安全梯度。

configure 还创建：

text
footprint 订阅
published_footprint 发布
Costmap2DPublisher
三类 Clear Costmap 服务

ROS 回调被放入一个 MutuallyExclusive callback group，并交给独立的 SingleThreadedExecutor + NodeThread。

3.2 ACTIVATE：先等 TF，再跑更新循环 ​

activate 先激活 Costmap 和 Footprint Publisher，然后循环等待：

text
global_frame ← robot_base_frame

没有这个 TF，系统无法知道机器人位于哪个栅格，也无法建立滚动窗口中心。当前实现会持续等待并周期打印错误，而不是带着未知位姿开始更新。

TF 可用后创建独立 map_update_thread，以 update_frequency 调用 updateMap()，再激活全部插件和 Filter 的订阅。

因此存在两类执行上下文：

text
callback executor thread  处理 TF、传感器、地图、Footprint、服务等回调
map update thread         周期读取最新缓存并融合 Costmap

两者通过各层和 Master Costmap 的 mutex 保证一致性。

3.3 更新频率不等于发布频率 ​

update_frequency 决定内部融合多久执行一次；publish_frequency 决定多快把结果发给外部订阅者。

Planner 和 Controller 在同一进程内通常直接读取 Master Costmap，因此即使发布频率较低，它们也能看到更高更新频率的内部结果。

update_frequency=0 会直接禁用更新循环。publish_frequency≤0 则禁用周期发布，两者含义不同。

四、静态地图怎样进入 StaticLayer ​

StaticLayer 订阅配置的 map_topic。默认支持 transient local、reliable、KeepLast(1)，因此可以收到 Map Server 早先发布的最近地图。

收到 OccupancyGrid 后，StaticLayer 先检查宽、高、分辨率和原点。

对于非滚动 Global Costmap，如果 Master 尺寸不匹配，且尺寸未被锁定，StaticLayer 会调用 LayeredCostmap::resizeMap()，让整个 Layered Costmap 与静态地图一致。

每个 OccupancyGrid 值再由 interpretValue() 转成内部代价，受这些参数影响：

text
track_unknown_space
unknown_cost_value
lethal_cost_threshold
trinary_costmap

静态层可以 true overwrite 或 maximum 方式合入 Master。滚动窗口下，如果 StaticLayer 的地图 frame 与 Costmap global frame 不同，还要通过 TF 逐栅格转换。

所以 /map 显示正常，不代表 StaticLayer 必然正常：QoS、frame、尺寸锁定和阈值解释都可能阻断或改变静态代价链。

五、一帧 LaserScan 怎样变成障碍物 ​

ObstacleLayer 的 observation_sources 可以配置多个来源。当前支持 LaserScan 和 PointCloud2；Range 由独立 RangeSensorLayer 处理。

5.1 MessageFilter 先保证 TF 可用 ​

LaserScan 或 PointCloud2 不是一收到就立即写栅格。订阅器先经过 tf2_ros::MessageFilter，等待数据能够转换到 Costmap 的 global_frame。

如果 TF 缺失、时间戳超出 Buffer 或消息队列溢出，这帧数据不会进入障碍处理。此时 Topic 有频率，也不等于 Costmap 收到了有效观测。

LaserScan 会投影成 PointCloud2，再交给对应 ObservationBuffer。

5.2 ObservationBuffer 保存统一观测 ​

Buffer 保存：

text
传感器原点
已转换点云
obstacle_min／max_range
raytrace_min／max_range
observation_persistence
expected_update_rate

observation_persistence 控制观测保留多久；expected_update_rate 用来判断数据是否仍 current。它们不是同一个参数。

5.3 Clearing：沿射线清出自由空间 ​

配置 clearing: true 的观测，会从传感器原点向每个端点执行 raytrace，把射线经过的旧障碍栅格清为 FREE_SPACE。

清除距离由 raytrace_min_range 和 raytrace_max_range 控制。

这解释了动态障碍消失后的清理机制：不是“没有新点就自动消失”，而是新的传感器射线明确告诉系统这段空间现在为空。

5.4 Marking：把命中点写成致命障碍 ​

配置 marking: true 的观测经过高度、地图边界和 obstacle range 过滤。有效命中栅格写为：

text
LETHAL_OBSTACLE = 254

obstacle_max_range 控制障碍标记距离，raytrace_max_range 控制自由空间清除距离。常见配置让 raytrace 稍远于 obstacle range，以便清除障碍边缘后的旧数据。

5.5 Footprint Clearing ​

ObstacleLayer 默认可清空机器人 Footprint 内部的栅格，避免传感器看到机器人自身结构后把底盘内部标成障碍物。

这不是忽略 Footprint 周围障碍，只是把变换后的机器人多边形内部设为 FREE_SPACE。

六、VoxelLayer 与 ObstacleLayer 的区别 ​

ObstacleLayer 直接在二维栅格上维护障碍。VoxelLayer 额外维护三维体素结构，按 z 方向累计 mark 与 clear，再把结果投影到二维 Master Costmap。

两者都消费 LaserScan 或 PointCloud2，也都使用 ObservationBuffer，但 VoxelLayer 更适合需要高度维度过滤或多层点云占用的场景。

最终 Planner 和 Controller 仍消费二维 Master Costmap，不直接读取体素网格。

七、一次 updateMap() 为什么分两阶段 ​

每轮融合都持有 Master Costmap mutex，避免 VoxelLayer 等非线程安全更新与外部读取交叉。

7.1 updateBounds() ​

所有插件和 Filter 按配置顺序执行：

cpp
updateBounds(robot_x, robot_y, robot_yaw,
             &min_x, &min_y, &max_x, &max_y);

这一阶段主要做两件事。

7.1.1 更新各层私有状态 ​

读取各层最新缓存，更新各层私有状态。

7.1.2 合并公共更新边界 ​

把本轮可能发生变化的世界坐标范围并入公共边界。

边界只能扩大，不能缩小前一层已经声明的范围。源码会检测非法缩小并指出具体 Layer 或 Filter。

合并后的世界坐标再通过 worldToMapEnforceBounds() 转成并裁剪为栅格窗口：

text
x0 ～ xn
y0 ～ yn

这样大地图上只有变化区域需要重算和发布，而不是每周期全图处理。

7.2 updateCosts() ​

没有 Filter 时，系统清空 combined_costmap_ 的更新窗口，再依次让每个插件写入。

存在 Filter 时，按以下步骤处理。

7.2.1 写入 Primary Costmap ​

插件写入 primary_costmap_。

7.2.2 复制 Combined Costmap 更新窗口 ​

把更新窗口复制到 combined_costmap_。

7.2.3 执行 Filter 后处理 ​

Filter 依次后处理 combined_costmap_。

这个双缓冲设计防止 Keepout 或 Speed Filter 的结果反过来成为下一轮基础插件的输入。基础环境代价保存在 primary，语义约束只作用于最终 combined 输出。

八、插件顺序为什么会改变结果 ​

Layer 不是简单求和。每个插件自己选择组合方法：覆盖、真覆盖、取最大值或不写入。

例如默认顺序：

text
StaticLayer
→ ObstacleLayer
→ InflationLayer

Static 先提供墙体，Obstacle 再加入动态致命障碍，Inflation 最后扫描当前 Master 中的致命种子并生成梯度。

如果 Inflation 放在 Obstacle 前面，本轮新标记的动态障碍可能来不及参与相同期望顺序的膨胀。自定义 Layer 插入位置也会改变它看到的上游代价。

因此排障必须同时核对 plugins 数组顺序和每个 <plugin_name>.plugin 类型，不能只确认动态库成功加载。

九、Footprint 怎样影响代价安全边界 ​

机器人几何来自两条互斥配置路径：

text
footprint 有效 → 使用多边形
footprint 为空或无效 → 使用 robot_radius 生成近似圆

footprint_padding 会扩张基础几何。LayeredCostmap::setFootprint() 保存 padded footprint，并计算：

text
inscribed_radius     机器人中心到边界的最短距离
circumscribed_radius 机器人中心到边界的最长距离

随后通知所有 Layer 和 Filter 执行 onFootprintChanged()。

Costmap2DROS 还订阅 footprint Topic，运行中收到新 Polygon 时会重新计算上述数据，并通过 published_footprint 发布机器人当前位姿下的定向多边形。

十、Inflation Layer 怎样生成安全梯度 ​

Inflation 不是把障碍物尺寸简单放大一圈，而是根据到最近障碍的距离赋值。

它把 LETHAL_OBSTACLE，以及可选的 unknown 栅格，作为距离为 0 的种子；按距离桶从近到远扩散到相邻栅格。

关键参数是：

text
inflation_radius
cost_scaling_factor
inflate_unknown
inflate_around_unknown

成本语义大致为：

text
障碍物本体                         254
Footprint 内切半径以内              253
内切半径外、inflation_radius 内     指数衰减
膨胀半径以外                       保留原代价

cost_scaling_factor 越大，代价衰减越快；它不是“越大越保守”。inflation_radius 才决定梯度传播到多远。

当 Footprint 变化时 Inflation 会重建缓存并触发全区域重新膨胀。如果 inflation_radius 小于 inscribed_radius，代码会明确报错，因为此时膨胀范围连机器人自身内切半径都覆盖不了。

十一、滚动窗口如何跟着机器人移动 ​

Local Costmap 常配置 rolling_window: true。

每轮 LayeredCostmap::updateMap() 根据机器人位姿把原点更新为：

text
origin_x = robot_x - size_x_meters / 2
origin_y = robot_y - size_y_meters / 2

Costmap2D::updateOrigin() 不会无脑清空整张图。它计算新旧窗口重叠区域，把仍有效的旧数据复制到新位置，新增区域再用默认值初始化。

因此滚动窗口是在固定大小内移动栅格坐标原点，不是创建无限增长地图。

Global Costmap 通常关闭 rolling window，让 StaticLayer 的地图尺寸、分辨率和原点决定全局范围；Local Costmap 通常围绕机器人保持较小窗口，用高频传感器数据服务控制器。

十二、Costmap Filter 为什么独立于普通 Layer ​

Filter 也实现 Layer 接口，但它们表达的是语义规则，不是基础环境观测。

典型 Filter 包括：

text
KeepoutFilter  禁止进入区域
SpeedFilter    限速区域
BinaryFilter   基于掩码开关某种二值行为

它们通常订阅两类数据：

text
filter_mask OccupancyGrid
CostmapFilterInfo：type、mask topic、base、multiplier

Filter 在普通插件完成后处理 combined_costmap_。Clear Costmap 服务不会清理 Filter，因为过滤规则应该持续存在，不能因一次恢复动作而丢失禁行区或限速区。

十三、Costmap 怎样发布给外部 ​

Costmap2DPublisher 提供三条 Topic 和一个服务。

13.1 costmap ​

这是 nav_msgs/msg/OccupancyGrid。内部 0～255 被翻译为 -1～100：

text
0   → 0
253 → 99
254 → 100
255 → -1
1～252 → 1～98 线性缩放

它适合 RViz2 和通用 OccupancyGrid 工具，但不能无损保留全部内部代价等级。

13.2 costmap_raw ​

这是 nav2_msgs/msg/Costmap，保留内部 0～255 数据和 Master metadata，适合 Nav2 工具与精确代价分析。

13.3 costmap_updates ​

当尺寸、分辨率和原点没有变化，且 always_send_full_costmap=false 时，可只发布本轮更新窗口的 map_msgs/msg/OccupancyGridUpdate。

如果滚动窗口导致 origin 变化，或地图尺寸／分辨率变化，则必须重新发布完整 Costmap。

这三类 Publisher 都使用 transient local 和 reliable。实际准备与发布还会检查订阅者数量，避免没有消费者时重复序列化大数组。

13.4 get_costmap ​

GetCostmap Service 返回完整 Raw Costmap 快照，适合按需查询。

十四、Planner 和 Controller 是否通过 Topic 读取 Costmap ​

通常不是。

Planner Server 和 Controller Server 内部持有各自的 Costmap2DROS，算法插件通过指针取得 Master Costmap，并在需要时锁 mutex 直接读取。

Topic 主要用于可视化、跨节点工具和调试。把 publish_frequency 调高不会让同进程 Planner 更快得到内部更新；真正影响算法新鲜度的是 update_frequency、传感器到达、TF 和 Layer current 状态。

十五、Footprint Collision Checker 检查了什么 ​

FootprintCollisionChecker 把基础 Footprint 变换到候选 x、y、theta，使用 worldToMap 定位各顶点，再沿多边形边界进行栅格线遍历，返回边界上的最大代价。

如果 Footprint 顶点越出 Costmap，返回 LETHAL_OBSTACLE。

这个检查重点是多边形边界，不是对内部每个栅格做完整填充扫描。通常配合已经膨胀的 Costmap 使用，借助 Inflation 把机器人实体尺寸编码进周围梯度。

十六、三类清图服务究竟清什么 ​

每个 Costmap2DROS 创建：

text
clear_entirely_<costmap_name>
clear_around_<costmap_name>
clear_except_<costmap_name>

clear_around 清理以机器人为中心的方形区域；clear_except 保留中心方形区域、清理外部；clear_entirely 调用 resetLayers 重置全部可重置插件。

区域清理只遍历普通 plugins 中 isClearable() 为 true 的 CostmapLayer。Filter 不参与清理。

清理后 Layer 会添加 extra bounds，迫使下一轮更新覆盖相关区域。否则数组虽被清空，增量融合和发布可能不知道哪些位置已经变化。

清图不是永久删除静态地图和当前可见障碍。下一轮 StaticLayer、ObstacleLayer 仍会根据现有输入重新写回有效代价。

十七、isCurrent() 为什么重要 ​

LayeredCostmap 的 current 状态是所有已启用 Layer 和 Filter current 状态的逻辑与。

ObstacleLayer 根据 ObservationBuffer 的 expected_update_rate 判断传感器是否过期；StaticLayer 在收到并处理地图后才 current；Filter 也可以维护自己的新鲜度。

Costmap initialized 只表示至少完成了一次融合，current 则表示当前依赖数据没有被判定为过期。两者不能互换。

Controller Server 常要求 Costmap current，防止使用长时间未更新的障碍数据继续输出速度。

十八、最常见的九个排障边界 ​

18.1 Topic 有消息不等于 Layer 收到有效数据 ​

MessageFilter 还需要对应时间戳的 TF。

18.2 标记与清除距离必须分别配置 ​

obstacle_max_range 控制标记，raytrace_max_range 控制清除，不能只改一个。

18.3 数据保留与新鲜度不是同一参数 ​

observation_persistence 是数据保留时间，expected_update_rate 是新鲜度判断，不是同一作用。

18.4 更新频率不等于发布频率 ​

Planner／Controller 内部读取与 RViz2 Topic 显示可能不同步。

18.5 插件数组顺序会改变融合结果 ​

尤其要核对 Inflation 与自定义 Layer 的相对位置。

18.6 联合检查 Footprint、Padding 和 Inflation ​

只增大 robot_radius 不一定影响已经显式配置的 polygon footprint。

18.7 两张 Costmap 不一定使用相同坐标系 ​

Local Costmap 的 global frame 常为 odom，Global Costmap 常为 map。不能假设两张图使用同一坐标系或同一原点。

18.8 Clear 服务不会永久移除持续规则 ​

Clear 服务只清理可清理 Layer，Filter 和持续输入会在下一轮重新施加规则。

18.9 RViz2 Costmap 不是内部原始代价 ​

RViz2 显示的是转换后的 OccupancyGrid，不是内部原始 0～255 Costmap；精确分析应查看 costmap_raw 或直接查询 Master。

十九、建议的观测顺序 ​

19.1 检查 Costmap Lifecycle ​

确认 Costmap Lifecycle 是否 active。

19.2 检查机器人位姿 TF ​

确认 global_frame ← robot_base_frame TF 是否可用。

19.3 检查插件配置 ​

确认 plugins／filters 名称、类型和顺序是否正确。

19.4 检查 StaticLayer ​

确认 StaticLayer 是否收到 /map，QoS 和 frame 是否匹配。

19.5 检查传感器 MessageFilter ​

确认传感器 MessageFilter 是否因 TF 丢弃消息。

19.6 检查 ObservationBuffer ​

确认 ObservationBuffer 是否 current。

19.7 检查更新线程 ​

确认 update_frequency 是否大于 0，更新线程是否运行。

19.8 检查机器人安全边界参数 ​

确认 Footprint、padding、inflation_radius 是否一致。

19.9 对比内部与外部 Costmap ​

确认内部 Master、costmap_raw 与 RViz2 costmap 是否一致。

19.10 检查清图后的数据回写 ​

确认 Clear 服务后相关 Layer 是否被持续输入重新写回。

二十、结语 ​

nav2_costmap_2d 的完整主链可以压缩成四次转换：

text
地图／传感器／TF
→ 各插件私有状态
→ 更新窗口内按顺序融合
→ 与机器人尺寸相关的最终 Master Costmap

再由 Master Costmap 分出三条用途：

text
同进程直接读取 → Planner／Controller／碰撞检查
转换发布         → RViz2／跨节点工具
服务修改         → 查询与恢复清图

理解更新窗口、插件顺序、Footprint 和 Inflation 这四个核心点后，Costmap 就不再是一张颜色复杂的图，而是一套能够解释每一个障碍来源、每一个代价值和每一次更新时机的导航安全数据流。

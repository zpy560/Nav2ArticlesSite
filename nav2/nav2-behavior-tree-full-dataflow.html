Nav2 为什么能边规划边控制？拆解 nav2_behavior_tree 调用全数据流 ​

一台机器人收到导航目标后，并不是简单地依次调用规划器和控制器。

它要周期性重规划，要在路径变化时更新控制目标，要判断故障发生在规划侧还是控制侧，还要决定清代价地图、旋转、等待和后退的执行顺序。用户取消导航时，已经下发到各服务器的异步任务也必须一起停下来。

Nav2 把这套决策编排放进了行为树。nav2_behavior_tree 则是行为树与 ROS 2 Action、Service、Topic 之间的连接层。

这篇文章不只看 XML，而是从一个 /navigate_to_pose 目标出发，完整追踪目标、路径、反馈、恢复次数、取消请求和最终结果怎样流过整个系统。

一、先给结论：它不是导航算法，而是导航调度运行时 ​

nav2_behavior_tree 不计算全局路径，也不直接输出速度。

它承担五类职责：

1.1 加载行为树节点插件 ​

把 XML 标签变成可执行的 C++ 节点。

1.2 创建和运行行为树 ​

以固定周期调用 tickRoot()。

1.3 通过 Blackboard 传递数据 ​

在节点之间传递目标、路径、TF、里程计工具和恢复次数。

1.4 转换 ROS 2 调用 ​

把树内节点转换成 ROS 2 Action 或 Service 客户端，调用 planner_server、controller_server、behavior_server 和 costmap 服务。

1.5 返回任务状态 ​

把取消、抢占、节点状态日志和最终结果送回外层导航 Action。

因此，完整调用链不是“行为树直接控制机器人”，而是：

text
导航目标
  → bt_navigator
  → BtActionServer
  → BehaviorTreeEngine.tickRoot()
  → BT Action／Service 插件
  → planner_server／controller_server／behavior_server
  → 路径或运动结果
  → Blackboard／树节点状态
  → 导航 feedback／result

二、配置阶段：先造工厂，再造树 ​

BtActionServer<ActionT> 是外层导航 Action 与行为树运行时之间的总入口。NavigateToPoseNavigator 和 NavigateThroughPosesNavigator 都通过这个模板类获得自己的 Action Server。

在 on_configure() 阶段，它不会立刻执行 XML，而是先完成运行环境装配。

2.1 创建专用 client node ​

BtActionServer 创建一个普通 rclcpp::Node，名字带 _rclcpp_node 后缀，并把父 LifecycleNode 的参数复制过来。

这个节点不是新的导航服务器，它是行为树内部所有 ROS 客户端的共同宿主。树内的 Action、Service、订阅器和状态日志发布器都从 Blackboard 取出这个节点。

2.2 动态注册插件 ​

BehaviorTreeEngine 构造时遍历 plugin_lib_names：

cpp
factory_.registerFromPlugin(loader.getOSName(plugin));

每个插件动态库通过 BT_REGISTER_NODES 注册自己的 XML 标签。例如：

text
ComputePathToPose → ComputePathToPoseAction
FollowPath        → FollowPathAction
ClearEntireCostmap → ClearEntireCostmapService
RecoveryNode      → RecoveryNode
RoundRobin        → RoundRobinNode

这解释了一个常见误区：nav2_tree_nodes.xml 主要描述 Groot 可识别的节点模型和端口，真正决定运行时能否实例化节点的是 plugin_lib_names 与动态库注册代码。

2.3 建立 Blackboard 基础设施 ​

根 Blackboard 首先写入：

text
node                     行为树 ROS 客户端节点
server_timeout           单次请求确认／响应超时
bt_loop_duration         行为树循环周期
wait_for_service_timeout 等待服务上线的超时
tf_buffer                TF 查询入口
odom_smoother             平滑速度入口
number_recoveries         恢复动作计数

进入 on_activate() 后，服务器读取默认 XML；如果导航目标指定了另一个 behavior_tree 文件，则接收目标时重新加载。createTreeFromText() 根据 XML 标签实例化已经注册的插件，并为 subtree Blackboard 补写共同的 node 和 timeout 数据。

最后才激活 /navigate_to_pose 或 /navigate_through_poses Action Server。

三、一个导航目标如何进入行为树 ​

当 /navigate_to_pose 收到 Goal，外层先经过 Navigator 互斥检查。同一时间只允许一个 Navigator 处于导航状态，避免单目标导航和多目标导航同时控制系统。

目标通过检查后，NavigateToPoseNavigator::goalReceived() 做两件事。

3.1 加载行为树文件 ​

加载 Goal 指定的行为树文件；字段为空时继续使用默认树。

3.2 写入任务数据 ​

把 goal->pose 写入 Blackboard 的 goal 键，并把 number_recoveries 清零。

3.3 运行行为树循环 ​

随后 BtActionServer::executeCallback() 调用：

cpp
bt_->run(&tree_, on_loop, is_canceling, bt_loop_duration_);

BehaviorTreeEngine::run() 的循环很短，但它是整套调度的时钟：

text
检查取消
  → tree.tickRoot()
  → 发布 feedback，刷新行为树日志
  → 按 bt_loop_duration 休眠
  → 再次 tick

默认 bt_loop_duration 为 10 ms。这里使用 WallRate，如果一次 tick 和回调处理超过周期，系统会发出 tick rate exceeded 告警，而不是同时启动另一个 tick。

四、一次 tick 怎样变成 ROS 2 Action ​

以 ComputePathToPose 为例，它继承 BtActionNode<nav2_msgs::action::ComputePathToPose>。

4.1 首次 Tick 并发送 Goal ​

节点第一次从 IDLE 被 tick 时，会把自己设为 RUNNING，执行派生类的 on_tick()，从 XML 输入端口读取 goal、planner_id 和可选起点，然后调用 async_send_goal()。

4.2 推进异步 Action ​

这次调用不会阻塞整个行为树直到规划结束。节点使用自己的互斥 callback group 和 SingleThreadedExecutor，每次 tick 只处理一小段异步进展：

text
等待 GoalHandle → RUNNING
GoalHandle 已确认但结果未到 → spin_some() → RUNNING
结果到达 → 映射为 SUCCESS／FAILURE
超过 server_timeout → FAILURE

为了避免一次等待吃掉整个行为树周期，单次内部等待上限被设为 bt_loop_duration × 0.5。因此其他条件节点、控制节点和外层反馈仍能持续推进。

4.3 处理规划结果 ​

规划成功后，ComputePathToPoseAction::on_success() 把返回的 nav_msgs/Path 写入输出端口 path。规划中止或节点被 halt 时，它会写入空路径，避免旧路径继续污染后续执行。

4.4 更新 FollowPath Goal ​

FollowPathAction 以相同框架调用 /follow_path。它在等待结果期间不断重新读取 Blackboard 中的 path。一旦周期重规划生成了新路径，就设置 goal_updated_ 并向 controller server 发送更新后的目标。

这正是 Nav2 能“边控制边重规划”的关键：规划器更新共享路径，控制节点在后续 tick 中发现变化，再更新底层 FollowPath Goal。

五、Blackboard 不是缓存，而是数据总线 ​

XML 中的 {goal}、{path} 不是字符串替换，而是 Blackboard 端口绑定。

5.1 传递目标与路径 ​

默认单目标导航中，最重要的数据闭环是：

text
NavigateToPose Goal
  → Blackboard[goal]
  → ComputePathToPose.goal
  → planner_server
  → ComputePathToPose.path
  → Blackboard[path]
  → FollowPath.path
  → controller_server

5.2 生成外层 Action Feedback ​

Blackboard 还连接了行为树与外层 Action feedback。

每轮 onLoop() 中，NavigateToPoseNavigator 查询当前 TF 位姿，从 Blackboard 读取当前全局路径，计算路径剩余距离；同时从 odom_smoother 获取速度，估算剩余时间，再读取 number_recoveries。

最终发布的外层反馈包括：

text
current_pose
navigation_time
estimated_time_remaining
number_of_recoveries
distance_remaining

需要区分两层反馈：树内 /follow_path feedback 由 BtActionNode 接收，用来驱动具体插件逻辑；外层 /navigate_to_pose feedback 则由 Navigator 每轮汇总 TF、路径、速度和恢复计数后发布。

六、Service 节点怎样接入 ​

BtServiceNode<ServiceT> 与 Action 节点结构相似，但它处理的是一次请求和一次响应。

6.1 构造并发送 Service Request ​

第一次 tick 时，派生类在 on_tick() 填充 request，然后执行 async_send_request()。

6.2 检查异步响应 ​

后续 tick 使用独立 executor 检查 future：响应完成则调用 on_completion()，未完成且未超时则返回 RUNNING，超时则返回 FAILURE。

6.3 调用 Clear Costmap Service ​

例如 ClearEntireCostmap 调用：

text
global_costmap/clear_entirely_global_costmap
local_costmap/clear_entirely_local_costmap

清图动作开始时还会递增 Blackboard 中的 number_recoveries，所以 RViz2 看到的恢复次数并不是 RecoveryNode 重试轮数，而是具体恢复插件主动累计的次数。

七、默认导航树如何安排规划与控制 ​

默认 navigate_to_pose_w_replanning_and_recovery.xml 的主流程由三层关键控制节点组成。

7.1 PipelineSequence：让上游持续更新 ​

普通 Sequence 中，前一个孩子成功后通常不会在后续周期重新执行。PipelineSequence 则会在后面的孩子仍为 RUNNING 时重新 tick 已经走过的上游节点。

配合 RateController hz="1.0"，它形成如下流水线：

text
每秒重新计算一次全局路径
  ↓
FollowPath 持续控制机器人
  ↓
路径变化后更新 controller server 的目标

7.2 局部 RecoveryNode：先处理上下文故障 ​

规划分支失败时，先清理 global costmap，再重试一次规划。

控制分支失败时，先清理 local costmap，再重试一次控制。

RecoveryNode 必须恰好有两个孩子。第一个孩子是主任务，第二个孩子是恢复动作。主任务失败且仍有重试额度时，它 halt 主任务、执行恢复；恢复成功后增加重试计数，再回到第一个孩子。

7.3 系统级 RecoveryNode：轮换恢复策略 ​

如果局部恢复仍不能解决问题，最外层 NavigateRecovery 执行系统级恢复分支。

ReactiveFallback 先检查 GoalUpdated。目标已经改变时，当前恢复链可以被新目标打断；否则进入 RoundRobin，依次尝试：

text
清理 local 和 global costmap
→ 原地旋转
→ 等待
→ 后退

RoundRobin 每次有一个孩子成功，就记住下一次应从哪个孩子开始；只有所有孩子都失败才整体失败。恢复成功后，外层 RecoveryNode 回到主导航流程重新规划和控制，最多进行 XML 指定的 6 轮系统级重试。

八、条件节点和装饰节点控制“什么时候执行” ​

Action 和 Service 决定“做什么”，Condition、Decorator 和 Control 节点决定“何时做、按什么顺序做”。

典型 Condition 包括 GoalUpdated、GoalReached、IsPathValid、IsStuck、TransformAvailable 和电池状态判断。它们读取 Blackboard、TF、Topic 或 Service，只返回 SUCCESS 或 FAILURE，用结果改变树的分支。

典型 Decorator 包括：

text
RateController       限制孩子 tick 频率
DistanceController   每移动一定距离触发
SpeedController      根据速度调整执行频率
SingleTrigger        只触发一次
GoalUpdatedController 目标更新时放行

这使同一批规划、控制和恢复插件可以通过不同 XML 组合出不同导航策略，而不需要重新编译 Navigator。

九、取消和 halt 为什么必须向下传播 ​

如果用户取消 /navigate_to_pose，只停止外层循环是不够的。此时 /compute_path_to_pose、/follow_path 或 /spin 可能仍在底层服务器执行。

9.1 检查取消并 Halt 根节点 ​

BehaviorTreeEngine::run() 每轮 tick 前检查取消请求。发现取消后，它先调用根节点 halt()，再返回 BtStatus::CANCELED。

9.2 向底层 Action 传播 Halt ​

控制节点会把 halt 传播给正在运行的孩子。BtActionNode::halt() 检查底层 GoalHandle；如果 Action 仍为 ACCEPTED 或 EXECUTING，就发送异步取消，并等待 cancel 与 result future 完成，最后把自身重置为 IDLE。

9.3 清理残留 Running 节点 ​

执行回调结束后，haltAllActions() 还会递归访问整棵树，对任何仍为 RUNNING 的节点再次调用 halt。这是最后一道一致性保护。

9.4 映射最终状态 ​

最终映射关系为：

text
BT SUCCESS  → succeeded_current(result)
BT FAILURE  → terminate_current(result)
BT CANCELED → terminate_all(result)

十、抢占不是无条件换树 ​

导航运行期间收到 pending goal 时，onLoop() 会调用 Navigator 的 onPreempt()。

只有新旧目标使用同一份行为树 XML，才接受真正的抢占，并直接更新 Blackboard 中的目标。这样当前树能够继续运行，规划节点在下一轮读取到新目标。

如果 pending goal 指定了不同 XML，系统会拒绝该 pending goal，并继续执行当前导航。原因很直接：运行中替换整棵树需要先取消旧树，而不是在同一执行上下文里无缝抢占。

十一、行为树状态如何被观测 ​

每次树节点状态变化时，RosTopicLogger 记录：

text
节点名称
前一状态
当前状态
状态变化时间

每轮 onLoop() 调用 flush()，把累计事件发布到 /behavior_tree_log。因此这个 Topic 描述的是树节点状态迁移，不是导航 Action feedback，也不是 Groot 的 XML 模型文件。

排障时可以按数据层级检查：

11.1 检查外层目标 ​

确认外层目标是否进入 /navigate_to_pose/_action/status。

11.2 检查行为树状态日志 ​

确认 /behavior_tree_log 中哪个节点从 RUNNING 变为 FAILURE。

11.3 检查底层接口 ​

确认对应底层 Action 或 Service 是否在线，例如 /compute_path_to_pose、/follow_path 和 costmap clear 服务。

11.4 检查 Blackboard 数据 ​

确认 Blackboard 关键数据是否有效，尤其是 goal、path 和恢复次数。

11.5 检查取消状态 ​

确认取消后底层 Action 是否同步进入 canceled 状态。

十二、最容易混淆的五个边界 ​

12.1 Tick 不是全局 Spin ​

行为树 tick 不是 ROS executor 的全局 spin。每个 BT Action／Service 节点拥有自己的 callback group executor，并在 tick 内有限度推进异步回调。

12.2 RUNNING 不代表持续占用线程 ​

RUNNING 不是线程一直占用 CPU。它表示异步任务尚未完成，控制权已经返回行为树主循环。

12.3 Blackboard Path 是实时通道 ​

Blackboard 中的 path 不只是规划结果存档，它还是规划器向控制器更新目标的实时通道。

12.4 恢复次数不等于所有重试次数 ​

恢复次数不是所有重试的总和。当前实现由具体恢复 Action／Service 插件调用 increment_recovery_count() 维护。

12.5 XML、插件库与 ROS Graph 缺一不可 ​

XML 决定调用结构，插件库决定 XML 标签能否执行，ROS graph 决定底层调用能否真正完成。三者缺一不可。

十三、结语 ​

nav2_behavior_tree 的价值不在于替代规划和控制算法，而在于把分散的 ROS 2 能力组织成一套可观察、可取消、可恢复、可替换策略的导航运行时。

从数据角度看，它完成了三次关键转换：

text
导航目标 → Blackboard 数据
Blackboard 数据 → 底层 Action／Service 请求
底层结果 → 树状态、恢复分支和外层导航结果

理解这三次转换后，再看复杂的 Nav2 XML，就不再是一堆嵌套标签，而是一张清晰的数据流与状态调度图。

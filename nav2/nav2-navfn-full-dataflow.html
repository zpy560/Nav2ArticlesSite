Dijkstra 还是 A*，一张代价地图如何长出路径？拆解 nav2_navfn_planner 势场搜索全数据流 ​

给机器人一个起点、一个目标点和一张代价地图，怎样才能得到一条绕开障碍的全局路径？

很多人会把答案简单概括成“跑一次 Dijkstra 或 A*”。但在 Nav2 的 nav2_navfn_planner 中，真正的数据链路还包括插件加载、Lifecycle 资源管理、代价重编码、势场传播、目标容差搜索、梯度路径提取、坐标还原和末姿态修正。

本文基于当前工程中的 nav2_navfn_planner 1.1.20 源码，完整拆解这个经典规划器的所有调用、状态和输入输出数据流。

一、先给结论：NavFn 不是节点，而是 Planner Server 里的算法插件 ​

nav2_navfn_planner 不创建独立 ROS 2 节点，也不直接提供 Topic、Service 或 Action。

它构建的是共享库 nav2_navfn_planner，通过 pluginlib 导出：

  • Plugin Name：nav2_navfn_planner/NavfnPlanner。
  • C++ Type：nav2_navfn_planner::NavfnPlanner。
  • Base Class：nav2_core::GlobalPlanner。

上游 PlannerServer 收到 /compute_path_to_pose 或 /compute_path_through_poses 请求后，负责获取机器人位姿、处理 TF、选择 Planner ID，再在同一进程中调用插件的：

createPlan(start, goal) -> nav_msgs::msg::Path

因此，本包的职责边界非常清楚：

  • Planner Server 管理 ROS 接口、全局代价地图和插件调度。
  • NavfnPlanner 包装层负责坐标与参数适配、容差选点和 Path 封装。
  • NavFn 内核负责代价转换、Dijkstra／A* 势场传播和梯度路径提取。

它不负责定位，不负责 TF 转换，不负责局部控制，也不直接发布规划结果。

二、两层实现：外层是 Nav2 插件，内层是 NavFn 势场内核 ​

本包主要由两组类组成。

2.1 外层 NavfnPlanner ​

它实现 nav2_core::GlobalPlanner 接口，持有：

  • 父 Lifecycle Node 弱引用。
  • TF Buffer 指针。
  • Global Costmap 裸指针。
  • Global Frame 名称和 Plugin ID。
  • 四个插件参数。
  • 一个 std::unique_ptr<NavFn> 内核。

虽然 configure() 会保存 TF Buffer，但当前实现中没有任何 tf_->transform() 或 lookupTransform() 调用。它假设传入的起点和目标已经由 Planner Server 转换到 Global Costmap Frame。

2.2 内层 NavFn ​

它维护栅格算法需要的全部数组：

  • costarr：转换后的通行代价。
  • potarr：从传播源扩展出的导航势能。
  • pending：单元是否已经在等待队列中。
  • gradx、grady：势场梯度缓存。
  • pathx、pathy：亚栅格路径点。
  • curP、nextP、overP：三组波前优先级缓冲区。

外层回答“怎么接入 Nav2”，内层回答“怎么从代价地图算出路径”。

三、第一类状态：插件生命周期决定资源何时存在 ​

NavfnPlanner 不是 Lifecycle Node，但它的四个生命周期函数由 Planner Server 的 Lifecycle 状态驱动。

3.1 configure()：建立规划上下文 ​

Planner Server 把父节点、Plugin ID、TF Buffer 和 Global Costmap 传进来。插件随后：

3.1.1 保存 Costmap 指针和 Global Frame ​

3.1.2 获取父节点的 Clock 与 Logger ​

3.1.3 声明并读取四个参数 ​

3.1.4 按当前 Costmap 尺寸创建 NavFn 内核 ​

3.2 activate()：打开动态参数入口 ​

插件注册 add_on_set_parameters_callback()。从这一刻起，四个插件参数可以在运行时更新。

3.3 deactivate()：关闭动态参数入口 ​

插件释放回调句柄，停止接收动态参数更新，但 NavFn 数组仍然保留。

3.4 cleanup()：释放规划内核 ​

插件执行 planner_.reset()，NavFn 的 Cost Array、Potential Array、Gradient Array、Path Array 和三个优先级缓冲区随之释放。

四、输入输出接口：没有 ROS 通信接口，只有一次进程内函数调用 ​

4.1 直接输入：Start Pose ​

类型是 geometry_msgs::msg::PoseStamped。

坐标应当已经处于 Global Costmap Frame。插件在常规分支中只读取 Pose，不检查 header.frame_id，也不执行 TF 转换。

4.2 直接输入：Goal Pose ​

同样是 geometry_msgs::msg::PoseStamped，并假设已转换到全局坐标系。

目标的 XY 用于搜索，目标 Orientation 用于默认末姿态；如果启用 use_final_approach_orientation，末姿态会改成路径最后一段的切线方向。

4.3 环境输入：Global Costmap ​

插件从 Costmap2DROS 取得底层 Costmap2D*。每次常规规划时，在 Costmap Mutex 保护下读取 Char Map，并转换为 NavFn 私有的 Cost Array。

4.4 配置输入：四个参数 ​

  • tolerance：默认 0.5 m。
  • use_astar：默认 false。
  • allow_unknown：默认 true。
  • use_final_approach_orientation：默认 false。

4.5 唯一直接输出：Path ​

返回 nav_msgs::msg::Path：

  • header.stamp 使用父节点 Clock 的当前时间。
  • header.frame_id 使用 Global Costmap Frame。
  • poses 按真实机器人起点到目标方向排列。

如果失败，插件不抛出规划异常，而是返回 poses 为空的 Path。Planner Server 再把空路径转换成上层 Action 的失败结果。

五、代价转换：NavFn 并不直接拿 ROS Cost 值传播 ​

Global Costmap 的 Char Map 进入 NavFn::setCostmap() 后，会先变成 NavFn 自己的代价数组。

5.1 普通栅格 0..252 ​

转换公式是：

navfn_cost = 50 + 0.8 × ros_cost

这意味着自由空间也不是零，而是从 COST_NEUTRAL=50 开始。越靠近膨胀障碍，传播代价越大，全局路径越倾向远离高代价区。

5.2 Inscribed 与 Lethal 栅格 ​

ROS 值 253 和 254 都转为 COST_OBS=254，势场不会进入这些单元。

5.3 Unknown 栅格 255 ​

当 allow_unknown=true 时，未知单元转为 253：仍可传播，但代价非常高。

当 allow_unknown=false 时，未知单元保持障碍代价 254，规划不能穿越。

因此，“允许未知空间”不等于“把未知空间当自由空间”，而是把它当成最后才考虑的高风险通道。

六、第二类状态：一次规划请求怎样流过整个算法 ​

6.1 检查内核尺寸 ​

createPlan() 先比较 NavFn 的 nx／ny 与当前 Costmap 尺寸。尺寸变化时重新创建内部数组。

但当前常规分支进入 makePlan() 后还会无条件调用一次 setNavArr()，即使尺寸没有变化，也会重新分配 Cost、Potential、Pending 和 Gradient 数组。

6.2 处理 Start 与 Goal 重合 ​

如果起终点 XY 完全相同，插件直接返回只包含一个 Pose 的 Path。

  • 该栅格是 Lethal Obstacle：返回空 Path。
  • 默认模式：单 Pose 使用 Goal Orientation。
  • use_final_approach_orientation=true：保留 Start Orientation，避免控制器为了目标角度原地旋转。

6.3 验证起点并清除机器人单元 ​

常规分支把 Start World 坐标转换为 Map 坐标。离开 Global Costmap 立即失败。

随后 clearRobotCell() 会把机器人所在的共享 Costmap 栅格直接改成 FREE_SPACE，避免机器人因自身障碍痕迹而无法起步。

要注意，这不是只修改 NavFn 私有副本，而是修改 Planner Server 持有的底层 Global Costmap。

6.4 锁定并复制 Costmap ​

插件获取 Costmap Mutex，调用 setNavArr() 和 setCostmap()，把当前 Char Map 转换到私有 costarr，然后立即释放锁。

后面的势场传播和路径提取不再占用 Costmap Mutex，因此地图更新线程可以继续运行；本次规划使用的是刚刚复制下来的地图快照。

6.5 转换 Goal ​

Goal 离开 Global Costmap 时直接失败。转换成功后进入势场传播。

七、最容易看反的一段：内部 Start 与 Goal 为什么交换了 ​

7.1 设置反转后的内部起终点 ​

  • NavFn::setStart(map_goal)。
  • NavFn::setGoal(map_start)。

也就是说，NavFn 内部的 Start 是真实目标，内部的 Goal 是真实机器人起点。

这不是把最终 Path 算反了，而是 NavFn 势场的实现约定。

7.2 setupNavFn() 把内部 Goal 势能设为零 ​

7.3 波前从真实机器人起点向外扩散 ​

7.4 判断真实目标与机器人起点是否连通 ​

当真实目标获得有限势能时，说明它与机器人起点连通。

7.5 calcPath() 从真实目标沿势能下降方向回到真实起点 ​

7.6 包装层逆序读取路径点 ​

输出仍然是机器人起点到目标。

理解这次“双重反转”，才能正确阅读后面的势场和路径数组。

八、Dijkstra 与 A*：势能计算相同，入队优先级不同 ​

8.1 初始化传播状态 ​

两种模式都会先执行 setupNavFn(true)。

8.1.1 把全部 potarr 设为 POT_HIGH=1e10 ​

8.1.2 清零梯度缓存和 Pending 标记 ​

8.1.3 把地图最外圈强制设为障碍 ​

8.1.4 初始化 curP、nextP、overP 三个缓冲区 ​

8.1.5 把传播源势能设为零并初始化当前缓冲区 ​

传播源的上下左右邻居随后加入当前缓冲区。

8.2 Dijkstra 模式 ​

updateCell() 根据上下左右四个邻居中的最低势能，以及当前栅格通行代价，用二次近似更新平面波势能。

它不加入到目标的启发距离，波前按累计代价向四周扩展。

8.3 A* 模式 ​

updateCellAstar() 使用相同的势能更新公式，但在决定单元进入哪个优先级缓冲区时，额外叠加到内部 Start，也就是真实目标的欧氏距离启发项。

因此 A* 通常访问更少单元；两者最终都在同一个 potarr 上进行梯度取路。

8.4 三个优先级缓冲区 ​

  • curP：当前阈值内正在处理的单元。
  • nextP：当前单元更新后，可在本阈值继续推进的邻居。
  • overP：势能超过当前阈值，留到后续处理的单元。

当当前层清空时，curT 增加 priInc，Overflow Buffer 接管下一层传播。

九、目标被占用时，tolerance 到底怎样选替代终点 ​

势场完成后，插件先检查原始 Goal 的 Potential。

如果小于 POT_HIGH，原始目标可达，直接作为 Path 终点。

如果不可达，插件在：

  • X：goal.x - tolerance 到 goal.x + tolerance。
  • Y：goal.y - tolerance 到 goal.y + tolerance。
  • 步长：Global Costmap Resolution。

组成的正方形区域内逐点检查 Potential，并选择与原始 Goal 欧氏距离平方最小的可达点。

这里有三个容易混淆的结论：

  • 容差搜索区域是正方形采样范围，不是严格的圆形半径。
  • 排序依据是离原目标最近，不是候选点的路径总代价最低。
  • 找到替代终点后，输出 Path 会终止在替代点，而不是穿过障碍强行补到原目标。

十、从 Potential Array 到 Path：不是沿栅格边一格一格走 ​

10.1 梯度提取 ​

calcPath() 从真实目标开始，读取四个相邻格点的梯度，再做双线性插值。默认 pathStep=0.5，每次前进约半个栅格，因此 Path 点可以位于亚栅格坐标，不局限于栅格中心。

10.2 边界退化 ​

遇到高势能边界或检测到两步振荡时，算法不再使用连续梯度，而是在八邻域中选择 Potential 最低的格点继续前进。

越界、零梯度、高势能包围或超过 4 × max(size_x, size_y) 个提取步数时，路径提取失败。

10.3 路径顺序还原 ​

NavFn 内核得到的 Path 从真实目标指向真实起点。包装层从数组尾部向头部遍历，再用 mapToWorld() 转回世界坐标，最终输出真实起点到目标顺序的 Path。

10.4 终点修正 ​

离散势场的最后一个点可能没有精确落在选定目标上。smoothApproachToGoal() 会比较末段距离：

  • 用目标替换原末点更短：直接替换。
  • 否则：在 Path 尾部追加目标。

这一步只是修正最后接近目标的离散伪影，不是对整条 Path 做曲率平滑。

十一、末姿态状态：目标朝向还是最后进近方向 ​

11.1 使用目标朝向 ​

默认 use_final_approach_orientation=false：

  • 中间路径点 Orientation 都是单位四元数。
  • 最后一个 Pose 使用原目标或容差替代目标携带的 Orientation。

11.2 使用最后进近方向 ​

启用 use_final_approach_orientation=true：

  • 插件取最后一个 Pose 与倒数第二个有效 Pose 的方向。
  • 通过 atan2(dy, dx) 计算最后进近航向。
  • 最后一个 Pose Orientation 改成这段路径的切线方向。

如果最后两个点完全重合，会再向前找一个点；如果 Path 只有一个 Pose，则使用 Start Orientation。

该参数解决的是“到达位置后是否还要为了目标角度旋转”，不改变 Dijkstra／A* 的 XY 搜索过程。

十二、当前工程里，同一个插件怎样同时变成 Dijkstra 和 A* ​

nav2_regulated_modules 配置了两个 Plugin ID，但它们加载的是同一个 C++ Type：

12.1 GridBased ​

  • plugin: nav2_navfn_planner/NavfnPlanner。
  • use_astar: false。
  • 运行 Dijkstra 势场传播。

12.2 GridBasedAstar ​

  • plugin: nav2_navfn_planner/NavfnPlanner。
  • use_astar: true。
  • 运行带欧氏启发的 A* 势场传播。

Planner Server 会为两个 ID 分别创建 NavfnPlanner 实例，因此它们各自持有参数和 NavFn 内核，不是一个实例反复切换。

当前配置又设置：

selected_planner: GridBasedAstar

所以自研规控导航即使在 Action Goal 里请求其他 Planner ID，Planner Server 仍优先选择 GridBasedAstar。

十三、动态参数：什么时候能改，改了影响哪一次规划 ​

动态参数回调只在插件 Active 期间存在。

回调按参数类型和完整名称更新四个成员变量，并始终返回 successful=true。它不会：

  • 检查 tolerance 是否非负。
  • 检查参数组合是否合理。
  • 重建 NavFn 内核。
  • 对参数读写增加插件级互斥锁。

下一次进入 createPlan() 时会读取最新成员值。正在执行的规划如果与参数更新并发，当前实现没有提供一致快照保证。

十四、源码函数地图：每一层分别负责什么 ​

14.1 NavfnPlanner 生命周期入口 ​

  • configure()：接收 Planner Server 上下文，读取参数并创建 NavFn。
  • activate()：注册动态参数回调。
  • deactivate()：移除动态参数回调。
  • cleanup()：释放 NavFn。

14.2 NavfnPlanner 请求入口 ​

  • createPlan()：处理尺寸变化和起终点重合，再进入常规规划。
  • isPlannerOutOfDate()：比较内核数组与 Costmap 尺寸。
  • makePlan()：完成地图快照、势场传播、容差选点、路径提取和末姿态处理。
  • getPlanFromPotential()：调用 calcPath()，逆序取出内核路径并生成 PoseStamped。
  • smoothApproachToGoal()：修正或追加最终目标 Pose。
  • getPointPotential()：查询某个世界坐标对应的势能。
  • worldToMap()／mapToWorld()：在世界坐标与 NavFn 亚栅格坐标之间转换。
  • clearRobotCell()：把共享 Costmap 的机器人栅格清为空闲。
  • dynamicParametersCallback()：按类型更新四个运行参数。

14.3 NavFn 势场内核 ​

  • setNavArr()：按地图尺寸分配 Cost、Potential、Pending 和 Gradient 数组。
  • setCostmap()：把 ROS Cost 编码成 NavFn Cost。
  • setStart()／setGoal()：保存内部反转后的起终点。
  • setupNavFn()／initCost()：重置传播状态并初始化零势能源。
  • updateCell()：执行 Dijkstra 的单元势能更新。
  • updateCellAstar()：执行带欧氏距离入队优先级的 A* 更新。
  • propNavFnDijkstra()／propNavFnAstar()：驱动三个 Priority Buffer 循环。
  • calcPath()：沿势能梯度提取亚栅格路径。
  • gradCell()：计算并缓存单元梯度。

当前头文件还声明了 computePotential()，但 navfn_planner.cpp 中没有实现，正常插件调用链也没有使用它。create_nav_plan_astar() 同样只保留声明，源码中的示例实现被注释；这两个符号都不是 Planner Server 运行 NavfnPlanner 的入口。

十五、失败返回和当前源码边界 ​

15.1 返回空 Path 的主要情况 ​

  • Start 离开 Global Costmap。
  • Goal 离开 Global Costmap。
  • 起终点相同，但该单元是 Lethal Obstacle。
  • 原目标不可达，容差区域内也没有可达候选点。
  • 梯度提取越界、零梯度、陷入高势能区或路径过长。

15.2 同点离图风险 ​

起终点 XY 相同时，快速分支调用 Costmap2D::worldToMap() 后没有检查返回值，随后立即读取该栅格代价。当前 checkout 对离开地图的同点请求缺少常规分支已有的保护。

15.3 起点清障会改共享地图 ​

clearRobotCell() 在取得 Costmap Mutex 之前直接调用 setCost(..., FREE_SPACE)。该修改发生在共享 Global Costmap 上，并且 setCost() 自身不加锁。

15.4 固定容量波前缓冲区 ​

三个 Priority Buffer 的容量固定为 10000。Push 宏只有在缓冲区未满时才加入单元，满载时没有异常或警告。在超大地图或极宽波前场景中，这是需要关注的容量边界。

15.5 Dijkstra 的 Debug Path Cost 不可靠 ​

last_path_cost_ 只在 A* 传播末尾赋值，但路径提取成功后两种模式都会读取它输出 Debug 日志。Dijkstra 模式下这条日志不能当成有效路径代价；它不参与 Path 计算和上层结果判断。

十六、排查 NavFn 规划问题时，优先看这八个点 ​

16.1 Action 有请求，但插件没有运行 ​

先检查 Planner Server 是否 Active，以及请求的 Planner ID 是否实际选择到 nav2_navfn_planner/NavfnPlanner。

16.2 明明配置 Dijkstra，却跑了 A* ​

检查 selected_planner。它会覆盖 Action Goal 中的 planner_id。

16.3 起点离图 ​

检查定位和 Global Costmap Origin／Size。NavfnPlanner 不做 TF，传入 Pose 必须已经在 Global Frame。

16.4 目标被占用仍然成功 ​

检查 tolerance。输出终点可能是目标附近最近可达点，而不是原始目标。

16.5 路径穿过 Unknown ​

检查 allow_unknown。为真时 Unknown 是高代价可通行区，不是障碍。

16.6 路径贴障碍 ​

NavFn 使用的是已经膨胀后的 Global Costmap。重点检查 Inflation Layer，而不是在 NavFn 中寻找机器人 Footprint 参数。

16.7 到点后机器人是否旋转不符合预期 ​

检查 use_final_approach_orientation，并同时确认 Controller 的 Goal Checker 对目标角度的要求。

16.8 大地图偶发无路 ​

除地图连通性外，还要关注 PRIORITYBUFSIZE=10000 和固定传播／路径提取步数上限。

十七、把整个包压缩成一句话 ​

nav2_navfn_planner 是 Planner Server 内部的经典全局规划插件：它把 Global Costmap 转换成 NavFn 代价数组，用 Dijkstra 或 A* 从真实起点传播导航势场，再从真实目标沿势场梯度反向取路，最终还原成起点到目标的 nav_msgs/Path。

它的稳定来自简单清晰的二维势场模型；它的边界也同样明确：只理解 XY 栅格代价，不理解车辆运动学，不拥有 ROS 导航状态机，也不负责路径执行。

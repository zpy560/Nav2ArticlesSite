一帧激光如何变成控制器手里的避障地图？拆解 Nav2 局部 Costmap 全数据流 ​

局部 Costmap 看起来像一张不断刷新的二维图片，但在当前 nav2_regulated_modules 中，它其实是一条横跨 Launch、ROS 参数、Lifecycle、TF、消息过滤、点云缓存、三维体素、二维代价融合和 RPP 控制器的进程内数据链。

这条链最容易被说错的地方有两个：系统订阅的不是点云 Topic，而是 /c200_lidar_node/scan 上的 LaserScan，点云只是在回调内部生成的中间数据；RPP 也不是订阅发布出来的 Costmap Topic，而是直接持有 Controller Server 内嵌 Costmap2DROS 的共享指针。

本文以当前 learningnav2/nav2_regulated_modules/launch/regulated_modules.launch.py、regulated_modules.yaml、nav2_controller、nav2_costmap_2d 和 RPP 源码为基线，把一帧激光怎样最终影响线速度、角速度和碰撞判定完整串起来。

一、先给结论：控制器使用的是共享内存地图 ​

当前链路可以压缩成下面这段：

text
regulated_modules.launch.py
  → RewrittenYaml(configured_params)
  → ControllerServer
  → 内嵌 Costmap2DROS("local_costmap")
  → VoxelLayer 订阅 LaserScan
  → TF 门控后投影成 PointCloud2
  → ObservationBuffer 保存 map 坐标系观测
  → 5 Hz 更新 VoxelLayer 与 InflationLayer
  → combined_costmap_ 完成二维风险场
  → RPP 在 20 Hz 控制循环中锁图读取
  → 代价减速 + 运动弧 Footprint 碰撞预测
  → cmd_vel_nav
  → Velocity Smoother
  → /cmd_vel 或 fixed_path 的 Collision Monitor 安全链

这里没有“Costmap 节点发布一张地图，RPP 再从 Topic 订阅回来”的过程。Controller Server 构造时创建局部 Costmap 对象，配置 RPP 插件时把同一个对象传进去。Costmap 对外发布主要服务 RViz 和调试工具，控制器读取的是进程内 Master Costmap。

二、Launch 怎样把参数送到内嵌局部地图 ​

2.1 params_file 默认指向哪份配置 ​

Launch 参数 params_file 的默认值是包内 params/regulated_modules.yaml。源码随后用 RewrittenYaml 处理 use_sim_time、autostart、地图路径和 namespace，结果包装成 configured_params。

controller_server 节点的 parameters 接收这份 configured_params。所以 YAML 中：

yaml
local_costmap:
  local_costmap:
    ros__parameters:

并不是给一个 Launch 中显式声明的独立 local_costmap 进程使用，而是给 Controller Server 内部创建的同名 LifecycleNode 使用。

2.2 costmap_ros_->configure() 到底配置了什么 ​

ControllerServer 构造函数执行：

cpp
costmap_ros_ = std::make_shared<nav2_costmap_2d::Costmap2DROS>(
  "local_costmap", get_namespace(), "local_costmap");

进入 ControllerServer::on_configure() 后，costmap_ros_->configure() 触发内嵌 LifecycleNode 的 Costmap2DROS::on_configure()。它会读取的正是上述嵌套命名空间下的参数，而不是 Controller Server 顶层的控制器参数。

紧接着创建的 nav2_util::NodeThread 负责 spin 这个内嵌节点，使 TF、LaserScan、Footprint 和服务回调真正获得执行机会。

2.3 当前局部 Costmap 的有效尺寸 ​

当前参数是：

text
global_frame       map
robot_base_frame   base_link
rolling_window     true
width              7 m
height             5 m
resolution         0.05 m/cell
plugins            voxel_layer → inflation_layer

因此二维栅格尺寸为：

text
size_x = 7 / 0.05 = 140 cells
size_y = 5 / 0.05 = 100 cells

机器人 Footprint 是前后半长 0.6 m、左右半宽 0.4 m 的矩形。这个几何既参与 Costmap 的车体内部清理，也参与 RPP 的完整足迹碰撞检查。

三、原点不是从地图文件里读出来的 ​

3.1 get_parameter("origin_x", origin_x_) 的来源 ​

Costmap2DROS 构造时声明 origin_x 和 origin_y，默认值都是 0.0。当前局部 Costmap YAML 没有覆写这两个参数，因此 get_parameter() 初次取得的是默认值。

这个初值只用于 configure 阶段首次分配 140 × 100 栅格。因为当前启用了 rolling_window: true，它不会长期作为局部地图固定原点。

3.2 滚动窗口每轮怎样重算原点 ​

LayeredCostmap::updateMap(robot_x, robot_y, robot_yaw) 每轮根据机器人在 map 中的位置计算：

text
new_origin_x = robot_x - 7 / 2
new_origin_y = robot_y - 5 / 2

也就是说，局部窗口始终以机器人为中心，X 方向覆盖机器人前后各约 3.5 m，Y 方向覆盖左右各约 2.5 m。窗口移动时，updateOrigin() 尽量保留重叠区域的旧栅格，再为新进入窗口的区域建立默认值。

所以当前局部地图原点的真实来源是“机器人实时 map 位姿减去半个窗口尺寸”，不是静态地图 YAML 的 origin，也不是雷达坐标原点。

四、Configure 为什么先创建订阅又立刻退订 ​

4.1 while (ss >> source) 在遍历什么 ​

VoxelLayer 继承 ObstacleLayer，初始化时先执行 ObstacleLayer::onInitialize()。源码把 observation_sources 读成一个普通字符串：

cpp
std::stringstream ss(topics_string);
std::string source;
while (ss >> source) {
  // 为每个 source 读取私有参数并创建数据通道
}

operator>> 会跳过空格、Tab 和换行，再读取一个由空白分隔的单词。当前参数是：

yaml
observation_sources: scan

因此循环只执行一次，source == "scan"。如果配置成 scan scan2，循环会执行两次，依次读取：

text
voxel_layer.scan.topic
voxel_layer.scan.data_type
voxel_layer.scan.marking
voxel_layer.scan.clearing

voxel_layer.scan2.topic
voxel_layer.scan2.data_type
voxel_layer.scan2.marking
voxel_layer.scan2.clearing

这段循环的作用不是读取激光消息，而是根据源名批量搭建每个传感器的 ObservationBuffer、Subscriber 和 MessageFilter。

4.2 带参构造函数已经订阅了 Topic ​

LaserScan 分支创建：

cpp
auto sub = std::make_shared<message_filters::Subscriber<
  sensor_msgs::msg::LaserScan,
  rclcpp_lifecycle::LifecycleNode>>(
    node, topic, custom_qos_profile, sub_opt);
sub->unsubscribe();

message_filters::Subscriber 的带参构造函数内部立即调用 subscribe(node, topic, qos, options)，最终执行 node->create_subscription()。所以构造完成时，底层 ROS 订阅确实已经存在。

紧随其后的 unsubscribe() 只执行：

cpp
sub_.reset();

它释放底层 rclcpp::Subscription，停止接收数据，但不会清空先前保存的 topic_、qos_、options_ 和节点指针。

4.3 这是一种 Lifecycle 资源管理方式 ​

Configure 的职责是准备对象和连接关系，但节点还处于 inactive，不应该持续接收传感器数据。于是代码先利用构造函数保存完整订阅配置，再主动退订。

Costmap 激活时，ObstacleLayer::activate() 先清理 MessageFilter 队列，再调用无参 subscribe()。该函数使用保存的节点、Topic、QoS 和 options 重建底层订阅。停用时再次调用 unsubscribe()，下一次激活仍可恢复。

这段代码的状态语义是：

text
configure   对象存在，订阅配置存在，底层 ROS subscription 不存在
activate    底层 ROS subscription 被重建，开始收 LaserScan
deactivate  底层 ROS subscription 被释放，配置继续保留
cleanup     插件和缓存对象整体销毁

五、收到的明明是 LaserScan，点云从哪里来 ​

5.1 当前订阅端的真实类型 ​

当前参数明确写着：

yaml
topic: /c200_lidar_node/scan
data_type: "LaserScan"

因此 ROS 通信层接收的是 sensor_msgs/msg/LaserScan。把这条链称为“订阅激光点云”并不精确，更准确的说法是“订阅二维激光扫描，并在 Costmap 内部投影成点云”。

5.2 MessageFilter 是 TF 门卫 ​

Subscriber 并没有直接绑定 laserScanCallback()，它先连接 tf2_ros::MessageFilter。过滤器的目标坐标系是局部 Costmap 的 global_frame，当前为 map，队列长度是 50。

当一帧扫描到达时，过滤器检查扫描时间戳对应的传感器坐标系能否转换到 map。只有 TF 可用，回调才会继续；TF 长时间缺失、时间戳落在 Buffer 范围外或队列溢出时，这帧数据不会进入 ObservationBuffer。

这里用到的 tf2_ros::Buffer 在 Costmap2DROS::on_configure() 中由：

cpp
tf_buffer_ = std::make_shared<tf2_ros::Buffer>(get_clock());
tf_listener_ = std::make_shared<tf2_ros::TransformListener>(*tf_buffer_);

创建。Buffer 使用 Costmap 节点时钟管理带时间戳的变换缓存，Listener 将 /tf 和 /tf_static 数据写入 Buffer。MessageFilter、ObservationBuffer、机器人位姿查询和 RPP 路径变换共享这套 TF 数据。

5.3 LaserScan 在回调里投影成 PointCloud2 ​

TF 门控通过后，ObstacleLayer::laserScanCallback() 使用 laser_geometry::LaserProjection::transformLaserScanToPointCloud() 生成 PointCloud2。随后回调锁住对应 ObservationBuffer，调用 bufferCloud(cloud)。

ObservationBuffer::bufferCloud() 继续完成：

  • 选择显式 sensor_frame，或使用点云消息自身的 frame_id。
  • 把传感器原点 (0, 0, 0) 变换到 map。
  • 把整个 PointCloud2 变换到 map。
  • 按最小和最大障碍高度过滤点。
  • 为观测保存标障和清障距离。
  • 更新 last_updated_ 并清理超出保留时间的旧观测。

此后 VoxelLayer 不再关心原始数据来自 LaserScan 还是原生 PointCloud2，它消费的是统一的 Observation：传感器原点、map 坐标点云和量程约束。

六、同一帧观测为什么既能清障又能标障 ​

当前 scan 同时配置：

yaml
clearing: true
marking: true
raytrace_max_range: 3.0
obstacle_max_range: 2.5

初始化时，同一个 ObservationBuffer 会同时进入 clearing_buffers_ 和 marking_buffers_。Costmap 更新线程读取的是同一帧观测，但用两套算法解释它。

6.1 Clearing 表达“射线经过处是空的” ​

VoxelLayer 从传感器原点向每个扫描端点做三维射线追踪，把沿途体素和二维投影清为自由空间。清障最大距离为 3.0 m。

动态障碍消失后，旧栅格不是因为“没有新点”自动清除，而是后续扫描射线明确穿过这片区域，证明它现在可见且为空。

6.2 Marking 表达“射线终点有实体” ​

标障分支计算命中点到传感器原点的三维距离。当前只有距离小于 2.5 m、高度不超过 2.0 m、并且能映射到体素网格的点才继续处理。

命中点先写入三维 VoxelGrid。当某个 XY 列达到 mark_threshold，对应二维栅格被写成 LETHAL_OBSTACLE。当前 mark_threshold: 0，意味着有效占用能非常直接地投影成二维致命障碍。

6.3 Footprint Clearing 避免机器人标记自己 ​

VoxelLayer 更新完传感器障碍后，还会根据机器人当前 x、y、yaw 变换矩形 Footprint，并清理轮廓内部的障碍栅格。它的作用是减少车体反射、安装误差或近场噪声导致“机器人被自己的 Costmap 困住”。

6.4 InflationLayer 把一个点变成安全梯度 ​

LayeredCostmap 按配置顺序执行：

text
voxel_layer
inflation_layer

VoxelLayer 先提供自由空间和致命障碍，InflationLayer 再以 0.45 m 为膨胀半径、5.0 为代价衰减系数，在致命障碍周围生成连续梯度。

RPP 的代价减速不是只看 254 这个致命值。它读取机器人所在栅格的膨胀代价，并用同样的 inflation_cost_scaling_factor=5.0 反推出距障碍的大致距离。因此 RPP 参数中的衰减系数必须与 InflationLayer 一致，否则控制器会用错误模型解释 Costmap 代价。

七、5 Hz 更新和 2 Hz 发布不是一回事 ​

7.1 地图更新线程以 5 Hz 融合 ​

激活 Costmap 时，Costmap2DROS 创建 map_update_thread，以 update_frequency=5.0 调用 updateMap()。每轮先通过 TF 查询 map → base_link 得到机器人位姿，再进入 LayeredCostmap::updateMap()。

LayeredCostmap 持有 Master Costmap 互斥锁，完成下面这组原子流程：

text
根据机器人位姿移动滚动窗口
调用所有插件的 updateBounds()
把世界坐标更新范围换算成栅格窗口
重置需要重算的窗口
按顺序调用插件 updateCosts()
记录本轮有效边界

当前没有 Costmap Filter，因此 VoxelLayer 和 InflationLayer 直接顺序写 combined_costmap_，它就是控制器最终读取的 Master Costmap。

7.2 对外发布只有 2 Hz ​

publish_frequency=2.0 控制 Costmap2DPublisher 多久发送一次 costmap、costmap_raw 或更新消息。它主要影响 RViz 和外部工具看到地图的刷新速度。

RPP 不走这个 Topic，因此不能根据 RViz 的 2 Hz 刷新速度推断控制器只拿到 2 Hz 地图。只要 5 Hz 更新线程完成一次融合，下一次 RPP 锁图时就能直接看到新结果。

八、RPP 怎样把地图变成速度约束 ​

8.1 配置阶段保存的是同一个 Costmap 对象 ​

Controller Server 加载控制器插件时调用：

cpp
controller->configure(
  node,
  controller_id,
  costmap_ros_->getTfBuffer(),
  costmap_ros_);

RPP 在 configure() 中保存 costmap_ros_，并通过 getCostmap() 得到 Master Costmap 指针。这里没有序列化，没有 DDS，也没有中间消息副本。

8.2 每个控制周期都先锁住地图 ​

ControllerServer 以 20 Hz 调用 RPP 的 computeVelocityCommands()。RPP 进入函数后同时保护动态重配置状态和 Costmap：

cpp
std::lock_guard<std::mutex> lock_reinit(mutex_);
std::unique_lock<Costmap2D::mutex_t> lock(*costmap->getMutex());

因此它看到的是一张已经完成本轮融合的完整地图，不会读到 VoxelLayer 写了一半、InflationLayer 还没处理的中间状态。代价是 RPP 计算期间，地图更新线程需要等待同一把 Costmap 锁。

8.3 机器人当前位置的代价用于主动减速 ​

RPP 的 costAtPose(x, y) 先把世界坐标转换成栅格索引，再读取一个 unsigned char 代价值。applyConstraints() 同时计算曲率限速和障碍代价限速，取两者中更低者，再叠加接近终点减速。

当前相关开关均已启用：

yaml
use_regulated_linear_velocity_scaling: true
use_cost_regulated_linear_velocity_scaling: true
use_collision_detection: true

所以局部 Costmap 会以两种方式影响速度：膨胀代价让机器人在靠近障碍时提前降速；致命障碍和 Footprint 检查则可能直接拒绝当前候选速度。

8.4 运动弧碰撞预测决定“能不能发这条速度” ​

RPP 根据算出的线速度和角速度向前离散积分，预测范围不超过前视点，也不超过 max_allowed_time_to_collision_up_to_carrot=1.0 s。

每个预测位姿都调用 footprintCostAtPose()，用完整矩形 Footprint 检查局部 Costmap。发现致命碰撞后，isCollisionImminent() 返回 true，控制器抛出：

text
RegulatedPurePursuitController detected collision ahead!

Controller Server 会按 failure_tolerance 决定短暂输出零速还是终止 FollowPath。这个错误并不只说明激光正前方有一个点，它还可能来自 Footprint 尺寸、膨胀参数、TF、残留障碍、窗口范围或预测运动弧。

九、三类执行流怎样避免互相踩数据 ​

当前系统至少有三类重要执行上下文：

  • Costmap 回调执行器处理 LaserScan、TF 和其他 ROS 回调，将新点云写入 ObservationBuffer。
  • map_update_thread 以 5 Hz 读取 ObservationBuffer，融合 VoxelLayer 和 InflationLayer。
  • Controller Server 的 FollowPath 执行流以 20 Hz 调用 RPP，读取 Master Costmap 并计算速度。

ObservationBuffer 自己有锁，保护传感器回调写入与地图线程读取。Master Costmap 也有锁，保护插件融合与控制器读取。

频率关系为：

text
LaserScan 输入频率    由雷达驱动决定
Costmap 内部更新      5 Hz
RPP 控制计算          20 Hz
Costmap 对外发布      2 Hz

因此一份完整地图通常会被连续约四个控制周期读取。这里是“同一张内存地图被多次查询”，不是每次控制都复制一张地图，也不是控制循环会强制等待下一帧激光。

十、观测缓存的默认值藏着什么风险 ​

10.1 observation_persistence=0 不是不保存 ​

当前 YAML 没有显式设置 observation_persistence，所以使用默认 0.0 s。ObservationBuffer 每次把新观测放到链表头部，清理逻辑在保留时间为零时只留下最新观测。

它表达的是“不做多帧时间积累”，不是“回调结束后立刻没有数据”。Costmap 更新线程仍能读取最新一帧。

10.2 expected_update_rate=0 会关闭过期检查 ​

当前也没有设置 expected_update_rate，默认值为 0.0 s。ObservationBuffer::isCurrent() 对零值直接返回 true。

这意味着雷达停止更新后，VoxelLayer 不会仅凭这个参数把自己标为 stale，Controller Server 的：

cpp
while (!costmap_ros_->isCurrent()) {
  // wait
}

也不会因为该扫描源超时而阻断控制。

如果工程目标是“雷达超过某个周期没数据就不允许继续控制”，应为该源配置合理的非零 expected_update_rate，并结合实际雷达频率、DDS 抖动和 TF 延迟验证，不能只依赖 Topic 名字存在。

10.3 0.8 m 体素高度与 2.0 m 障碍上限不一致 ​

当前体素垂向范围为：

text
origin_z + z_voxels × z_resolution
= 0.0 + 16 × 0.05
= 0.8 m

但 max_obstacle_height 是 2.0 m。高度过滤允许 0～2.0 m 的点进入 Observation，而 VoxelGrid 只能表示到约 0.8 m。变换后 Z 值超出体素范围的点会在 worldToMap3D() 失败后跳过。

对水平安装的二维雷达，这不一定造成实际问题，因为有效点的 Z 往往接近雷达安装高度；但如果传感器 TF 让点落在 0.8 m 以上，配置就会出现“消息收到了、点云也生成了、二维地图却没有障碍”的现象。最终判断必须核对真实 sensor_frame → map 变换和点云 Z 分布。

十一、TF 故障会在哪些位置截断数据 ​

TF 在这条链里不是一次查询，而是多处共同依赖：

  • Costmap 激活时等待 map ← base_link 可用。
  • MessageFilter 等待每帧扫描时间戳对应的传感器坐标系到 map 变换。
  • LaserProjection 在扫描束时间模型下投影 LaserScan。
  • ObservationBuffer 变换传感器原点和完整 PointCloud2 到 map。
  • Costmap 更新线程查询机器人当前 map 位姿。
  • RPP 使用同一 TF Buffer 变换全局路径和机器人位姿。

如果扫描 Topic 有频率但 Costmap 没障碍，排查重点不是“订阅是否创建”这一项，而要同时检查消息时间戳、frame_id、静态 TF、动态 TF 缓存范围和目标 map 坐标系。

如果 Costmap2DROS::updateMap() 取不到机器人位姿，它会跳过整轮地图融合。即使 ObservationBuffer 中有新点云，滚动窗口也无法根据机器人位置移动，插件不会进入正常更新链。

十二、Collision Monitor 为什么不能算作局部 Costmap 的下一层 ​

当前 Launch 还创建 Collision Monitor，并在 fixed_path 模式把 Velocity Smoother 输出送入其安全链。它可能订阅同一个 /c200_lidar_node/scan，但这不代表它消费局部 Costmap。

两条链的职责不同：

  • 局部 Costmap 把传感器历史、清障、体素占用和膨胀梯度融合成二维风险场，供 RPP 代价调速和运动弧碰撞检查。
  • Collision Monitor 自己创建 Source，直接把传感器点与 Polygon 或 Circle 区域比较，执行 STOP、SLOWDOWN 或 APPROACH 动作。

它们没有共享 ObservationBuffer，也没有“RPP 发布 Costmap 给 Collision Monitor”的连接。即使使用同一束激光，两条链也会分别做订阅、TF 和数据处理。

这也是定位问题时必须分开的边界：

text
RPP 报 detected collision ahead
  → 优先检查局部 Costmap、Footprint、膨胀、预测弧和 TF

最终 /cmd_vel 被压低或归零，但 RPP 输出正常
  → 检查 Velocity Smoother 和 fixed_path Collision Monitor

十三、按数据流排查，比盯着 RViz 更可靠 ​

13.1 先确认运行参数，而不是只看 YAML ​

Launch 支持自定义 params_file、namespace 和运行时重写。排查时应确认 local_costmap.local_costmap 的实际参数，尤其是 global_frame、尺寸、分辨率、插件顺序、observation_sources 和传感器 Topic。

13.2 再确认消息与 TF 是否在同一时间线上 ​

检查 LaserScan 的 header.frame_id 和时间戳，确认该时间点存在传感器到 map 的变换。Topic 有数据只能证明 Publisher 正常，不能证明 MessageFilter 已经放行。

13.3 再看 Observation 与图层结果 ​

确认清障距离、标障距离、高度过滤、体素 Z 范围和 Footprint 是否符合真实安装。publish_voxel_map: true 可以辅助判断点有没有进入三维体素，而局部 Costmap 则显示二维投影与膨胀结果。

13.4 最后区分地图更新、地图发布和控制读取 ​

内部更新是 5 Hz，外部发布是 2 Hz，控制读取是 20 Hz 的进程内共享访问。RViz 看起来慢半拍，不等于 RPP 同样慢；RPP 报碰撞，也不等于 Collision Monitor 做了停车裁决。

十四、总结 ​

当前 nav2_regulated_modules 的局部 Costmap 数据流，本质上是一套有生命周期、有 TF 时间门控、有缓存、有三维到二维投影、有插件顺序、有互斥锁保护的实时共享状态。

它从 LaserScan 开始，却不会以 LaserScan 结束。扫描经 MessageFilter 验证 TF 后被投影成 PointCloud2，ObservationBuffer 将它统一到 map，VoxelLayer 用同一帧数据清除自由空间并标记三维体素，InflationLayer 把致命障碍扩展为连续风险梯度，最终由 RPP 在同一进程内锁图读取。

理解这条链后，几个常见疑问就有了明确答案：while (ss >> source) 是在遍历传感器配置名；构造后 unsubscribe() 是为了遵守 Lifecycle；origin_x 在滚动窗口中会被机器人位姿持续替代；publish_frequency 不等于控制器读图频率；Collision Monitor 也不是 Costmap 的下游插件。

真正驱动控制的，不是 RViz 上那张图，而是刚刚完成插件融合、仍在进程内存中的 combined_costmap_。

一个节点失联，为什么整套 Nav2 都要停？逐函数拆解 Lifecycle Manager ​

Nav2 里真正决定“整套导航什么时候可以工作”的，并不是 Planner Server 或 Controller Server，而是一个自身并非 Lifecycle Node 的普通 ROS 2 节点：nav2_lifecycle_manager。

它接收启动、暂停、恢复、复位和关闭命令，按依赖顺序调用各服务器的 Lifecycle Service；节点进入 ACTIVE 后，它还用 Bond 心跳监视进程存活。一旦某个关键服务器失联，它会让其余节点一起退出工作状态，避免规划仍在发布路径、控制器却已经失去地图或行为服务器。

本文以当前工程中的 nav2_lifecycle_manager 1.1.20 为准，覆盖两个生产类和独立进程入口的 32 个生产函数。测试函数、Launch 测试和组件注册宏不计入函数数量；rclcpp、nav2_util、bondcpp、Lifecycle Service 与诊断框架等包外调用只解释接口契约和数据流，不展开其他包源码。

一、包边界：它管理状态，不执行导航算法 ​

1.1 本包的输入 ​

LifecycleManager 在构造时读取五个参数。

  • node_names：被管理节点名称数组，数组顺序同时定义启动顺序。
  • autostart：初始化完成后是否自动执行 startup。
  • bond_timeout：Bond 心跳超时，单位为秒；小于或等于零时关闭 Bond 监控。
  • bond_respawn_max_duration：进程失联后等待所有服务器重新出现的最长 ROS 时间。
  • attempt_respawn_reconnection：Bond 断裂后是否启动自动重连流程。

运行期输入来自两个 Service。<manager_name>/manage_nodes 接收 nav2_msgs::srv::ManageLifecycleNodes，请求里只有一个 command；<manager_name>/is_active 接收空的 Trigger 请求。

内部输入还包括各被管理节点的 change_state、get_state Service 响应，Bond 心跳状态，200 ms 与 1 s 的 Wall Timer 回调，以及 rcl Context 的 pre-shutdown 事件。

1.2 本包的输出 ​

最重要的输出不是 Topic，而是一组同步 Service 调用。Manager 通过包外 nav2_util::LifecycleServiceClient 向每个节点发送 Lifecycle Transition，并再次读取 State，确认节点确实到达预期主状态。

面向调用方的输出有三类：

  • manage_nodes 的 response.success 表示本次管理命令是否被 Manager 判定为成功。
  • is_active 返回内部成员 system_active_。
  • diagnostic_updater 输出 Nav2 active 或 inactive 的诊断摘要。

ACTIVE 节点还会与 Manager 建立 bond Topic 心跳。Bond 不是业务数据，也不负责 Lifecycle 状态切换；它只回答“对端进程是否仍在正常心跳”。

1.3 本包明确不负责什么 ​

Lifecycle Manager 不创建地图，不计算路径，不输出速度，也不理解被管理节点的业务依赖。它只相信 node_names 的排列。如果配置把 Controller 放在 Planner 前面，源码不会替用户修正顺序。

它也不是被管理节点的父进程。节点崩溃后的进程重启通常由 Launch 的 respawn 机制完成；Manager 只检测 Service 是否重新出现，并在条件满足时重新执行 startup。

二、构造阶段：普通 Node 如何搭起独立管理线程 ​

2.1 LifecycleManager() 声明参数和通信接口 ​

LifecycleManager() 继承 rclcpp::Node，固定基础节点名为 lifecycle_manager，同时把自身交给 diagnostic_updater::Updater。Launch 可以通过 name= 重映射成 lifecycle_manager_navigation、lifecycle_manager_localization 等实例名，Service 名也会随 get_name() 改变。

构造函数声明并立即读取五个参数。bond_timeout 从 double 秒转换成 std::chrono::milliseconds；bond_respawn_max_duration 转成 rclcpp::Duration。本包没有动态参数回调，后续通过 ros2 param set 改参数存储不会同步这些成员。

它调用 registerRclPreshutdownCallback() 注册进程退出清理，又创建一个 MutuallyExclusive CallbackGroup，并把 automatically_add_to_executor_with_node 设为 false。两个 Service 都放入这个组，因此管理命令、状态查询和后续 Bond Timer 不会并发修改 node_map_、bond_map_ 与 system_active_。

构造函数还建立两张查表：

  • transition_state_map_ 把 configure、cleanup、activate、deactivate、unconfigured shutdown 映射到预期 Primary State。
  • transition_label_map_ 为相同 Transition 保存日志动词。

最后注册 Nav2 Health 诊断任务，并创建一个零周期初始化 Wall Timer。零周期不是后台忙循环，而是把需要 shared_from_this() 的初始化推迟到对象已经由 shared_ptr 托管之后。

2.2 零周期初始化回调建立 Service Client ​

初始化 Timer 触发后立即取消自身，调用 createLifecycleServiceClients()，为 node_names_ 中每个节点创建包外 LifecycleServiceClient。

如果 autostart_ 为 true，成员 init_timer_ 会改为另一个零周期 Timer。该 Timer 位于专用 CallbackGroup，触发时取消自身并调用 startup()。这里没有等待 Launch 中所有进程显式就绪的独立阶段，真正的可用性等待发生在包外 Lifecycle Service Client 内。

同一个初始化回调创建 SingleThreadedExecutor，只加入专用 CallbackGroup，再交给 nav2_util::NodeThread 独立 spin。外层 rclcpp::spin(node) 负责默认 CallbackGroup，内部线程负责管理 Service、autostart 和 Bond Timer。这个拆分避免同步 Lifecycle Service 调用阻塞 Manager 主执行器中的其他默认回调。

2.3 ~LifecycleManager() 释放专用执行线程 ​

~LifecycleManager() 记录销毁日志，然后 reset service_thread_。智能指针负责其余 ROS 实体的析构。

它没有在析构函数里调用 shutdown()。正常 rcl Context 退出前会先触发 onRclPreshutdown()；显式关闭被管理节点应通过 manage_nodes 的 SHUTDOWN 命令完成，不能把 C++ 对象析构等同于 Nav2 Lifecycle shutdown。

三、三个外部可见回调：命令、状态与诊断 ​

3.1 managerCallback() 分派五种命令 ​

managerCallback() 是 ManageLifecycleNodes Service 回调。输入是 request header、请求和响应；header 没有参与业务判断。函数读取 request->command，分别调用 startup()、reset()、shutdown()、pause() 或 resume()，再把布尔返回值写入 response->success。

这个回调只做分派，不直接遍历节点。请求中的 command 如果不是五个已知常量，switch 没有 default 分支，响应字段保持 ROS 消息的默认值，源码也不会记录未知命令日志。

3.2 isActiveCallback() 返回内部活动标志 ​

isActiveCallback() 忽略空请求内容，把 system_active_ 复制到 response->success。它不会逐节点调用 get_state()，不会检查 Bond，也不会验证所有服务器是否仍处于 ACTIVE。

因此这个 Service 的准确语义是“最近一次完整 startup／resume 是否成功，并且之后是否没有被 Manager 自己置为 inactive”，不是分布式系统的即时一致性快照。

3.3 CreateActiveDiagnostic() 复用相同标志 ​

CreateActiveDiagnostic() 接收 DiagnosticStatusWrapper。system_active_ 为 true 时写入 OK 和 Nav2 is active；否则写入 ERROR 和 Nav2 is inactive。

诊断与 is_active 没有两套独立判断，它们共享同一个布尔成员。因此诊断为 OK 也不代表函数刚刚查询过每个节点。

3.4 message() 统一输出管理日志 ​

message() 接收字符串并通过 LOG_INFO 输出。源码保留了 ANSI 蓝色宏，但当前函数没有使用颜色转义，只交给本工程的 spdlog_wrapper 日志宏。

这个函数没有状态副作用，却贯穿 Client 创建、状态切换、Bond Timer 和故障恢复，是观察 Manager 决策路径的主要日志入口。

四、Lifecycle Service Client：从节点名变成可调用对象 ​

4.1 createLifecycleServiceClients() 建立节点表 ​

createLifecycleServiceClients() 遍历 node_names_，以节点名为 key，在 node_map_ 中保存 nav2_util::LifecycleServiceClient。

包外 Client 通常根据节点名连接该节点的 change_state 与 get_state Service。Manager 不缓存目标节点对象，也不要求进程内组合；只要 ROS 图中存在对应 Service，独立进程和 Component 都可以被相同方式管理。

4.2 destroyLifecycleServiceClients() 释放 Client 指针 ​

destroyLifecycleServiceClients() 遍历 node_map_，对每个 shared pointer 调用 reset。它没有执行 node_map_.clear()，也没有清空 node_names_。

这个实现适合把 SHUTDOWN 当作 Manager 会话的终止命令。若 shutdown 后仍对同一 Manager 实例调用 startup，changeStateForNode() 会从 map 取出空指针并解引用；当前源码没有重新创建 Client 的恢复路径。

五、单节点与整组节点如何切换状态 ​

5.1 changeStateForNode() 发送 Transition 并复核 State ​

changeStateForNode(node_name, transition) 先用 transition_label_map_ 组合日志，然后通过 node_map_[node_name] 调用包外 change_state(transition)。

仅有 Service 返回成功还不够。函数紧接着调用 get_state()，并与 transition_state_map_[transition] 比较。change_state 失败或实际 State 不等于预期值都会返回 false。

activate 成功后，函数调用 createBondConnection(node_name)；deactivate 成功后，从 bond_map_ 删除该节点。configure、cleanup 和 shutdown 不直接改 Bond。

输入是节点名与 Transition ID，输出是布尔结果；副作用包括 Lifecycle Service 调用、日志、状态查询和 Bond map 更新。

5.2 changeStateForAllNodes() 决定遍历方向 ​

changeStateForAllNodes(transition, hard_change) 是批量切换核心。configure 与 activate 使用 node_names_ 正向遍历；deactivate、cleanup 和 shutdown 使用反向遍历。

假设启动顺序是 Map Server、Planner Server、Controller Server，关闭时就会让 Controller 先停、Planner 随后停、Map 最后停。这不是按节点类型硬编码，而是对用户数组做反向遍历。

普通模式中，任何节点返回 false 就停止整批操作。hard_change=true 时，返回 false 的节点不会阻止遍历继续，适合故障后尽量清理仍存活的其他节点。

函数只捕获 std::runtime_error。一旦捕获异常，无论 hard_change 是否为 true，都会记录错误并立即返回 false。因此 hard reset 的“尽量继续”只覆盖普通失败返回值，不覆盖异常。

5.3 顺序就是隐式依赖图 ​

本包没有 DAG、拓扑排序或依赖声明。node_names_ 是唯一的顺序来源。configure 与 activate 都完整走一遍正向数组，不是对单个节点连续执行 configure＋activate。

这意味着整个 startup 的实际形态是“所有节点配置完成”之后，才开始“所有节点激活”。这样可以在业务流启动前确保整套资源已经配置，但也要求每个节点的 on_configure 不依赖后序节点已经 ACTIVE。

5.4 状态复核的价值与限制 ​

get_state() 复核可以发现 change_state Service 返回成功、节点却没有进入目标主状态的情况。但它只在管理命令执行时查询一次，不会持续轮询。

持续存活交给 Bond，业务健康则交给各服务器自身诊断。Lifecycle State、进程存活和算法输出正常是三种不同概念。

六、五种管理命令的完整语义 ​

6.1 startup() 配置并激活整组节点 ​

startup() 调用两批状态切换：configure 正向遍历全部节点，全部成功后 activate 再正向遍历全部节点。任一批失败都会返回 false。

两批都成功后，函数把 system_active_ 设为 true，调用 createBondTimer()，最后返回 true。

当前实现没有失败回滚。若 configure 到中间节点失败，前序节点会停留在 INACTIVE；若 activate 到中间节点失败，前序节点可能已经 ACTIVE。此时 system_active_ 仍为 false，Bond 检查 Timer 也不会创建，但部分节点状态已经改变。

6.2 pause() 只停用，不清理资源 ​

pause() 先把 system_active_ 设为 false，并销毁 Bond 检查 Timer，然后反向执行 deactivate。成功后节点停留在 INACTIVE，配置资源仍保留。

这适合短暂停止导航：地图、插件、Publisher 和 Service 的 configure 资源不必重建。某个节点 deactivate 失败时函数返回 false，前面已经成功停用的后序节点不会自动重新激活。

6.3 resume() 从 INACTIVE 重新激活 ​

resume() 正向执行 activate，不调用 configure。全部成功后设置 system_active_=true 并重建 Bond 检查 Timer。

所以 resume 的前置条件是节点仍处于 INACTIVE。如果已经 reset 到 UNCONFIGURED，应调用 startup；如果已经 shutdown 到 FINALIZED，当前进程中的 Lifecycle Node 通常不能再回到 UNCONFIGURED。

6.4 reset() 回到 UNCONFIGURED ​

reset(hard_reset) 先清除活动标志和 Bond Timer，然后反向执行 deactivate，再反向执行 cleanup。成功结果是全部节点回到 UNCONFIGURED，Service Client 仍然保留，因此后续可以重新 startup。

默认 hard_reset=false，失败会终止并返回 false。Bond 故障路径调用 reset(true)，意图是在崩溃节点无法响应时仍尽量清理其他节点。

6.5 shutdownAllNodes() 发出终止 Transition ​

shutdownAllNodes() 依次请求三批操作：deactivate、cleanup、unconfigured shutdown。每批内部都按反向节点顺序执行。

该函数返回 void，并忽略三次 changeStateForAllNodes() 的返回值。某批失败后，它仍会尝试下一批；对状态不匹配的节点，这些后续 Transition 也可能失败。

6.6 shutdown() 结束 Manager 会话 ​

shutdown() 清除 system_active_，销毁 Bond 检查 Timer，调用 shutdownAllNodes()，再调用 destroyLifecycleServiceClients()，最后固定返回 true。

因此 manage_nodes 的 SHUTDOWN success 不能证明每个节点都已到达 FINALIZED。真正结果需要结合 Lifecycle Manager 错误日志和各节点 State 检查。由于 Client 指针被释放，同一 Manager 实例也不适合在 shutdown 后再次 startup。

七、Bond：ACTIVE 之后的进程存活保护 ​

7.1 createBondConnection() 为单个节点建立心跳 ​

createBondConnection() 接收 node_name，把 bond_timeout_ 转成秒。如果该节点尚无 Bond 且 timeout 大于零，就创建 bond::Bond("bond", node_name, shared_from_this())。

Manager 设置心跳超时为参数值，心跳周期固定为 0.10 s，随后 start，并最多等待 bond_timeout/2 形成连接。连接未形成时返回 false，因此节点即使已经进入 ACTIVE，整个 activate 批次仍可能被判定失败。

timeout 小于或等于零时函数不建 Bond，直接返回 true。这会关闭进程失联保护，而不影响 Lifecycle 状态切换。

7.2 createBondTimer() 启动周期检查 ​

createBondTimer() 在 Bond 启用时创建 200 ms Wall Timer，回调是 checkBondConnections()，并放在专用 MutuallyExclusive CallbackGroup。

Wall Timer 使用墙上时间，不依赖 /clock。它与 Service 回调在同一单线程执行器内串行执行，所以一个耗时的同步管理命令会推迟心跳检查回调。

7.3 destroyBondTimer() 停止正常心跳巡检 ​

destroyBondTimer() 检查 bond_timer_，存在时 cancel 并 reset。pause、reset、shutdown 和 pre-shutdown 都会调用它。

该函数只处理正常巡检 Timer，不处理 bond_respawn_timer_。故障后的自动恢复 Timer 有自己的停止条件。

7.4 checkBondConnections() 发现断链就整体降级 ​

checkBondConnections() 在系统非 active、rcl 已退出或 Bond map 为空时直接返回。正常情况下按 node_names_ 遍历，并调用每个 Bond 的 isBroken()。

发现任意节点断链后，它记录关键故障，调用 reset(true) 尽量把其余节点反向 deactivate＋cleanup，再清空整个 bond_map_。这里选择整体降级，是因为导航服务器之间存在强耦合：继续让部分节点 ACTIVE 往往比统一停机更危险。

如果 attempt_respawn_reconnection_ 为 true，函数创建 1 s Wall Timer，进入 checkBondRespawnConnection() 恢复路径；随后立即返回，不再检查剩余 Bond。

7.5 checkBondRespawnConnection() 等待 Service 恢复 ​

checkBondRespawnConnection() 在首次回调中把 bond_respawn_start_time_ 设为 now()。如果系统已由外部重新激活、rcl 退出或节点数组为空，它清零起始时间并销毁自身 Timer。

恢复检查逐节点调用 node_map_[node_name]->get_state()。只要调用不抛异常，就把服务器计为 live；它此时不要求特定 Lifecycle State。发现某个服务器仍不可达便停止本轮遍历。

当 live 数量等于节点总数时，函数销毁恢复 Timer 并调用 startup()，让所有重生节点重新 configure＋activate。达到 bond_respawn_max_duration_ 后仍未全部恢复，则停止自动重连。

这里存在时间域组合：1 s 检查由 Wall Timer 触发，最大恢复时长却用 ROS 时钟 now() 计算。若 use_sim_time=true 且 /clock 停止，回调仍会每秒运行，但 ROS Duration 不会达到超时阈值。

八、进程退出与 Context 收尾 ​

8.1 registerRclPreshutdownCallback() 注册退出钩子 ​

registerRclPreshutdownCallback() 从 Node Base Interface 取得 rcl Context，调用包外 add_pre_shutdown_callback()，绑定 onRclPreshutdown()。

这个回调属于 rcl Context 关闭序列，不是 Lifecycle 的 on_shutdown，也不是 manage_nodes 的 SHUTDOWN 命令。

8.2 onRclPreshutdown() 防止退出期访问失效资源 ​

onRclPreshutdown() 销毁正常 Bond Timer，reset 专用 Service 线程，并清空 node_names_、node_map_ 与 bond_map_。

它的目标是停止退出期回调继续访问 Bond 和 Client，而不是逐节点发送 Lifecycle shutdown。因此直接结束 Manager 进程不等于有序关闭所有 Nav2 节点。

九、LifecycleManagerClient：调用方如何使用 Manager ​

9.1 LifecycleManagerClient() 构造两个 Service Client ​

LifecycleManagerClient() 接收 name 与 parent_node，根据 Manager 名称拼出 <name>/manage_nodes 与 <name>/is_active，保存调用方提供的普通 rclcpp Node，然后创建两个包外 nav2_util::ServiceClient。

它不创建自己的执行线程，也不持有 Lifecycle Manager 对象。日志、Service 等待和同步 invoke 都借用 parent_node。

9.2 startup()、shutdown()、pause()、resume()、reset() ​

客户端五个同名函数都只做命令映射：

  • startup(timeout) 传入 STARTUP。
  • shutdown(timeout) 传入 SHUTDOWN。
  • pause(timeout) 传入 PAUSE。
  • resume(timeout) 传入 RESUME。
  • reset(timeout) 传入 RESET。

它们统一调用 callService()，返回 Manager 响应里的 success。默认 timeout 是 std::chrono::nanoseconds(-1)，表示使用包外 Service Client 所定义的无限等待语义。

9.3 callService() 等待管理 Service 并发送命令 ​

callService(command, timeout) 创建 ManageLifecycleNodes Request 并写入 command。它循环调用 manager_client_->wait_for_service(timeout)；如果等待期间 rclcpp::ok() 变为 false，返回 false。

Service 出现后，它同步调用 invoke(request, timeout)，返回 future_result->success。invoke 抛出 std::runtime_error 时函数吞掉异常并返回 false。

注意 timeout 同时用于每次 wait 和 invoke。调用方传入有限时长时，while 可能开始下一轮等待，因此它不是一个自行维护的“整个函数绝对截止时间”。

9.4 is_active() 返回 ACTIVE、INACTIVE 或 TIMEOUT ​

is_active() 接收 timeout 并创建 Trigger 请求。它等待 is_active Service 的时长固定为 1 s，与传入 timeout 无关；Service 存在后，传入 timeout 才用于同步 invoke。

Service 不存在或 invoke 抛出 runtime_error 时返回 SystemStatus::TIMEOUT；响应 success 为 true 时返回 ACTIVE，否则返回 INACTIVE。

三态枚举解决了“Manager 明确回答 inactive”和“根本联系不上 Manager”不能都压成 false 的问题，但 ACTIVE 仍只是 Manager 内部 system_active_ 的映射。

十、独立进程入口与组件形式 ​

10.1 main() 管理进程生命周期 ​

main() 接收 argc 与 argv，调用 rclcpp::init()，再调用 SpdlogWrapper::init("nav2_lifecycle_manager", "lifecycle_manager")。它创建 LifecycleManager shared pointer，进入 rclcpp::spin(node)。

spin 返回后执行 rclcpp::shutdown()，最后调用 SpdlogWrapper::shutdown() 并返回零。日志包装器属于本工程的包外依赖，不改变 Lifecycle 状态机。

10.2 Component 注册提供进程内组合 ​

RCLCPP_COMPONENTS_REGISTER_NODE 不是普通函数，未计入 32 个生产函数。它让同一个 LifecycleManager 类可以由 ComponentManager 动态创建。

CMake 同时产出共享库 nav2_lifecycle_manager_core 和独立可执行文件 lifecycle_manager。两种部署方式使用相同构造函数、Service 和 Bond 逻辑。

10.3 多个 Manager 实例彼此独立 ​

Nav2 Bringup 常把定位节点和导航节点交给不同实例，例如 lifecycle_manager_localization 与 lifecycle_manager_navigation。每个实例有独立 node_names、Service 名、system_active_、Bond map 和诊断状态。

一个实例 ACTIVE 不代表另一个实例 ACTIVE。客户端必须使用准确的 Manager 名称，不能只调用默认 /lifecycle_manager/manage_nodes。

十一、把数据流串成两个完整场景 ​

11.1 正常 startup 的输入输出链 ​

外部调用方把 STARTUP 写入 ManageLifecycleNodes Request。managerCallback() 进入 startup()，configure 批次按 node_names 正序调用每个 change_state，每次都用 get_state 验证 INACTIVE。

configure 全部成功后，activate 批次再次正序执行。每个节点进入 ACTIVE 后建立 Bond。全部节点和 Bond 都成功，system_active_ 才变为 true，200 ms Bond Timer 启动，Service response.success 返回 true。

随后 is_active Service 和 Diagnostics 都读取相同标志；真正导航数据仍由 Planner、Controller、Costmap 等包外节点产生。

11.2 节点失联后的降级与恢复链 ​

Bond Timer 发现任一连接 broken，checkBondConnections() 调用 hard reset。仍可响应的节点尽量反向 deactivate＋cleanup，活动标志变为 false，所有旧 Bond 清空。

启用重连时，1 s Timer 周期调用每个 Lifecycle Service Client 的 get_state。Launch 或系统进程管理器负责让崩溃进程重新出现；全部 Service 可达后，Manager 再执行完整 startup，并重新建立 Bond。

恢复失败并达到最长 ROS Duration 后，Manager 保持 inactive，不会无限重试。若仿真时钟停止，该最长时长不会自然到达。

十二、当前源码最值得记住的边界 ​

12.1 system_active_ 不是实时聚合状态 ​

它是管理流程成功后写入的缓存标志。节点绕过 Manager 被手动切换、短暂卡死但 Bond 尚未超时、业务算法失效但进程仍心跳时，标志都可能仍为 true。

12.2 管理命令不是数据库事务 ​

批量操作没有原子提交和自动回滚。startup、pause、resume 或 reset 中途失败时，系统可能处于混合 State。失败后的正确动作应先检查每个节点 State，再决定 hard reset、进程清理或重新 Launch。

12.3 shutdown 的 success 不能当逐节点证明 ​

shutdownAllNodes() 不返回结果，shutdown() 固定返回 true。调用方收到 success 只说明 shutdown 流程已经被执行，不能证明全部目标节点已 FINALIZED。

12.4 hard reset 也有异常边界 ​

hard_change=true 能越过普通 false，却不能越过捕获到的 runtime_error。源码中的“尽量清理全部节点”不是无条件保证。

12.5 Bond Timer 与重生 Timer 是两套对象 ​

destroyBondTimer() 不会取消 bond_respawn_timer_。故障恢复期间再发手动 pause、reset 或 shutdown，需要留意恢复 Timer 仍可能运行；当前停止条件主要依赖 system_active、rcl 状态、节点数组、全部恢复或超时。

12.6 参数只在构造时生效 ​

node_names、autostart、Bond timeout 和重连策略没有动态参数回调。运行中修改参数存储不会重建 Client、Timer 或 Bond，应通过重启 Manager 让配置一致生效。

12.7 bond_timeout 为零等于关闭故障联动 ​

关闭 Bond 后，startup 仍可成功，is_active 也可返回 ACTIVE；但节点进程随后失联时，Manager 不会自动整体 reset。调试环境可以这样降低耦合，生产系统必须明确承担失联不可见的风险。

十三、实际调用与排查入口 ​

13.1 发送 startup 命令 ​

Manager 名称为 lifecycle_manager_navigation 时，可以直接调用：

bash
ros2 service call /lifecycle_manager_navigation/manage_nodes \
  nav2_msgs/srv/ManageLifecycleNodes "{command: 0}"

命令数值来自当前 ManageLifecycleNodes 接口定义。工程脚本更适合使用命名常量或 LifecycleManagerClient::startup()，避免硬编码跨版本变化。

13.2 查询 Manager 活动标志 ​

bash
ros2 service call /lifecycle_manager_navigation/is_active \
  std_srvs/srv/Trigger "{}"

返回 success=true 只代表 Manager 标志 active。排查混合状态时，还应查询具体 Lifecycle Node 的 get_state Service，并结合 Bond 和 Manager 日志。

13.3 判断故障发生在哪一层 ​

manage_nodes Service 不存在，优先检查 Manager 进程、命名空间和专用执行线程初始化。

configure／activate 返回失败，查看日志中最后一个 Configuring 或 Activating 节点，再检查该节点 Lifecycle Service 和 on_configure／on_activate 错误。

节点已经 ACTIVE 但 startup 失败，重点检查 Bond 是否形成、被管理节点是否创建同名 Bond，以及 bond_timeout 是否合理。

运行一段时间后整套系统突然 reset，搜索 CRITICAL FAILURE 和失联节点名，再区分节点真实退出、执行器长时间阻塞、DDS 通信问题和机器负载导致的心跳超时。

十四、总结：Lifecycle Manager 是 Nav2 的状态一致性守门员 ​

32 个生产函数最终围绕四件事工作：把五种外部命令翻译为 Lifecycle Transition；用数组正序启动、反序收尾；用 change_state 后的 get_state 复核结果；用 Bond 把单节点失联升级为整套系统的安全降级。

理解本包时，最重要的不是背诵 STARTUP 对应 configure＋activate，而是分清三种状态：Lifecycle State 描述节点资源阶段，Bond 描述进程心跳，system_active_ 描述 Manager 最近一次管理结果。三者有关联，却从来不是同一个事实。

当 Nav2 出现“部分节点 active、部分节点 inactive”“启动失败却仍有服务器在工作”或“一个节点退出后整套导航被拉回 unconfigured”时，沿着 Manager Service、批量切换顺序、State 复核、Bond 和重生 Timer 这条链检查，才能找到真正的断点。

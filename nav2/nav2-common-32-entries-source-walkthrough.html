没有一个 ROS 节点，却在启动前改写整套 Nav2：逐函数拆解 nav2_common 的 32 个入口 ​

打开 nav2_common，你找不到订阅器、发布器、Action Server，也找不到 main()。但 Nav2 启动时使用哪张地图、是否使用仿真时间、参数是否包进机器人命名空间、RViz Topic 是否加前缀，以及数十个 C++ 包用什么标准和告警规则编译，都可能经过它。

它做的事情发生在机器人开始导航之前。Python 部分嵌入 ROS 2 Launch 的替换机制，把命令行参数、YAML 和 RViz 配置变成运行期临时文件；CMake 部分通过 find_package(nav2_common) 向下游导出统一宏，把构建约束铺到规划、控制、地图、行为等包。

本文以本地 navigation2、包版本 1.1.20 为事实基线。生产源码共有 31 个 Python 函数／方法，另有 1 个公开 CMake 宏，合计 32 个入口。内部递归函数 process_value() 也单独计入，因为它承担了完整的数据遍历职责。

一、先把结论说清楚 ​

1.1 它不是运行期 ROS 节点 ​

nav2_common 不创建 Topic、Action、Service、Timer 或 Executor。本文提到的“回调”主要指 Launch 系统在需要一个 Substitution 的最终文本时调用 perform(context)，不是 ROS 消息到达后触发的回调。

这一区别很重要。RewrittenYaml 改的是节点启动前要读取的配置文件路径，并不会在节点已经运行后监听参数变化。运行期动态参数仍要由具体节点自己的参数回调处理。

1.2 它同时工作在两个时间平面 ​

  • Launch 平面发生在启动描述展开和进程参数组装期间，输入是 LaunchConfiguration、文件和命令行文本，输出通常是临时文件路径或条件判断文本。
  • CMake 平面发生在配置与编译期间，输入是下游项目当前的 CMake 状态，输出是目录级编译、链接和平台规则。

两个平面没有共享运行状态。它们只是被放在同一个“公共基础设施包”里统一分发。

1.3 它修改副本，不修改原配置 ​

RewrittenYaml 和条件成立时的 ReplaceString 都创建 NamedTemporaryFile(delete=False)。原始 YAML 或 RViz 文件保持不变，Launch 后续拿到的是新文件路径。

这保证了多机器人启动时可以从同一份模板生成多个命名空间版本，但也意味着临时文件不会由本包自动删除。长时间频繁拉起 Launch 时，系统临时目录可能积累历史副本。

1.4 “公共”不等于“没有边界” ​

RewrittenYaml 不是通用 YAML Schema 引擎；ReplaceString 也不是语法感知的配置编辑器。前者依赖点分路径、同名键和 ros__parameters 约定，后者只是逐行字符串替换。输入格式超出这些假设时，源码可能跳过、部分写入或直接抛异常。

二、包边界与真实调用链 ​

2.1 Python 导出边界 ​

nav2_common/launch/__init__.py 没有定义函数，只把四个类重新导出：HasNodeParams、RewrittenYaml、ReplaceString 和 ParseMultiRobotPose。因此包外 Launch 通常写：

python
from nav2_common.launch import RewrittenYaml

nav2_common/__init__.py 本身为空。源码树中的 __pycache__ 是 Python 生成物，不是新的接口，也不纳入函数统计。

2.2 Launch Substitution 数据流 ​

典型调用链是：

text
LaunchConfiguration
  → RewrittenYaml／ReplaceString 对象
  → ParameterFile 或 Node 参数消费该对象
  → Launch 调用 perform(context)
  → 返回临时文件路径
  → 节点进程读取最终配置

构造函数只保存尚未解析的 Substitution。真正的命名空间、地图路径、仿真时间等值，要等 LaunchContext 已经包含启动参数后才能解析。这就是“延迟求值”的意义。

2.3 CMake 导出数据流 ​

nav2_common 自身用 ament_python_install_package(nav2_common) 安装 Python 包，用普通 install(DIRECTORY cmake ...) 安装宏文件，并通过 ament_package(CONFIG_EXTRAS "nav2_common-extras.cmake") 导出额外 CMake 配置。

下游执行 find_package(nav2_common REQUIRED) 时，Ament 加载 extras 文件；extras 再 include() 宏文件。此后下游当前目录才能调用 nav2_package()。

三、HasNodeParams 的四个函数 ​

3.1 HasNodeParams.__init__() ​

  • 作用：构造一个“参数文件是否包含指定节点顶层键”的 Launch Substitution。
  • 输入：source_file 可以是字符串或其他 Launch Substitution；node_name 是普通文本。
  • 输出：没有直接返回业务数据；对象内部保存规范化后的源文件 Substitution 列表和节点名。
  • 数据流／回调：调用 normalize_to_list_of_substitutions()，让源路径可以延迟到 LaunchContext 中解析。
  • 包外调用：当前仓库只在 nav2_bringup/launch/slam_launch.py 实例化一次，用来检查参数文件是否含 slam_toolbox。

node_name 没有像 source_file 一样被规范化。因此这个实现适合构造时就确定的节点名，不适合把节点名本身做成 LaunchConfiguration。

3.2 HasNodeParams.name ​

  • 作用：暴露源文件对应的 Substitution 列表。
  • 输入：没有显式输入，读取私有成员 __source_file。
  • 输出：List[launch.Substitution]。
  • 数据流／回调：perform() 通过这个属性取得待解析的源文件表达式。
  • 包外调用：当前仓库没有直接读取该属性的包外代码；它主要服务类内 perform()。

属性名叫 name，实际保存的是文件路径表达式，不是节点名。读源码时不要被命名误导。

3.3 HasNodeParams.describe() ​

  • 作用：满足 Launch Substitution 的描述接口。
  • 输入：没有显式输入。
  • 输出：空字符串。
  • 数据流／回调：Launch 在日志或实体描述场景下可以调用，但这里没有提供可读内容。
  • 包外调用：没有发现生产代码显式调用，由 Launch 基类契约间接使用。

空描述不影响条件判断，但会降低 Launch 调试输出的可解释性。

3.4 HasNodeParams.perform() ​

  • 作用：真正读取 YAML，并判断目标节点名是否为顶层键。
  • 输入：当前 LaunchContext。
  • 输出：文本 "True" 或 "False"，不是 Python 布尔值。
  • 数据流／回调：Launch 条件求值时触发；先解析文件路径，再用 yaml.safe_load() 读取，最后检查 self.__node_name in data.keys()。
  • 包外调用：slam_launch.py 把同一个对象分别交给 UnlessCondition 与 IfCondition。没有 slam_toolbox 参数时走默认配置分支；存在时把用户参数文件传给 SLAM Toolbox。

返回文本是为了直接适配 Launch 条件表达式。源码假定 YAML 顶层一定是映射；空文件会得到 None，列表顶层也没有预期的键语义，两者都可能在 data.keys() 处失败。文件通过 open() 直接交给 safe_load()，没有使用上下文管理器显式关闭。

四、ParseMultiRobotPose 的三个函数 ​

4.1 ParseMultiRobotPose.__init__() ​

  • 作用：创建多机器人位姿解析器，并立即保存目标命令行参数的原始值。
  • 输入：目标参数名，例如 "robots"。
  • 输出：没有直接返回值；私有成员 __args 保存解析结果。
  • 数据流／回调：构造期间同步调用 __parse_argument()，不是 Launch 延迟求值。
  • 包外调用：当前只在 nav2_bringup/launch/cloned_multi_tb3_simulation_launch.py 中以 ParseMultiRobotPose('robots').value() 使用。

这个类没有继承 launch.Substitution。它读取的是生成 LaunchDescription 时进程已经拥有的 sys.argv，因此工作时机比 RewrittenYaml.perform() 更早，也不能随 LaunchContext 变化。

4.2 ParseMultiRobotPose.__parse_argument() ​

  • 作用：从 ROS 2 Launch 进程命令行中取出 <target>:=<value>。
  • 输入：目标参数名。
  • 输出：找到时返回去掉前缀的原始文本；找不到时返回空字符串。
  • 数据流／回调：只有 len(sys.argv) > 4 才扫描，并固定跳过前四项；遇到第一个匹配项立即返回。
  • 包外调用：私有函数，只由构造函数调用。

实现通过 startswith() 判断前缀，再用 replace() 删除前缀。它依赖 ros2 launch 当前的命令行排列约定，不读取 LaunchConfiguration，也不处理同名参数的后续重复定义。

4.3 ParseMultiRobotPose.value() ​

  • 作用：把多机器人文本变成“机器人名到六自由度位姿字典”的映射。
  • 输入：隐式读取构造时保存的原始字符串。
  • 输出：Dict；没有参数时返回空字典。
  • 数据流／回调：按分号拆机器人项，按等号拆名称和 Pose，使用 yaml.safe_load() 解析花括号内容，再为缺失的 x、y、z、roll、pitch、yaw 补 0.0。
  • 包外调用：克隆多机器人 Launch 遍历返回字典，为每个机器人创建 namespace、初始 Pose 和一组 Bringup Action。

等号拆分没有设置最大次数，拆出数量不是二时直接跳过。重复机器人名会被后项覆盖。源码也没有验证 Pose 的类型；如果 YAML 解析成标量或空值，后续成员检查可能抛异常。

五、ReplaceString 的七个函数 ​

5.1 ReplaceString.__init__() ​

  • 作用：保存源文件、字符串替换表和可选条件。
  • 输入：source_file、replacements 字典，以及可选 launch.Condition。
  • 输出：一个可延迟执行的 Launch Substitution。
  • 数据流／回调：源文件和每个替换值都经过 normalize_to_list_of_substitutions()；替换键本身保持原对象。
  • 包外调用：标准 Bringup 用它改多机器人参数模板和 RViz 配置；本项目 myagv_test_bringup、nav2_regulated_modules 的 RViz Launch 也在使用。

替换值可以由 ('/', namespace) 这种 Substitution 序列组成，直到 LaunchContext 就绪后才拼成真实文本。替换键必须最终是字符串，否则执行阶段会抛 TypeError。

5.2 ReplaceString.name ​

  • 作用：返回源文件 Substitution 列表。
  • 输入：没有显式输入。
  • 输出：List[launch.Substitution]。
  • 数据流／回调：perform() 用它解析真实文件路径。
  • 包外调用：没有发现直接包外调用。

与 HasNodeParams.name 一样，这个名字表示“被替换的源”，不是文件内的配置名称。

5.3 ReplaceString.condition ​

  • 作用：暴露构造时保存的可选条件。
  • 输入：没有显式输入。
  • 输出：launch.Condition 或 None。
  • 数据流／回调：perform() 读取它，决定生成替换副本还是直接返回原路径。
  • 包外调用：没有发现直接包外调用。

条件只控制文件是否改写，不控制引用该 Substitution 的整个 Node 是否启动。

5.4 ReplaceString.describe() ​

  • 作用：满足 Launch Substitution 描述接口。
  • 输入：没有显式输入。
  • 输出：空字符串。
  • 数据流／回调：可能由 Launch 的描述和调试路径间接触发。
  • 包外调用：没有显式调用点。

5.5 ReplaceString.perform() ​

  • 作用：根据条件返回原文件路径，或生成完成文本替换的临时副本。
  • 输入：当前 LaunchContext。
  • 输出：原路径或临时文件路径。
  • 数据流／回调：先解析源路径；条件成立时创建输出文件，调用 resolve_replacements() 和 replace()，关闭输入输出后返回临时路径。
  • 包外调用：由 ParameterFile、Node 的 arguments 等 Launch 消费者间接触发。

当前仓库共有四个实际实例。标准 bringup_launch.py 的参数模板替换受 use_namespace 条件控制；三个 RViz Launch 则在命名空间分支实际消费替换后的配置。

异常处理有一个值得注意的缺口。replace() 抛错后，函数只打印错误，仍可能返回空或部分写入的临时文件；如果源文件连 open() 都失败，finally 又会调用尚未赋值的 input_file.close()，新的局部变量异常会覆盖原始文件错误。

5.6 ReplaceString.resolve_replacements() ​

  • 作用：把替换表中的延迟值解析成最终文本。
  • 输入：当前 LaunchContext。
  • 输出：普通字典，键保持不变，值变成字符串。
  • 数据流／回调：逐项调用 launch.utilities.perform_substitutions()。
  • 包外调用：没有包外调用，只由 perform() 使用。

例如值 ('/', namespace) 会在这里变成 /robot1。同一个 ReplaceString 对象在不同 Context 中理论上可以解析出不同结果。

5.7 ReplaceString.replace() ​

  • 作用：执行不理解文件语法的逐行全局字符串替换。
  • 输入：可迭代输入文件、可写输出文件、已经解析的替换字典。
  • 输出：没有返回值；结果写入输出文件。
  • 数据流／回调：每读一行，就按字典插入顺序检查全部替换对；命中时用 Pythonstr.replace() 替换该行所有出现位置。
  • 包外调用：没有包外调用，只由 perform() 使用。

它不会解析 YAML、RViz 或 XML，也不会区分注释、键、值和普通文本。较早的替换结果还可能再次命中较晚的替换键，因此多个替换对存在顺序效应。

六、DictItemReference 的三个函数 ​

6.1 DictItemReference.__init__() ​

  • 作用：把“某个字典中的某个键”包装成可原地更新的轻量引用。
  • 输入：目标字典和目标键。
  • 输出：一个保存字典对象与键名的引用对象。
  • 数据流／回调：不复制字典，后续写入会直接反映到原 YAML 对象。
  • 包外调用：没有包外调用；由 RewrittenYaml.getYamlLeafKeys() 创建。

Python 普通标量没有 C++ 引用语义，这个包装器让遍历函数既能告诉调用者“发现了哪个键”，又能让调用者覆盖对应值。

6.2 DictItemReference.key() ​

  • 作用：读取被引用的键名。
  • 输入：没有显式输入。
  • 输出：字符串键名。
  • 数据流／回调：substitute_params() 用返回值查询同名改写表。
  • 包外调用：没有包外调用。

6.3 DictItemReference.setValue() ​

  • 作用：原地覆盖被引用键的值。
  • 输入：新的 YAML 标量值。
  • 输出：没有返回值。
  • 数据流／回调：执行 dictionary[dictKey] = value，直接修改 safe_load() 生成的数据树。
  • 包外调用：没有包外调用，只由 substitute_params() 使用。

类型注解把字典值写成 YamlValue，但遍历过程中引用也可能指向一个嵌套字典。运行时 Python 不强制这个注解。

七、RewrittenYaml 的入口与总流水线 ​

7.1 RewrittenYaml.__init__() ​

  • 作用：保存 YAML 源与四类改写策略，等待 LaunchContext 就绪后执行。
  • 输入：源文件、param_rewrites、可选 root_key、可选 key_rewrites、可选 value_rewrites、convert_types。
  • 输出：一个 Launch Substitution 对象。
  • 数据流／回调：源文件、三组改写目标值和根键都被规范化为 Substitution 列表；键仍保留为普通 Python 字典键。
  • 包外调用：全仓有 25 个实际实例，是本包最常用的接口。

生产 Bringup 常把 use_sim_time、autostart、yaml_filename 放入 param_rewrites，把 namespace 放入 root_key，并开启 convert_types=True。

7.2 RewrittenYaml.name ​

  • 作用：返回源 YAML 的 Substitution 列表。
  • 输入：没有显式输入。
  • 输出：list[launch.Substitution]。
  • 数据流／回调：总入口 perform() 用它解析实际文件路径。
  • 包外调用：没有直接包外调用。

7.3 RewrittenYaml.describe() ​

  • 作用：满足 Launch Substitution 描述接口。
  • 输入：没有显式输入。
  • 输出：空字符串。
  • 数据流／回调：只参与 Launch 实体描述契约，不改 YAML。
  • 包外调用：没有显式调用点。

7.4 RewrittenYaml.perform() ​

  • 作用：组织一次完整 YAML 改写，并返回临时文件路径。
  • 输入：当前 LaunchContext。
  • 输出：包含最终 YAML 的临时文件路径。
  • 数据流／回调：解析源路径，创建临时文件，调用 resolve_rewrites()，安全加载 YAML，然后依次执行参数替换、参数新增、键替换、值替换、可选根键包装和 yaml.dump()。
  • 包外调用：由 ParameterFile 或其他 Launch 参数消费者间接触发。

顺序固定为：

text
substitute_params
  → add_params
  → substitute_keys
  → substitute_values
  → root_key 包装
  → yaml.dump

后执行的阶段可以覆盖前阶段的结果。例如先把键名改掉，再按值表匹配改名后的内容。输出是重新序列化的 YAML，因此原注释和排版不会保留。

7.5 RewrittenYaml.resolve_rewrites() ​

  • 作用：把参数、键和值三组改写目标解析成普通字符串。
  • 输入：当前 LaunchContext。
  • 输出：三个 dict[str, str]。
  • 数据流／回调：逐项调用 perform_substitutions()，保持改写表的键不变。
  • 包外调用：没有包外调用，只由 perform() 调用。

这个函数只解析“要写入什么”，不检查源 YAML 是否存在对应路径。存在性与创建逻辑属于后续函数。

八、RewrittenYaml 的参数路径与类型函数 ​

8.1 RewrittenYaml.substitute_params() ​

  • 作用：替换已有参数，支持同名键匹配和点分绝对路径匹配。
  • 输入：YAML 数据树和已经解析的参数改写表。
  • 输出：没有返回值；原地修改数据树。
  • 数据流／回调：先遍历 getYamlLeafKeys()，所有同名键都被替换；再用 pathify() 枚举叶路径，对命中的绝对路径调用 updateYamlPathVals()。
  • 包外调用：没有包外调用，只由 perform() 使用。

同名改写是全树范围。例如不同节点各有一个 use_sim_time，一条改写会同时覆盖它们。绝对路径阶段随后执行，所以更精确的路径项可以覆盖同名阶段刚写入的值。

源码注释说“只替换叶参数”，但 getYamlLeafKeys() 在递归后也会为映射值的父键生成引用。如果改写表正好包含这个父键，整个子映射也可能被标量替换。

8.2 RewrittenYaml.add_params() ​

  • 作用：创建源 YAML 中不存在的新 ROS 参数路径。
  • 输入：YAML 数据树与参数改写表。
  • 输出：没有返回值；符合条件的路径被原地加入。
  • 数据流／回调：重新调用 pathify() 获取现有叶路径；缺失路径只有包含 ros__parameters 段时才会送给 updateYamlPathVals()。
  • 包外调用：没有包外调用，只由 perform() 使用。

这个限制避免任意字符串在 YAML 顶层制造结构，但它只检查路径片段中是否出现精确文本 ros__parameters，并不验证完整 ROS 参数文件 Schema。

8.3 RewrittenYaml.updateYamlPathVals() ​

  • 作用：沿点分路径递归写入字典或列表。
  • 输入：当前子树、剩余键列表和目标值。
  • 输出：更新后的当前子树，同时原对象已被修改。
  • 数据流／回调：逐层从 yaml_key_list 弹出路径；字典缺少中间键时以空字典创建，列表路径则把文本索引转换成整数。
  • 包外调用：没有包外调用；由已有绝对路径替换和缺失参数新增共同使用。

列表索引必须有效且可转成整数。点分路径也无法无歧义地区分“层级分隔符”和“原始键名自身的点号”。

8.4 RewrittenYaml.convert() ​

  • 作用：把 Launch 解析出的文本转换成有限的 YAML 标量类型。
  • 输入：字符串。
  • 输出：str、int、float 或 bool。
  • 数据流／回调：开启 convert_types 时，含点号的文本尝试转 float，否则尝试转 int；随后无论开关状态如何，都识别大小写不敏感的 true 与 false。
  • 包外调用：没有包外调用；参数替换、新增参数和值替换都会使用。

本地行为探针确认：12 变成整数，3.5 变成浮点数，true 与 False 变成布尔值；1e-3 因为不含点号而先尝试整数，失败后保持字符串，null 也保持字符串。这不是完整 YAML 标量推断器。

九、RewrittenYaml 的键、值与递归函数 ​

9.1 RewrittenYaml.substitute_values() ​

  • 作用：启动对整棵 YAML 树的标量值替换。
  • 输入：YAML 顶层字典和值改写表。
  • 输出：没有返回值；顶层每个键对应的值都被递归处理结果覆盖。
  • 数据流／回调：定义内部 process_value()，再遍历顶层键调用它。
  • 包外调用：没有包外调用，只由 perform() 使用。

值匹配通过 str(value) 完成，因此原值是整数、浮点数或布尔值时，也会先转换成字符串再查表。

9.2 RewrittenYaml.substitute_values.process_value() ​

  • 作用：递归遍历字典、列表和标量，并完成值级替换。
  • 输入：任意当前 YAML 值。
  • 输出：原字典、重建的列表、转换后的替换值，或原标量。
  • 数据流／回调：字典逐项原地更新；列表用列表推导递归重建；标量字符串化后查询 value_rewrites，命中时调用 convert()。
  • 包外调用：内部函数，只由 substitute_values() 及自身递归调用。

这是 31 个 Python 入口中唯一的嵌套函数。把它单独统计，是因为列表中的字典能够被值替换完整遍历，而后面的键替换并不具备同样的列表递归能力。

9.3 RewrittenYaml.substitute_keys() ​

  • 作用：递归修改字典键名。
  • 输入：当前 YAML 字典与键改写表。
  • 输出：没有返回值；字典结构被原地修改。
  • 数据流／回调：复制当前键列表以避免遍历时改字典；命中时先写入新键再删除旧键；随后只对字典值继续递归。
  • 包外调用：没有包外调用，只由 perform() 使用。

它不会递归进入列表中的字典。新键已经存在时，源码直接覆盖目标值，没有冲突检测；原键随后删除。键改写属于结构操作，不适合在不了解完整 YAML 的情况下大范围使用。

9.4 RewrittenYaml.getYamlLeafKeys() ​

  • 作用：深度优先生成可更新的字典键引用。
  • 输入：当前 YAML 字典。
  • 输出：Generator[DictItemReference, None, None]。
  • 数据流／回调：非字典直接结束；遇到字典子节点先递归，再为当前层这个键生成引用。
  • 包外调用：没有包外调用，只由 substitute_params() 使用。

由于每个键最终都会 yield，函数名中的 Leaf 并不严格。叶值键和指向子字典的父键都会出现；列表内部的字典则不会进入。

9.5 RewrittenYaml.pathify() ​

  • 作用：把嵌套字典和列表展平为“点分路径到叶值”的字典。
  • 输入：任意 YAML 子树、可选当前路径、可选结果字典和连接符。
  • 输出：叶路径字典。
  • 数据流／回调：入口调用时创建结果字典并从空路径递归；字典追加键，列表追加数字索引，只有标量叶值写入结果。
  • 包外调用：没有包外调用；substitute_params() 和 add_params() 使用。

例如：

text
node.ros__parameters.plugins.0.name

可以表示列表中的某个叶值。但原始 YAML 键若含点号，会与层级表达产生歧义。函数也只记录叶值路径，不会记录一个字典节点本身的路径。

十、CMake 的公开宏 ​

10.1 nav2_package() ​

  • 作用：给下游 Nav2 CMake 项目建立统一构建基线。
  • 输入：没有宏参数，读取并修改当前 CMake 目录状态与缓存变量。
  • 输出：没有返回值；可能设置构建类型、C++ 标准、编译选项、链接标志和 Windows 定义。
  • 数据流／回调：在下游 find_package(nav2_common REQUIRED) 载入宏后，由对应 CMakeLists.txt 配置阶段显式调用。
  • 包外调用：当前仓库有 32 个调用点，覆盖 AMCL、BT、Behavior、Controller、Costmap、Planner、Smoother、Map Server、Route、Velocity Smoother 等包和 DWB 子包。

宏内部规则包括：

  • 单配置生成器没有显式构建类型时，把 CMAKE_BUILD_TYPE 强制缓存为 Release，并给 GUI 设置四个候选值。
  • 没有显式 CMAKE_CXX_STANDARD 时设置 C++17。源码旁注仍写“默认 C++14”，代码才是实际事实。
  • GCC 或 Clang 增加 -Wall -Wextra -Wpedantic -Werror -Wdeprecated -fPIC。
  • COVERAGE_ENABLED 默认关闭；开启时给编译、可执行链接和共享库链接加入 --coverage。
  • MSVC 开启 CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS，并定义 _USE_MATH_DEFINES。

这些设置作用在宏调用所在的 CMake 目录及其后续目标。宏不是目标级封装，因此调用顺序与子目录边界会影响覆盖范围。

十一、四个 Launch 工具在仓库外怎样被调用 ​

11.1 RewrittenYaml 的 25 个实例 ​

生产 Bringup 中，nav2_bringup、myagv_test_bringup、mytb3_bringup、myworld_bringup、nav2_simple_commander、nav2_collision_monitor 和 nav2_regulated_modules 都在使用它；nav2_system_tests 的行为、Costmap Filter、系统失败和 Waypoint 测试 Launch 也在使用。

最常见的数据流是：

text
params_file
  + namespace
  + use_sim_time
  + autostart／yaml_filename
  → RewrittenYaml
  → ParameterFile(allow_substs=True)
  → 多个 Nav2 节点

因此一个 use_sim_time Launch 参数可以统一覆盖同一 YAML 中多个节点的同名字段。

11.2 ReplaceString 的四个实例 ​

标准 bringup_launch.py 用它在多机器人参数模板中把 <robot_namespace> 替换成真实 namespace。标准 RViz Launch、myagv_test_bringup RViz Launch 和 nav2_regulated_modules RViz Launch 则用它改 RViz 配置中的同名占位符。

这里选择文本替换而不是 YAML 改写，是因为 RViz 配置和占位符场景只需要保持原文件其余内容不变。

11.3 HasNodeParams 的一个实例 ​

nav2_bringup/slam_launch.py 同时创建两个 IncludeLaunchDescription：

  • 参数文件含 slam_toolbox 顶层键时，条件文本为真，传入 slam_params_file。
  • 参数文件不含该键时，反向条件成立，不传用户参数文件，让 SLAM Toolbox 使用自己的默认文件。

两条分支互斥，但判断对象相同。它解决的是“是否应该传参数文件”，不是检查单个 ROS 参数是否存在。

11.4 ParseMultiRobotPose 的一个实例 ​

cloned_multi_tb3_simulation_launch.py 在生成 LaunchDescription 时立即解析 robots:=...，再用普通 Python 循环为每个机器人创建 RViz、仿真实体和 Nav2 Bringup。

这条链与另外三个工具不同：没有 perform(context)，也没有临时文件。输出直接成为 Launch Action 列表的结构输入。

十二、源码中最容易误判的边界 ​

12.1 convert_types=False 仍会转布尔值 ​

数字转换受开关控制，true 和 false 转布尔不受控制。若调用者真的需要字符串 "true"，不能只依赖关闭 convert_types。

12.2 同名改写可能替换整棵子树 ​

getYamlLeafKeys() 实际生成所有字典键引用。改写键若与一个父级映射键同名，setValue() 可以把整个子字典替换成标量。参数名应尽量选择真正的 ROS 参数叶键，结构改写则用更精确的机制。

12.3 临时文件失败可能延迟暴露 ​

ReplaceString.perform() 捕获错误后仍可能返回临时路径。真正的失败可能直到 RViz 或节点读取配置时才出现，看起来像下游解析故障。排障时应先核对 Launch 返回的临时文件内容。

12.4 ParseMultiRobotPose 对输入格式很信任 ​

它只补默认字段，不验证数值是否有限、四元数是否合法或 namespace 是否可用。后续 Gazebo 与 Nav2 启动失败时，根因可能仍是最初的命令行 Pose 文本。

12.5 CMake 宏把警告提升为错误 ​

GCC／Clang 分支包含 -Werror。下游依赖升级后新增的弃用告警可能直接让构建失败。这是统一质量门槛带来的有意结果，排障时不要简单归因为编译器“太严格”。

十三、建议的源码阅读顺序 ​

13.1 从实际 Launch 调用点进入 ​

先看 nav2_bringup/launch/bringup_launch.py 中 ReplaceString 与 RewrittenYaml 如何串联，再回到两个类的 perform()。这样能先知道输入和消费者，不会把工具函数当成孤立算法。

13.2 顺着 RewrittenYaml 的固定流水线下钻 ​

从 perform() 依次进入 resolve_rewrites()、substitute_params()、add_params()、substitute_keys() 和 substitute_values()，再分别追踪 pathify()、getYamlLeafKeys()、updateYamlPathVals() 与 convert()。

13.3 把另外三个 Launch 工具看成不同粒度 ​

  • ReplaceString 面向文件文本。
  • HasNodeParams 面向 YAML 顶层结构和条件分支。
  • ParseMultiRobotPose 面向 ROS 2 Launch 进程命令行。

三者输入层级不同，不能互相替代。

13.4 最后阅读 CMake 导出链 ​

从本包 CMakeLists.txt 的 CONFIG_EXTRAS 进入 nav2_common-extras.cmake，再进入 nav2_package.cmake，最后任选一个下游包核对 find_package() 与 nav2_package() 的调用顺序。

十四、把 32 个入口压缩成一张心智图 ​

14.1 Launch 平面的核心 ​

RewrittenYaml 处理结构化配置，ReplaceString 处理模板文本，HasNodeParams 决定参数分支，ParseMultiRobotPose 把命令行压成 Launch 结构。前三者依赖 Launch 延迟求值，后者在普通 Python 执行阶段立即完成。

14.2 CMake 平面的核心 ​

nav2_package() 不生成库，也不链接运行代码。它把 Release、C++17、严格告警、覆盖率和 Windows 导出规则统一注入调用它的下游目录。

14.3 真正的数据边界 ​

这个包接收的是“配置描述”，输出的是“启动前可消费的配置”或“编译前可继承的规则”。机器人位姿、地图、速度参数最终会进入具体节点，但 nav2_common 自己不持有导航状态，也不参与规划控制循环。

看懂它之后，再遇到“YAML 明明写的是一个值，节点为何读到另一个值”“namespace 为什么只在某些配置里生效”“同一批包为何突然把警告当错误”，就应该先检查启动前和构建前的这层基础设施，而不是直接怀疑运行中的 Nav2 算法。

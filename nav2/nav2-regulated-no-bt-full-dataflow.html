砍掉行为树之后，Nav2 还能怎么跑？一套自研规控导航的状态机与全数据流拆解 ​

Nav2 的默认导航入口是 bt_navigator：它读取行为树 XML，再把规划、控制、恢复行为组织成一棵运行时任务树。

但行为树不是 Nav2 规划器和控制器运行的必要条件。真正执行路径搜索、路径平滑、轨迹跟踪和速度约束的，仍然是 Planner Server、Smoother Server、Controller Server 与 Velocity Smoother。

本文拆解的 nav2_regulated_modules 做了一件很直接的事：

删除 bt_navigator、behavior_server 和 waypoint_follower，保留 Nav2 规划控制主链，用一个显式 C++ 状态机重新实现目标接入、Action 编排、周期重规划、定位保护、取消抢占和轻量自恢复。

它不是“把 Nav2 全部推倒重写”，而是替换 Nav2 的任务编排层。

一、先给结论：被替换的是编排层，不是规划控制算法 ​

这个包启动的导航主链是：

text
目标输入
  ↓
regulated_navigator
  ↓ ComputePathToPose／ComputePathThroughPoses
planner_server
  ↓ Path
smoother_server
  ↓ SmoothPath
controller_server
  ↓ cmd_vel_nav
velocity_smoother
  ↓ cmd_vel
controlpub
  ↓
/control_to_uart

1.1 保留的模块 ​

  • map_server：发布静态地图。
  • Global Costmap：供全局规划使用。
  • Local Costmap：供局部控制使用。
  • planner_server：加载 NavFn、SMAC、Theta* 等全局规划插件。
  • smoother_server：提供路径平滑。
  • controller_server：加载 DWB、RPP、MPPI 等控制插件。
  • velocity_smoother：对速度做限幅和加减速平滑。
  • Lifecycle Manager：按依赖顺序激活和停用节点。

1.2 不启动的模块 ​

  • bt_navigator。
  • behavior_server。
  • waypoint_follower。
  • AMCL。

1.3 轻量恢复边界 ​

不启动 behavior_server，不等于任何异常处理都被删除。当前自研节点没有 Spin、BackUp、Wait 等 Nav2 Behavior Action，但仍保留“停车、清理双 Costmap、等待地图更新、重新规划”的轻量自恢复。

二、启动文件怎样构造整套系统 ​

regulated_modules.launch.py 把系统分成两组 Lifecycle。

2.1 地图服务 Lifecycle 组 ​

只管理 map_server，由 lifecycle_manager_localization 激活。

2.2 规控 Lifecycle 组 ​

按顺序管理：

text
planner_server
controller_server
smoother_server
velocity_smoother
regulated_navigator

regulated_navigator 放在最后激活，因为它一旦接收目标，就会立即等待规划、平滑和控制 Action Server。停机时顺序相反，规控入口先停止，避免下游服务器退出后仍接收新任务。

2.3 进程部署方式 ​

非组合模式下，各服务器是独立进程；组合模式下，Planner、Controller、Smoother、Velocity Smoother 和 Lifecycle Manager 可以装入组件容器，但自研 regulated_navigator 与 controlpub 仍作为普通节点启动。

三、所有输入输出：一张图看清数据从哪里来、到哪里去 ​

3.1 外部目标输入 ​

3.1.1 /navigate_to_pose ​

  • 类型：nav2_msgs/action/NavigateToPose。
  • 方向：外部客户端调用 regulated_navigator。
  • 作用：提交单个目标位姿，并接收当前位置、剩余距离、预计时间和恢复次数反馈。
  • 约束：behavior_tree 字段必须为空；传入 XML 会被明确拒绝。

3.1.2 /navigate_through_poses ​

  • 类型：nav2_msgs/action/NavigateThroughPoses。
  • 方向：外部客户端调用 regulated_navigator。
  • 作用：提交一组连续目标位姿。
  • 特有反馈：除通用导航反馈外，还返回剩余目标点数量。

3.1.3 /goal_pose ​

  • 类型：geometry_msgs/msg/PoseStamped。
  • 方向：RViz 或简单上层节点发布给 regulated_navigator。
  • 作用：提供不需要 Action 结果的兼容单点入口。
  • 行为：新 Topic 目标同样采用替换式抢占，但没有外层 Action 反馈和结果。

所有目标都必须包含有效 frame_id、有限数值的位置和非零范数四元数。

3.2 自研定位输入 ​

3.2.1 map -> base_link ​

  • 类型：TF 动态变换。
  • 方向：外部自研定位系统提供给规控节点和两张 Costmap。
  • 作用：获取当前位姿、生成导航反馈、判断定位超时和跳变、计算是否有真实运动进展。
  • 关键点：本方案不依赖 map -> odom -> base_link，也不读取里程计消息判断规控进展。

3.3 地图和传感器输入 ​

3.3.1 地图 YAML／PGM ​

  • 消费者：map_server。
  • 输出：/map，类型为 nav_msgs/msg/OccupancyGrid。
  • 下游：Global Costmap 的 Static Layer。

3.3.2 /c200_lidar_node1/scan ​

  • 类型：sensor_msgs/msg/LaserScan。
  • 消费者：Global Costmap 的 Obstacle Layer、Local Costmap 的 Voxel Layer。
  • 作用：同时参与全局动态绕障和局部实时避障。

3.4 路径与控制输出 ​

3.4.1 /plan ​

  • 类型：nav_msgs/msg/Path。
  • 发布者：Planner Server。
  • 作用：全局路径可视化和调试。

3.4.2 /cmd_vel_nav ​

  • 类型：geometry_msgs/msg/Twist。
  • 发布者：Controller Server，也可能由规控节点连续发布三帧零速度。
  • 消费者：Velocity Smoother。

3.4.3 /cmd_vel ​

  • 类型：geometry_msgs/msg/Twist。
  • 发布者：Velocity Smoother。
  • 消费者：controlpub。

3.4.4 /control_to_uart ​

  • 发布者：controlpub。
  • 作用：把平滑后的速度转换为底盘串口控制链所需数据。

3.5 规控节点调用的内部 Action 和 Service ​

3.5.1 /compute_path_to_pose ​

  • 类型：nav2_msgs/action/ComputePathToPose。
  • 服务端：Planner Server。
  • 请求核心字段：单目标、planner_id、是否使用指定起点。
  • 返回核心数据：nav_msgs/msg/Path 和规划时间。

3.5.2 /compute_path_through_poses ​

  • 类型：nav2_msgs/action/ComputePathThroughPoses。
  • 服务端：Planner Server。
  • 请求核心字段：剩余目标数组和 planner_id。
  • 返回核心数据：贯穿多个目标的 Path。

3.5.3 /smooth_path ​

  • 类型：nav2_msgs/action/SmoothPath。
  • 服务端：Smoother Server。
  • 请求核心字段：原始 Path、smoother_id、最大平滑时间、是否检查碰撞。
  • 返回核心数据：平滑 Path。

3.5.4 /follow_path ​

  • 类型：nav2_msgs/action/FollowPath。
  • 服务端：Controller Server。
  • 请求核心字段：Path、controller_id、goal_checker_id。
  • 反馈核心数据：剩余距离和当前速度。

3.5.5 /local_costmap/clear_entirely_local_costmap ​

  • 类型：nav2_msgs/srv/ClearEntireCostmap。
  • 调用时机：轻量恢复。
  • 作用：清空 Local Costmap，随后由激光观测重新填充动态障碍。

3.5.6 /global_costmap/clear_entirely_global_costmap ​

  • 类型：nav2_msgs/srv/ClearEntireCostmap。
  • 调用时机：轻量恢复。
  • 作用：清空 Global Costmap，再由静态地图层和激光层重新融合。

3.6 地图、可视化和生命周期接口 ​

3.6.1 /map 与 Map Server Service ​

  • /map：nav_msgs/msg/OccupancyGrid，为 Global Costmap 提供静态底图。
  • /map_server/map：nav_msgs/srv/GetMap，供外部主动读取当前地图。
  • /map_server/load_map：nav2_msgs/srv/LoadMap，运行时加载新地图。

3.6.2 Costmap 调试输出 ​

  • /global_costmap/costmap：全局主代价地图。
  • /local_costmap/costmap：局部主代价地图。
  • /local_costmap/voxel_grid：局部 Voxel Layer 的体素调试数据。
  • 这些 Topic 主要供 RViz 和诊断工具使用；Planner 和 Controller 在各自进程内直接读取 Costmap 对象。

3.6.3 /tf 与 /tf_static ​

  • Launch 支持命名空间重映射。
  • 当前规控主链只要求动态 map -> base_link；测试激光的 frame_id 直接为 base_link。

3.6.4 Lifecycle 接口 ​

  • map_server 由独立 Lifecycle Manager 管理。
  • Planner、Controller、Smoother、Velocity Smoother 和 regulated_navigator 由规控 Lifecycle Manager 管理。
  • 每个 Lifecycle 节点仍暴露标准 change_state、get_state 等 Service；Manager 通过状态转换和 Bond 监控完成自动拉起与故障检测。

四、10 个状态怎样替代一棵行为树 ​

行为树把执行状态隐藏在树节点、黑板和 Tick 流程里；当前实现则把任务阶段写成一个显式枚举。

4.1 IDLE ​

没有活动任务。新目标到来后创建 NavigationTask，分配新的 generation，再进入规划。

4.2 PLANNING ​

首次请求全局路径。单点任务调用 ComputePathToPose，多点任务调用 ComputePathThroughPoses。

4.3 SMOOTHING ​

规划成功且 use_smoother=true 时调用 SmoothPath。如果平滑 Goal 被拒绝、执行失败或返回空路径，不直接终止任务，而是回退使用原始规划路径。

4.4 CONTROLLING ​

向 Controller Server 发送 FollowPath。规控节点从 FollowPath 反馈中读取：

text
distance_to_goal
speed

再结合 TF 生成对外导航反馈。

4.5 REPLANNING ​

控制过程中按 replan_frequency 周期重新计算路径。重规划不先停止当前控制；新路径准备完成后，再用新的 FollowPath Goal 替换旧路径。

如果后台重规划暂时失败，但旧 FollowPath 仍有效，并且连续失败未达到上限，状态回到 CONTROLLING，继续沿旧路径运动。

4.6 CLEARING_COSTMAP ​

规划或控制失败、长时间无位移时进入轻量恢复：取消下游 Goal、停车、调用两张 Costmap 的完整清理 Service，等待配置时间后重新规划。

4.7 LOCALIZATION_LOST ​

超过 localization_timeout 无法获得 map -> base_link 后，立即取消控制并停车。定位恢复后必须连续稳定达到 localization_stable_duration，才重新规划。

4.8 CANCELING ​

外层客户端请求取消时进入。规控节点取消规划、平滑和控制子 Goal，发送零速度，并把外层 Action 标记为 canceled。

4.9 SUCCEEDED ​

FollowPath 成功后，结束对应的单点或多点 Action，再重置为 IDLE。

4.10 FAILED ​

依赖服务器不可用、恢复次数耗尽或定位恢复超时后进入。外层 Action 返回 abort，任务随后重置。

五、一个单点目标到底经过了哪些调用 ​

一次正常单点导航可以拆成八步。

5.1 接收并校验目标 ​

节点只有处于 Lifecycle Active 时才接受目标。目标无 frame、包含非法浮点数、四元数无效或携带行为树 XML，都会在 Action Goal 阶段被拒绝。

5.2 替换旧任务 ​

当前若已有任务，新目标采用 replace 策略：旧的规划、平滑和控制 Goal 全部取消；旧外层 Action 返回 abort；机器人收到零速度。

5.3 等待依赖 ​

规控节点确认以下 Action Server 可用：

text
compute_path_to_pose
compute_path_through_poses
smooth_path（启用时）
follow_path

任一依赖在 server_timeout 内不可用，任务直接失败。

5.4 计算路径 ​

规控节点向 Planner Server 发送目标和 planner_id。use_start=false，意味着 Planner Server 根据 TF 获取当前机器人起点。

5.5 平滑或回退 ​

原始 Path 被保存到 pending_raw_path_。平滑成功则使用平滑 Path；失败则使用原始 Path，避免平滑器成为单点故障源。

5.6 跟随路径 ​

规控节点向 Controller Server 发送：

text
path
controller_id
goal_checker_id

Controller 读取 Local Costmap，以配置频率输出 /cmd_vel_nav。

5.7 周期监控和重规划 ​

200 ms 监控定时器检查 TF、定位跳变、真实位移进展、多点通过情况和重规划时间；反馈定时器按 feedback_frequency 向外层 Action 发布反馈。

5.8 结果收口 ​

FollowPath 成功则外层导航成功；失败则进入轻量恢复；取消或抢占则所有旧回调失效并停车。

六、多点任务不是 Waypoint Follower ​

多点入口沿用标准 NavigateThroughPoses，但实现不依赖 waypoint_follower 插件。

规控节点把剩余目标数组整体发送给 ComputePathThroughPoses。监控阶段通过当前 TF 与第一个目标的平面距离判断是否通过中间点：距离小于 passed_goal_radius 时，从数组头部删除该点，但至少保留最后一个终点。

这意味着它提供的是“沿一条连续路径经过多个位姿”，而不是 Waypoint Follower 那种“到点后执行拍照、等待或自定义插件任务”。

七、异步 Action 最危险的问题：旧回调覆盖新任务 ​

ROS 2 Action 是异步的。一个旧规划请求可能在新目标已经开始后才返回；如果直接接收结果，旧路径就会覆盖新路径。

当前实现使用三层标识：

text
task_generation
plan_sequence
follow_sequence

generation 区分整个导航任务；两个 sequence 分别区分同一任务中的多次规划和多次 FollowPath。

每个 Action 回调都捕获发送时的 generation 和 sequence，执行前重新比较：

text
回调 generation == 当前任务 generation
并且
回调 sequence == 当前阶段 sequence

取消、抢占、恢复和重新下发路径都会递增相应序号。旧回调即使迟到，也只会被忽略，不能再修改当前状态。

这套机制承担了行为树 Halt、节点状态和黑板任务隔离的一部分职责，也是自研异步编排最不能省略的安全边界。

八、没有 Behavior Server 后，异常怎样处理 ​

8.1 规划失败 ​

首次规划失败会进入恢复。周期重规划失败时，只要旧 FollowPath 仍在执行且连续失败次数未达到阈值，就继续使用旧路径。

8.2 控制失败或无进展 ​

FollowPath 返回失败，或者 map -> base_link 在 progress_timeout 内没有产生至少 progress_min_translation 的位移，都会触发轻量恢复。

8.3 轻量恢复的实际动作 ​

text
取消 ComputePath／SmoothPath／FollowPath
→ 连续发布 3 帧零速度
→ clear_entirely_local_costmap
→ clear_entirely_global_costmap
→ 非阻塞等待 Costmap 重新填充
→ 从当前 TF 重新规划

它没有 Spin、BackUp 和 Behavior Wait，也不保证能从所有局部困境中脱困。它解决的是地图观测污染、旧路径失效和短时控制失败，不是完整的机动恢复策略。

8.4 定位超时与跳变 ​

定位暂时丢失时，节点先停车而不是盲目沿旧路径运动。定位恢复后还要经过稳定窗口。

相邻监控周期若出现超过阈值的平移或旋转跳变，则立即废弃旧路径并重新规划。这里使用的是外部自研 map -> base_link，没有 odom 兜底，因此定位质量直接决定规划控制安全边界。

九、速度为什么分成三段 ​

Controller Server 的 cmd_vel 在 Launch 中被重映射为 /cmd_vel_nav。

Velocity Smoother 订阅 /cmd_vel_nav，根据最大速度、最小速度、加速度和减速度限制，输出 /cmd_vel。当前配置为 OPEN_LOOP，不订阅 odom，而是使用上一周期输出作为平滑起点。

controlpub 再把 /cmd_vel 转发或转换到 /control_to_uart。

这个拆分带来三个控制点：

  • Controller 只负责算理想速度。
  • Velocity Smoother 负责速度连续性和超时停车。
  • controlpub 负责适配真实底盘协议。

规控节点的停车指令直接写入 /cmd_vel_nav，因此仍会经过 Velocity Smoother。若安全需求要求立即硬停车，还需要结合底盘协议评估平滑器减速度和 UART 超时，而不能只看上层已经发布零速度。

十、源码怎样按职责拆开 ​

当前实现保持一个 RegulatedNavigator 状态所有者，但把函数按调用阶段拆到不同编译单元。

10.1 regulated_navigator.cpp ​

  • 参数声明。
  • Action、Topic、Service、TF 和定时器创建。
  • Lifecycle 配置、激活、停用和清理。

10.2 navigator_goal_handler.cpp ​

  • 单点、多点 Goal 校验。
  • 取消请求。
  • Topic 目标。
  • 标准导航反馈。

10.3 navigator_planning.cpp ​

  • 依赖等待。
  • ComputePath 请求。
  • SmoothPath 请求。
  • 原始路径回退。

10.4 navigator_control.cpp ​

  • FollowPath 下发。
  • 控制反馈和结果。
  • 三帧零速度停车。

10.5 navigator_monitor.cpp ​

  • 200 ms 任务监控。
  • TF 超时和跳变。
  • 真实运动进展。
  • 周期重规划。
  • 清图恢复入口。

10.6 navigator_task_manager.cpp ​

  • 子 Goal 取消。
  • 抢占、成功、失败和任务重置。

这种拆分没有把状态分散到多个对象。所有编译单元仍操作同一个 NavigationTask，能够避免跨节点状态同步再次变成新的复杂度来源。

十一、这套架构适合什么，不适合什么 ​

11.1 适用场景 ​

  • 导航流程固定，希望执行路径可预测。
  • 已有自研定位，直接提供 map -> base_link。
  • 不需要运行时更换行为树 XML。
  • 希望减少 BT 插件、黑板和 Behavior Server 的集成成本。
  • 愿意用 C++ 状态机明确维护每一条异常分支。

11.2 不适用场景 ​

  • 需要大量任务级行为动态组合。
  • 需要到点拍照、等待、充电等 Waypoint Task Executor。
  • 需要 Spin、BackUp 等完整恢复动作轮换。
  • 产品侧频繁调整导航策略，但不希望重新编译 C++。

取消行为树并不会自动让系统更简单。它只是把复杂度从 XML、Tick 和黑板，转移到了状态、异步回调、取消语义和恢复边界。

真正可靠的自研规控层，至少必须回答四个问题：

text
当前任务属于谁？
旧回调为什么不能覆盖新任务？
定位异常时怎样保证停车？
每一种失败最终怎样收口？

nav2_regulated_modules 的核心价值，不是“少启动了几个节点”，而是把这四个问题写成了可以逐行审计的确定性代码。

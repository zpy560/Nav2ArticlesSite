一个目标点要闯过多少关？逐函数拆解 Nav2 Planner Server 的 21 段数据流 ​

给 Nav2 一个目标点，真正负责“算路”的并不是 planner_server 本身。

nav2_planner 更像一座全局规划调度中心：它管理 Global Costmap 和 Lifecycle，接收单目标或多目标 Action，把位姿转换到统一坐标系，选择已经加载的 GlobalPlanner 插件，再把插件返回的 nav_msgs/Path 交给上层导航流程。

这篇文章基于当前工程中的 nav2_planner 1.1.20、现用 regulated_modules.yaml 和本包测试代码，完整覆盖 main.cpp 与 planner_server.cpp 的 21 个生产函数。每个函数都按作用、输入、输出、回调位置、共享状态和包外调用展开，同时保留可直接落地的配置、调用、切换与排障方法。

一、先把职责边界说清楚 ​

1.1 Planner Server 负责什么 ​

Planner Server 对外提供两类路径计算 Action、一个路径有效性 Service 和一个路径可视化 Topic：

  • /compute_path_to_pose：从起点规划到单个目标。
  • /compute_path_through_poses：依次经过多个目标点。
  • /is_path_valid：检查现有路径的剩余部分是否撞上当前 Costmap 障碍。
  • /plan：发布最近一次成功路径，供 RViz 或调试节点观察。

它还负责管理规划插件的 Lifecycle，在请求进入时取得机器人当前位姿，等待 Global Costmap 更新，把起点和目标转换到 Costmap 的全局坐标系，并统一处理取消、失败、结果和耗时告警。

1.2 Planner Server 不负责什么 ​

它不实现 Dijkstra、A*、Hybrid-A*、State Lattice 或 Theta*，也不发布 cmd_vel。

真正的搜索发生在包外插件的：

cpp
nav2_core::GlobalPlanner::createPlan(start, goal)

路径跟踪由 Controller Server 完成，路径平滑由 Smoother Server 完成，周期重规划由行为树或本工程的 regulated_navigator 调度。expected_planner_frequency 不会在 Planner Server 内创建重规划定时器。

1.3 一次请求的完整数据流 ​

text
BT／Simple Commander／自研 Navigator
                ↓ Action Goal
         Planner Server
                ↓ 等待 Costmap current
        Robot Pose／请求起点
                ↓ TF 到 global_frame
      已加载 GlobalPlanner 插件
                ↓ createPlan()
           nav_msgs/Path
          ↙              ↘
 Action Result          /plan

理解这个边界后，规划失败就可以分成接口、Lifecycle、TF、Costmap、插件选择和算法结果几个层面，而不是把所有问题都归结为“A* 算不出来”。

二、运行前必须满足的四个条件 ​

2.1 Planner Server 必须处于 active ​

PlannerServer 继承 nav2_util::LifecycleNode。进程存在不等于服务可用，只有节点进入 active，两个 Action Server、/plan Publisher、Global Costmap、规划插件和 /is_path_valid Service 才真正工作。

检查状态：

bash
ros2 lifecycle get /planner_server

正常结果应为：

text
active [3]

如果还是 unconfigured 或 inactive，先检查 Lifecycle Manager 的 node_names 是否包含 planner_server，以及 autostart 是否开启。

2.2 Global Costmap 必须能够持续更新 ​

Planner Server 自己创建名为 global_costmap 的 Costmap2DROS。它依赖静态地图、传感器层、机器人 Footprint 和 TF。

Action 回调在计算前调用 waitForCostmap()，以 100 Hz 轮询 costmap_ros_->isCurrent()。当前实现没有超时，所以地图或传感器时间戳异常时，请求可能一直停在等待阶段。

2.3 TF 必须能把请求位姿变到全局坐标系 ​

当 use_start=false 时，Planner Server 需要从 Costmap 获取机器人位姿。随后起点和目标都会通过 transformPoseToGlobalFrame() 转到 Global Costmap 的 global_frame，本工程通常为 map。

常用检查：

bash
ros2 run tf2_ros tf2_echo map base_link

如果目标使用 odom、base_link 或其他 Frame，还必须保证该 Frame 到 map 的变换在目标时间戳处可用。

2.4 至少一个规划插件必须成功配置 ​

on_configure() 按 planner_plugins 读取每个 <planner_id>.plugin，通过 pluginlib 创建实例，并调用插件的 configure()。

插件类型拼写错误、库未安装或插件配置抛出异常，都会让 Planner Server 配置失败，节点无法进入 active。

三、如何正确配置规划插件 ​

3.1 planner_plugins 是实例清单 ​

当前工程一次加载六个规划器实例：

yaml
planner_server:
  ros__parameters:
    expected_planner_frequency: 20.0
    use_sim_time: false
    selected_planner: "GridBasedAstar"
    planner_plugins:
      - "GridBased"
      - "GridBasedAstar"
      - "Smac2D"
      - "SmacHybrid"
      - "SmacLattice"
      - "ThetaStar"

列表里的字符串是实例 ID，不是 C++ 类型。Action 的 planner_id、selected_planner 和插件参数前缀都使用这个 ID。

3.2 <planner_id>.plugin 决定实现类型 ​

同一种 C++ 插件可以创建多个配置实例。当前 GridBased 和 GridBasedAstar 都使用 NavFn，只靠 use_astar 区分搜索方式：

yaml
GridBased:
  plugin: "nav2_navfn_planner/NavfnPlanner"
  tolerance: 0.5
  use_astar: false
  allow_unknown: true

GridBasedAstar:
  plugin: "nav2_navfn_planner/NavfnPlanner"
  tolerance: 0.5
  use_astar: true
  allow_unknown: true

因此，“插件 ID”和“插件 Type”必须分开理解：ID 是一次配置实例的名字，Type 是 pluginlib 要创建的类。

3.3 六个实例分别适合什么场景 ​

  • GridBased：NavFn Dijkstra，势场传播完整，适合做稳定基线。
  • GridBasedAstar：NavFn A*，通常扩展更少，本工程当前默认强制选择它。
  • Smac2D：二维代价感知 A*，可把 Costmap 代价更明显地写入路径选择。
  • SmacHybrid：状态包含位置和航向，适合存在最小转弯半径的车辆。
  • SmacLattice：使用预生成运动基元，适合把底盘可执行运动直接放入搜索空间。
  • ThetaStar：允许任意角连接，适合减少传统栅格路径的折线感。

算法选择没有脱离 Costmap 参数的“绝对最优”。相同插件在不同 Inflation、Footprint、未知空间策略和目标容差下，也会得到完全不同的路径。

3.4 selected_planner 与 planner_id 的优先级 ​

当前源码最终使用：

cpp
const std::string requested_planner_id =
  selected_planner_id_.empty() ? planner_id : selected_planner_id_;

所以：

text
selected_planner 非空
  → 服务器强制使用 selected_planner

selected_planner 为空
  → 每个 Action Goal 的 planner_id 生效

现用配置是：

yaml
selected_planner: "GridBasedAstar"

即使客户端请求 SmacHybrid，服务器仍会使用 GridBasedAstar。要做多算法 A／B 对比，应先把 selected_planner 设为空，再分别发送不同 planner_id。

四、推荐启动方式与接口检查 ​

4.1 通过完整 Bringup 启动 ​

Planner Server 强依赖地图、TF、Costmap 和 Lifecycle。最稳妥的方式是通过已经配置好的 Bringup 启动，而不是只运行一个裸进程。

当前工程可使用：

bash
source /path/to/nav2_demo/nav2_ws/install/setup.bash

ros2 launch nav2_regulated_modules regulated_modules.launch.py \
  use_rviz:=False \
  use_sim_time:=false

如果使用外部地图和参数：

bash
ros2 launch nav2_regulated_modules regulated_modules.launch.py \
  map:=/absolute/path/to/map.yaml \
  params_file:=/absolute/path/to/regulated_modules.yaml \
  use_rviz:=False \
  use_sim_time:=false

4.2 裸进程为什么经常“启动了却不能规划” ​

下面的命令只创建 Lifecycle 节点进程：

bash
ros2 run nav2_planner planner_server \
  --ros-args \
  --params-file /absolute/path/to/nav2_params.yaml

它还需要完整的 global_costmap 参数、地图输入、TF 和 Lifecycle 切换。若没有 Lifecycle Manager，可手动执行：

bash
ros2 lifecycle set /planner_server configure
ros2 lifecycle set /planner_server activate

手动激活只改变状态，不会替你补齐缺失的地图、传感器或 TF。

4.3 启动后检查哪些接口 ​

bash
ros2 action list -t | grep compute_path
ros2 service list -t | grep is_path_valid
ros2 topic info /plan
ros2 param get /planner_server planner_plugins
ros2 param get /planner_server selected_planner

也可以直接核对消息定义：

bash
ros2 interface show nav2_msgs/action/ComputePathToPose
ros2 interface show nav2_msgs/action/ComputePathThroughPoses
ros2 interface show nav2_msgs/srv/IsPathValid

五、单目标规划如何调用 ​

5.1 让服务器自动使用机器人当前位置 ​

use_start=false 时，请求中的 start 被忽略，Planner Server 通过 Global Costmap 获取当前机器人位姿。

bash
ros2 action send_goal \
  /compute_path_to_pose \
  nav2_msgs/action/ComputePathToPose \
  "{
    goal: {
      header: {frame_id: map},
      pose: {
        position: {x: 2.0, y: 1.0, z: 0.0},
        orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
      }
    },
    planner_id: GridBasedAstar,
    use_start: false
  }"

这种模式适合真实导航，因为路径从机器人当前实际位置开始。

5.2 使用显式起点做离线规划 ​

use_start=true 时，服务器使用 Goal 内的 start。这适合地图选点、算法对比和不依赖机器人当前位置的路径查询。

bash
ros2 action send_goal \
  /compute_path_to_pose \
  nav2_msgs/action/ComputePathToPose \
  "{
    start: {
      header: {frame_id: map},
      pose: {
        position: {x: 0.0, y: 0.0, z: 0.0},
        orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
      }
    },
    goal: {
      header: {frame_id: map},
      pose: {
        position: {x: 2.0, y: 1.0, z: 0.0},
        orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
      }
    },
    planner_id: Smac2D,
    use_start: true
  }"

若 selected_planner 仍为 GridBasedAstar，这里填写的 Smac2D 不会真正生效。

5.3 Result 里有什么 ​

ComputePathToPose 没有 Feedback 字段。成功 Result 只包含：

  • path：插件返回的 nav_msgs/Path。
  • planning_time：从 Action 回调开始到结果收口的总耗时。

这个耗时包含等待 Costmap、获取位姿、TF 转换和插件计算，不是纯搜索算法耗时。

六、多目标规划如何调用 ​

6.1 一次发送多个途经点 ​

bash
ros2 action send_goal \
  /compute_path_through_poses \
  nav2_msgs/action/ComputePathThroughPoses \
  "{
    goals: [
      {
        header: {frame_id: map},
        pose: {
          position: {x: 1.0, y: 0.5, z: 0.0},
          orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
        }
      },
      {
        header: {frame_id: map},
        pose: {
          position: {x: 2.0, y: 1.0, z: 0.0},
          orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
        }
      }
    ],
    planner_id: GridBasedAstar,
    use_start: false
  }"

6.2 多目标不是一次联合搜索 ​

当前 computePlanThroughPoses() 会逐段调用同一个 getPlan()：

text
机器人或显式起点
  → goals[0]
  → goals[1]
  → goals[2]
  → 拼接 Path

后续段起点取上一段实际 Path 的最后 Pose，而不是机械地使用上一个请求目标。这样可以兼容规划插件的目标容差：插件即使停在目标附近，下一段也能从真实终点继续。

6.3 拼接结果的两个边界 ​

各段 Path 的 poses 被直接追加，相邻分段的共同端点可能重复，Planner Server 不做去重。

另外，空 goals 在当前源码中虽然会调用 terminate_current()，但没有立即 return。客户端应在发送前保证数组非空，不要依赖服务器替空请求完成干净收口。

七、Planner Server 内部怎样完成一次规划 ​

7.1 Action 状态与取消检查 ​

回调先确认 Action Server 已激活，再检查取消请求。取消被发现时调用 terminate_all()，结束当前及挂起 Goal。

7.2 等待 Global Costmap current ​

waitForCostmap() 会一直等待。当前循环没有超时、没有 rclcpp::ok() 条件，也不在循环内重新检查取消。

这意味着“Action 已发出但长时间没有结果”时，优先检查 Costmap 是否 current，而不是立刻怀疑规划算法。

7.3 取得起点并统一坐标系 ​

服务器根据 use_start 选择显式起点或机器人当前位姿，再把起点和目标都转换到 Global Costmap Frame。

任一 Pose 转换失败，Action 直接终止，规划插件不会被调用。

7.4 选择插件并调用 createPlan() ​

getPlan() 先计算最终 Planner ID，再在 planners_ 中查找实例，最后调用包外插件：

cpp
return planners_[requested_planner_id]->createPlan(start, goal);

插件抛出的标准异常会被 Action 回调捕获并终止当前 Goal。

7.5 验证、发布并返回 ​

validatePath() 只检查 path.poses 是否为空。非空后，服务器可选发布 /plan，填写 planning_time，再把 Action 标记为成功。

因此，“Action 成功”只说明插件给出了非空 Path，不代表服务器已经逐点做过完整碰撞检查。

八、Planner ID 的回退逻辑 ​

8.1 多插件场景 ​

加载多个插件时，最终 Planner ID 必须命中 planners_。无效 ID 会记录错误，返回空 Path，随后 Action 因 validatePath() 失败而终止。

8.2 单插件场景 ​

只加载一个插件时，空 ID 会回退到唯一插件；错误 ID 也会回退到唯一插件，并输出一次警告。

这种兼容逻辑方便最小配置，却可能掩盖客户端拼写错误。生产系统即使只有一个插件，也建议统一使用明确、可校验的 ID。

8.3 如何确认真正生效的 Planner ​

同时检查服务器强制值和请求值：

bash
ros2 param get /planner_server selected_planner
ros2 param get /planner_server planner_plugins

若 selected_planner 非空，以它为准。若为空，再检查 Action Goal 的 planner_id。

日志中的：

text
Action requested planner ..., but selected_planner is ...

表示请求值已被服务器配置覆盖。

九、/plan Topic 应该怎样理解 ​

9.1 它是观测输出，不是规划接口 ​

publishPlan() 只有在 Lifecycle Publisher 已激活且至少存在一个订阅者时才真正发布。

bash
ros2 topic echo /plan --once

没有订阅者不会影响 Action Result，发布失败也不是规划失败的判据。上层导航应该读取 Action Result，而不是依赖 /plan 接收路径。

9.2 它不是固定频率 Topic ​

Planner Server 不会按 expected_planner_frequency 周期发布路径。只有外部调度器再次发送规划 Action，才会产生新路径。

因此：

bash
ros2 topic hz /plan

看到低频或无连续频率并不一定异常，它只反映外部重规划请求的节奏。

十、如何使用 /is_path_valid ​

10.1 Service 的输入输出 ​

请求是完整 nav_msgs/Path，响应包含：

  • is_valid：路径剩余部分是否避开当前致命障碍。
  • invalid_pose_indices：接口预留的无效点索引。

查看接口：

bash
ros2 interface show nav2_msgs/srv/IsPathValid

10.2 检查从机器人最近点开始 ​

服务先取得机器人当前 Pose，寻找整条 Path 中欧氏距离最近的点，只检查该点到终点。已经驶过的路径即使后来被障碍占据，也不会让剩余路径被判无效。

圆形机器人直接读取路径点所在 Costmap Cell；非圆形 Footprint 调用 FootprintCollisionChecker，按每个 Pose 的位置和航向检查占用。

10.3 当前实现的使用边界 ​

当前代码不会填充 invalid_pose_indices，调用方只能可靠使用 is_valid。

服务假定 Path Pose 已经处于 Costmap 世界坐标系，不会逐点做 TF 转换。传入其他 Frame 的路径可能得到错误结论。

如果获取机器人 Pose 失败，response->is_valid 会保留初始化的 true。安全关键调用方应先独立确认定位和 TF 正常，不能把一次 true 直接当成完整安全证明。

十一、运行时怎样切换 Planner ​

11.1 在已加载插件之间切换 ​

节点处于 active 时，可以修改：

bash
ros2 param set /planner_server selected_planner Smac2D

成功后，后续单目标和多目标请求都会优先使用 Smac2D。

恢复由 Action Goal 自主选择：

bash
ros2 param set /planner_server selected_planner "''"

再核对：

bash
ros2 param get /planner_server selected_planner

11.2 修改耗时告警阈值 ​

bash
ros2 param set /planner_server expected_planner_frequency 5.0

服务器把它换算成：

text
max_planner_duration = 1 / 5.0 = 0.2 s

单次 Action 总耗时超过 0.2 s 时输出告警。设为零或负值会关闭这类告警，但参数更新仍返回成功。

11.3 哪些配置不能真正热加载 ​

planner_plugins 和 <planner_id>.plugin 只在 on_configure() 中用于创建 planners_。运行期修改参数存储，不会创建、配置或激活新插件。

要增加、删除或更换插件 Type，需要让节点完成：

text
deactivate
  → cleanup
  → 修改参数
  → configure
  → activate

仅执行 deactivate／activate 不会重建插件表。

11.4 动态参数为什么可能等待很久 ​

两个规划 Action 和动态参数回调共用 dynamic_params_lock_，而且 Action 在完整规划流程期间一直持锁。

慢规划正在运行时，ros2 param set 会等待 Action 释放锁。参数命令延迟不一定是参数服务故障，也可能是当前规划仍占用互斥锁。

十二、最实用的排障路径 ​

12.1 Action 根本不存在 ​

检查节点和 Lifecycle：

bash
ros2 node list | grep planner_server
ros2 lifecycle get /planner_server
ros2 action list -t | grep compute_path

节点不存在时检查 Launch；节点存在但不 active 时检查 Lifecycle Manager、插件加载错误和 Global Costmap 配置。

12.2 Action 已接受但一直不返回 ​

重点检查 Global Costmap 数据与时间：

bash
ros2 topic echo /map --once
ros2 topic echo /global_costmap/costmap --once
ros2 run tf2_ros tf2_echo map base_link

当前 waitForCostmap() 无超时，Costmap 不 current 会让请求一直等待。

12.3 日志提示无法转换起点或目标 ​

检查请求 header.frame_id、时间戳和 TF 链。用于静态测试时可以省略时间戳，让消息使用默认零时间；真实系统应保证传感器、定位和节点时间源一致。

12.4 日志提示 Planner ID 无效 ​

bash
ros2 param get /planner_server planner_plugins
ros2 param get /planner_server selected_planner

确认 ID 大小写完全一致，并判断是否被非空 selected_planner 覆盖。修改插件清单后必须重新 configure，不能只热改参数。

12.5 Action 返回失败或空 Path ​

先区分“插件没有被调用”和“插件返回空路径”：

  • TF 失败、起点获取失败、Server inactive 时，插件不会执行。
  • Planner ID 无效或插件找不到可行路时，getPlan() 返回空 Path。
  • 插件抛异常时，Action 回调捕获异常并终止。

随后检查目标是否落在地图外、障碍内部或未知区域，机器人 Footprint 是否过大，Inflation 是否封死通道，以及插件的 tolerance、allow_unknown、最大搜索时间和运动学约束。

12.6 /plan 没消息但 Action 成功 ​

先启动订阅者再发 Goal：

bash
ros2 topic echo /plan

当前 publishPlan() 在没有订阅者时不会发布；真正可靠的路径仍在 Action Result 中。

十三、源码阅读后必须知道的实现边界 ​

13.1 抢占 Goal 没有回写调用者 ​

getPreemptedGoalIfRequested() 的 Goal shared pointer 按值传入。函数内部接受 pending Goal 后只修改本地副本，不会更新 Action 回调里的 goal 变量。当前抢占行为不能按接口名字想当然理解。

13.2 Costmap 等待缺少退出条件 ​

等待循环没有超时、取消复查或 rclcpp::ok() 条件，而且发生在完整规划锁内。Costmap 长期不 current 时，规划和动态参数更新都可能被拖住。

13.3 validatePath() 只判断非空 ​

函数名容易让人误以为它会做碰撞检查，但它只判断 path.poses.size() 是否为零。路径碰撞检查要显式调用 /is_path_valid，或依赖具体规划插件的搜索约束。

13.4 多目标空数组终止后仍继续 ​

goals.empty() 分支调用 terminate_current() 后没有立即返回。客户端应在输入侧拒绝空数组，服务端源码也应补充明确的 return。

13.5 路径有效性失败可能被误判为有效 ​

isPathValid() 获取机器人 Pose 失败时不会把结果改为 false；invalid_pose_indices 也没有填充。安全流程需要把定位健康、TF 可用和路径检查三者联合判断。

13.6 动态参数批量更新不具备成员回滚 ​

回调在遍历参数时直接修改 C++ 成员。如果同一批原子参数中的后续项被拒绝，ROS 参数存储不会提交，但此前成员副作用不会自动回滚。

运行时建议一次只改一个 Server 参数；源码层更稳妥的实现是先校验整批参数，再统一写入成员。

十四、21 个生产函数逐个拆解 ​

14.1 main()：把 Planner Server 作为独立进程运行 ​

  • 作用：完成 ROS 2 上下文初始化、日志系统初始化、节点构造、Executor 阻塞运行和退出清理，是独立可执行文件 planner_server 的进程入口。
  • 输入：操作系统传入的 argc 与 argv，其中可能包含 ROS 参数文件、命名空间、节点重命名和日志级别等 ROS 参数。
  • 输出：正常结束时返回整数 0；运行期间产生一个 PlannerServer 节点，并把节点的 base interface 交给 rclcpp::spin()。
  • 数据流与回调：函数本身不处理规划请求。spin() 持续驱动 Lifecycle、Action、Service 和参数回调，直到 ROS 上下文关闭。
  • 包外调用：rclcpp 负责进程级 ROS 初始化与事件循环；SpdlogWrapper 在 ROS 节点创建前建立文件日志，在 ROS 关闭后释放日志资源。

14.2 PlannerServer()：声明参数并搭起资源外壳 ​

  • 作用：构造名为 planner_server 的 Lifecycle 节点，准备 GlobalPlanner 插件加载器，声明规划器清单、强制选择和耗时告警参数，并创建名为 global_costmap 的 Costmap 节点外壳。
  • 输入：rclcpp::NodeOptions，允许组件容器或独立进程传入参数覆盖、命名空间和进程内通信选项。
  • 输出：构造完成的 PlannerServer 对象；成员中已有 gp_loader_、planner_ids_ 和 costmap_ros_，但插件、Action、Publisher 与 Costmap 数据还没有进入可用状态。
  • 数据流与回调：这是对象创建入口，不是 Lifecycle 回调。真正的资源初始化被推迟到 on_configure()，因此“进程存在”不等于“能够规划”。
  • 包外调用：基类 nav2_util::LifecycleNode 提供 Lifecycle 能力；pluginlib::ClassLoader 只准备插件工厂；nav2_costmap_2d::Costmap2DROS 创建独立的 Global Costmap 生命周期节点。

14.3 ~PlannerServer()：为异常退出保留最后一道清理 ​

  • 作用：清空插件映射并停止 Costmap 专用线程，防止正常 deactivate／cleanup 流程没有执行时留下后台执行资源。
  • 输入：没有显式参数，输入是对象析构时仍然存活的成员状态。
  • 输出：没有返回值；副作用是销毁 planners_ 中的插件智能指针，并释放 costmap_thread_。
  • 数据流与回调：它不是 Lifecycle 回调，而是 C++ 对象生命期的兜底。正常停机仍应先走 on_deactivate() 与 on_cleanup()，让插件按协议完成各自清理。
  • 包外调用：插件对象和 nav2_util::NodeThread 都通过 RAII 析构释放，本函数不再主动调用包外业务接口。

14.4 on_configure()：一次性建立全部规划能力 ​

  • 作用：配置 Global Costmap，取得 Costmap 裸指针和 TF Buffer，按 planner_plugins 创建并配置每个 GlobalPlanner 插件，创建 /plan Publisher 和两个规划 Action Server。
  • 输入：Lifecycle 状态参数在当前实现中未使用；真实输入来自 ROS 参数、插件库、地图配置、TF 配置和 Costmap 配置。
  • 输出：成功时返回 CallbackReturn::SUCCESS；插件实例化异常时返回 FAILURE。成功副作用包括写入 planners_、planner_types_、planner_ids_concat_、max_planner_duration_、selected_planner_id_ 与多个接口句柄。
  • 数据流与回调：Lifecycle Manager 触发该回调。函数先配置 Costmap，再启动 Costmap 的 NodeThread，随后把同一份 TF 与 Costmap 句柄交给每个规划插件，最后创建 Action 与 Publisher。
  • 包外调用：Costmap 包提供地图、机器人模型和 TF；nav2_util::get_plugin_type_param()读取 <ID>.plugin；pluginlib 创建动态库实例；每个 nav2_core::GlobalPlanner 插件接收节点、实例 ID、TF 和 Costmap。

14.5 on_activate()：把已配置资源切换为可服务状态 ​

  • 作用：激活 Path Publisher、两个 Action Server、Global Costmap 和所有规划插件，并创建 /is_path_valid Service、动态参数回调与 Lifecycle Bond。
  • 输入：Lifecycle 激活事件，以及 on_configure() 已经建立的全部资源。
  • 输出：返回 CallbackReturn::SUCCESS；副作用是对外接口真正可用、参数修改开始被 Server 回调拦截、Lifecycle Manager 能通过 Bond 监控节点存活。
  • 数据流与回调：Lifecycle Manager 触发激活。激活之后，规划 Goal 才会进入 computePlan() 或 computePlanThroughPoses()，参数提交才会进入 dynamicParametersCallback()。
  • 包外调用：Lifecycle Publisher 与 SimpleActionServer 完成激活；Costmap 和每个规划插件接收各自的 activate()；ROS 2 参数系统注册提交前回调；nav2_util::LifecycleNode 创建 Bond。

14.6 on_deactivate()：停止规划入口但保留已配置资源 ​

  • 作用：停用两个规划 Action、Path Publisher、Global Costmap 和全部插件，注销动态参数回调并销毁 Bond。
  • 输入：Lifecycle 停用事件，以及 active 状态中的资源句柄。
  • 输出：返回 CallbackReturn::SUCCESS；插件表、Action 对象和 Publisher 对象仍然保留，可供后续再次激活。
  • 数据流与回调：Lifecycle Manager 触发停用。函数切断新规划请求和参数热更新，但不会执行插件 cleanup()，因此它对应“暂停服务”，不是“彻底释放”。
  • 包外调用：SimpleActionServer、Lifecycle Publisher、Costmap、GlobalPlanner 插件和 Bond 分别执行停用协议。普通 ROS Service 不具备 Lifecycle 自动停用语义，当前代码也没有在这里释放 is_path_valid_service_。

14.7 on_cleanup()：拆掉 configure 阶段建立的资源 ​

  • 作用：释放两个 Action Server、Path Publisher、TF Buffer、插件表和 Costmap 线程，把 costmap_ 裸指针清空，并让 Costmap 与插件执行清理。
  • 输入：Lifecycle cleanup 事件，以及 configure 或 deactivate 状态留下的资源。
  • 输出：返回 CallbackReturn::SUCCESS；节点回到未配置状态，下一次使用前必须重新执行 on_configure()。
  • 数据流与回调：Lifecycle Manager 触发清理。资源释放顺序先清 Action、Publisher 和 TF 句柄，再清 Costmap 与插件，最后停止线程并清空裸指针。
  • 包外调用：Costmap 与每个 GlobalPlanner 插件执行 cleanup()；NodeThread 析构停止 Costmap 的独立执行器。当前函数没有显式释放 is_path_valid_service_，这是需要额外注意的生命周期边界。

14.8 on_shutdown()：记录进入最终状态 ​

  • 作用：响应 Lifecycle shutdown 事件并记录日志。
  • 输入：Lifecycle 状态对象，当前函数不读取其中字段。
  • 输出：固定返回 CallbackReturn::SUCCESS，不直接释放插件、Costmap、Action 或 Service。
  • 数据流与回调：它只标记 Lifecycle 的最终状态；实际资源释放仍依赖此前的停用／清理流程和 C++ 析构兜底。
  • 包外调用：没有规划业务调用，只使用日志设施。

14.9 isServerInactive()：Action 回调的入口守卫 ​

  • 作用：确认目标 Action Server 指针存在并处于 active，避免未配置、已停用或正在清理时继续执行规划。
  • 输入：单目标或多目标 SimpleActionServer 智能指针的引用。
  • 输出：返回布尔值；true 表示调用者应立即结束，false 表示可以继续。
  • 数据流与回调：computePlan() 和 computePlanThroughPoses() 进入 try 后首先调用它，它只读 Action Server 状态，不改变 Goal。
  • 包外调用：nav2_util::SimpleActionServer::is_server_active() 查询 Action 生命周期状态。

14.10 waitForCostmap()：在算法运行前等待地图新鲜 ​

  • 作用：以 100 Hz 轮询 Global Costmap 的 isCurrent()，确保清图恢复或传感器更新后地图重新有效。
  • 输入：没有显式参数；隐式输入是 costmap_ros_ 的 current 状态。
  • 输出：没有返回值。只有 Costmap 变为 current 后函数才结束，否则一直阻塞。
  • 数据流与回调：两个规划 Action 在检查 active 与取消之后调用它。等待时间被计入 planning_time，并且等待期间仍持有 dynamic_params_lock_。
  • 包外调用：Costmap 提供 isCurrent()；rclcpp::Rate 提供轮询节拍。当前循环没有超时、rclcpp::ok() 检查或再次检查取消请求。

14.11 isCancelRequested()：把客户端取消转换为 Action 终止 ​

  • 作用：检查规划 Goal 是否收到取消请求，收到后终止该 Action Server 管理的全部 Goal。
  • 输入：单目标或多目标 Action Server 智能指针的引用。
  • 输出：返回布尔值；取消时返回 true，并调用 terminate_all()；未取消时返回 false。
  • 数据流与回调：两个规划 Action 只在进入等待 Costmap 之前调用一次。进入 waitForCostmap() 或插件 createPlan() 后，本函数不会被周期性复查。
  • 包外调用：SimpleActionServer 提供取消状态和 Action 终止能力，ROS 2 Action 层负责把终止状态反馈给客户端。

14.12 getPreemptedGoalIfRequested()：尝试接收抢占 Goal ​

  • 作用：检查是否有 pending Goal；存在时调用 accept_pending_goal() 取得新 Goal。
  • 输入：Action Server 引用和当前 Goal 的 shared_ptr。
  • 输出：没有返回值；设计意图是让后续规划使用新 Goal。
  • 数据流与回调：两个规划 Action 在 Costmap current 后调用它。当前 Goal 参数按值传入，函数内部替换的只是局部智能指针，调用者保存的 goal 不会改变，因此抢占 Goal 实际没有进入后续规划数据流。
  • 包外调用：SimpleActionServer 管理 pending Goal 与抢占状态。本包之外的 Action 层能够接受新 Goal，但本函数的 C++ 传参方式切断了回写。

14.13 getStartPose()：在显式起点与机器人当前位置之间选择 ​

  • 作用：根据 Goal 的 use_start 决定规划起点；显式模式复制 goal->start，自动模式从 Global Costmap 获取机器人当前 Pose。
  • 输入：Action Server、Action Goal 和用于承接结果的 PoseStamped & start。
  • 输出：成功时返回 true 并写入 start；自动取位姿失败时终止当前 Goal 并返回 false。
  • 数据流与回调：它同时服务单目标和多目标 Action。输出起点还没有保证处于 global frame，随后必须交给 transformPosesToGlobalFrame()。
  • 包外调用：Costmap 通过 TF 查询机器人位姿；SimpleActionServer 在失败时负责终止当前 Action。

14.14 transformPosesToGlobalFrame()：把算法输入统一到 Costmap 坐标系 ​

  • 作用：分别把当前起点与当前目标原地转换到 Global Costmap 的 global frame。
  • 输入：Action Server，以及可写的 curr_start 与 curr_goal。
  • 输出：两次转换都成功时返回 true，两个 Pose 被原地改写；任一转换失败时终止当前 Goal 并返回 false。
  • 数据流与回调：单目标 Action 调用一次；多目标 Action 对每一段调用一次。它是 Action 消息与 GlobalPlanner 插件之间的坐标系适配层。
  • 包外调用：Costmap2DROS::transformPoseToGlobalFrame() 使用 TF Buffer 和消息时间戳完成转换；SimpleActionServer 负责失败状态。

14.15 validatePath()：只做最小的非空结果守卫 ​

  • 作用：判断插件返回的 nav_msgs::Path 是否至少包含一个 Pose。
  • 输入：Action Server、当前目标、插件返回的 Path 和用于日志的 planner_id。
  • 输出：Path 非空返回 true；Path 为空时记录目标坐标、终止当前 Goal 并返回 false。
  • 数据流与回调：它位于 getPlan() 之后、publishPlan() 之前。单目标调用一次，多目标对每一段调用一次。
  • 包外调用：只借助 SimpleActionServer 终止失败 Goal。它不会调用 Costmap 或碰撞检查器，因此函数名中的“validate”不代表完整路径安全验证。

14.16 computePlanThroughPoses()：把多个目标拆成多次插件调用 ​

  • 作用：实现 /compute_path_through_poses Action 回调，把 goals[] 拆成连续分段，对每段调用一次 getPlan()，再直接拼接全部 Pose。
  • 输入：从 action_server_poses_ 读取 goals[]、start、use_start 和 planner_id，同时读取 Costmap、TF、插件表与耗时阈值。
  • 输出：成功时返回拼接后的 Path 与从回调入口开始计算的 planning_time，同时按条件发布 /plan 并把 Action 标为成功；失败时终止当前 Goal。
  • 数据流与回调：函数全程持有 dynamic_params_lock_。首段使用请求起点或机器人 Pose，后续段使用上一段 Path 的真实末点；每段依次经过 TF、getPlan() 和非空校验。
  • 包外调用：SimpleActionServer 提供 Goal、Result 与状态；Costmap／TF 提供环境和坐标；GlobalPlanner 插件真正搜索路径；ROS 时钟计算耗时。各段直接追加，交界 Pose 可能重复。

14.17 computePlan()：单目标规划的总编排回调 ​

  • 作用：实现 /compute_path_to_pose Action 回调，把状态守卫、Costmap 等待、起点选择、TF、插件调用、Path 校验、发布、耗时和异常处理串成一次事务。
  • 输入：从 action_server_pose_ 读取 goal、start、use_start 与 planner_id，并读取共享的 Costmap、插件表、强制 Planner ID 和耗时阈值。
  • 输出：成功时返回 path 与 planning_time，发布可视化 Path 并把 Goal 标记为成功；守卫或异常失败时终止 Goal。
  • 数据流与回调：函数由 SimpleActionServer 的执行回调触发，全程持有 dynamic_params_lock_。planning_time 包含等待 Costmap、获取机器人 Pose、TF 转换和插件计算，不只是算法耗时。
  • 包外调用：Action Server 管理 Goal 状态，Costmap 和 TF 准备输入，GlobalPlanner 生成路径，Lifecycle Publisher 提供观察旁路，ROS 时钟用于耗时统计。

14.18 getPlan()：决定最终调用哪个规划插件 ​

  • 作用：在 selected_planner_id_ 与 Action planner_id 之间确定最终实例，从 planners_ 查找插件并调用 createPlan(start, goal)。
  • 输入：已经转换到 global frame 的起点、目标和 Action 请求的 Planner ID。
  • 输出：命中插件时返回该插件生成的 Path；多插件且 ID 无效时返回空 Path；只有一个插件时可对空 ID 或错误 ID自动回退到唯一实例。
  • 数据流与回调：selected_planner_id_ 非空时拥有最高优先级，会覆盖两个 Action 传入的 planner_id。返回的 Path 随后进入 validatePath()。
  • 包外调用：nav2_core::GlobalPlanner::createPlan() 是本包与具体 NavFn、Smac 或 Theta* 算法的统一边界。算法内部怎样搜索不在本包展开，本函数只负责实例选择和调用。

14.19 publishPlan()：把结果复制到可视化旁路 ​

  • 作用：把 Path 封装为独占消息，并在 Publisher 已激活且至少存在一个订阅者时发布 /plan。
  • 输入：成功规划得到的 nav_msgs::Path 常量引用。
  • 输出：没有返回值；可能产生一次 Topic 消息，也可能因为没有订阅者而不发送。
  • 数据流与回调：单目标或多目标 Action 成功校验后调用。它不改变 Action Result，业务调用者仍应从对应 Action Result 获取 Path。
  • 包外调用：ROS 2 Lifecycle Publisher 管理 active 状态、订阅计数和消息发布；RViz 或调试节点通常是订阅者。

14.20 isPathValid()：检查机器人前方的剩余 Path ​

  • 作用：实现 /is_path_valid Service，先找机器人当前位置最近的 Path 点，再从该点向终点检查每个 Pose 是否与当前 Costmap 冲突。
  • 输入：Request 中的完整 Path，以及共享的机器人 Pose、Costmap、圆形／多边形机器人模型和 Path Pose 航向。
  • 输出：Response 的 is_valid；空 Path 或检测到致命冲突时为 false，全部通过时为 true。接口定义中的 invalid_pose_indices 当前没有填写。
  • 数据流与回调：普通 ROS Service 请求直接触发。圆形模型读取 Pose 所在 Cell 的代价值，多边形模型调用 Footprint 碰撞检查；已经驶过的 Path 前缀不再检查。
  • 包外调用：Costmap 提供机器人 Pose、地图互斥锁、世界坐标转栅格和 Cell cost；TF2 从四元数提取航向；FootprintCollisionChecker 计算多边形轮廓覆盖代价。当前没有逐点转换 Path frame，机器人 Pose 获取失败时响应会保留初始 true。

14.21 dynamicParametersCallback()：在参数提交前更新运行成员 ​

  • 作用：处理运行期参数批次，把 expected_planner_frequency 转换为单次规划耗时阈值，并校验／更新 selected_planner。
  • 输入：ROS 2 参数系统提交的 std::vector<rclcpp::Parameter>，其中只识别目标名称和匹配类型。
  • 输出：返回 SetParametersResult。Planner ID 合法或清空时返回成功；非空 ID 未出现在 planners_ 时拒绝整批提交并给出原因。
  • 数据流与回调：只在 active 阶段注册。它与两个规划 Action 共用 dynamic_params_lock_，因此参数更新不会与一次规划并发改写成员，但慢规划、Costmap 永久等待或插件阻塞也会拖住参数服务。
  • 包外调用：ROS 2 参数系统把返回值当作提交前票决。插件表不会因为参数变化而重建；本函数只在 configure 阶段已加载的实例之间切换。批次遍历中先写成员、后遇到非法参数时，ROS 参数存储会拒绝提交，但已经发生的成员写入不会自动回滚。

十五、把 Planner Server 用稳的配置原则 ​

15.1 先建立单插件基线 ​

调试新地图时，先只加载一个熟悉的二维规划器，确认地图、TF、Footprint、Inflation 和 Action 链路正确，再增加 Hybrid、Lattice 或 Theta*。这样能避免接口问题与算法问题互相干扰。

15.2 多算法测试时清空强制选择 ​

要比较 Action 中不同 planner_id，必须保证 selected_planner 为空。否则所有请求都被服务器强制到同一个插件，测试结果看似来自多种算法，实际只跑了一种。

15.3 把耗时告警与重规划频率分开配置 ​

expected_planner_frequency 只定义“单次规划多慢算超时告警”。真正的 replan_frequency 应配置在行为树或上层 Navigator。

本工程当前 expected_planner_frequency=20.0，对应 0.05 s 告警阈值；而 regulated_navigator.replan_frequency=1.0，表示控制期间每秒发起一次后台重规划。两者不是同一个频率。

15.4 用 Action Result 做业务输入 ​

/plan 是可视化旁路，Action Result 才是请求与结果一一对应的数据。上层要记录规划耗时、Planner ID、目标和 Path，才能在失败时还原一次完整请求。

15.5 结论 ​

nav2_planner 的价值不在于“又实现了一套 A*”，而在于把 Lifecycle、Global Costmap、TF、插件、Action、Service 和结果状态收敛成统一运行时。

真正用好它，需要同时回答几个问题：节点是否 active，Costmap 是否 current，TF 是否完整，最终 Planner ID 到底是谁，插件是否已经在 configure 阶段装载，Path 是空还是异常，以及上层是否真的在发起重规划。

把这些边界理顺后，切换算法、做 A／B 对比、定位规划卡住和解释路径差异，都会从“盲调参数”变成可验证的数据流排查。

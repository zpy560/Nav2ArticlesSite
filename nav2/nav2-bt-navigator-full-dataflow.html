一条导航目标如何指挥整套 Nav2？拆解 nav2_bt_navigator 全数据流 ​

向 RViz 发送一个导航目标后，全局规划、路径跟踪、代价地图清理、原地旋转和失败重试看似是一条自动运转的链路。但这些模块并不知道“导航任务”的全局进度，真正把它们组织成一个完整任务的是 nav2_bt_navigator。

bt_navigator 不计算路径，也不生成速度。它是 Nav2 的任务编排中枢：对外提供导航 Action，对内加载 XML 行为树，通过 blackboard 在树节点间传递目标和路径，再用 Action 或 Service 调用 planner、controller、costmap 和 behavior server。

本文按照真实数据流，从节点启动一直拆到结果返回。

一、bt_navigator 在 Nav2 中站在哪里 ​

navigation_launch.py 会以独立进程或 Component 方式启动 bt_navigator，并把它交给 lifecycle_manager_navigation 管理。因此它不是一启动就立即接任务，而是先经过 configure 和 activate。

1.1 构造阶段 ​

构造阶段声明默认参数和 49 个 BT 插件库。这些库覆盖四类能力。

1.1.1 Action 节点 ​

例如 ComputePathToPose、FollowPath、Spin、Wait 和 BackUp。

1.1.2 Condition 节点 ​

例如 GoalUpdated、GoalReached、IsStuck 和 IsPathValid。

1.1.3 Control 节点 ​

例如 RecoveryNode、PipelineSequence 和 RoundRobin。

1.1.4 Decorator 节点 ​

例如 RateController、DistanceController 和 SpeedController。

1.2 Configure 阶段 ​

Configure 阶段创建 TF Buffer、TransformListener 和 OdomSmoother，然后配置两个导航器：

text
NavigateToPoseNavigator
  → /navigate_to_pose

NavigateThroughPosesNavigator
  → /navigate_through_poses

两者各有一个 BtActionServer、一棵行为树和一份 blackboard，但共享 TF、平滑里程计和 NavigatorMuxer。这个 muxer 保证同一时刻只有一种导航任务在运行，避免单目标和多目标任务同时指挥底层服务器。

1.3 Activate 阶段 ​

Activate 阶段加载默认 XML，激活两个 Action Server，并与 lifecycle manager 建立 bond。到这一步，节点才真正进入可接收任务的 ACTIVE 状态。

二、导航目标如何进入行为树 ​

bt_navigator 有三种常见入口：单目标 Action、多目标 Action，以及 RViz 使用的 goal_pose topic。

2.1 Action 入口 ​

Action 客户端可以直接发送 NavigateToPose 或 NavigateThroughPoses。单目标消息包含一个 PoseStamped 和可选的 behavior_tree 文件路径；多目标消息则包含一组 PoseStamped 和可选 XML 路径。

2.2 RViz goal_pose 入口 ​

RViz 发布 goal_pose 时，NavigateToPoseNavigator 不会绕开 Action 机制直接改行为树。它会把 topic 消息封装成 NavigateToPose::Goal，再通过自己的 Action Client 发给 /navigate_to_pose。因此来自 RViz 和来自调度系统的单目标，最终走的是同一条执行链。

2.3 写入 Blackboard ​

目标通过 muxer 检查后，导航器把任务数据写入 blackboard：

text
单目标：blackboard["goal"]  = PoseStamped
多目标：blackboard["goals"] = PoseStamped[]
共享路径：blackboard["path"]  = nav_msgs/Path

每个新任务还会清零 number_recoveries，记录开始时间，并根据 Goal 中的 behavior_tree 字段决定使用默认 XML 还是任务指定 XML。

三、XML 为什么能变成可执行的 ROS 2 流程 ​

XML 只是树结构的文本描述。真正让 <ComputePathToPose> 这样的标签具备 ROS 2 能力的，是 nav2_behavior_tree::BehaviorTreeEngine 和动态插件库。

3.1 加载并注册 BT 插件 ​

BehaviorTreeEngine 构造时逐个加载 plugin_lib_names，每个动态库通过 BT_REGISTER_NODES 向 BehaviorTreeFactory 注册自己的标签名和节点构造方法。

3.2 解析 XML 并创建节点 ​

当 BtActionServer 读取 XML 后，createTreeFromText() 按标签找到已注册类型，创建真实节点对象，再把同一份 blackboard 交给它们。blackboard 中不只有目标和路径，还包含：

text
node                     BT 节点共用的 ROS 2 Client Node
tf_buffer                当前位姿查询
odom_smoother            平滑后的机器人速度
server_timeout           单次 Action / Service 等待超时
bt_loop_duration         BT 主循环周期
wait_for_service_timeout 等待底层服务就绪的超时
number_recoveries        已执行恢复动作次数

3.3 周期 Tick 行为树 ​

当前参数中 bt_loop_duration=10 ms，表示行为树决策主循环最快约以 100 Hz 调用 tickRoot()。这不等于全局规划也以 100 Hz 运行，因为 XML 中的 RateController 还会对规划分支单独限频。

3.4 判断是否重新加载 XML ​

同一 XML 已加载且 always_reload_bt_xml=false 时，新任务会复用当前树；传入不同 XML，或显式开启 always reload，才会重新解析和构建。

四、单目标如何变成路径跟踪任务 ​

4.1 加载默认单目标主链 ​

默认单目标行为树是 navigate_to_pose_w_replanning_and_recovery.xml。主链由 RecoveryNode → PipelineSequence → RateController → ComputePathToPose → FollowPath 组成。

4.2 调用 Planner Server ​

每次规划时，ComputePathToPose 从 blackboard[goal] 取出目标，组装 nav2_msgs/action/ComputePathToPose Goal，发给 planner server 的 /compute_path_to_pose。

默认 XML 传入 planner_id="GridBased"。当前项目又在 planner server 中增加了 selected_planner：如果该参数非空，planner server 会优先使用它，因此实际插件可以由服务端统一覆盖 XML 中的 GridBased。

4.3 写入 Path 并调用 Controller Server ​

规划成功后，ComputePathToPose 把返回的 nav_msgs/Path 写入 blackboard[path]。FollowPath 在下一分支读取该路径，发送 nav2_msgs/action/FollowPath 给 controller server。

4.4 选择 Controller 插件 ​

默认 XML 把 controller_id 留空。本项目的 FollowPathAction 在发现 ID 为空时，会读取 bt_navigator.selected_controller。因此实车参数可选 DWB，仿真参数可选 TEB，而不需要修改默认 XML。

4.5 PipelineSequence 周期重规划 ​

PipelineSequence 是这条数据流的关键。普通 Sequence 进入后一个 RUNNING 子节点后，不会继续 tick 前面已成功的节点；PipelineSequence 则会在 FollowPath 跟踪当前路径时，继续回头 tick 规划分支。RateController hz="1.0" 将重规划限制为 1 Hz，新 Path 写入 blackboard 后，FollowPath 检测到路径变化并更新正在执行的 controller Goal。

五、多目标导航不是简单循环单目标 ​

默认多目标树是 navigate_through_poses_w_replanning_and_recovery.xml。它与单目标共享控制和恢复框架，但规划分支不同。

5.1 移除已经经过的目标 ​

它先用 RemovePassedGoals radius="0.7" 删除已经经过的目标点，再把剩余序列写回 blackboard[goals]。随后 ComputePathThroughPoses 一次性把剩余目标交给 /compute_path_through_poses，生成一条贯穿多个目标的全局 Path。

5.2 限制多目标重规划频率 ​

多目标树的 RateController 是 0.333 Hz，约每 3 秒重规划一次。它比单目标的 1 Hz 更低，可以避免较长的多段路径过于频繁地重算。

5.3 保持连续的多目标任务 ​

这种设计与 waypoint follower 的“一个点完成后再发下一个单目标”不同。NavigateThroughPoses 保持一个连续 Action，让 planner 同时看到剩余目标序列，也让反馈中能持续返回 number_of_poses_remaining。

六、规划或控制失败后，行为树如何分层恢复 ​

默认树不会一遇到错误就立即判定导航失败。它有两层恢复。

6.1 上下文恢复 ​

ComputePathToPose 或 ComputePathThroughPoses 失败时，先调用 global_costmap/clear_entirely_global_costmap，再重试一次规划。FollowPath 失败时，先清理 local costmap，再重试跟踪。

6.2 系统级恢复 ​

上下文恢复仍失败后，顶层 RecoveryNode 进入 RecoveryFallback。它先检查 GoalUpdated；如果上层已经换了目标，就不必继续恢复旧任务。否则 RoundRobin 按顺序尝试：

text
清理 local + global costmap
  → Spin 1.57 rad
  → Wait 5 s
  → BackUp 0.30 m，0.05 m/s

一个恢复动作成功后，树回到主导航分支重试。顶层 number_of_retries="6"，表示默认树最多允许 6 轮系统级恢复；超过后整棵树返回 FAILURE。

七、反馈、抢占、取消和最终结果如何回到上层 ​

7.1 生成 Action Feedback ​

每轮 tickRoot() 后，BtActionServer 调用导航器的 onLoop() 生成 Action Feedback。单目标和多目标反馈都包含：

text
current_pose
navigation_time
estimated_time_remaining
number_of_recoveries
distance_remaining

多目标反馈还包含 number_of_poses_remaining。

7.2 计算剩余距离与时间 ​

当前位姿来自 global_frame → robot_base_frame TF。剩余距离不是直线距离，而是先在 blackboard[path] 中找到最靠近当前位姿的路径点，再累加该点到路径末端的长度。预计剩余时间由这个距离除以 OdomSmoother 给出的当前线速度；只有速度大于 0.01 m/s 且剩余距离大于 0.1 m 时才会计算。

7.3 处理任务抢占 ​

抢占不是无条件换树。待处理目标与当前任务使用同一 XML 时，导航器可以直接接受 pending goal，更新 goal 或 goals blackboard，让当前树继续运行。如果新目标要求不同 XML，则拒绝真抢占；上层应先取消旧任务，再发送新任务。

7.4 传播取消与停止信号 ​

取消、Action Server 失活或 ROS 关闭时，BehaviorTreeEngine 调用 halt() 向整棵树传播停止信号。所有仍处于 RUNNING 的 Action 节点都必须被终止，否则上层已经显示“已取消”，底层 controller 或 recovery 仍可能继续运动机器人。

7.5 返回最终结果 ​

树根最终返回 SUCCESS、FAILURE 或收到取消后，BtActionServer 把它转换为 SUCCEEDED、FAILED 或 CANCELED Action 结果，停止所有残留节点，最后通过 NavigatorMuxer 释放导航占用状态。到这里，一个导航任务才算完整结束。

八、完整数据流可以压缩成一条链 ​

text
RViz / 调度系统
  → NavigateToPose / NavigateThroughPoses
  → NavigatorMuxer 互斥检查
  → 目标写入 blackboard
  → 加载默认或任务指定 XML
  → BehaviorTreeEngine 周期 tickRoot()
  → ComputePath Action 调用 planner_server
  → Path 写回 blackboard
  → FollowPath Action 调用 controller_server
  → 失败时调用 costmap Service 和 behavior server
  → TF + /odom + Path 组合成 Action Feedback
  → SUCCEEDED / FAILED / CANCELED 返回上层

这条链里，blackboard 是数据中心，XML 是流程规则，BT 插件是 ROS 2 适配层，BehaviorTreeEngine 是状态推进器，而 BtActionServer 则负责把整棵树包装成标准导航 Action。

九、调试 bt_navigator 时最该查什么 ​

9.1 检查 Action 入口 ​

确认 /navigate_to_pose 或 /navigate_through_poses 有活动服务端，并检查 Goal 中的 frame_id、时间戳和 behavior_tree 路径。

9.2 检查 XML 与插件是否匹配 ​

XML 中任何标签没有对应动态库，或端口类型不匹配，都会在 createTreeFromText() 阶段失败，任务不会进入规划。

9.3 检查 Blackboard 关键名 ​

XML 中的 {goal}、{goals} 和 {path} 必须与 goal_blackboard_id、goals_blackboard_id 和 path_blackboard_id 对应，否则节点之间传不到数据。

9.4 区分 BT Tick 频率与业务频率 ​

bt_loop_duration=10 ms 只代表决策轮询，规划频率还受 RateController、planner server 和代价地图更新频率限制。

9.5 按层排查机器人不动 ​

先看 BT 是否进入 ComputePath，再看 path 是否写回，然后看 FollowPath 是否 active，最后才看 /cmd_vel。只看速度 topic，无法区分“没收到目标”、“行为树未加载”、“规划失败”和“控制失败”。

十、核心结论 ​

nav2_bt_navigator 的价值不在于某一个算法，而在于它把导航系统从“节点集合”变成了“可描述、可替换、可恢复的任务流程”。

目标、路径和恢复计数通过 blackboard 流动；planner、controller 和 behavior server 通过 Action 被调度；XML 决定顺序、并行关系、重试次数和恢复策略；最终统一暴露为 NavigateToPose 和 NavigateThroughPoses。

所以，当需要改变 Nav2 的任务逻辑时，第一反应不应是修改 planner 或 controller，而是先判断：这是算法问题，还是行为树的数据流和恢复策略问题。

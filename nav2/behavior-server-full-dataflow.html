机器人“自救”时，数据到底怎么流？拆解 Nav2 Behavior Server 全链路 ​

规划失败后原地旋转、控制失败后短距离后退、等待障碍物离开、在遥控速度可能撞障碍物时主动限速——这些动作看起来很简单，但它们不是几段散落的速度控制代码。

在 Nav2 中，它们被组织成一套完整的行为服务系统：行为树发出 Action Goal，behavior_server 装载对应插件，插件读取 TF、局部代价地图和机器人轮廓，向前预测运动是否安全，再发布速度、反馈执行进度，最后把结果送回行为树。

本文以本项目源码 navigation2/nav2_behaviors/src/behavior_server.cpp 为入口，沿着真实代码把这条链路拆到底。

读完你会得到四个答案：

  • behavior_server.cpp 自己做什么，又刻意不做什么？
  • Spin、BackUp、DriveOnHeading、Wait、AssistedTeleop 的输入输出如何流动？
  • 代价地图、Footprint、TF 和 cmd_vel 如何形成安全闭环？
  • 取消、失败、新目标和生命周期切换时，系统怎样收尾？

一、先给结论：Behavior Server 是“行为插件容器”，不是动作算法本身 ​

BehaviorServer 的职责可以压缩为五件事：

  • 声明并读取行为相关参数。
  • 建立 TF、代价地图和 Footprint 数据入口。
  • 通过 pluginlib 动态创建行为插件。
  • 把共享的碰撞检查器交给每个插件。
  • 统一管理插件的 configure、activate、deactivate 和 cleanup。

真正的旋转、后退、直行、等待和辅助遥控算法，分别位于 Spin、BackUp、DriveOnHeading、Wait、AssistedTeleop 插件中。

它们又共同继承 TimedBehavior<ActionT>。这个模板类负责 Action Server、执行循环、取消处理、反馈与结果，以及 cmd_vel 发布器。

因此，整体结构不是“一个 Server 写死五套动作”，而是：

text
BehaviorServer
  ├── 管理生命周期与共享数据
  ├── pluginlib 装载 nav2_core::Behavior
  └── 每个插件继承 TimedBehavior<ActionT>
        ├── 通用 Action 执行框架
        └── 插件自己的 onRun() / onCycleUpdate()

源码构造函数的默认插件列表只有 spin、backup、drive_on_heading 和 wait。但本项目的 myworld2.yaml 与 nav2_params.yaml 都显式配置了 assisted_teleop，因此当前工程实际装载 5 个插件。

二、生命周期：先把数据通道接好，再允许行为接单 ​

2.1 构造阶段：只声明，不执行 ​

BehaviorServer 是名为 behavior_server 的 Lifecycle Node。构造时主要声明以下参数：

yaml
costmap_topic: local_costmap/costmap_raw
footprint_topic: local_costmap/published_footprint
cycle_frequency: 10.0
behavior_plugins: [spin, backup, drive_on_heading, wait]
global_frame: odom
robot_base_frame: base_link
transform_tolerance: 0.1

如果 behavior_plugins 仍是默认列表，构造函数还会声明 spin.plugin、backup.plugin 等插件类型参数。

注意：参数的最终值以启动时加载的 YAML 为准。本项目的两套配置都把 assisted_teleop 加入列表；实车配置使用 global_frame: map、robot_base_frame: base_link，仿真配置使用 global_frame: odom、robot_base_frame: base_footprint。

2.2 Configure 阶段：建立共享基础设施 ​

on_configure() 依次完成：

2.2.1 创建 TF Buffer 与 Transform Listener ​

创建 tf2_ros::Buffer 和 TransformListener。

2.2.2 订阅 Local Costmap ​

订阅 local_costmap/costmap_raw。

2.2.3 订阅机器人 Footprint ​

订阅 local_costmap/published_footprint。

2.2.4 创建碰撞检查器 ​

创建共享的 CostmapTopicCollisionChecker。

2.2.5 读取行为插件类型 ​

遍历 behavior_plugins，读取每个 <id>.plugin。

2.2.6 创建行为插件实例 ​

通过 plugin_loader_.createUniqueInstance() 创建插件。

2.2.7 配置行为插件 ​

调用插件的 configure()，传入节点、插件名、TF 和碰撞检查器。

插件基类是 nav2_core::Behavior。只要某个插件类型拼写错误、共享库找不到，或者插件配置抛出异常，整个 BehaviorServer 的 configure 都会失败，不会带着一半插件进入工作状态。

2.3 Activate 阶段：Action Server 才真正接单 ​

on_activate() 会激活每个插件，并创建 Lifecycle Bond。插件内部随之激活：

  • cmd_vel Lifecycle Publisher；
  • 对应的 SimpleActionServer；
  • 插件自己的订阅或其他资源。

只有节点处于 ACTIVE 状态，目标才会进入行为执行循环。

2.4 Deactivate 与 Cleanup：停止接单，再释放资源 ​

deactivate 会禁用插件的 Action Server 和速度发布器，并销毁 Bond。cleanup 则进一步清空插件实例，释放 TF、代价地图订阅器、Footprint 订阅器和碰撞检查器。

这套顺序很重要：先停止外部请求，再拆内部资源，避免行为执行到一半时依赖对象已经消失。

三、请求从哪里来：行为树把恢复动作转换成 Action Goal ​

默认的 navigate_to_pose_w_replanning_and_recovery.xml 中，系统级恢复分支是：

xml
<RoundRobin name="RecoveryActions">
  <Sequence name="ClearingActions">...</Sequence>
  <Spin spin_dist="1.57"/>
  <Wait wait_duration="5"/>
  <BackUp backup_dist="0.30" backup_speed="0.05"/>
</RoundRobin>

当规划或控制在局部恢复后仍然失败，行为树按 RoundRobin 顺序尝试清图、旋转、等待和后退。

以 Spin 为例，数据链是：

text
<Spin spin_dist="1.57"/>
  → SpinAction 读取 BT 端口
  → 构造 nav2_msgs/action/Spin Goal
  → 发送到 /spin
  → Spin 插件的 SimpleActionServer 接收
  → TimedBehavior::execute()
  → Spin::onRun() / onCycleUpdate()

5 个行为对应 5 个 Action Server：

行为插件Action 名称Goal 关键字段Feedback
Spin/spintarget_yaw、time_allowanceangular_distance_traveled
BackUp/backuptarget、speed、time_allowancedistance_traveled
DriveOnHeading/drive_on_headingtarget、speed、time_allowancedistance_traveled
Wait/waittimetime_left
AssistedTeleop/assisted_teleoptime_allowancecurrent_teleop_duration

所有结果都包含 total_elapsed_time。

Spin、Wait 和 BackUp 直接出现在默认恢复树中。DriveOnHeading 可用于直线运动或里程计标定行为树；AssistedTeleop 是独立的辅助遥控行为，并不在默认导航恢复 RoundRobin 中。

四、TimedBehavior：五个插件共用的一台执行状态机 ​

每个插件在 configure 时，TimedBehavior<ActionT> 都会创建：

text
SimpleActionServer<ActionT>(behavior_name)
LifecyclePublisher<Twist>("cmd_vel")

当 Action Goal 到达，execute() 按以下顺序工作。

4.1 确认节点仍然启用 ​

若插件没有 ACTIVE，目标不会进入动作算法。

4.2 调用一次 onRun(goal) ​

这是插件的“起跑准备”阶段，负责：

  • 校验 Goal 参数；
  • 查询初始 TF；
  • 保存起始位姿或起始角度；
  • 计算 time allowance；
  • 初始化插件状态。

onRun() 返回失败，执行直接终止，不进入周期循环。

4.3 以 cycle_frequency 循环 ​

本项目配置为 10 Hz。每一轮先检查取消和 pending goal，再调用 onCycleUpdate()。

插件返回三种内部状态：

  • RUNNING：睡眠到下一周期；
  • SUCCEEDED：填入耗时并成功结束当前 Goal；
  • FAILED：填入耗时并终止当前 Goal。

4.4 处理取消与新 Goal ​

收到取消时，框架会调用 stopRobot() 发布零 Twist，然后终止全部目标。

收到新 Goal 时，当前 Humble 版本明确记录“preemption not implemented”，同样先停车并终止当前 Goal。也就是说，这套行为 Action 不是无缝抢占模型。

这里还要区分 AssistedTeleop 的 preempt_teleop 话题：它是辅助遥控插件自己的“正常结束遥控”信号，不等于 Action Server 收到一个 pending goal。

五、碰撞检查：不是看当前位置，而是先看未来会不会撞 ​

5.1 获取碰撞检查输入 ​

共享的 CostmapTopicCollisionChecker 接收两类数据：

  • local_costmap/costmap_raw：局部代价地图快照。
  • local_costmap/published_footprint：机器人实时轮廓。

插件再通过 TF 获取机器人当前位姿，把候选速度向未来积分，得到一串预测 Pose2D。

5.2 检查每个预测位姿 ​

对每个预测位姿，碰撞检查器执行以下步骤。

5.2.1 变换机器人 Footprint ​

把机器人 Footprint 旋转、平移到预测位姿。

5.2.2 映射代价地图网格 ​

将世界坐标映射到代价地图网格。

5.2.3 计算覆盖区域代价 ​

计算 Footprint 覆盖区域的代价值。

5.2.4 判断致命障碍 ​

判断是否达到 LETHAL_OBSTACLE。

如果预测位姿落到地图之外、代价地图不可用、Footprint 不可用，检查器也按“不安全”处理。

为了减少同一轮预测中的重复复制，插件通常只在第一个预测点刷新 Costmap 和 Footprint，后续预测点复用同一份快照。这样同一条预测轨迹基于一致的数据时刻，同时降低循环开销。

5.3 Spin 的预测 ​

Spin 以当前角速度在 simulate_ahead_time 内逐步增加 yaw，检查原地旋转时的轮廓是否扫到障碍物。

5.4 DriveOnHeading 与 BackUp 的预测 ​

两者以候选线速度沿当前朝向积分 x、y，检查未来直线路径上的每个机器人轮廓。

5.5 AssistedTeleop 的预测 ​

它同时积分线速度和角速度。若第一步就碰撞，直接把速度置零；若更远处才碰撞，则按“安全时间 ÷ projection_time”缩放整条 Twist，使机器人越接近风险速度越小。

六、五个插件的数据流差异 ​

6.1 Spin：目标角度 → 已转角 → 制动角速度 ​

Spin::onRun() 先用 TF 获取起始姿态，记录目标 yaw 和允许时间。

每周期再次获取当前姿态，通过相邻 yaw 差并处理 ±π 跳变，累计真实旋转角度。剩余角度用于计算制动速度：

text
rot_vel = sqrt(2 × rotational_acc_lim × remaining_yaw)

随后把速度限制在 min_rotational_vel 与 max_rotational_vel 之间，再根据目标方向设置正负号。碰撞预测通过后，发布只有 angular.z 的 Twist。

达到目标、超时或预测碰撞时，Spin 会先发布零速，再返回成功或失败。

6.2 DriveOnHeading：目标距离 → 实际位移 → 受限线速度 ​

Goal 只允许使用 target.x，target.y 和 target.z 必须为零，而且 target 与 speed 的符号必须一致。

插件用当前位姿与起始位姿之间的欧氏距离作为 distance_traveled。候选速度由目标速度、每周期加速度、减速度和剩余制动距离共同决定。

如果 acceleration/deceleration 参数均为零，就直接使用 Goal speed；否则按周期限制速度变化，并在接近目标时减速。

6.3 BackUp：先把方向强制为负，再复用直行算法 ​

BackUp 继承 DriveOnHeading。它不重新实现周期控制，只在 onRun() 中把：

text
target.x = -abs(target.x)
speed    = -abs(speed)

然后复用 DriveOnHeading 的距离反馈、速度约束、前向预测和结果处理。

这里的“前向预测”指沿候选速度积分；当速度为负时，预测轨迹自然向机器人后方展开。

6.4 Wait：只消费时钟，不产生运动 ​

Wait 保存 now + goal.time 为结束时刻。每周期计算 time_left 并发布反馈，到零后成功返回。

它不读取 TF，不读取代价地图，也不发布运动 Twist。

6.5 AssistedTeleop：把人工速度变成碰撞约束后的速度 ​

AssistedTeleop 订阅 cmd_vel_teleop，保存最新人工速度；每周期从 TF 获取当前位姿，并在 projection_time 内按 simulation_time_step 向前投影。

输出可能是：

  • 原始遥控速度；
  • 按碰撞时间比例缩小后的速度；
  • 零速度。

达到 time allowance 会失败并停车；收到 preempt_teleop 信号会停车并成功结束。

七、输出链路：Behavior Server 的速度不经过 Velocity Smoother ​

当前 navigation_launch.py 对 Controller Server 做了如下重映射：

text
controller_server: cmd_vel → cmd_vel_nav
velocity_smoother:  cmd_vel_nav → cmd_vel

但 Behavior Server 只应用 TF remapping，没有把 cmd_vel 重映射为 cmd_vel_nav。

因此两条速度路径不同：

text
正常路径跟踪：controller_server → cmd_vel_nav → velocity_smoother → cmd_vel
恢复／行为动作：behavior_server ─────────────────────────────→ cmd_vel

这意味着 Spin、BackUp、DriveOnHeading 和 AssistedTeleop 的速度直接进入最终 cmd_vel，不会再经过当前 Nav2 Velocity Smoother。

调参和排障时不能只观察 cmd_vel_nav。如果导航恢复阶段机器人在动而 cmd_vel_nav 没有数据，这是预期现象，应同时检查 /spin、/backup 等 Action 状态和最终 /cmd_vel。

它也意味着行为插件自己的速度限制、加减速和停车分支更加关键。

八、结果如何回到行为树 ​

插件每周期通过 Action Feedback 返回进度。Behavior Tree 的 Action 节点接收后维持 RUNNING，直到收到最终结果。

常见闭环如下：

text
Spin 成功
  → /spin Action succeeded
  → BT Spin 节点返回 SUCCESS
  → RoundRobin 当前恢复动作完成
  → 外层 RecoveryNode 再次执行规划与控制

如果行为失败，BT 节点返回 FAILURE，恢复控制节点根据重试次数和 RoundRobin 状态决定尝试下一个动作，或让整次导航失败。

取消导航时，取消会从上层 Action 传播到当前 BT Action 节点，再取消具体行为 Action。TimedBehavior 收到取消后发布零速并结束目标。

九、源码审查中值得特别注意的三个边界 ​

9.1 框架的 FAILED 分支不统一补发零速 ​

TimedBehavior::execute() 在取消和不支持的抢占分支会显式调用 stopRobot()，但插件返回 FAILED 时，通用框架只终止当前 Goal，没有统一再发布一次零速。

Spin 和 DriveOnHeading 在超时、碰撞等主要失败路径会自行停车；但在周期中获取当前 TF 失败的分支，代码直接返回 FAILED，没有先调用 stopRobot()。

因此新增自定义 Behavior 时，不能假设“返回 FAILED 后框架一定停车”。所有可能在此前发布过非零速度的失败路径，都应自行检查是否需要 stopRobot()。

9.2 Costmap 和 Behavior 的 global_frame 必须一致可转换 ​

行为插件用 global_frame → robot_base_frame 获取当前姿态，碰撞检查使用订阅到的局部代价地图。

仿真配置中两者都是 odom；实车配置中两者都是 map。若修改其中一处却没有同步另一处，可能出现位姿查询成功但碰撞坐标不一致，或 TF 直接失败。

9.3 Behavior Action 不支持无缝 Goal 抢占 ​

收到 pending goal 时，当前实现会停车并终止当前目标，而不是接受新目标继续执行。上层若需要连续改变旋转角度或直行距离，应先明确取消、等待终态，再发送新 Goal。

十、排障时按这条顺序查 ​

10.1 行为插件没有出现 ​

检查：

bash
ros2 lifecycle get /behavior_server
ros2 param get /behavior_server behavior_plugins
ros2 action list | grep -E 'spin|backup|drive_on_heading|wait|assisted_teleop'

如果节点无法 configure，重点检查 <id>.plugin 类型名和 pluginlib 导出 XML。

10.2 Action 一直 RUNNING，但机器人不动 ​

检查最终输出而不是只看平滑器输入：

bash
ros2 topic echo /cmd_vel
ros2 topic hz /local_costmap/costmap_raw
ros2 topic hz /local_costmap/published_footprint

同时确认 global_frame 到 robot_base_frame 的 TF 可用。

10.3 行为一启动就报碰撞 ​

依次核对：

10.3.1 核对 Footprint ​

确认 Footprint 是否与真实车体一致。

10.3.2 核对机器人自身障碍 ​

确认局部代价地图是否把机器人自身标成障碍物。

10.3.3 核对 Costmap 范围 ​

确认当前位姿是否落在 Costmap 范围内。

10.3.4 核对预测时间 ​

确认 simulate_ahead_time 是否过大。

10.3.5 核对频率匹配 ​

确认速度、周期频率和地图更新频率是否匹配。

10.4 取消后仍观察到速度 ​

先确认速度来自哪个发布者：

bash
ros2 topic info /cmd_vel --verbose

Behavior Server 和 Velocity Smoother 都可能发布最终 cmd_vel。必须区分是行为取消未生效，还是另一条控制链仍在输出。

十一、把完整数据流压缩成一张脑图 ​

text
导航失败或独立行为请求
  → BT Action 节点构造 Goal
  → /spin /backup /drive_on_heading /wait /assisted_teleop
  → TimedBehavior::execute()
      → onRun() 校验与初始化
      → 10 Hz onCycleUpdate()
          → TF 获取当前位姿
          → 计算进度与候选速度
          → Costmap + Footprint 前向碰撞预测
          → 发布 Feedback
          → 发布 cmd_vel 或零速
      → Action Result
  → BT 收到 SUCCESS / FAILURE
  → 重试导航、切换恢复动作或结束任务

behavior_server.cpp 的价值，不是亲自计算每一个动作，而是把插件、生命周期、共享环境数据和 Action 执行框架稳定地拼在一起。

理解这条数据链之后，再定位“为什么不旋转”“为什么一后退就失败”“为什么恢复速度没经过平滑器”，就不需要在整个 Nav2 中盲找：先看 Action，再看 TF 与碰撞输入，然后看插件周期状态，最后看最终 cmd_vel。

这就是 Behavior Server 真正的系统边界。

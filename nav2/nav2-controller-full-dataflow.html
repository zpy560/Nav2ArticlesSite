一条路径如何变成速度？拆解 nav2_controller 的插件矩阵与闭环数据流 ​

全局规划器给出一条 Path，机器人却不能直接“沿线走”。真正让底盘动起来的，是一个持续重复的闭环：读取当前位姿和速度，观察局部障碍，选择控制算法，计算速度，检查是否仍在前进，再判断是否到达目标。

在 Nav2 中，这个闭环由 nav2_controller 承担。

它不是某一种局部规划算法，也不等同于 DWB、RPP 或 MPPI。更准确地说，nav2_controller 是一个具备 Lifecycle、Action、局部代价地图和插件调度能力的控制任务服务器。它把不同控制算法、进度判定和到达判定统一装进 /follow_path 这条标准接口。

本文基于当前工程中的 nav2_controller 1.1.20 源码，完整拆解它的调用关系、三层状态、插件体系，以及从路径输入到速度输出的数据流。

一、先给结论：Controller Server 是控制闭环的“运行时容器” ​

nav2_controller 的核心节点是 ControllerServer。它做六件事：

  • 对上提供 nav2_msgs/action/FollowPath Action。
  • 接收全局路径，并按 Goal 中的 ID 选择 Controller 和 Goal Checker。
  • 自己持有并运行一个 local_costmap。
  • 从 TF 获取机器人位姿，从 /odom 获取机器人速度。
  • 调用 Controller 插件计算 cmd_vel。
  • 用 Progress Checker 识别“卡住”，用 Goal Checker 判断“到达”。

所以它在导航栈中的位置不是“路径规划”，而是“路径执行”。

上游可以有多种调用者：

  • 标准 Nav2 中，行为树的 FollowPath 节点调用 /follow_path。
  • 本项目取消行为树后，RegulatedNavigator 直接作为 Action Client 调用 /follow_path。
  • nav2_simple_commander 也可以绕过完整导航编排，直接发送已知路径。

下游同样可以变化。源码发布的逻辑名称是 cmd_vel，标准 Bringup 和本项目的规控 Launch 都把它重映射为 cmd_vel_nav，再交给 Velocity Smoother 输出最终 /cmd_vel。

这说明 ControllerServer 的边界很清楚：它负责产生原始导航速度，不负责全局规划，也不负责最后一级底盘通信。

二、第一层状态：Lifecycle 决定控制能力是否存在 ​

ControllerServer 继承 nav2_util::LifecycleNode。它的资源不是在构造函数里一次性全部创建，而是跟随 ROS 2 Lifecycle 分阶段建立、激活和释放。

2.1 UNCONFIGURED：只有节点骨架 ​

构造函数完成服务器级参数声明，建立三个 Pluginlib Loader，并创建名为 local_costmap 的 Costmap2DROS 对象。

此时还不能接收 FollowPath 目标，也不会发布速度。

默认插件类型在这一阶段确定：

  • 默认 Progress Checker：nav2_controller::SimpleProgressChecker。
  • 默认 Goal Checker：nav2_controller::SimpleGoalChecker。
  • 默认 Controller：dwb_core::DWBLocalPlanner。

注意，DWB 只是默认加载类型，不是 nav2_controller 包自己导出的插件。

on_configure() 的主要调用顺序如下。

2.2.2 配置 Local Costmap ​

2.2.3 创建 Progress Checker ​

2.2.4 创建 Goal Checker ​

创建一个或多个 Goal Checker 实例。

2.2.5 创建 Controller ​

创建一个或多个 Controller 实例，并把 TF Buffer 和 Costmap2DROS 共享指针传进去。

2.2.6 创建 Odom 订阅 ​

创建 /odom 订阅。

2.2.7 创建速度发布器 ​

与 Lifecycle Manager 建立 Bond。

此时节点进入 ACTIVE，才真正具备闭环控制能力。

2.4 on_deactivate：先停任务，再停速度 ​

停用阶段会先停 Action Server，再停 Controller 插件和 local_costmap，随后发布一次零速度，最后停用速度 Publisher、移除动态参数回调并断开 Bond。

这个顺序表达了一个重要安全原则：控制能力退出前，先让正在执行的任务失效，并尝试把速度收敛到零。

2.5 on_cleanup：释放运行资源 ​

Cleanup 会清理 Controller、Goal Checker、Costmap、Action Server、Odom Subscriber、Costmap Thread、速度 Publisher 和 Speed Limit Subscriber，使节点重新回到 UNCONFIGURED。

on_shutdown() 在当前实现中只记录停机日志，不承担额外资源编排。

三、第二层状态：三类插件各自回答一个问题 ​

Controller Server 同时管理三类插件，但三类插件的职责不能混淆。

3.1 Controller：下一帧速度应该是多少？ ​

Controller 插件实现 nav2_core::Controller，核心接口包括：

  • configure()：获得父节点、插件名、TF Buffer 和 Costmap。
  • setPlan()：接收当前要执行的全局路径。
  • computeVelocityCommands()：根据当前位姿、当前速度和 Goal Checker 计算速度。
  • setSpeedLimit()：接收绝对速度或百分比限速。
  • activate()、deactivate()、cleanup()：跟随服务器生命周期。

nav2_controller 包本身没有在 plugins.xml 中导出任何 Controller 算法。DWB、RPP、MPPI、TEB 等都来自其他包，通过相同基类被 Controller Server 加载。

当前项目的 regulated_modules.yaml 一次加载五个 Controller：

  • DWB：轨迹采样并用 Critic 打分。
  • RPP：受约束纯跟踪，按曲率、障碍和接近目标状态调速。
  • MPPI：批量采样控制序列并用代价函数优化。
  • GracefulController：用平滑姿态控制律收敛到路径和目标姿态。
  • RotationShimController：先对齐路径初始方向，再委托内部主控制器跟踪。

工程的 myworld2.yaml 还加载了 TEB。这些是“Controller Server 托管的插件”，不是“本包源码实现的插件”。

3.2 Progress Checker：机器人是否在规定时间内取得进展？ ​

本包导出两个 Progress Checker。

3.2.1 SimpleProgressChecker ​

它保存一个基准位姿和基准时间。如果机器人相对基准点移动超过 required_movement_radius，就更新基准并返回成功；如果一直没有移动到要求距离，且超过 movement_time_allowance，则返回失败。

默认值分别是 0.5 m 和 10 s。

3.2.2 PoseProgressChecker ​

它继承 SimpleProgressChecker，并增加 required_movement_angle。只要平移距离或旋转角度有一个超过阈值，就认为机器人取得了进展。

这对“允许原地旋转也是有效动作”的底盘更合理，避免机器人明明正在调整航向，却被纯平移判定误认为卡死。

3.3 Goal Checker：机器人是否已经到达？ ​

本包导出三个 Goal Checker。

3.3.1 SimpleGoalChecker ​

同时检查 XY 位置误差和 Yaw 航向误差。stateful=true 时，一旦 XY 进入容差范围，后续只继续检查航向，不会因为末端旋转时位置轻微漂移而退回位置阶段。

当前源码还支持 symmetric_yaw_tolerance。启用后，对称机器人既可以匹配目标航向，也可以匹配目标航向加 180°。

3.3.2 StoppedGoalChecker ​

先复用 SimpleGoalChecker 的位置与航向判断，再额外检查平移速度和旋转速度是否低于阈值。适合“进入目标框还不算结束，必须真正停稳”的任务。

3.3.3 PositionGoalChecker ​

只检查 XY 位置，完全忽略目标朝向。stateful=true 时，一旦进入位置容差就保持到达状态。

这里还要区分两个名字：

  • Plugin ID 是参数和 Action Goal 中使用的实例名，例如 general_goal_checker、DWB。
  • Plugin Type 是 Pluginlib 加载的 C++ 类型，例如 nav2_controller::SimpleGoalChecker、dwb_core::DWBLocalPlanner。

Action 传错的是 ID 时，即使对应 Type 已经安装，Controller Server 仍会拒绝该目标。

四、输入输出接口：一条 Action 串起五类数据 ​

4.1 Action 输入：/follow_path ​

类型为 nav2_msgs/action/FollowPath。

Goal 包含：

  • path：nav_msgs/Path，要执行的路径。
  • controller_id：本次任务选择的 Controller Plugin ID。
  • goal_checker_id：本次任务选择的 Goal Checker Plugin ID。

如果只加载一个 Controller 或 Goal Checker，且 Goal 中 ID 为空，服务器会自动使用唯一实例并输出一次警告；如果加载了多个插件却不给有效 ID，目标会失败。

4.2 Action 输出：Feedback 与终态 ​

Feedback 包含：

  • distance_to_goal：从当前路径中距离机器人最近的路径点开始，累加到路径末端的剩余路径长度。
  • speed：本周期 Controller 输出指令的平面线速度模长。

这里有两个常见误解。

4.2.1 distance_to_goal 的含义 ​

distance_to_goal 不是机器人到目标点的直线距离，而是沿当前路径计算的剩余长度。

4.2.2 speed 的含义 ​

speed 来自本周期计算出的速度指令，不是 /odom 中测得的真实车速。

当前版本的 Result 负载只有一个空消息，真正的结果信息依赖 Action 终态：SUCCEEDED、ABORTED 或 CANCELED。失败原因主要从 Controller Server 日志和上层恢复逻辑获得。

4.3 Topic 输入：/odom ​

OdomSubscriber 默认订阅相对名称 odom，消息类型为 nav_msgs/Odometry。

Controller Server只取：

  • twist.twist.linear.x。
  • twist.twist.linear.y。
  • twist.twist.angular.z。

随后用 min_x_velocity_threshold、min_y_velocity_threshold 和 min_theta_velocity_threshold 把微小速度压成零，再传给 Controller 和 Goal Checker。

Odom 在这里提供的是“当前运动速度”，机器人位姿并不从 Odom 消息直接读取。

4.4 Topic 输入：speed_limit ​

默认 Topic 名称为相对名称 speed_limit，类型为 nav2_msgs/SpeedLimit。

收到消息后，Controller Server 会遍历所有已加载 Controller，逐个调用 setSpeedLimit(speed_limit, percentage)。因此限速不是只作用于当前 Controller，而是同步更新全部已加载实例，方便后续切换插件时保持一致的限速状态。

4.5 TF 与 Local Costmap 输入 ​

ControllerServer 自己持有 local_costmap。当前位姿通过 costmap_ros_->getRobotPose() 获取，Controller 插件同时得到 Costmap 和 TF Buffer 的共享指针。

因此控制闭环实际依赖：

  • TF 中从 Costmap Global Frame 到 Robot Base Frame 的可用变换。
  • Local Costmap 当前有效。
  • 障碍层、膨胀层、Footprint 等局部环境信息已经更新。

源码在每个循环开始前检查 costmap_ros_->isCurrent()。清图或传感器更新期间，如果 Costmap 还没有恢复为当前状态，控制计算会等待，而不是使用过期地图直接出速度。

4.6 Topic 输出：cmd_vel ​

源码创建 geometry_msgs/Twist 的 Lifecycle Publisher，逻辑 Topic 为 cmd_vel。

本项目把它重映射为 cmd_vel_nav，随后形成：

text
Controller Server /cmd_vel_nav
  -> Velocity Smoother /cmd_vel
  -> controlpub /control_to_uart
  -> 底盘

publishVelocity() 只有在 Publisher 已激活且至少存在一个订阅者时才真正发布。这意味着下游控制链未连接时，日志里即使完成了速度计算，也可能看不到 cmd_vel 消息。

五、核心调用链：一帧 cmd_vel 是怎样生成的 ​

/follow_path 的执行回调是 computeControl()。它持有服务器级动态参数互斥锁，并按 controller_frequency 循环调用控制函数。

完整调用顺序如下。

5.1 接收 Goal 并选插件 ​

computeControl() 读取 controller_id 和 goal_checker_id，分别调用 findControllerId() 与 findGoalCheckerId()。

ID 有效后，进入 setPlannerPath()。

5.1.1 拒绝空路径 ​

拒绝空路径。

5.1.2 下发路径 ​

调用当前 Controller 的 setPlan(path)。

5.1.3 保存终点 ​

保存路径终点到 end_pose_。

5.1.4 重置 Goal Checker ​

Reset 当前 Goal Checker。

5.1.5 保存当前路径 ​

保存路径到 current_path_。

新任务开始时还会 Reset Progress Checker，清空上一任务的进度基线。

5.2 等待 Costmap 可用 ​

控制循环以 100 Hz 检查 local_costmap 是否 Current。只有地图有效后才进入本周期计算。

5.3 处理新路径抢占 ​

updateGlobalPath() 检查 Action Server 是否存在 Pending Goal。

如果有新目标，则按以下步骤处理。

5.3.1 接受 Pending Goal ​

接受 Pending Goal。

5.3.2 重新选择插件 ​

重新选择 Controller 和 Goal Checker。

5.3.3 替换路径 ​

调用 setPlannerPath() 替换路径。

5.3.4 重置 Goal Checker ​

Reset Goal Checker。

这里不会 Reset Progress Checker，所以抢占更新路径后，进度检查仍沿用当前 FollowPath 执行过程的基线。

5.4 获取当前位姿并检查进展 ​

computeAndPublishVelocity() 首先从 Costmap 获取当前机器人位姿。

获取失败会抛出 PlannerException，终止当前 Action。

随后调用 Progress Checker 的 check(pose)。如果机器人在允许时间内没有达到最小移动量，同样抛出异常，最终使 FollowPath 失败。

5.5 读取当前速度并调用 Controller ​

服务器从 /odom 取得速度，应用三个最小速度阈值，再调用：

cpp
controller->computeVelocityCommands(
  current_pose,
  thresholded_odom_velocity,
  current_goal_checker);

Controller 同时拥有已设置的 Path、TF Buffer 和 Local Costmap，因此能把路径、位姿、速度和障碍信息合成下一帧速度命令。

5.6 发布反馈和速度 ​

计算成功后，服务器更新“最近一次有效速度指令时间”，计算剩余路径长度和指令速度，发布 Action Feedback，再发布 cmd_vel。

5.7 判断是否到达 ​

isGoalReached() 再次获取机器人位姿，读取阈值处理后的 Odom 速度，把路径终点转换到 Costmap Global Frame，最后调用当前 Goal Checker 的 isGoalReached()。

未到达则等待下一控制周期；到达则跳出循环，根据 publish_zero_velocity 决定是否发布零速度，并把 Action 标记为成功。

六、第三层状态：FollowPath 的执行、抢占、取消和失败 ​

Lifecycle ACTIVE 只说明服务器可以工作，并不代表当前一定有控制任务。每个 FollowPath Goal 还有自己的运行状态。

6.1 正常成功 ​

Goal Checker 返回 true 后，控制循环结束。publish_zero_velocity=true 时先发布零速度，再调用 succeeded_current()，当前 Goal 进入 SUCCEEDED。

6.2 客户端取消 ​

循环检测到取消请求后，会调用 terminate_all() 并发布零速度。

SimpleActionServer 看到 Goal Handle 正处于 canceling，会把它标记为 CANCELED；如果还有 Pending Goal，也一并终止。

6.3 新目标抢占 ​

新 Goal 先进入 Pending。控制循环接受它时，SimpleActionServer::accept_pending_goal() 会把旧 Goal 标记为 ABORTED，再让新 Goal 成为 current。

因此抢占在服务器内部表现为“控制循环不中断地切换路径”，但从客户端看，旧 Goal 的终态是 ABORTED，不是 CANCELED。

6.4 Controller 暂时算不出速度 ​

Controller 的 computeVelocityCommands() 抛出 PlannerException 时，处理方式由 failure_tolerance 决定：

  • 0：立即向上抛出，FollowPath 失败。
  • 大于 0：先输出零速度，在容忍时间内允许后续周期恢复。
  • -1：不因 Controller 耐心超时而失败，持续允许零速度等待。

即使设为 -1，也不代表任务永远不会失败。Progress Checker 仍可能因为长期无进展终止任务，TF 位姿获取失败和其他异常也仍会中止 Action。

6.5 明确失败入口 ​

当前实现的主要 ABORTED 入口包括：

  • controller_id 不存在。
  • goal_checker_id 不存在。
  • 输入 Path 为空。
  • 无法从 TF／Costmap 获取机器人位姿。
  • Progress Checker 判定长期无进展。
  • Controller 连续异常超过 failure_tolerance。
  • Controller 或其他调用抛出未恢复异常。

这些失败只负责结束 FollowPath。是否清 Costmap、重新规划、后退或等待，由上层行为树或自研规控状态机决定。

七、动态参数：为什么导航过程中有些参数改不了 ​

Controller Server 自己注册动态参数回调，支持运行时更新：

  • controller_frequency。
  • min_x_velocity_threshold。
  • min_y_velocity_threshold。
  • min_theta_velocity_threshold。
  • failure_tolerance。

但 computeControl() 在整个 FollowPath 执行期间持有 dynamic_params_lock_。服务器级回调使用 try_lock()，所以导航正在运行时修改这些顶层参数会被拒绝，而不是在控制循环中途改变频率或阈值。

名字中含 . 的插件参数会被服务器级回调跳过，由各插件自己的动态参数回调处理，例如：

  • progress_checker.required_movement_radius。
  • general_goal_checker.xy_goal_tolerance。
  • general_goal_checker.yaw_goal_tolerance。

这形成了两层参数所有权：服务器只管理控制框架参数，插件管理自己的算法参数。

九、调试时最值得先看的八个点 ​

9.1 有路径但没有速度 ​

先确认 Controller Server 是 ACTIVE，再检查 cmd_vel 是否被 Launch 重映射，以及速度 Publisher 是否真的有订阅者。

9.2 一直等待，不进入 Controller ​

检查 local_costmap 是否 Current。传感器、TF 或 Costmap 更新异常都会让控制循环停在地图等待阶段。

9.3 很快报“Failed to make progress” ​

核对 required_movement_radius 和 movement_time_allowance 是否适合车辆速度。低速车在短窗口内达不到较大半径，会被误判为卡住。

9.4 到目标附近反复前后修正 ​

检查 Goal Checker 的 stateful。启用后，XY 达标后不会在最终旋转阶段反复退回位置判定。

9.5 只想走到位置，不关心朝向 ​

选择 PositionGoalChecker，不要靠把 Yaw 容差设置得极大来模拟“忽略朝向”。前者的语义更直接。

9.6 目标已进入容差，但 Action 仍不成功 ​

如果使用 StoppedGoalChecker，还必须满足平移和旋转速度阈值。此时要同时检查 Odom 和三个最小速度阈值。

9.7 Feedback 的速度与实车速度不一致 ​

这是设计行为。Feedback 的 speed 是 Controller 输出命令，不是 Odom 测量值。

9.8 抢占后旧客户端收到 ABORTED ​

当前 SimpleActionServer 接受 Pending Goal 时会 Abort 旧 Goal。这不是控制循环崩溃，而是当前版本的抢占终态语义。

十、把整个包压缩成一句话 ​

nav2_controller 做的事情可以概括为：

用 Lifecycle 管理一套可插拔的局部控制运行时，通过 FollowPath 接收 Path 和插件选择，融合 Local Costmap、TF、Odom 与 Speed Limit，循环生成 cmd_vel，并用 Progress Checker 和 Goal Checker把“卡住”与“到达”变成明确的 Action 终态。

理解这句话，就能把 Controller Server、局部控制算法、进度检查、目标检查和上层恢复机制准确地拆开。

路径只是意图，速度才是执行。而 nav2_controller，就是 Nav2 从意图走向运动的那一层。

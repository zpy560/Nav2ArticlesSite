控制器只发 20 Hz，底盘为何还能更丝滑？逐函数拆解 Nav2 Velocity Smoother ​

Controller Server 给出的 cmd_vel 往往每个控制周期跳变一次：这一拍需要直行，下一拍可能急转，再下一拍又要求停车。底盘若原样执行，速度阶跃会放大机械冲击、电流峰值和轮胎打滑。

nav2_velocity_smoother 位于控制器与底盘之间。它不重新规划轨迹，也不判断障碍物，而是以独立频率持续逼近期望速度，把三轴速度限制、加速度、减速度、死区和命令超时统一变成最终 Twist。

本文以当前工程中的 nav2_velocity_smoother 1.1.20 为准，覆盖 VelocitySmoother 的 12 个生产函数与独立进程 main()，合计 13 个生产函数。测试函数和组件注册宏不计入函数数量；nav2_util::OdomSmoother、Lifecycle、Bond、rclcpp Timer 等包外调用只解释接口与数据流，不展开其他包源码。

一、包边界：它整形速度，不替控制器做决策 ​

1.1 输入 Topic 与真实工程重映射 ​

源码创建普通 geometry_msgs::msg::Twist 订阅，Topic 相对名为 cmd_vel，QoS depth 为 1。输入通常来自包外 Controller Server。

当前 myagv_test_bringup 与 nav2_regulated_modules 的 Launch 都把输入重映射成 cmd_vel_nav。因此源码中的 cmd_vel 是接口默认名，运行图里的实际名称由 Launch 决定。

CLOSED_LOOP 模式还会间接消费 Odometry。订阅并不在本包中手写，而是由包外 nav2_util::OdomSmoother 根据 odom_topic 创建并维护。

1.2 输出 Topic 与下游 ​

源码创建 Lifecycle Publisher，默认相对名为 cmd_vel_smoothed，消息仍是 Twist。当前两套本地 Bringup 把它重映射为 cmd_vel，交给底盘桥接、controlpub 或其他包外执行链。

本包只写 linear.x、linear.y 与 angular.z。Twist 的 linear.z、angular.x 和 angular.y 保持默认零，不参与平滑。

1.3 生命周期与参数输入 ​

节点由包外 Lifecycle Manager 执行 configure、activate、deactivate、cleanup 和 shutdown。ACTIVE 后建立 Bond，让 Lifecycle Manager 可以监测进程心跳。

运行期还接收参数批次。参数控制频率、反馈模式、三轴速度、加减速度、死区、Odometry 时间窗和命令超时。

二、VelocitySmoother() 与析构：最小构造，延迟配置 ​

2.1 VelocitySmoother() 初始化节点和时间类型 ​

VelocitySmoother() 调用包外 nav2_util::LifecycleNode("velocity_smoother", "", options)，并用节点 Clock 类型构造零值 last_command_time_。

构造函数不声明参数、不创建 Topic，也不启动 Timer。所有可能失败的配置都推迟到 on_configure()，符合 Lifecycle 的资源管理方式。

它只记录创建日志。独立进程中的 SpdlogWrapper::init() 不在构造函数里调用，因此 Component 模式不会由本类重复初始化全局日志包装器。

2.2 ~VelocitySmoother() 兜底取消 Timer ​

~VelocitySmoother() 检查 timer_，存在时 cancel 并 reset。正常 Lifecycle 路径应在 deactivate 阶段已经完成这件事，析构只提供退出兜底。

析构函数不发布零速度。进程异常结束时能否让底盘停车，还依赖下游命令看门狗和整车安全链，不能只依赖本节点析构。

三、on_configure()：参数、校验与通信对象一次建立 ​

3.1 平滑元数据 ​

on_configure() 通过包外 declare_parameter_if_not_declared() 声明并读取：

  • smoothing_frequency：Timer 目标频率，默认 20 Hz。
  • feedback：OPEN_LOOP 或 CLOSED_LOOP。
  • scale_velocities：是否用统一 η 比例缩放三轴速度差。

回调输入的 Lifecycle State 没有参与逻辑。成功输出是 CallbackReturn::SUCCESS；无效配置主要通过抛出 std::runtime_error 让 configure 失败。

3.2 三轴运动学参数 ​

max_velocity、min_velocity、max_accel、max_decel 都按 x、y、theta 排列。默认 y 轴上下限为零，对应差速底盘；全向底盘可以配置非零 y。

源码要求 max_accel 非负、max_decel 非正，并要求每个轴 min_velocity<=max_velocity。这些符号直接参与单周期速度变化窗口，减速度若误写成正数会破坏公式。

当前校验顺序有一个重要边界：函数先用下标访问数组前三项做符号与大小比较，随后才统一检查五个数组的 size 是否等于 3。长度不足时，size 错误还没被抛出，就已经存在越界访问风险。

3.3 Odometry、死区与超时 ​

函数读取 odom_topic、odom_duration、deadband_velocity 和 velocity_timeout。timeout 从 double 秒转换成 rclcpp::Duration。

deadband 同样必须是三项，但 configure 只检查长度，不检查是否非负。负死区会让 fabs(v)<deadband 永远为 false，等于静默关闭该轴死区。

3.4 OPEN_LOOP 与 CLOSED_LOOP 初始化 ​

feedback 为 OPEN_LOOP 时只设置 open_loop_=true。feedback 为 CLOSED_LOOP 时设置 false，并创建包外 nav2_util::OdomSmoother(node, odom_duration, odom_topic)。

字符串不匹配两个合法值就抛异常。比较区分大小写，open_loop 或 Closed_Loop 都不会被接受。

3.5 创建 Publisher 与 Subscription ​

on_configure() 创建 cmd_vel_smoothed Lifecycle Publisher 和 cmd_vel Subscription。输入订阅是普通 rclcpp Subscription，不会因为节点 INACTIVE 自动停收消息。

因此节点 configure 后即使尚未 activate，inputCommandCallback() 仍可能更新 command_ 与 last_command_time_。activate 只决定 Timer 和 Lifecycle Publisher 是否工作。

四、Lifecycle 激活、停用与清理 ​

4.1 on_activate() 启动周期执行 ​

on_activate() 激活 smoothed_cmd_pub_，用 1000/smoothing_frequency 计算毫秒周期，转成 int 后创建 Wall Timer，回调绑定 smootherTimer()。

它随后注册 dynamicParametersCallback()，再调用 LifecycleNode 的包外 createBond()。成功输出固定为 SUCCESS。

毫秒整数转换会截断小数。例如 30 Hz 变成 33 ms，实际约 30.3 Hz；频率超过 1000 Hz 时周期可能截成 0 ms。源码没有验证 frequency 必须大于零，也没有设置最小 Timer 周期。

4.2 on_deactivate() 停止输出和热更新 ​

on_deactivate() cancel 并 reset Timer，停用 Lifecycle Publisher，reset 动态参数回调句柄，再调用包外 destroyBond()。

Subscription 没有销毁，所以 INACTIVE 阶段仍能缓存新命令。动态参数回调已经注销，此时参数存储可能改变，但 C++ 成员不会同步；单纯再次 activate 也不会重新读参数。

4.3 on_cleanup() 释放 configure 资源 ​

on_cleanup() reset Publisher、OdomSmoother 与 Subscription，返回 SUCCESS。按照合法 Lifecycle 顺序，Timer 和参数回调应已由 deactivate 清理。

函数没有显式清空 command_、last_cmd_、stopped_ 或 last_command_time_。同一对象重新 configure 后，旧命令状态仍可能保留，直到新命令到达或 timeout 路径处理。

4.4 on_shutdown() 只记录状态 ​

on_shutdown() 只输出日志并返回 SUCCESS，不发布零速度，也不主动释放资源。正常 shutdown transition 之前通常已经经过 deactivate 与 cleanup。

五、inputCommandCallback()：只缓存目标，不在回调里平滑 ​

5.1 拒绝 NaN 与 Inf ​

inputCommandCallback() 接收 Twist shared pointer，先调用包外 nav2_util::validateTwist()。任一分量包含 NaN 或 Inf 时记录错误并返回。

无效消息不会覆盖上一条合法 command_，也不会刷新 last_command_time_。如果上游持续发送无效值，旧合法命令最终仍会按 velocity timeout 进入停车流程。

5.2 保存指针和接收时间 ​

合法输入直接赋给 command_，并用节点 now() 更新 last_command_time_。函数不复制 Twist、不做限速，也不立即发布。

这种设计把“上游消息到达频率”和“下游平滑发布频率”解耦。Controller 可能 20 Hz 更新目标，Smoother 可以用更高频 Timer 在两个目标之间逐步逼近。

5.3 QoS depth=1 的语义 ​

输入队列只保留很浅的最新数据，适合速度控制：处理积压旧命令没有意义。真正每周期使用的是成员 command_ 中最近一次已经执行回调的目标。

六、OPEN_LOOP 与 CLOSED_LOOP：当前速度从哪里来 ​

6.1 OPEN_LOOP 使用 last_cmd_ ​

OPEN_LOOP 把上一周期内部计算的 last_cmd_ 当作当前速度。它假设底盘能够及时跟随上一条平滑输出。

优点是不受 Odometry 频率、噪声和延迟影响；代价是轮胎打滑、急停、底盘饱和或通信丢包不会反馈到平滑器。

6.2 CLOSED_LOOP 使用 OdomSmoother ​

CLOSED_LOOP 调用包外 odom_smoother_->getTwist()。OdomSmoother 通常订阅 odom_topic，对 odom_duration 时间窗中的 Twist 做平滑，再返回机器人实测当前速度。

本包不使用 Odometry Pose、协方差或 TF。它只需要速度反馈作为下一周期约束起点。

6.3 反馈频率与窗口的取舍 ​

如果 smoothing frequency 明显高于 Odometry 更新频率，多个 Timer 周期会重复看到同一份或滞后的速度；窗口过长又会增加相位延迟。结果可能是响应变慢甚至振荡。

当前本地 myagv_test_bringup 与 nav2_regulated_modules 都配置 feedback=OPEN_LOOP、odom_topic=/odometry、odom_duration=0.1。此时 Odom 参数已存在，但 configure 阶段不会创建 OdomSmoother。

七、findEtaConstraint()：找出三轴最严格的比例 ​

7.1 加速与减速如何分类 ​

findEtaConstraint() 输入当前速度、目标速度、最大加速度和最大减速度，计算 dv=v_cmd-v_curr。

目标绝对值不小于当前绝对值并且两者同号时，函数视为加速，单周期允许变化范围是 ±accel/frequency。其他情况视为减速，包括速度幅值下降和正负号反转，范围由负数 decel/frequency 构造。

换向不会直接从正速度跳到负速度，而是先按减速度穿过零，随后按加速度建立反向速度。

7.2 返回值 -1 与正 η ​

如果 dv 已在允许窗口内，函数返回 -1.0，表示该轴不需要比例缩放。

dv 超过上界时返回 upper/dv，低于下界时返回 lower/dv。正常参数下得到的正 η 不大于 1，代表这一周期只能完成目标速度差的一部分。

7.3 scale_velocities 如何选择 η ​

smootherTimer() 对 x、y、theta 分别调用该函数，并选择与 1 差距最大的正 η。对 0～1 范围而言，这就是最小、最严格的比例。

三个速度差共用同一 η，可以尽量保持 [dvx,dvy,dtheta] 的方向。例如 x 轴受限到只能完成目标差的 30%，其他轴也按 30% 推进，而不是各自一步到位。

八、applyConstraints()：把比例变成单轴输出 ​

8.1 输入输出公式 ​

applyConstraints() 使用与 findEtaConstraint() 相同的加速／减速分类，重新计算单周期上下界，返回：

v_next = v_curr + clamp(eta * dv, lower, upper)

即使统一 η 让某个轴出现特殊边界，最终 clamp 仍保证该轴不超过自己的加减速度范围。

8.2 scale_velocities=false 的行为 ​

关闭比例缩放时，Timer 保持 eta=1.0。三个轴分别执行 clamp，各自以最大允许步长逼近目标。

这能更快利用每个轴能力，但目标速度变化向量的方向可能改变。是否需要保持方向取决于底盘类型和控制需求。

8.3 频率直接改变单周期步长 ​

加速度单位是每秒变化量，源码用它除以 smoothing frequency 得到每周期步长。频率越高，每次变化越小，但单位时间理论总变化量保持近似相同。

Timer 实际周期被整数毫秒截断，极端频率或调度抖动时，公式仍使用配置频率而不是实测 dt。因此它是固定步长离散器，不是按真实时间间隔积分。

九、smootherTimer()：一个周期内速度如何流动 ​

9.1 没有命令就不发布 ​

smootherTimer() 检查 command_。尚未收到合法 Twist 时直接返回，不发布默认零速度。

这避免节点刚 activate 就抢占其他速度源，但也意味着下游必须有自己的“无消息停车”安全策略。

9.2 timeout 把目标改成零 ​

函数用 ROS 时间比较 now()-last_command_time_ 与 velocity_timeout_。超时且内部已经是零或 stopped_ 为 true 时，本周期返回并保持停止。

超时但仍有速度时，它把 *command_ 原地改成零 Twist，随后继续正常约束流程。输出不会瞬间跳零，而是按照 max_decel 多周期减速。

9.3 选择 current 并限制绝对速度 ​

OPEN_LOOP 取 last_cmd_，CLOSED_LOOP 取 OdomSmoother Twist。接着把 command_ 的 x、y、theta 原地 clamp 到 min／max velocity。

原地修改意味着超限目标的信息会丢失。即使随后动态放宽 max velocity，在新上游命令到达前，成员里仍是之前被截断的目标。

9.4 η 与逐轴约束 ​

启用 scale velocities 时，函数计算三个 curr_eta 并选择最严格者。随后对 x、y、theta 分别调用 applyConstraints()，得到本周期输出。

计算结果先写入 last_cmd_，作为 OPEN_LOOP 下一周期 current。

9.5 deadband 与发布 ​

函数最后比较输出绝对值与 deadband_velocity，小于阈值的轴写成零，再通过 Lifecycle Publisher 发布。

关键顺序是 last_cmd_ 在 deadband 之前保存。某轴计算为 0.05、死区为 0.1 时，实际发布零，但 OPEN_LOOP 内部仍认为上一周期速度是 0.05。内部状态和下游收到的 Twist 因此可能不同。

十、超时停车与时钟边界 ​

10.1 渐进停车而非单帧急停 ​

velocity timeout 的目的不是立即覆盖成零输出，而是把期望目标置零，再复用减速度约束。这样上游停止发布后，底盘仍能收到一串逐渐减小的速度。

当 last_cmd_ 精确为默认零 Twist或 stopped_ 已经置 true，Timer 不再持续发布零。下游若需要恒定零指令，必须自行配置命令看门狗。

10.2 Wall Timer 与 ROS 时间混用 ​

平滑周期由 Wall Timer 驱动，不受 /clock 暂停影响；timeout 判断使用节点 ROS 时间。use_sim_time=true 且仿真时钟停止时，Timer 仍运行，但旧命令的 ROS 时间年龄不再增长。

这可能让平滑器持续重复旧目标，而不是进入 timeout。仿真暂停是否应该冻结底盘取决于系统设计，实车配置通常应使用连续推进的系统时间。

10.3 pause／resume 的旧命令 ​

deactivate 会停止 Timer，却不清空 command_ 和 last_command_time_。恢复 activate 后，如果旧命令已经超时，Timer 会沿减速度路径停车；如果 ROS 时间没有推进，旧命令可能继续被使用。

十一、dynamicParametersCallback()：热更新能力与副作用 ​

11.1 double 参数 ​

dynamicParametersCallback() 初始设置 result.successful=true，逐个检查参数类型和名称。

更新 smoothing_frequency 时先写成员，取消旧 Timer，再以新频率立即创建 Timer。函数没有检查零、负数或过高频率。

velocity_timeout 直接重建 ROS Duration。odom_duration 写成员后立即创建新的 OdomSmoother，即使当前是 OPEN_LOOP。

11.2 double array 参数 ​

任何 double array 的长度不等于 3 都会让整批返回失败，即使名称不是本包关心的参数。

max_velocity、min_velocity 和 deadband_velocity 直接覆盖成员。动态路径没有重新检查 min<=max，也不检查 deadband 非负。

max_accel 出现负数或 max_decel 出现正数时会把 result 置为 false，但循环结束后仍把整个数组写入成员。ROS 参数事务可能被拒绝，运行时 C++ 成员却已经变成无效值。

11.3 string 参数 ​

feedback=OPEN_LOOP 设置开环并 reset OdomSmoother；feedback=CLOSED_LOOP 设置闭环并新建 OdomSmoother。其他字符串让结果失败并 break。

更新 odom_topic 会写入新名称并立即重建 OdomSmoother，同样不判断当前是否开环。

11.4 批量更新不是原子成员事务 ​

回调按顺序产生副作用。如果频率已重建 Timer，后续数组又因长度错误失败，ROS 参数批次可能整体不提交，但 Timer 和成员不会自动回滚。

安全改进应先完整校验整个 parameters 批次，把候选值保存在局部变量中；全部合法后再一次性更新成员与外部资源。

11.5 Lifecycle 有效期 ​

动态回调只在 ACTIVE 的 on_activate() 注册，在 deactivate 时注销。INACTIVE 阶段设置参数可能更新参数服务器存储，却不会更新运行时成员；再次 activate 只创建 Timer，不重新读取全部参数。

需要一致刷新时，应让节点经过 cleanup 和 configure，或修改实现使 activate 主动重新同步。

十二、main() 与 Component 部署 ​

12.1 main() 的进程数据流 ​

main() 调用 rclcpp::init()，初始化 SpdlogWrapper("nav2_velocity_smoother","velocity_smoother")，创建 VelocitySmoother shared pointer，并 spin 其 Node Base Interface。

spin 返回后执行 rclcpp::shutdown() 和 SpdlogWrapper::shutdown()，最后返回零。独立进程只管理节点和日志生命周期，不参与平滑数学。

12.2 共享库和组件注册 ​

CMake 生成 velocity_smoother_core 共享库与 velocity_smoother 可执行文件。RCLCPP_COMPONENTS_REGISTER_NODE 让同一个类也能由 ComponentManager 加载；宏不计入生产函数。

独立进程与组合部署使用相同 Topic、参数、Lifecycle 和 Timer 实现，差异主要在进程边界与执行器调度。

十三、当前本地配置如何经过这套算法 ​

13.1 当前三轴限制 ​

myagv_test_bringup 与 nav2_regulated_modules 当前都使用：

  • 最大速度 [0.26,0.0,1.0]。
  • 最小速度 [-0.26,0.0,-1.0]。
  • 最大加速度 [2.5,0.0,3.2]。
  • 最大减速度 [-2.5,0.0,-3.2]。
  • smoothing frequency 20 Hz。
  • deadband 全零。
  • velocity timeout 1 s。

y 轴被固定为零，符合差速底盘。单个理想周期内 x 最大变化约 0.125 m/s，theta 最大变化约 0.16 rad/s。

13.2 当前反馈和 Topic 链 ​

feedback 为 OPEN_LOOP，所以 current 取 last_cmd_，不创建 Odometry 反馈链。cmd_vel_nav 进入平滑器，输出重映射成最终 cmd_vel。

odom_topic=/odometry 与 odom_duration=0.1 只有切到 CLOSED_LOOP 后才真正参与 Timer current 计算。

13.3 调参应沿数据流定位 ​

绝对速度过高，先检查 max／min velocity；速度爬升或刹车过快，检查 accel／decel 与 frequency；多轴方向失真，评估 scale velocities；小命令导致电机嗡鸣，检查 deadband；上游停止后仍运动，检查 timeout、ROS Clock 和下游看门狗。

CLOSED_LOOP 响应迟缓或振荡，应同时核对 Odometry 频率、延迟、噪声与 odom duration，不能只增大加速度参数。

十四、总结：平滑器不是低通滤波器，而是离散运动学限幅器 ​

这 13 个生产函数构成一条清晰链路：输入回调缓存最新目标，独立 Wall Timer 选择开环或闭环 current，绝对速度先 clamp，可选 η 保持三轴变化方向，逐轴加减速度限制生成下一帧，timeout 把目标切到零，deadband 决定最终发布。

它没有对历史 cmd_vel 做均值、卷积或传统低通滤波。真正的核心是“每个离散周期最多允许速度变化多少”，以及“当前速度来自上一帧输出还是 Odometry 时间窗”。

阅读和调试本包时，应始终区分四个量：上游原始 command_、反馈得到的 current、本周期约束后的 last_cmd_、deadband 处理后的实际发布 Twist。多数看似矛盾的现象，都来自把这四个量误认为同一个速度。

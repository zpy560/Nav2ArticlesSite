一个进程装下整套 ROS 2？从 ComponentManager 一路拆到 rcl、rmw 与进程内通信 ​

本文以本机 ROS 2 Humble 16.0.12 为实现基线，整理 Composition 的机制演变、组件注册、动态加载、Executor 调度、进程内与跨进程消息路径，以及与 rcl、rmw 的底层边界。文中的“全部 rclcpp 调用”特指 Composition 从注册、加载到消息回调这一完整相关链路，不泛指 rclcpp 的全部 API。

一、先给结论：Composition 改的是进程拓扑，不是节点语义 ​

ROS 2 Composition 的核心，是把“节点写成什么样”和“节点运行在哪个进程”解耦。

同一个 rclcpp::Node 派生类可以：

  • 由自己生成的 main() 单独运行。
  • 在编译期链接进自定义进程。
  • 以共享库形式，在运行时装入通用组件容器。
  • 由 launch 文件声明多个 ComposableNode，统一加载进一个容器。

节点的 Topic、Service、Action、Parameter、Lifecycle 和 TF 语义都不因为 Composition 而改变。改变的是这些实体由哪个进程持有、由哪个 Executor 调度，以及消息是否具备走进程内路径的条件。

这带来三个必须分开的概念：

  • Composition：多个节点位于同一进程。
  • Executor：决定这些节点的回调在哪些线程、按什么互斥规则执行。
  • Intra-process communication：在满足条件时绕过序列化与 DDS 数据路径。

三者有关联，但不是同一件事。

二、机制是怎样演变来的 ​

2.1 ROS 1：Node 与 Nodelet 是两套编程模型 ​

ROS 1 普通节点编译成独立可执行文件，Nodelet 则编译成共享库，再装入 Nodelet Manager。Nodelet 能降低同机大数据消息的复制成本，但开发者需要面对不同基类、不同初始化入口和不同部署方式。

这意味着“要不要共进程”在很大程度上会反向影响代码结构。

2.2 ROS 2：统一为 Node API，把进程布局推迟到部署阶段 ​

ROS 2 推荐把可复用节点写成 Component。Component 通常仍是 rclcpp::Node 的子类，只是构造函数接收 rclcpp::NodeOptions，并导出一个节点工厂入口。

于是，业务代码不需要为了独立进程或组合进程维护两套实现。部署者可以根据故障隔离、调试、内存、延迟和调度需求选择进程布局。

2.3 运行时组件管理：Service 驱动动态装载 ​

rclcpp_components::ComponentManager 提供 LoadNode、UnloadNode 和 ListNodes 三个 Service。ros2 component、launch 或其他客户端都可以在容器运行后请求装载组件。

2.4 进程内通信的第一次实现：环形缓冲区加元消息 ​

早期 ROS 2 进程内通信以 Publisher 环形缓冲区保存原消息，再通过中间件发送只包含 Publisher ID 和缓冲位置的元消息。订阅端收到元消息后，再回到 IntraProcessManager 取原数据。

这种方式仍依赖中间件通知，并且在共享指针、内存占用和性能方面存在限制。

2.5 Dashing 之后：订阅端缓冲区加 GuardCondition ​

新的实现让每个进程内订阅拥有自己的缓冲区。Publisher 把消息直接交给 IntraProcessManager，管理器按订阅回调的所有权需求选择共享、复制或转移 unique_ptr，然后触发订阅对应的 GuardCondition。Executor 把它作为 Waitable 处理，不再依赖元消息唤醒。

Humble 当前使用的就是这条架构。

2.6 容器调度继续细分 ​

当前 Humble 提供三种通用容器：

  • component_container：所有组件共享一个 SingleThreadedExecutor。
  • component_container_mt：所有组件共享一个 MultiThreadedExecutor。
  • component_container_isolated：每个组件拥有独立 Executor 和线程。

这一步让“同进程低开销”和“调度隔离”不再只能二选一，但同进程组件仍共享地址空间，内存破坏和进程崩溃无法隔离。

三、一个类怎样变成可发现的 Component ​

Component 类需要满足两个关键约定：

  • 构造函数接收单个 rclcpp::NodeOptions。
  • 能返回 NodeBaseInterface。继承 rclcpp::Node 时天然满足这一点。

源文件末尾调用：

cpp
RCLCPP_COMPONENTS_REGISTER_NODE(my_pkg::MyNode)

这个宏不会创建 ROS 节点。它展开为 CLASS_LOADER_REGISTER_CLASS，注册的实际类型是：

text
rclcpp_components::NodeFactoryTemplate<my_pkg::MyNode>
  implements rclcpp_components::NodeFactory

工厂的 create_node_instance() 才会在运行时执行：

text
std::make_shared<MyNode>(options)
  -> NodeInstanceWrapper
       ├─ std::shared_ptr<void> 保存真实对象
       └─ get_node_base_interface() 提供给 Executor

CMake 侧的 rclcpp_components_register_nodes() 做另一半工作：它要求目标是共享库，并向 ament resource index 写入“插件类名；共享库路径”。

所以组件发现依赖两份信息同时存在：

  • 共享库内部的 class_loader 工厂注册。
  • 安装空间 ament index 中的类名与库路径映射。

少任何一个，ros2 component types 或 ComponentManager 都无法正确实例化组件。

四、容器进程启动时，rclcpp 做了什么 ​

以单线程容器为例，main() 非常短：

text
rclcpp::init(argc, argv)
  -> 创建 SingleThreadedExecutor
  -> 创建 ComponentManager(executor)
  -> executor.add_node(component_manager)
  -> executor.spin()

ComponentManager 本身也是一个 rclcpp::Node。构造时创建三个管理 Service：

  • ~/_container/load_node
  • ~/_container/unload_node
  • ~/_container/list_nodes

假设容器节点名为 /nav2_container，第一个私有名称会展开为：

text
/nav2_container/_container/load_node

Load 和 Unload Service 的 QoS 深度在当前实现中被设为 200。ComponentManager 自己默认关闭参数 Service 和参数事件发布器，但会声明只读参数 thread_num，供多线程容器决定线程数量。

容器启动后还没有业务组件。此时 Executor 只调度 ComponentManager 自己的三个 Service 和节点基础实体。

五、LoadNode 请求携带哪些输入 ​

5.1 请求字段 ​

composition_interfaces/srv/LoadNode 请求包含：

  • package_name：组件所属 ROS 包。
  • plugin_name：注册到索引中的插件类名。
  • node_name：实例节点名，可为空。
  • node_namespace：实例命名空间，可为空。
  • log_level：请求字段；Humble 当前 create_node_options() 没有消费它。
  • remap_rules：组件专属 remapping。
  • parameters：已解析为 rcl_interfaces/msg/Parameter 的参数覆盖。
  • extra_arguments：容器专属键值参数。

5.2 响应字段 ​

响应包含：

  • success。
  • error_message。
  • full_node_name。
  • 容器内唯一的 unique_id。

5.3 Extra Arguments ​

Humble 当前识别两个关键 extra argument：

  • use_intra_process_comms：写入 NodeOptions::use_intra_process_comms()。
  • forward_global_arguments：决定组件是否接收容器进程的全局 ROS 参数。默认关闭，以防某个组件被不属于它的全局 remap 或参数影响。

launch 中的 LoadComposableNodes 会先解析名字、命名空间、参数文件、remapping 和 extra arguments，构造 LoadNode 请求，然后按列表顺序逐个调用容器 Service。参数文件路径本身不会传给 ComponentManager；launch 已经把它转换成 Parameter 数组。

六、动态装载全链路：从 Service 到 dlopen ​

外部客户端发送 LoadNode 请求后，容器侧走的是普通 ROS 2 Service 数据路径：

text
rmw_wait
  -> rcl_wait
  -> Executor 发现 Service ready
  -> execute_service()
  -> ServiceBase::take_type_erased_request()
  -> rcl_take_request()
  -> rmw_take_request()
  -> ComponentManager::on_load_node()

on_load_node() 内部按下面的顺序执行。

6.1 读取 Ament Index ​

ament_index_cpp::get_resource() 读取包在 rclcpp_components 资源索引中的条目。

6.2 解析插件与共享库 ​

找到与 plugin_name 相同的类名和共享库绝对路径。

6.3 打开动态库 ​

为该共享库创建或复用 class_loader::ClassLoader，底层打开动态库。

6.4 创建 NodeFactory ​

寻找 NodeFactoryTemplate<组件类>，创建 NodeFactory。

6.5 构造 NodeOptions ​

把参数、remap、名字、命名空间和 extra arguments 转成 NodeOptions。

6.6 分配唯一 ID ​

分配容器内唯一 ID。

6.7 构造组件实例 ​

工厂执行 std::make_shared<NodeT>(options)，组件构造函数在这里运行。

6.8 保存实例包装器 ​

NodeInstanceWrapper 同时保存真实对象和 NodeBaseInterface 访问器。

6.9 加入 Executor ​

Executor::add_node() 把组件的自动 callback groups 纳入调度集合。

6.10 返回装载结果 ​

返回完整节点名与唯一 ID，再由 Service 通过 rcl_send_response() 和 rmw_send_response() 发回客户端。

6.11 装载失败出口 ​

装载失败的主要出口包括：

  • ament index 找不到包资源。
  • 资源条目格式错误。
  • 共享库打开失败。
  • 找不到请求的插件类。
  • extra argument 类型错误。
  • 组件构造函数抛异常。

这些错误写入 success=false 和 error_message，不会把半初始化组件加入 Executor。

七、Unload 与 List：被销毁的是实例，不一定立即卸载动态库 ​

7.1 ListNodes ​

ListNodes 遍历 node_wrappers_，返回平行数组 full_node_names 和 unique_ids。

7.2 UnloadNode ​

UnloadNode 只接收 unique_id，并按以下步骤执行。

7.2.1 查找实例 ​

在 node_wrappers_ 查找实例。

7.2.2 移除 Callback Groups ​

Executor::remove_node() 移除其 callback groups。

7.2.3 擦除实例包装器 ​

从 map 擦除 NodeInstanceWrapper。

7.2.4 析构节点资源 ​

共享指针引用归零时，节点及其 Publisher、Subscription、Timer、Service 等实体析构。

当前 ComponentManager 会缓存每个共享库对应的 ClassLoader。卸载一个组件实例时不会同步擦除这个 loader，因此“节点对象已销毁”不等于“共享库立刻 dlclose”。这是避免频繁开关动态库的一种实现结果，也解释了为什么卸载后静态变量和库级资源不一定马上消失。

八、Executor 怎样调度同一进程中的所有组件 ​

组件加入 Executor 后，不是获得自己的 spin()。Component 自己没有主线程控制权，所有回调由容器 Executor 统一调度。

单线程 Executor 的核心循环可以概括为：

text
while context ok:
  get_next_executable()
  execute_any_executable()

8.1 wait_for_work() 等待流程 ​

当没有立即可执行的任务时，wait_for_work() 按以下步骤执行。

8.1.1 收集 Callback Groups ​

收集各节点自动加入的 CallbackGroup。

8.1.2 收集可执行实体 ​

由 MemoryStrategy 收集 Subscription、Timer、Service、Client、GuardCondition 和 Waitable。

8.1.3 调整 WaitSet ​

清空并调整 rcl_wait_set_t 容量。

8.1.4 加入实体句柄 ​

将各实体句柄加入 WaitSet。

8.1.5 调用 rcl_wait() ​

调用 rcl_wait()。

8.1.6 进入 RMW 等待 ​

rcl_wait() 将等待请求交给 rmw_wait()，再由具体 RMW／DDS 实现阻塞等待数据或事件。

8.1.7 选择可执行任务 ​

醒来后删除未就绪的空句柄，从 ready 集合选择一个 AnyExecutable。

Humble 当前普通 Executor 的选择顺序是 Timer、Subscription、Service、Client、Waitable。选中互斥 CallbackGroup 后，会先把 can_be_taken_from 置为 false，执行结束再恢复，防止多线程 Executor 同时运行同组回调。

8.2 execute_any_executable() 回调分发 ​

execute_any_executable() 再按实体类型分发：

  • Timer：TimerBase::execute_callback()。
  • Subscription：execute_subscription()。
  • Service：take_type_erased_request() 后执行服务回调。
  • Client：take_type_erased_response() 后完成 Future 和回调。
  • Waitable：take_data() 后执行 execute()，进程内订阅就是这一类。

这解释了一个常见误区：组件共进程后，如果使用单线程容器，而某个回调长时间阻塞，其他组件的 Timer、Service 和 Subscription 一样会被拖住。

九、跨进程消息：仍然经过 rcl 与 rmw ​

当未启用进程内通信，或订阅者位于其他进程时，Publisher 的路径是：

text
rclcpp::Publisher<MessageT>::publish()
  -> do_inter_process_publish()
  -> rcl_publish()
  -> rmw_publish()
  -> 具体 DDS／中间件发送

订阅端由 WaitSet 唤醒后：

text
Executor::execute_subscription()
  -> SubscriptionBase::take_type_erased()
  -> rcl_take()
  -> rmw_take()
  -> Subscription::handle_message()
  -> AnySubscriptionCallback::dispatch()
  -> 用户回调

因此，同一容器里两个组件即使物理上共进程，只要 use_intra_process_comms 没开启，它们仍走普通 RMW 通信路径。

十、进程内消息：不序列化，但也不是永远零复制 ​

NodeOptions::use_intra_process_comms 在 Humble 默认是 false。通过 Component 的 extra argument 打开后，Publisher 和 Subscription 会向同一个 rclcpp::Context 持有的 IntraProcessManager 注册。

10.1 通信匹配条件 ​

注册时，管理器按两个条件匹配通信对：

  • 完全相同的最终 Topic 名称。
  • QoS 兼容。

10.2 unique_ptr 发布链路 ​

Publisher 发布 unique_ptr 时，调用链变为：

text
Publisher::publish(unique_ptr)
  -> do_intra_process_publish()
  -> IntraProcessManager::do_intra_process_publish()
  -> 按订阅所有权类型选择目标
  -> 写入每个 SubscriptionIntraProcessBuffer
  -> 触发 GuardCondition
  -> Executor 将其作为 Waitable 取出
  -> SubscriptionIntraProcess::take_data()
  -> dispatch_intra_process()
  -> 用户回调

10.3 消息所有权与复制 ​

复制次数由订阅回调类型决定：

  • 全部订阅只要求共享所有权时，unique_ptr 可提升为共享指针，多个订阅共享消息。
  • 有订阅要求独占所有权时，除最后一个接收者可以获得原 unique_ptr 外，其他独占订阅仍需要复制。
  • 共享订阅与多个独占订阅混合时，需要为不同所有权分支创建副本。
  • 使用 publish(const MessageT&) 时，为进入进程内所有权链，Publisher 会先在堆上复制成 unique_ptr。
  • Humble 的进程内路径不支持 serialized message；LoanedMessage 与进程内通信同时启用时也不支持。

如果同一 Publisher 同时存在进程内和外部订阅，rclcpp 会先走进程内分发，再调用 rcl_publish() 满足外部订阅。订阅端若从 RMW 路径收到来自本进程已匹配 Publisher 的重复副本，会根据 Publisher GID 丢弃，避免同一回调收到两次。

10.4 零复制成立条件 ​

所以“同进程”只是前提，“零复制”仍取决于：

  • 是否显式启用 IPC。
  • Publisher 与 Subscription 是否共享同一个 Context。
  • Topic 和 QoS 是否匹配。
  • 发布参数是否转移所有权。
  • 订阅回调要求 shared ownership 还是 unique ownership。
  • 是否还存在外部订阅者。

十一、三个容器该怎样选 ​

11.1 component_container ​

所有组件共享一个线程，行为最容易推理，适合回调短小、无阻塞、并发要求低的系统。任何长回调都会阻塞整个容器。

11.2 component_container_mt ​

所有组件共享线程池。是否真能并发由 CallbackGroup 决定；如果所有实体都留在同一个默认 MutuallyExclusive 组，即使有多个线程，同一节点内部也不会自动并行。

11.3 component_container_isolated ​

每个组件创建独立 Executor 和线程，卸载时取消对应 Executor 并 join 线程。它增强调度隔离，却仍共享进程地址空间和全局 Context。

11.4 容器选择顺序 ​

工程上可以按以下顺序判断。

11.4.1 判断是否需要进程隔离 ​

需要进程级故障隔离或单节点调试最优先时，选择独立进程。

11.4.2 判断单线程是否足够 ​

回调都很短、追求简单与低开销时，选择单线程容器。

11.4.3 判断是否需要并行 ​

存在并行图像、点云或规划任务，并已设计 CallbackGroup 时，选择多线程容器。

11.4.4 判断是否需要调度隔离 ​

希望共享进程但减少组件间调度干扰时，选择隔离容器。

十二、Composition 与 Lifecycle、Action、Parameter 的关系 ​

12.1 Composition 与 Lifecycle ​

Composition 不替代 Lifecycle。一个 LifecycleNode 被加载后，状态仍从 Unconfigured 开始，必须由 LifecycleManager 或客户端执行 configure、activate 等转换。

12.2 Composition 与 Action ​

Composition 也不改变 Action 的五路 Topic／Service 语义；Action Server 和 Client 仍由 rclcpp_action 创建底层实体，再由同一个 Executor 调度。

12.3 Composition 与 Parameter ​

Parameter 覆盖在构造组件时通过 NodeOptions 注入，但运行期参数 Service 是否存在，取决于组件自身 NodeOptions 和节点实现。ComponentManager 关闭的是自己的参数 Service，不是被加载组件的参数 Service。

十三、最容易踩的十个坑 ​

13.1 只写注册宏 ​

没有调用 CMake 注册函数时，共享库能编译，但 ament index 找不到它。

13.2 只调用 CMake 注册 ​

没有在某个翻译单元中导出工厂时，索引里有名字，动态库里却没有可实例化类。

13.3 在组件构造函数里阻塞 ​

构造发生在 LoadNode Service 回调中，会阻塞后续加载和容器调度。

13.4 把 Composition 当作 IPC 开关 ​

共进程不自动启用 use_intra_process_comms。

13.5 把 IPC 当作绝对零复制 ​

回调所有权和订阅数量仍可能产生副本。

13.6 在单线程容器执行耗时回调 ​

这会导致同容器全部节点“像一起卡死”。

13.7 多线程容器缺少 CallbackGroup 设计 ​

结果可能是并发度没有变化，或者共享状态出现竞态。

13.8 认为卸载组件会立即卸载共享库 ​

当前 loader 缓存会继续持有库。

13.9 混淆 Lifecycle 与 Component 状态 ​

Loaded 只表示对象已经加入 Executor，不表示 Lifecycle Active。

13.10 依赖容器全局 Remap ​

ComponentManager 默认不把全局参数转发给组件，应显式传递 remapping 和参数，必要时才启用 forward_global_arguments。

十四、用 Nav2 看一个真实组合案例 ​

Nav2 中的 PlannerServer、ControllerServer、SmootherServer、BehaviorServer、LifecycleManager 等都通过 RCLCPP_COMPONENTS_REGISTER_NODE 导出。

当 use_composition=false 时，launch 运行各包自己的可执行文件；当 use_composition=true 时，LoadComposableNodes 把同样的类装入统一容器。节点名、参数、remapping、Lifecycle 接口和业务 Action 都保持不变，变化的是进程与 Executor 布局。

这正是 Composition 最重要的设计价值：业务架构不需要跟着部署拓扑重写。

十六、结语 ​

ROS 2 Composition 并不是简单地“少开几个进程”。它是一条完整的部署机制：构建阶段由 class_loader 和 ament index 建立可发现入口，运行阶段由 ComponentManager 通过 Service 动态构造节点，Executor 汇总全部 CallbackGroup，并沿 rcl_wait()、rmw_wait() 调度回调；需要时，IntraProcessManager 再把消息从 DDS 路径切到进程内缓冲区和 GuardCondition 路径。

理解这条链路后，才能正确回答三个工程问题：节点为什么加载失败、组件为什么共进程却没有变快，以及一个回调为什么能拖住同容器的整套系统。

敢让 AI 真动手，先把边界画清：Codex 权限、沙箱、审批与安全闭环 ​

Codex 最有价值的地方，是它不只给建议，还能读文件、改代码、运行命令和连接工具；它最大的风险也来自这里。真正可靠的 AI 编程，不是反复提醒模型“千万小心”，而是把能做什么、何时停下、谁来批准、怎样留证据写进可执行边界。

本文以教程第 15、16 篇为线索，对照 OpenAI Docs 的 Agent approvals & security、Permissions 与 Sandbox 章节。教程帮助理解风险场景，官方文档则明确当前控制模型：Sandbox 决定技术上能访问什么，Approval 决定何时必须暂停并请求审查，两者不能互相替代。

一、先把“会行动”理解成安全问题 ​

1.1 Prompt 约束不是强制隔离 ​

Prompt 可以要求代理只改某个目录、不要联网、不要发布，但自然语言本身不是操作系统边界。模型可能误解范围，仓库里的不可信文本也可能诱导它偏离任务。安全设计必须假设指令会被误读，再用沙箱、权限和审批限制后果。

1.2 自动化程度越高，边界越要外置 ​

人盯着每条命令时，可以临场阻止风险；非交互任务、长时间运行和多工具协作把判断移到后台，更需要预先定义文件、网络、凭据和外部动作的范围。可靠自动化不是取消人工，而是把人工判断留在高影响节点。

二、Sandbox 与 Approval 是两道不同的门 ​

2.1 Sandbox 定义技术能力 ​

沙箱约束代理启动的命令能够读取和写入哪些路径、能否访问网络，以及能否接触工作区之外的系统资源。即使模型想越界，受支持平台的运行时仍会执行这些限制。官方文档强调，Git、包管理器、测试程序等子进程同样继承边界。

2.2 Approval 定义决策流程 ​

审批策略决定某个动作是否需要暂停，让用户或自动审查器判断。批准一次越界，不等于永久授予整台机器权限；一个合格的请求应给出精确命令、目标范围、必要原因和关键风险。

2.3 自动审查不会扩大沙箱 ​

OpenAI Docs 当前区分 Ask for approval、Approve for me 和 Full access 等交互模式。把审批交给自动审查，只改变“谁来审”，不会自动放宽工作区边界。Full access 则移除重要隔离，应只在明确接受广泛访问时使用。

三、权限档位应围绕任务而不是围绕人 ​

3.1 只读适合调查与规划 ​

代码审计、架构梳理、日志分析和方案讨论通常不需要写权限。只读模式能证明本轮不会改变仓库状态，也迫使任务先形成事实地图。

3.2 工作区写入适合常规开发 ​

对版本控制仓库，常见低摩擦组合是在活动工作区内读写，并对网络或工作区外动作按需审批。这样代理可以连续完成搜索、编辑和本地测试，同时把系统级变化留给人工判断。

3.3 权限配置档适合最小授权 ​

官方 Permissions 文档提供内置只读、工作区和全访问档位，也支持用文件系统与网络规则定义命名 Profile。更窄的拒绝规则可以继续保护 .env 等敏感路径，即使工作区整体可写。权限配置档仍在演进，部署时要核对当前版本，不能把旧 sandbox 设置和新 profile 机制随意混用。

四、网络是另一条独立边界 ​

4.1 能读网页不等于命令可以联网 ​

Web Search、浏览器、插件和本地命令可能使用不同的网络控制。官方文档指出，本地 workspace-write 默认不等于开放命令网络；需要联网时应明确启用，并尽量通过域名策略收口目的地。

4.2 白名单只能缩小出口，不能证明内容可信 ​

允许访问官方文档域名，可以降低任意外连风险，但网页内容、依赖安装脚本和下载文件仍需视为不可信输入。网络许可解决“可以去哪里”，内容审查解决“拿回来的东西能否执行”。

4.3 凭据应在最短生命周期出现 ​

密钥不进入 Prompt、源码、提交和日志。云端环境适合把 Secrets 只提供给设置阶段，再在代理阶段移除；本地自动化则应使用受控环境变量或秘密管理系统，并避免回显。能用短期令牌，就不要共享长期 token。

五、审批请求本身也需要审查方法 ​

5.1 先看动作意图，再看精确目标 ​

审批界面出现“需要更高权限”时，不要只判断工具是否常用。应核对它要完成什么任务、将改动哪个路径或外部对象、为什么现有权限不能完成，以及是否存在更小范围方案。

5.2 再判断可逆性与影响对象 ​

读取官方文档与公开元数据通常低风险；安装依赖、修改系统配置、推送分支、发送消息、删除文件和生产变更会改变更广泛状态。越难恢复、影响的人越多，越应保留逐步批准。

5.3 最后选择最窄授权范围 ​

能只批准一个命令，就不批准整个会话；能只开放一个域名，就不开放任意网络；能在临时分支或草稿中完成，就不直接触碰正式状态。拒绝宽泛请求并不是阻碍代理，而是在要求它给出可审查的执行合同。

六、Prompt Injection 的根因是指令权混淆 ​

网页、Issue、日志、依赖说明和仓库文档都可能包含“忽略前文并执行某命令”之类的文本。代理必须把这些材料当作数据，而不是自动赋予其更高指令权。项目规则、用户授权和系统边界高于外部内容。

防护不能只依赖识别恶意措辞。更稳健的做法是同时限制秘密可读范围、网络目的地、工具副作用和最终发布动作。即使某段注入文本骗过模型，外层控制仍能缩小后果。

七、把高风险动作留在人类责任线上 ​

删除、覆盖 Git 历史、数据库迁移、密钥轮换、付款、合并、生产部署和公开发布，具有不可逆或多人影响。代理可以准备精确目标、影响分析、dry-run、恢复方案和验证清单，但最终确认应由拥有责任的人完成。

MCP 和连接器工具同样如此。工具若声明有副作用或破坏性，审批应覆盖它，而不是只盯 shell 命令。供应链中的 Skill、插件、MCP Server 与 Hook 也要审查来源、维护者、权限和停用路径。

八、结语 ​

让 Codex 安全行动的核心，不是“完全信任”或“完全禁止”二选一，而是让低风险动作在明确边界内连续进行，让跨界、高影响和不可逆动作及时停下。Sandbox 提供强制边界，Permission Profile 表达最小能力，Approval 承担例外决策，网络与秘密策略限制数据流，人工审查守住最终责任。

当每一次状态变化都能回答“谁发起、为什么需要、能碰哪里、怎样验证、如何恢复”，AI 编程才真正具备可扩大使用范围的安全基础。

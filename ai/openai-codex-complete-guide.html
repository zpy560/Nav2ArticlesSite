一篇讲透 OpenAI Codex：从第一次任务到企业级治理的完整指南 ​

Codex 真正改变的不是代码补全速度，而是软件任务的交付方式：模型进入受控环境，理解仓库现实，调用工具修改状态，再用构建、测试、Diff 和审查证据证明结果。只有把入口、上下文、权限、执行环境、扩展能力和组织治理连成一条链，AI 编程代理才会从偶尔有用变成稳定工程能力。

这篇长文以 OpenAI Codex 官方文档的主题结构为主线，把产品全景、快速上手、Prompt、配置、安全、Cloud、扩展、自动化、SDK 和企业治理合并为一套连续方法。读者可以从第一次本地任务开始，逐步走到可审计的团队级与企业级落地。

文中涉及的模型名称、功能入口和管理能力可能随产品版本变化。稳定方法写在正文中，易变事实应以文末列出的 OpenAI Docs 当前页面和本机实际帮助为准。

一、Codex 是什么：从生成答案到完成任务 ​

如果只把 Codex 理解成一个更聪明的代码补全工具，你会错过它真正的变化：模型不再只生成一段答案，而是进入一个受控执行环境，读取仓库、调用工具、修改文件、运行验证，再把差异和证据交还给人。OpenAI Docs 对 Codex 的核心定位，是能够代表开发者执行软件工程工作的编码代理，而不是脱离项目现实的聊天框。

1.1 Codex 是由五层组成的执行系统 ​

1.1.1 模型负责理解与推理 ​

模型读取用户目标、项目说明、代码、日志和工具结果，判断下一步要做什么。它决定分析深度，却不直接等于完整的 Codex。只比较模型榜单，无法解释代理为什么能修改仓库，也无法解释它为什么会被沙箱拦住。

1.1.2 上下文负责提供项目现实 ​

当前文件、目录结构、AGENTS.md、配置、测试、错误日志和对话历史共同组成任务上下文。模型能力再强，如果工作目录错误、日志过期或规则冲突，得到的仍可能是逻辑完整但不适用于当前仓库的答案。

1.1.3 工具负责改变外部状态 ​

搜索文件、读取源码、执行命令、编辑文件、浏览网页和调用 MCP 都属于工具层。工具把语言推理变成可观察动作，也是 Codex 与普通问答最明显的边界。

1.1.4 权限负责限制动作半径 ​

沙箱决定命令技术上能碰到什么，审批决定跨越边界前由谁判断。代理不是因为“答应小心”才安全，而是因为运行时把文件、网络和外部动作限制在明确范围。

1.1.5 验证负责决定任务能否结束 ​

Diff、测试、构建、静态检查、运行日志和人工 Review 是任务完成的证据。Codex 可以主动执行验证，但是否接受结果仍由开发者负责。

1.2 Agent 与聊天回答的差异在于闭环 ​

1.2.1 聊天回答交付建议 ​

普通问答通常在生成文本后结束。用户需要自己复制代码、切换终端、处理报错并判断结果。它适合解释概念、讨论方案和生成局部示例。

1.2.2 编码代理交付状态变化 ​

Codex 会持续观察工具结果并调整行动：搜索调用链、修改实现、运行测试、根据失败继续修正。这条观察、行动、验证、反馈的循环，才是 Agent 的核心。

1.2.3 人的职责从操作上移到决策 ​

代理承担机械搜索和执行，人负责目标、架构取舍、风险授权与最终验收。AI 没有消除人的责任，只是把人的注意力从逐行操作上移到更高价值判断。

1.3 不同入口共享能力，但运行位置不同 ​

1.3.1 本地入口使用本机项目现实 ​

ChatGPT 桌面端、Codex CLI 和 IDE 扩展可以在本机工作区执行任务。它们更容易使用尚未推送的修改、本地工具链和开发者当前环境，也因此必须尊重本机权限和未提交工作。

1.3.2 Cloud 入口使用可重建远程环境 ​

Codex Cloud 从连接的代码仓库与环境配置重建任务现场。它适合长任务和并行工作，但不能自动看到本机未提交状态。环境脚本、依赖、Secrets 和网络规则必须显式配置。

1.3.3 入口选择取决于任务摩擦 ​

局部编辑适合 IDE，终端密集任务适合 CLI，可视化并行与 Review 适合桌面端，可独立重建的长任务适合 Cloud。入口不同，不代表需要学习四套完全独立的方法。

1.4 Codex 不替开发者做最终判断 ​

1.4.1 它不能保证结果绝对正确 ​

模型可能误解业务、遗漏边界或编写只对当前样例成立的测试。代理能够运行命令，只能证明它执行了验证，不能证明验证覆盖了所有真实要求。

1.4.2 它不能猜出未表达的需求 ​

业务规则、兼容承诺、性能预算和组织红线必须由人给出。未写明的信息只能被推断，越高风险的任务越不能依赖默认猜测。

1.4.3 它不能绕过真实权限系统 ​

仓库、云环境、连接器和本地文件系统仍执行各自权限。ChatGPT Workspace 身份、GitHub 权限和 Platform API 凭据也不是同一套授权。

1.5 成本来自计算与上下文 ​

1.5.1 订阅与 API 是不同计费边界 ​

Codex 可以通过符合条件的 ChatGPT 方案使用，也可以在支持的程序化场景中使用 API 凭据。具体额度、模型和可用性变化较快，应实时查看官方 Pricing 页面，不在项目规范中永久写死。

1.5.2 无效上下文会制造隐性成本 ​

过大的日志、无关目录、重复对话和模糊目标会增加检索、推理与工具往返。真正的优化不是少写几个字，而是让每次计算都靠近可验收结果。

1.6 官方文档应成为易变事实的来源 ​

中文解读适合建立概念地图，项目文档适合记录本仓库规则，当前 CLI 帮助适合确认本机版本，OpenAI Docs 则负责产品能力、配置与安全边界。模型名称、价格、入口名称和实验功能发生变化时，应回到官方页面重新核验。

二、四种入口如何选择：App、CLI、IDE 与 Cloud ​

新手最容易把时间浪费在“到底装哪个 Codex”上。官方文档给出的答案并不是四选一，而是先区分运行位置和工作方式：本地入口共享当前工作区，Cloud 在托管环境中执行；桌面端强调任务编排与审阅，CLI 强调终端控制，IDE 强调编辑器上下文。

2.1 开始前先准备可恢复项目 ​

2.1.1 使用版本控制仓库 ​

Git 能让代理修改变成可观察 Diff，也让已有用户改动得到保护。第一次练习应选择可以丢弃的小仓库，不在生产仓库中测试未知权限与自动化行为。

2.1.2 确认工作目录与当前状态 ​

Codex 读取的是当前执行环境中的文件。启动前检查目录、分支、未提交修改和项目规则，避免代理在错误仓库中完成一个“看似正确”的任务。

2.1.3 把完成条件写进任务 ​

“帮我看看项目”没有明确终点。“解释入口、修改指定函数、运行某项测试并报告 Diff”才是一条可以验收的任务链。

2.2 桌面端适合可视化任务编排 ​

2.2.1 Thread 是任务边界 ​

一个 Thread 应围绕一个主目标，保留相关上下文、工具过程和反馈。将多个无关问题塞进同一线程，会让范围、权限和结束条件彼此污染。

2.2.2 Local 与 Worktree 提供不同隔离 ​

Local 直接使用当前工作区，适合继续开发者手上的任务；Worktree 为并行任务提供独立检出，减少两个任务互相读取未完成改动。隔离工作树并不自动解决公共接口冲突，最终仍需 Review。

2.2.3 Diff 面板是验收入口 ​

图形化 Review 能把代理解释与实际改动放在一起。用户对具体行的反馈会成为下一轮上下文，比一句“还是不对”更有信息量。

2.3 CLI 适合终端工作流 ​

2.3.1 交互模式适合边观察边纠偏 ​

在仓库中启动 codex 后，可以用自然语言描述任务、查看状态、调整权限并继续对话。它适合调试、搜索、构建和测试密集的项目。

2.3.2 斜杠命令管理会话而不是业务目标 ​

模型、权限、状态、Review 和压缩属于控制面；业务目标仍应写成自然语言。不要把项目约束寄托在某个短命令上。

2.3.3 非交互执行属于自动化章节 ​

codex exec 面向脚本与 CI，不是交互会话的简单别名。它需要确定输入、结构化输出、退出状态与预设权限，本文第八章单独展开。

2.4 IDE 入口用精确上下文降低噪声 ​

2.4.1 当前文件与选区提供定位 ​

编辑器知道正在查看的文件和选中代码，适合局部实现、解释和即时 Review。精确上下文减少无关搜索，却不意味着代理只会读取选区。

2.4.2 IDE 与 CLI 应共享项目规则 ​

同一仓库的构建、测试和代码风格不应为不同入口复制多份。AGENTS.md 与项目配置承担跨入口事实，临时要求保留在当前 Prompt。

2.4.3 复杂长任务可以转向其他执行域 ​

当任务需要大量构建、并行探索或长时间运行时，可以在 Worktree、CLI 或 Cloud 中执行，再回到 IDE 审查局部结果。

2.5 Cloud 必须从仓库重建现实 ​

2.5.1 Environment 定义依赖和工具 ​

Cloud 任务看不到本机隐藏状态，需要从仓库、设置脚本和环境配置建立可运行现场。能够在干净环境重建，是云端可靠性的前提。

2.5.2 设置阶段与代理阶段应分离 ​

官方安全模型允许设置阶段安装依赖并使用必要 Secrets，代理阶段默认更受限制。秘密不应作为长期上下文留给模型，也不应写进仓库。

2.5.3 远程结果仍要进入 Git 审查链 ​

Cloud 可以产出 Diff 或 Pull Request，但合并前仍需测试、Review 和仓库保护规则。远程完成不等于自动发布。

2.6 身份认证决定入口，不决定全部权限 ​

ChatGPT 登录、API Key、GitHub 连接和第三方系统授权属于不同边界。登录 Codex 不等于拥有仓库写入权限，连接 GitHub 也不等于本地命令能够访问网络。凭据应使用官方登录流程和安全存储，不进入 Prompt、源码或日志。

2.7 AGENTS.md 让入口共享项目契约 ​

2.7.1 写行动规则而不是百科全书 ​

有效内容包括仓库结构、构建测试命令、代码规范、禁止动作和完成标准。模糊口号会占用上下文，却不能指导具体行动。

2.7.2 更近的规则描述局部差异 ​

全局规则提供个人默认，仓库规则提供团队标准，子目录文件补充局部约束。代理应读取目标路径适用的规则链。

2.7.3 规则必须保持真实 ​

过时命令比没有命令更危险。团队应在构建方式、目录结构或发布流程变化后更新规则，并把临时任务要求留在 Prompt 中。

三、怎样描述任务：Prompt、上下文与完成证据 ​

高质量 Prompt 不是写得像法律合同，也不是堆满模型术语，而是让代理知道目标、相关事实、真正边界和完成证据。OpenAI Docs 当前建议从自然语言开始，对重要任务补充 Goal、Context、Output 与 Boundaries，并通过后续反馈持续收敛。

3.1 Prompt 先描述结果 ​

3.1.1 Goal 定义最终状态 ​

不要只写“优化”“检查”或“完善”。目标应说明哪种行为需要改变、面向谁、在哪个范围生效，以及什么现象代表成功。

3.1.2 Context 提供会改变判断的事实 ​

相关文件、报错、接口契约、版本和现有测试都属于上下文。只提供真正影响结果的材料，比把整个仓库和所有日志塞进对话更有效。

3.1.3 Output 定义交付形态 ​

需要代码、报告、表格、补丁还是只读诊断，应明确说明。输出格式会影响代理的调查深度与工具选择。

3.1.4 Boundaries 阻止真实损失 ​

不能改的模块、禁止新增的依赖、需要保留的 API，以及删除、发布、发送消息前的确认要求，都是高价值边界。边界应少而关键，不要把每一步都写死。

3.2 复杂任务先建立计划 ​

3.2.1 模糊任务需要先调查 ​

面对陌生仓库或跨模块问题，让代理先定位入口、调用链、配置源、测试方式和风险，再给出计划。没有事实地图的计划只是格式完整的猜测。

3.2.2 计划必须连接验证 ​

每个阶段都应说明改动点和验证方式。只列“分析、编码、测试”没有决策价值；真正计划会说明哪些文件受影响、何种失败会阻止下一阶段。

3.2.3 计划确认不代表无限授权 ​

批准方案不等于允许删除、发布或修改系统配置。任务范围与具体高风险动作仍应分别确认。

3.3 不同工作流需要不同证据 ​

3.3.1 探索任务交付事实地图 ​

成果应包含入口、关键模块、数据流和待确认项，不应在尚未理解系统时顺手重构。

3.3.2 Bug 修复先证明因果链 ​

可靠顺序是复现、定位、建立回归测试、最小修改和重新验证。靠近报错的警告不一定是根因，代理必须用源码和运行证据连接现象与原因。

3.3.3 重构先锁定外部行为 ​

重构改变结构而不应改变契约。现有测试、调用方和公开 API 构成保护网；保护网不足时，先补能固定行为的测试。

3.3.4 测试关注失败语义 ​

代理生成的测试可能只复述当前实现。人要检查断言是否真的验证需求，旧代码是否会失败，边界与错误分支是否被覆盖。

3.4 上下文管理决定长任务质量 ​

3.4.1 上下文容量不等于上下文质量 ​

无关文件、重复日志和过期结论会淹没关键约束。上下文工程的目标是提高信噪比，而不是追求最大输入量。

3.4.2 稳定事实应写入项目文件 ​

项目规范写入 AGENTS.md，进度写入 ROADMAP.md，架构决策进入专门文档，验证结果保留为可定位记录。这样任务不依赖模型永久记住长对话。

3.4.3 阶段边界适合压缩历史 ​

完成调查或一个实现阶段后，保留目标、决策、改动、证据和待办，压缩失败尝试与重复输出。压缩不能丢失风险和未完成事项。

3.5 反馈应减少歧义 ​

“不对”“再优化”几乎没有新信息。有效反馈会指出具体文件、实际行为、预期行为和违反的边界。桌面 Diff 中的行级评论、失败测试和可复现日志，都是比情绪评价更好的反馈。

当用户在 Codex 工作期间追加消息时，还要区分 Steer 与 Queue：前者改变当前运行方向，后者等待下一轮。方向性修正应及时 Steering，独立新任务应排队或创建新 Thread。

3.6 完成条件必须由外部证据定义 ​

代理停止输出不代表任务完成。每项要求应能对应 Diff、测试、构建、运行日志或人工检查；无法验证的部分要明确说明，未完成项不能藏在总结中。

一条成熟的任务链是：目标可观察、上下文可定位、边界可执行、计划可检查、修改可审查、验证可重复。Prompt 的价值最终体现在返工减少，而不是文本长度增加。

四、如何稳定运行：配置、模型选择与速度优化 ​

许多“模型不听话”的问题，根因其实是配置层级、工作目录、权限、工具或项目规则不一致。OpenAI Docs 把 Codex 配置拆成个人默认、项目配置、Profile 与一次性覆盖，并强调不同入口共享主要配置层。理解覆盖关系，比背诵某个版本的全部配置键更重要。

4.1 配置与项目知识不是同一层 ​

4.1.1 配置决定默认运行姿势 ​

模型、推理强度、权限、功能开关、MCP、Hooks 和界面行为属于配置。它们回答“Codex 默认怎样运行”。

4.1.2 AGENTS.md 决定项目做事规则 ​

构建命令、代码风格、目录边界和完成标准属于项目指令。它回答“在这个仓库应该怎样工作”。把项目百科塞进 config.toml，会让规则难以审查与共享。

4.1.3 Prompt 决定本次任务 ​

一次性的目标、文件范围和特殊约束应留在当前会话。不要为了一个临时任务修改全局默认。

4.2 配置优先级必须可解释 ​

4.2.1 个人配置提供跨项目默认 ​

用户级 config.toml 适合模型偏好、常用 Profile 和个人工具连接。默认值应保守，避免一个高权限项目习惯扩散到所有仓库。

4.2.2 项目配置提供可信仓库默认 ​

仓库级 .codex/config.toml 可以共享项目需要的配置，但只有在信任仓库时才应加载。外部仓库中的配置本身也属于不可信输入。

4.2.3 命令行覆盖只服务一次运行 ​

临时参数适合诊断或比较，不应成为团队不可见的长期事实。任务结束后要能从版本化配置重建行为。

4.2.4 Profile 让场景切换显式化 ​

只读审计、本地开发和 CI 可以使用不同 Profile。Profile 名称应表达用途，并与实际权限、模型和工具条件一致。

4.3 模型选择从任务特征开始 ​

4.3.1 复杂度决定推理需求 ​

机械修改、查找符号和固定格式转换通常不需要最高推理强度；跨模块设计、陌生系统诊断和长时间 Agent 任务需要更强规划。

4.3.2 风险决定验证强度 ​

简单但涉及身份、支付、迁移或公开接口的任务，仍需要严格 Review。模型强度不能替代安全与测试。

4.3.3 工具条件可能比模型更关键 ​

无法读取真实日志、运行测试或获取正确目录时，更强模型也只能基于缺失信息推断。先修复环境，再判断是否需要换模型。

4.3.4 用团队真实任务建立基准 ​

比较完成率、人工修正、验证通过率、总耗时和成本，而不是只看单次演示。官方可用模型和推荐会变化，选择应定期重测。

4.4 推理强度不是越高越好 ​

较低强度适合范围明确、反馈快速的任务；较高强度适合需要计划、权衡和多轮工具验证的任务。盲目提高强度会增加延迟和成本，却无法修复错误上下文。

可以在代表性任务上比较多个档位，并把结果记录为团队经验。具体档位名称和模型支持情况以当前界面与官方文档为准。

4.5 速度要看端到端链路 ​

4.5.1 缩小搜索范围 ​

指出入口、相关目录、错误日志和验证命令，是最便宜的加速方式。它减少无目的搜索和无关文件读取。

4.5.2 建立快速局部反馈 ​

先运行目标单元测试或静态检查，局部通过后再扩大验证。每轮全量构建会浪费时间，永远不跑集成验证又会遗漏风险。

4.5.3 使用可重建缓存 ​

依赖缓存和构建产物能减少等待，但必须有失效规则。来源不明的旧缓存会制造假通过。

4.5.4 分离独立任务 ​

互不依赖的调查或实现可以并行，修改同一接口的任务不应为了“多代理”强行并行。并行的收益来自独立性，不是代理数量。

4.6 诊断配置问题要看实际生效值 ​

遇到行为与预期不一致，依次核对当前工作目录、加载的配置层、选中 Profile、模型与推理强度、权限模式、Feature 状态、MCP 和项目规则。不要只盯着某一个 config.toml 文件，因为更高优先级覆盖可能已经改变结果。

4.7 配置治理的最终目标是可重建 ​

团队成员和 CI 应能从版本化仓库、明确个人前置条件和官方当前版本重建同类行为。任何只有某台机器“碰巧能跑”的配置，都不是可靠工程能力。

五、怎样控制风险：沙箱、审批、网络与秘密 ​

Codex 能读文件、运行命令和调用外部工具，因此安全不能只依赖一句“不要做危险操作”。OpenAI Docs 当前把本地控制拆成 Sandbox 与 Approval：前者决定技术上能接触什么，后者决定何时必须暂停并由人或自动审查器判断。

5.1 Sandbox 与 Approval 不能混用 ​

5.1.1 Sandbox 是强制执行边界 ​

它限制命令可以读取或写入的路径、是否能够访问网络，以及能否接触工作区外资源。Git、包管理器、测试程序和脚本子进程同样继承边界。

5.1.2 Approval 是例外决策机制 ​

当动作需要越过当前边界时，Codex 可以说明目标、范围和原因，再请求批准。批准一个精确动作，不等于永久放开全部系统。

5.1.3 自动审查只改变审查者 ​

Approve for me 或 Auto-review 可以处理符合条件的请求，但不会自动扩大 Sandbox。自动审查仍应执行组织策略，无法判断时应升级给人。

5.2 权限模式围绕任务选择 ​

5.2.1 只读适合调查与规划 ​

架构分析、日志诊断和方案讨论通常不需要修改文件。只读边界能证明本轮不会改变仓库状态。

5.2.2 工作区写入适合常规开发 ​

代理可以在活动工作区编辑并运行常规本地命令，网络和工作区外动作继续受到限制或审批。这是低摩擦开发的常见边界。

5.2.3 全访问必须明确接受风险 ​

Full access 或 danger-full-access 移除重要隔离，不应为了少几次提示而默认启用。高权限适用于用户明确接受广泛访问且环境本身已经隔离的场景。

5.2.4 Permission Profile 表达最小能力 ​

命名 Profile 可以组合文件与网络规则，让只读审计、项目编辑和特定工具访问形成可复用边界。更窄的拒绝规则应继续保护 .env 等敏感路径。

5.3 网络许可与内容可信是两回事 ​

5.3.1 默认关闭网络减少外泄面 ​

本地工作区写入不应被理解为任意联网。需要下载依赖或访问服务时，按任务启用网络，并尽量限制到必要域名。

5.3.2 Web Search 与命令网络可能分离 ​

搜索工具、浏览器、插件和本地命令使用不同控制。允许搜索官方文档，不代表任意脚本可以访问互联网。

5.3.3 白名单不能证明远端内容安全 ​

依赖脚本、Issue、网页和文档都可能包含恶意或误导内容。域名策略限制目的地，内容审查和工具权限限制后续动作。

5.4 Prompt Injection 是指令权混淆 ​

代理读取网页、仓库说明或日志时，其中的文字只是任务数据，不能自动覆盖系统、用户与项目规则。可靠防护不只识别“忽略前文”之类句式，而是同时限制秘密读取、网络出口、工具副作用和最终发布动作。

5.5 Secrets 必须离开普通上下文 ​

5.5.1 不把密钥写进 Prompt ​

Prompt、源码、提交和普通日志都不是秘密存储。需要认证时使用官方登录、受控环境变量或组织秘密管理系统。

5.5.2 缩短凭据生命周期 ​

能使用短期令牌就不共享长期 Token。云端环境可以把 Secrets 限制在设置阶段，避免在代理执行阶段持续暴露。

5.5.3 输出同样要防止泄漏 ​

命令回显、错误日志、Diff 和聊天回复都可能带出敏感值。验证流程应包含秘密扫描和输出边界检查。

5.6 高风险动作保留人工责任 ​

删除文件、覆盖 Git 历史、数据库迁移、密钥轮换、发送外部消息、合并、部署和公开发布，具有不可逆或多人影响。代理可以准备目标清单、影响分析、Dry-run、恢复方式和验证证据，最终确认仍由责任人完成。

审批时应核对动作意图、精确目标、必要原因、可逆性和授权范围。能批准一个命令，就不批准整个会话；能开放一个域名，就不开放任意网络。

六、任务在哪里执行：本地、Worktree、Cloud 与 Review ​

Codex 可以在当前工作区直接修改，也可以在独立 Worktree 或 Cloud Environment 中完成任务。三者不是性能档位，而是不同的状态与隔离边界：本地最贴近开发者当前现实，Worktree 隔离并行修改，Cloud 强调可重建和长时间执行。

6.1 本地工作区适合连续开发 ​

6.1.1 它能够看到未提交状态 ​

代理读取当前文件、依赖和工具链，适合继续开发者正在进行的工作。与此同时，未提交修改属于用户资产，代理不能静默覆盖、回退或混入无关提交。

6.1.2 本地结果最容易即时验证 ​

测试、调试器、模拟器和私有工具通常已经存在，反馈速度快。缺点是多个任务共享一个目录时容易互相污染。

6.1.3 开始前必须建立状态基线 ​

检查当前分支、Git 状态、适用规则和已有失败。没有基线，就无法判断后续差异属于谁。

6.2 Worktree 用目录隔离并行任务 ​

6.2.1 每个任务拥有独立检出 ​

Git Worktree 共享对象数据库，却为不同分支提供独立文件目录。一个任务的未完成文件不会被另一个任务直接读取。

6.2.2 隔离不等于没有设计冲突 ​

两个任务若修改同一接口，合并时仍会发生冲突。分派前要明确文件所有权、公共契约和合并顺序。

6.2.3 验证必须在对应 Worktree 中完成 ​

不能用主工作区的旧构建结果证明分支成功。每个工作树都要记录依赖、测试和实际提交。

6.3 Cloud 从仓库重建任务现场 ​

6.3.1 Repository 是远程事实入口 ​

Cloud 不会自动获得本机未提交文件。需要执行的代码、配置和说明必须进入连接仓库或明确环境映射。

6.3.2 Environment 描述依赖与设置 ​

设置脚本安装依赖、准备工具和缓存。可靠环境应可重复运行，不能依赖某次手工登录留下的隐式状态。

6.3.3 Secrets 与代理阶段分离 ​

官方云端安全模型区分设置和代理运行阶段，Secrets 可以只在设置时可用。这样依赖安装能够认证，模型执行阶段不必持续接触秘密。

6.3.4 Internet access 应按域名收口 ​

云端任务默认不应拥有任意网络。只开放完成任务需要的资源，并把网页与下载内容继续视为不可信输入。

6.4 Code Review 是独立质量环节 ​

6.4.1 Review 不等于让代理再写一遍 ​

审查关注正确性、回归、安全、可维护性和测试缺口，应以 Diff 与基线分支为事实。审查者不应在没有证据时重复实现者的假设。

6.4.2 自审与独立审查解决不同问题 ​

实现线程的自审能发现明显遗漏，独立上下文审查更容易挑战原有方向。高风险修改需要人类负责最终取舍。

6.4.3 发现必须可定位 ​

每条问题应关联文件、行、风险和触发条件。泛泛而谈的“可能有问题”难以行动，也容易制造 Review 噪声。

6.5 Git 是跨执行域的事实账本 ​

本地、Worktree 和 Cloud 最终都要用 Git 交付。一个提交应围绕可解释结果，包含与目标直接相关的文件和验证证据。推送、创建 Pull Request、合并与发布会影响外部协作者，必须遵循授权边界。

6.6 Windows 与 WSL 按目标工具链选择 ​

依赖 Windows SDK、PowerShell 或本机 GUI 的项目适合原生环境；依赖 Bash、容器和 Linux 工具的项目适合 WSL。仓库与构建目录尽量放在主要执行侧，明确路径、大小写、符号链接、可执行位和 CRLF 策略。

Windows 原生 Sandbox 与 WSL 使用不同平台机制，但目标相同：让命令在受控边界中运行。具体前置条件以当前官方页面为准，不通过关闭系统安全策略来掩盖配置问题。

七、如何扩展能力：Memory、MCP、Skills、Plugins 与多代理 ​

Codex 的扩展体系看起来名词很多，但每一层解决的问题不同：AGENTS.md 记录项目规则，Memory 保存跨任务经验，Skill 封装工作流，MCP 连接工具与数据，Plugin 负责打包分发，Hook 在生命周期节点执行机械检查，Subagent 用隔离上下文并行处理独立任务。

7.1 先按信息寿命选择承载层 ​

7.1.1 Prompt 保存一次性要求 ​

当前目标、临时范围和本次特殊输出只在当前 Thread 有效，不需要永久写入项目。

7.1.2 AGENTS.md 保存仓库规则 ​

构建、测试、目录边界、工程规范和完成标准由团队版本化维护。它是显式指令，不是自动推断的记忆。

7.1.3 Memory 保存可复用经验 ​

Memory 适合跨任务保留用户偏好、稳定上下文和历史经验，但任何会变化的事实都应在使用前重新验证。敏感值和未经确认的推断不应长期保存。

7.2 MCP 连接外部工具与数据 ​

7.2.1 MCP 是协议边界 ​

它允许 Codex 发现并调用外部工具、读取资源或使用服务提供的能力。MCP 解决“怎样连接”，不自动解决数据质量、身份、权限和审计。

7.2.2 工具描述决定代理怎样调用 ​

清晰名称、参数 Schema、返回结果和副作用标记能减少误用。破坏性工具必须显式标注，并进入审批链。

7.2.3 接入前先画数据流 ​

明确请求会带出哪些上下文、服务能访问什么、结果保存在哪里、失败如何处理。远程 MCP 和本地 STDIO Server 的信任面不同。

7.3 Skill 把重复经验封装成流程 ​

7.3.1 Skill 适合重复且边界稳定的任务 ​

源码审查、发布检查、固定格式报告和特定调试流程，都可以用 SKILL.md 描述触发条件、步骤、资源与验证。

7.3.2 渐进式披露控制上下文成本 ​

代理先看到能力摘要，确认匹配后再读取完整说明，只有需要时才加载参考和脚本。这样能力库可以增长，而不必把全部内容塞入每次会话。

7.3.3 Skill 必须拥有完成证据 ​

只有指导语而没有检查方法的 Skill，容易把错误流程稳定复用。可靠 Skill 应说明输入、产物、失败条件和验证。

7.4 Plugin 是能力分发单元 ​

7.4.1 一个 Plugin 可以携带多种能力 ​

Skills、MCP、Hooks、应用连接和资产可以被统一打包，便于团队安装、更新与停用。

7.4.2 安装会扩大信任边界 ​

管理员和用户需要审查来源、负责人、权限、数据流、版本与撤销方式。安装插件不等于批准其所有连接器动作。

7.4.3 公共能力优先组合而不是复制 ​

同一流程若在多个插件内复制，会产生版本漂移。稳定基础能力应共享，项目差异放进更靠近仓库的规则或 Skill。

7.5 Rules 与 Hooks 管理动作边界 ​

7.5.1 Rules 负责命令策略 ​

规则可以识别允许、需要审批或禁止的命令模式，减少低风险重复确认，同时保留高风险关口。

7.5.2 Hooks 负责生命周期检查 ​

Hook 在工具调用、命令执行或会话事件前后运行机械逻辑，适合格式检查、策略校验、日志记录和阻断。

7.5.3 机械执行必须保持简单 ​

Hook 的输入输出、退出码、超时和失败行为要明确。不要把复杂业务决策塞进难以观察的钩子。

7.6 Subagent 用隔离换取并行 ​

7.6.1 独立子任务才适合委派 ​

资料检索、互不重叠模块分析和独立测试调查可以并行。频繁共享状态或修改同一文件的任务更适合顺序执行。

7.6.2 子代理返回证据而不是只报结论 ​

主线程需要知道读取了哪些来源、得到什么结果、有哪些不确定项。验收责任不能外包给子代理。

7.6.3 并行数量受整合成本限制 ​

代理越多，协调、冲突和上下文回传成本越高。吞吐提升来自任务可分解，而不是盲目增加执行者。

7.7 建立扩展体系的推荐顺序 ​

先让 Prompt 与 AGENTS.md 稳定单代理工作，再把重复流程提炼为 Skill；确需外部数据时连接最小权限 MCP；需要团队分发时封装 Plugin；需要机械拦截时使用 Rules 和 Hooks；任务真正独立后才增加 Subagent。

7.8 扩展能力必须可撤销 ​

每项扩展都要有版本、负责人、复查日期和停用方法。外部服务失效、权限扩大或协议变化时，团队应能移除单项能力，而不是让整个 Codex 环境不可用。

八、怎样进入流水线：codex exec、GitHub Action 与定时任务 ​

交互会话中，人可以随时纠正代理；进入脚本、CI 和定时任务后，系统必须提前定义输入、权限、输出、失败状态和重复执行语义。自动化的成熟标志不是“没人看”，而是每一步都可以被机器判断、被人复盘。

8.1 自动化之前先定义机器合同 ​

8.1.1 输入必须确定 ​

仓库版本、任务文本、相关文件和环境都应可重建。依赖临时聊天、未提交文件或人工选择的流程不能直接搬进 CI。

8.1.2 输出必须可消费 ​

自然语言总结适合人阅读，后续程序需要结构化事件、指定输出文件和稳定 Schema。关键结论不能靠脆弱的字符串匹配提取。

8.1.3 退出状态必须真实 ​

任务失败却返回成功，会让流水线产生假绿灯。调用方要区分模型未完成、工具失败、验证失败和环境故障。

8.1.4 权限必须按阶段拆分 ​

只读分析、生成补丁、上传产物、评论 Pull Request 和发布不应共享同一最高权限。

8.2 codex exec 是非交互执行核心 ​

8.2.1 它面向脚本而不是持续对话 ​

codex exec 接收任务后独立运行，适合批量审计、固定报告、CI 诊断和后台 Job。需要多轮连续上下文时，应显式管理会话或使用 SDK。

8.2.2 标准输出与标准错误要分工 ​

机器结果、事件流和最终文件应有稳定位置，诊断信息进入可追踪日志。调用方不能假设所有文字都属于成功结果。

8.2.3 Sandbox 与 Approval 仍然生效 ​

非交互不等于全权限。自动化应使用预先批准的 Profile 或策略，无法获得的能力必须明确失败，而不是等待无人响应的提示。

8.3 重试、超时与幂等由调用方负责 ​

8.3.1 超时要覆盖外部工具 ​

依赖安装、构建、测试和网络可能长期阻塞。超时后应保留已完成阶段和失败证据。

8.3.2 重试要区分故障类型 ​

网络瞬时错误可以重试，确定性测试失败不应反复消耗计算。重试前要确认是否已有外部副作用。

8.3.3 幂等避免重复状态 ​

同一任务重复运行不能生成多个相同评论、分支、Issue 或部署。外层系统使用任务键和状态存储控制重复。

8.4 GitHub Action 把 Codex 放进 CI ​

8.4.1 从只读 Review 开始 ​

Action 可以审查 Pull Request、生成报告或补丁。低风险起点是只读仓库并输出发现，不直接持有推送和合并权限。

8.4.2 Workflow 权限比 Prompt 更强 ​

即使 Prompt 写着“只分析”，Job 若持有写权限和 Secrets，事故半径仍然扩大。permissions、Checkout、Secret 和 Sandbox 必须显式收口。

8.4.3 Prompt 文件进入版本控制 ​

固定自动化说明应与代码一起 Review，模型、推理强度、输出位置和验证命令都应可追踪。

8.4.4 写回动作放在后续 Job ​

分析、补丁、评论和合并使用不同阶段与权限。只有前置检查通过，后续动作才获得必要能力。

8.5 Scheduled Tasks 只自动化稳定流程 ​

8.5.1 周期任务需要明确时间与环境 ​

任务的时区、频率、仓库、输入和通知目标必须显式。计划本身不能依赖某个临时 Thread 的隐含背景。

8.5.2 无变化也是合法结果 ​

巡检、报告和监控经常没有新发现。系统应区分“没有变化”“执行失败”和“需要人工处理”。

8.5.3 连续失败要升级 ​

反复重试不能替代处理。达到阈值后停止同方向消耗，保留证据并通知责任人。

8.6 自动化交付必须保留审计证据 ​

记录任务来源、仓库提交、配置、工具事件、批准、输出、测试与最终状态。审计不需要保存模型全部内部推理，但必须能够解释外部状态为何改变。

九、如何嵌入产品：SDK、App Server、Slack 与 Linear ​

当 Codex 从个人终端进入内部平台、GitHub、Slack 或 Linear，外层系统必须承担身份、租户、业务状态、幂等、审计和回写责任。集成不是把 CLI 输出搬进网页，而是选择与产品需求匹配的程序化接口。

9.1 SDK 适合程序化 Agent 工作流 ​

9.1.1 应用拥有业务状态 ​

用户、工单、租户、重试和审批状态应保存在应用数据库。Codex Thread 负责代理上下文，不应成为唯一业务事实源。

9.1.2 Thread 保留连续任务上下文 ​

应用可以启动运行、继续同一 Thread，并消费事件或最终结果。Thread 标识必须与业务对象和访问主体正确关联。

9.1.3 结构化输出降低集成脆弱性 ​

机器需要稳定 Schema、错误分类和产物位置。自然语言总结可以展示给人，但不能成为关键权限或发布决策的唯一解析来源。

9.2 App Server 适合丰富客户端 ​

9.2.1 它管理完整交互生命周期 ​

App Server 提供认证、线程、回合、工具事件、历史、审批和流式通知，适合构建桌面端、IDE 或内部工作台。

9.2.2 协议以当前版本 Schema 为准 ​

客户端应从运行版本生成 TypeScript 或 JSON Schema，不长期复制文章中的示例。实验传输和字段可能变化，必须建立版本兼容策略。

9.2.3 远程连接需要安全传输与认证 ​

本机 stdio、Unix Socket 与远程 WebSocket 的风险不同。非本机连接需要 TLS、能力令牌或签名令牌，并避免在命令行暴露秘密。

9.3 Agents SDK 可以把 Codex 当专业工具 ​

更大的 Agent 系统可以通过 MCP Server 调用 Codex。上游 Agent 负责业务编排，Codex 在受控工作区完成代码任务并返回结果。外层仍要限制工作目录、权限、超时和输出去向。

MCP 只提供调用协议，不能自动继承业务用户权限。上游自然语言同样属于不可信输入，不能绕过 Codex 的沙箱和审批。

9.4 Slack 与 Linear 是协作入口 ​

9.4.1 消息与工单需要转成执行合同 ​

一句“修一下上面的问题”可能缺少仓库、版本、范围和验收条件。触发前应补齐目标与上下文，长线程需要在最新消息重述关键事实。

9.4.2 环境与仓库选择必须可见 ​

集成会在用户可访问环境中匹配仓库，歧义时可能使用最近环境。高价值任务应显式指定目标，并在结果中记录实际执行位置。

9.4.3 回复结果不等于允许合并 ​

Slack 或 Linear 中的摘要和任务链接方便协作，但代码仍要进入 Pull Request、Checks 和 Review。协作工具不能替代源代码平台治理。

9.5 集成平台必须补齐安全护栏 ​

9.5.1 身份映射 ​

不同系统中的账号要关联到真实责任主体，不能用共享长期 Token 混淆动作来源。

9.5.2 权限分层 ​

读取工单、访问仓库、写补丁、回复消息和合并代码使用不同权限，并分别接受组织与源系统控制。

9.5.3 幂等回写 ​

重试不能制造重复评论、分支或任务。应用用稳定业务键关联每次执行。

9.5.4 审计追踪 ​

请求、Thread、仓库版本、工具事件、批准、验证与外部状态必须能够串联。

9.6 选择接口看责任而不是功能数量 ​

固定批处理和后端 Job 使用 SDK；需要线程、流式事件和审批界面的客户端使用 App Server；已有 Agent 平台把 Codex 当专业执行器时使用 MCP；团队讨论和工单派发使用 Slack 与 Linear。选择最少承担额外责任的接口，通常比选择“功能最多”的接口更可靠。

十、如何规模化落地：身份、策略、审计与企业治理 ​

个人使用 Codex 时，边界通常是一台电脑和一个仓库；企业使用时，同时涉及 ChatGPT Workspace、本地运行时、Codex Cloud、Platform API、Plugins、Connectors 和源代码系统。官方 Administration 文档强调，这些控制面彼此关联却不互相替代。

10.1 企业先画清六个控制面 ​

10.1.1 Workspace 身份与角色 ​

成员、席位、组和角色决定用户可以访问哪些 Workspace 能力。管理员角色只授予真正负责管理的人。

10.1.2 本地运行时策略 ​

桌面端、CLI 和 IDE 在设备上执行命令时，受到 Permission Profile、Sandbox、Approval、Feature 和受管配置约束。

10.1.3 Codex Cloud 与仓库连接 ​

云端环境、Secrets、网络和源代码平台权限共同决定远程任务能访问什么。Workspace 身份不会绕过 GitHub 保护规则。

10.1.4 Platform API ​

API 组织、Project、Key、配额与账单属于独立边界。ChatGPT 方案不自动授予任意 API 权限。

10.1.5 Plugin 与 Connector ​

Workspace 控制能力是否可用，连接系统继续控制真实数据与动作。安装插件不代表批准所有外部副作用。

10.1.6 Analytics 与 Compliance ​

分析采用情况和导出审计事件服务不同目标，需要不同权限与下游保护。

10.2 角色与权限必须分层验证 ​

10.2.1 同一个人拥有多种系统身份 ​

工程师可能同时是 Workspace 成员、GitHub 写入者、API Project 使用者和本机管理员。每个身份都有独立审批者和生命周期。

10.2.2 最小权限围绕工作流分配 ​

代码只读 Review、生成补丁、Cloud 执行、评论 Pull Request 和生产发布是不同阶段，不应共用最高权限。

10.2.3 代表用户测试比配置截图可靠 ​

管理员应使用具有目标权限的真实成员验证登录、模型可见性、仓库访问、本地策略和连接器动作。页面显示“已启用”不等于端到端生效。

10.3 Managed Configuration 约束运行时 ​

10.3.1 默认值与强制要求分离 ​

默认配置提高一致性，requirements.toml 等受管要求限制成员不能超出的模型、权限和功能边界。

10.3.2 仓库配置不能授予组织权限 ​

.codex、.agents、Rules 和 Skills 适合共享项目工作流，但不能授予 Workspace、API 或源系统访问。

10.3.3 客户端版本需要治理 ​

新配置能力可能要求最低版本。组织需要分批更新、兼容期、验证和撤回路径，避免旧客户端静默忽略策略。

10.4 数据治理覆盖输入与输出 ​

10.4.1 数据分类决定可用能力 ​

公开代码、内部代码、客户数据和受监管信息采用不同模型、连接器、网络和日志策略。

10.4.2 Secrets 使用短期受控路径 ​

凭据不进入 Prompt、源码和普通日志。云端设置阶段、本地秘密管理和短期 Token 减少暴露面。

10.4.3 输出同样可能敏感 ​

Diff、任务摘要、聊天回复、Analytics 导出和 Compliance 记录都可能包含内部信息，需要访问、保留和删除策略。

10.5 插件与 Skills 属于供应链 ​

10.5.1 准入审查来源和能力 ​

确认负责人、目标用户、Skills、MCP、Hooks、Connector、数据和外部动作。

10.5.2 更新必须重新评估权限 ​

新版本可能新增工具或改变数据流。版本升级不能只看功能，需要比较能力清单。

10.5.3 每项能力都要能撤销 ​

记录复查日期、停用方式和事故负责人。源失联、权限扩大或协议变化时能够快速移除。

10.6 Analytics 与 Compliance 回答不同问题 ​

10.6.1 Analytics 观察采用和活动 ​

Workspace Analytics 与 Codex Analytics 适合交互查看趋势，Analytics API 适合把聚合指标接入数据仓库与 BI。

10.6.2 Compliance 支持审计和调查 ​

Compliance API 面向安全、法务和治理记录，不是生产力排行榜。字段、保留和访问要求以认证后的当前 API Reference 为准。

10.6.3 成本控制不替代安全治理 ​

Workspace Credits、使用限额和 Platform API 账单属于不同体系。限制花费不会自动限制文件、仓库和生产动作权限。

10.7 从试点到规模化逐级推进 ​

10.7.1 试点阶段验证低风险真实任务 ​

选择测试完备、数据风险低的仓库，跑通身份、项目规则、权限、Review 和支持流程。

10.7.2 团队阶段固化工作方式 ​

统一 AGENTS.md、验证命令、Review 清单和能力负责人，让成功不依赖少数高手。

10.7.3 平台阶段连接系统 ​

单仓库流程稳定后再接入 Cloud、CI、Slack、Linear、SDK 与 MCP，并补齐身份、幂等和审计。

10.7.4 持续阶段用证据调整 ​

定期复查访问、插件、客户端版本、成本、支持问题、回归缺陷和高风险事件。衡量可信交付，不以生成代码行数作为目标。

10.8 治理的最终产物是责任链 ​

企业需要能够回答：谁在什么身份下，对哪个仓库和数据，使用了什么模型与工具，经过哪些批准，产生了什么外部状态，并由什么证据完成验收。只有责任链稳定，Codex 才能从个人效率工具变成组织能力。

十一、把十章串成一条工程主线 ​

Codex 的能力可以沿着一条工程主线理解：先把目标写成可观察的状态，再提供与判断直接相关的上下文；让代理在匹配任务风险的权限和执行环境中工作；用规则、Memory、MCP、Skill 或 Plugin 补齐稳定能力；最后以构建、测试、Diff、Review、审计和责任链结束任务。任何一层缺失，都会把后续问题伪装成模型能力不足。

个人使用时，最值得先建立的是可恢复仓库、清晰任务、最小权限和真实验证。团队协作时，再增加共享规则、Worktree 或 Cloud 隔离、代码审查与自动化合同。进入平台和企业阶段后，身份映射、数据分类、插件供应链、策略下发、Analytics 与 Compliance 才成为必须建设的控制面。

成熟的 AI 编程系统不会追求让人彻底退出，而是把人的注意力从重复操作上移到目标、边界、例外和责任判断。代理负责在边界内高效执行，人负责定义什么值得做、什么风险可以接受，以及哪些证据足以让任务结束。

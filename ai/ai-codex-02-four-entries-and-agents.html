四种入口，一套大脑：从第一个任务到 AGENTS.md 的 Codex 上手地图 ​

很多人学 Codex 的顺序是反的：先背按钮，再背命令，最后才发现自己仍然不会稳定交付任务。正确的起点不是“哪个入口功能最多”，而是建立同一条工作主链：把项目交给代理，先确认它读懂，再允许局部修改，审查差异，运行验证，最后由人决定是否接受。

本文以教程第 06～11 篇为线索，对照 OpenAI Docs 的 App、CLI、IDE、Cloud 与 AGENTS.md 章节，把四个入口放进同一张执行地图。教程强调动手顺序，官方文档定义当前 Surface 与配置发现机制；本文以官方边界为准，避免把某个版本的界面当成永久规则。

一、第一个任务决定后面的使用习惯 ​

1.1 不要拿正式仓库当练习场 ​

初次使用最容易犯的错误，是直接把一个复杂正式项目交给代理，再用一句模糊要求测试它“聪不聪明”。项目越大，隐含规则越多，任何偏差都难以判断究竟来自模型、上下文、权限还是项目本身。

更有效的练习是建立一个可丢弃的小仓库：少量源文件、一条能够运行的测试、干净的 Git 状态。这个环境让每次读取、修改和命令执行都可观察，也让失败可以低成本复盘。

1.2 先让它读，再让它改 ​

在允许修改前，先让 Codex 解释项目用途、入口文件、关键数据流和测试方式。你不是为了得到一份漂亮介绍，而是在验证三件事：它是否进入了正确目录，是否加载了项目规则，是否识别了真正相关的文件。

如果解释已经偏离，立刻补充范围比让它带着错误理解继续修改更便宜。代理工作中最昂贵的不是停下来，而是错误方向上的连续行动。

1.3 修改之后必须审 diff ​

diff 是人与代理之间最重要的交接面。它比自然语言总结更接近事实，因为它精确展示状态发生了什么变化。

审查时重点看：改动是否只落在授权范围，原行为有没有被顺手改变，错误处理是否掩盖了失败，测试是否真的覆盖新行为，是否出现无关格式化、依赖或生成文件。拒绝一次修改并不是任务失败，而是给代理新的约束，让下一轮更接近目标。

二、桌面 App 适合可视化编排 ​

2.1 线程是任务边界，不是聊天标签 ​

一个线程最好只承载一件可以独立验收的工作。把探索、修复、重构和文档混进同一线程，会让上下文越来越杂，也让你难以判断某项修改来自哪个目标。

桌面端的优势在于能同时观察多个线程、打开审阅面板、查看终端和比较改动。它适合需要人持续把关、但又希望几条工作线并行推进的场景。

2.2 Local、Worktree 与 Cloud 对应不同隔离级别 ​

  • Local 直接面对当前本地工作树，适合短任务和需要现有未提交状态的工作。
  • Worktree 为同一仓库创建独立检出，适合互不重叠的并行任务。
  • Cloud 在托管环境重建仓库与依赖，适合长时间、可独立交付的任务。

选择模式前先问：任务依赖哪些未提交状态，会不会与其他工作修改同一文件，能否从 Git 和环境脚本完整重建。答案比“哪个模式更高级”更有意义。

2.3 图形审阅降低的是验收成本 ​

可视化 diff、逐块批注和内置终端不会让模型本身更强，但会降低人理解改动的成本。代理系统真正的瓶颈经常不是生成速度，而是人能否及时发现偏差。桌面端的价值就在于把验证和反馈做成持续动作，而不是任务结束后的补课。

三、CLI 是最容易组合的控制面 ​

3.1 交互模式适合边观察边修正 ​

在仓库目录运行 codex，你进入的是一个持续会话。它适合探索陌生项目、逐步缩小问题范围、查看命令输出并在中途追加约束。启动参数负责设定这次会话的工作目录、模型、沙箱等初始条件，斜杠命令负责在会话内部查看或改变状态。

3.2 非交互模式适合机器调用 ​

codex exec 面向脚本和 CI。它不依赖人在界面里持续输入，结果可以进入标准输出、文件或结构化事件流。它的设计重点不是“少一个聊天框”，而是可组合、可观测、可设置退出条件。

交互会话像结对编程，exec 更像流水线工位。前者允许随时讨论，后者要求输入、权限、输出和失败语义预先定义清楚。

3.3 CLI 不等于必须背参数 ​

稳定用法只需要记住少量入口：启动会话、查看帮助、检查版本、选择工作目录、查看状态、审查 diff、压缩上下文和退出。其余能力应在需要时通过帮助与当前版本文档查询。背诵易变命令表，反而会让旧知识覆盖真实界面。

四、IDE 扩展的核心是精确上下文 ​

4.1 当前文件和选区减少了检索噪声 ​

在 IDE 中，代理可以利用当前文件、打开的标签页、选中代码和显式提及的文件。这个优势看似只是少打几个路径，实质上是在缩小搜索空间。相关上下文越准确，代理越少需要凭文件名和全文检索猜测你的意图。

但自动上下文不是越多越好。打开几十个无关文件，会把原本精确的选区重新稀释。一个实用原则是：把直接定义、直接调用、相关测试和必要配置交给它，其余内容让代理根据证据按需读取。

4.2 IDE 与 CLI 应共享规则而非复制配置 ​

模型、项目规范、沙箱和部分登录状态应当有单一事实源。不要为了不同入口维护互相漂移的规则副本。入口只是界面，项目约束仍应集中在 AGENTS.md，工具行为集中在配置文件。

4.3 IDE 最适合局部实现与即时审查 ​

当任务围绕当前函数、组件或错误位置展开时，IDE 能让人和代理共享同一个视觉焦点。涉及大范围自动化、远程服务器或批量命令时，再切回 CLI 或云端更自然。好的工作流允许入口切换，而不是把所有任务硬塞进一个界面。

五、Cloud 是可重建的远程执行域 ​

5.1 云端任务必须从仓库重建现实 ​

云端环境看不到你本机随手安装的工具、未提交文件和本地秘密。它能依赖的输入通常包括仓库提交、环境配置、设置脚本、显式环境变量和 Secrets。

因此，云端任务暴露了项目是否真正可复现。如果换一台干净机器就无法安装依赖、启动服务或运行测试，问题不在云端代理，而在项目缺少明确的环境契约。

5.2 设置阶段与执行阶段是两个安全面 ​

安装依赖往往需要网络，代理真正处理代码时则应采用更严格的网络策略。把所有阶段都无限联网虽然方便，却扩大了提示注入和数据外传的通道。更稳的做法是区分依赖准备与任务执行，只开放必要域名，并把凭据放进 Secrets 而非普通配置。

5.3 云端交付仍然要经过人的合并门 ​

云端可以生成 diff、提交候选修改或创建 PR，但不应因为“测试通过”就自动获得生产决策权。测试只能证明已覆盖条件，不能证明需求理解、架构取舍和业务风险都正确。最终合并仍是人的责任。

六、AGENTS.md 是跨入口的项目契约 ​

6.1 写行动规则，不写项目百科 ​

一份有效的 AGENTS.md 应优先回答代理开工时最需要的问题：项目结构怎样理解，改动应落在哪里，什么命令用于验证，哪些文件不能碰，哪些操作必须先问，完成标准是什么。

背景故事、长期路线、详细 API 文档可以通过链接或其他文档承载。规则文件越长，不代表约束越强；关键规则被噪声淹没，执行反而更不稳定。

6.2 目录层级表达局部规则 ​

大型仓库不同目录可能使用不同语言、测试命令和维护边界。项目根规则定义全局共识，靠近子目录的规则补充局部要求，覆盖文件用于明确的临时或强制例外。

这是一种作用域设计：代理处理某个文件时，只应加载从仓库根到该文件目录路径上真正适用的规则。规则靠近对象，维护责任也更清楚。

6.3 好规则必须能够验证 ​

“保持代码优雅”无法直接执行，“修改 Python 后运行 pytest”可以验证；“注意安全”过于抽象，“不得读取 .env，删除和发布前必须询问”能够转成行动边界。

写规则时可以追问：如果代理违反这句话，我能否从 diff、命令或日志中证明？不能证明的表达通常还需要具体化。

七、把四个入口串成一条工作流 ​

7.1 探索阶段选择上下文最清楚的入口 ​

局部代码问题可以从 IDE 开始，大型仓库结构可以从 CLI 或桌面端开始。目标是尽快找到事实边界，而不是立刻修改。

7.2 实现阶段选择隔离最合适的执行域 ​

小改动可以留在 Local；互不重叠的并行任务使用 Worktree；耗时且可重建的任务交给 Cloud。隔离程度应由并行冲突和环境依赖决定。

7.3 验收阶段回到统一证据 ​

无论任务从哪个入口完成，最终都应回到相同证据：项目规则、文件 diff、测试输出、构建结果、运行日志和未验证边界。入口可以不同，交付门槛不能不同。

八、最小上手实践 ​

8.1 准备可丢弃仓库 ​

创建小项目并初始化 Git，确保工作区干净。加入一个简单函数和一条测试，让代理有明确可读对象与验收手段。

8.2 写一份短 AGENTS.md ​

只写项目用途、允许改动范围、测试命令、依赖限制和危险操作边界。启动 Codex 后先让它复述当前规则，确认发现链生效。

8.3 在两个入口重复同一任务 ​

分别在 CLI 和 IDE 或桌面端执行同一个局部任务，比较它们读取的上下文、审批行为和 diff 展示。你会看到，入口改变的是交互成本，工程主链保持不变。

九、结语 ​

Codex 的四种入口不是四套知识，而是同一个代理系统的四块工作台。上手的关键也不是熟悉所有按钮，而是建立稳定主链：先读懂、再授权、局部修改、审查 diff、运行验证、由人放行。

AGENTS.md 把这条主链中的项目规则固定下来，让桌面端、CLI、IDE 和云端在切换时仍然遵守同一份工程契约。掌握了这张地图，工具界面再变化，你仍然知道应该观察什么、约束什么、验证什么。

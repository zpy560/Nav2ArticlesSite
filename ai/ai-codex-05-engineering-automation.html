从单兵助手到自动化流水线：Worktree、GitHub、codex exec 与 CI 实战 ​

让 Codex 在本地改好一个文件，只是 AI 编程的起点。真正进入工程生产后，问题会变成：多个任务怎样互不干扰，改动怎样进入 Git，非交互任务怎样给机器调用，CI 失败怎样保留证据，来自 Slack 或 Linear 的需求又怎样安全落到代码。这里需要的不是更长的 Prompt，而是一条可追踪、可回滚、可审计的交付链。

本文归纳 Codex 系列第 25～29 篇，从 Worktree、Git 与 GitHub、自动化与 CI、codex exec，一直讲到 Slack、Linear、SDK 和 App Server。目标是把零散入口统一为工程流水线，而不是把代理变成不受约束的自动提交机器人。

一、并行开发的第一原则是隔离工作树 ​

1.1 同一目录不适合承载多个修改者 ​

人和代理同时在一个工作树修改文件，会出现状态互相污染：一个任务读到另一个任务未完成的改动，测试结果无法归属，Git diff 混在一起，回退也难以确定边界。

Worktree 为同一仓库提供独立目录和分支视图，共享对象数据库，却隔离工作文件。它特别适合两个互不重叠的功能、一个探索任务和一个修复任务并行推进。

1.2 隔离不是自动避免冲突 ​

如果两个任务修改同一接口，最终合并仍会冲突。Worktree 解决的是执行期污染，不解决设计上的依赖。因此分派前仍要明确文件所有权、公共接口和合并顺序。

1.3 每个工作树都要独立验证 ​

不要在 A 工作树修改，却拿 B 工作树的构建结果证明成功。依赖安装、生成文件和测试命令都应在对应环境执行，并在交付时记录分支、提交和验证证据。

二、Git 是代理改动的事实账本 ​

2.1 干净起点让差异可归因 ​

任务开始前先检查分支、工作树状态和远端关系。已有未提交修改属于谁、能否触碰，必须明确。代理不应覆盖、回退或顺手提交用户原有工作。

2.2 提交应围绕可解释结果 ​

一个提交最好对应一个可独立说明和验证的变化。提交信息要写清改了什么以及为什么，而不是泛泛写“优化”。生成文件、密钥、缓存和无关格式化不应混入。

2.3 推送和建 PR 是外部状态变更 ​

本地提交通常可恢复，推送、创建 PR、合并和发布则会影响协作者或公众。代理可以准备分支、摘要、测试证据和 PR 文案，但外部动作应遵守项目授权规则。

2.4 GitHub 工作流要以审查为中心 ​

Issue 提供问题上下文，分支承载实现，PR 汇总差异与验证，Review 处理反馈，Checks 提供自动证据。Codex 的价值是帮助贯通这些信息，不是绕开任何一个质量门。

三、自动化之前先把任务定义成机器合同 ​

3.1 自动化任务必须可重复 ​

同一输入在同一版本环境下，应产生可解释的相同类别结果。依赖隐式桌面状态、临时登录或人工选择的流程，不能直接搬进 CI。

3.2 输入、输出和退出状态缺一不可 ​

机器需要知道从哪里读取仓库和任务，结果写到哪里，成功和失败怎样通过退出码表达。只输出一段自然语言总结，却始终返回成功，会让流水线把失败当成通过。

3.3 权限要按流水线阶段拆分 ​

分析阶段只读仓库即可，生成补丁需要工作区写入，上传产物或评论 PR 才需要网络和令牌。不要为了最后一步方便，让所有阶段一开始就持有最高权限。

四、codex exec 是非交互执行核心 ​

4.1 它面向脚本而不是持续对话 ​

codex exec 接收明确任务，在非交互环境中运行，并把结果提供给后续程序。它适合批量审计、生成报告、处理固定格式任务和 CI 工位。

4.2 输出应优先结构化 ​

人可以阅读散文式总结，机器更需要 JSON、事件流、指定文件和稳定字段。结构化输出便于提取结果、设置阈值和关联日志，也减少对自然语言措辞的脆弱解析。

4.3 超时、重试与幂等需要调用方设计 ​

代理可能遇到网络、依赖或测试波动。流水线要设置合理超时，区分可重试故障和确定性失败，并避免重试造成重复评论、重复分支或重复发布。

4.4 非交互不代表无人负责 ​

即使没有人在终端中逐步确认，任务仍需要预先批准的权限范围、明确停止条件和完整审计记录。自动化越深入，运行边界越要显式。

五、CI 中的代理首先是一名诊断者 ​

5.1 先读取失败证据再修改 ​

可靠的 CI 修复从失败 Job、具体步骤、日志片段和相关提交开始。代理应区分产品缺陷、测试不稳定、环境故障和权限问题，再决定是否需要代码变更。

5.2 不要靠关闭检查换取绿色 ​

注释测试、吞掉异常、放宽断言或给命令追加忽略失败标记，只会把红灯藏起来。真正修复必须保留检查的原始意图，并让回归用例能在旧代码上失败、新代码上通过。

5.3 让产物支持复盘 ​

流水线应保留代理使用的任务说明、关键日志、补丁、测试结果和最终摘要。出现误修时，团队才能重建代理依据了什么，而不是只看到一个突然生成的提交。

5.4 写权限放在最后 ​

可以先让代理只读分析并产出建议；确认诊断可信后，再允许它在临时分支写补丁；推送、评论和开 PR 则使用单独授权。分段权限让每一步都能被检查。

六、Slack 与 Linear 是需求入口，不是信任源 ​

6.1 消息必须转译成工程任务 ​

一句“这个按钮坏了”缺少仓库、版本、复现步骤和验收条件。代理可以从对话或工单提取上下文，但正式执行前要把信息整理成目标、范围、约束和验证。

6.2 外部文本可能夹带不可信指令 ​

聊天消息、附件和工单描述都应作为数据处理，不能覆盖系统、团队和项目规则。连接器需要限制它能读取的频道、项目和字段，也要限制可执行动作。

6.3 回写要保留来源与状态 ​

当代理把分析结果回写到 Slack 或 Linear，应附上关联工单、分支或 PR、验证结果和仍待人工决定的事项。这样讨论和代码之间保持可追踪关系。

七、SDK 与 App Server 用来嵌入产品 ​

7.1 SDK 适合编排明确的代理流程 ​

当企业需要在内部工具中发起任务、订阅事件、收集结构化结果或加入自定义审批，SDK 比模拟 CLI 输出更稳定。应用负责业务状态，代理负责推理与工具调用。

7.2 App Server 提供长期运行的会话能力 ​

面向自定义客户端时，需要线程管理、消息流、工具事件和批准交互。App Server 把这些能力作为服务暴露，使桌面端、Web 工具或内部平台可以构建自己的交互界面。

7.3 嵌入后仍要保留平台边界 ​

产品层要处理身份、租户隔离、配额、审计和数据保留，不能把这些责任全部交给模型。代理能力只是系统中的一层，外层应用仍对用户和组织负责。

八、设计一条最小可用交付流水线 ​

一条稳健的流水线可以从工单读取需求，在隔离 Worktree 中启动只读分析，形成执行合同后运行 codex exec，通过测试与静态检查生成证据，再由人审查 diff。只有审查通过，才创建本地提交；是否推送和创建 PR，根据项目授权单独决定。

这条链路并不追求全自动。它追求的是每个状态变化都有输入、有责任边界、有验证、有恢复路径。自动化应减少重复劳动，而不是减少可见性。

九、工程化落地的检查清单 ​

  • 任务是否有唯一主目标和明确验收条件。
  • 工作树是否与其他任务隔离，已有修改是否得到保护。
  • 代理拿到的权限是否只覆盖当前阶段。
  • 输出是否可被机器解析，失败是否返回非零状态。
  • 测试、日志和补丁是否能重建本次决策。
  • 推送、PR、合并和发布是否保留授权关口。

当这些问题都有答案，Codex 才从“会帮我改代码的工具”变成可嵌入研发流程的工程组件。

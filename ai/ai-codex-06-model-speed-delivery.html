模型不背锅：Codex 选型、提速与迁移的系统方法 ​

AI 编程任务变慢或失败时，人们最容易先换模型。可真正决定交付质量的，往往是上下文是否失控、任务是否混杂、工具链能否验证、环境能否重建。模型当然重要，但它只是系统中的推理引擎，不是替所有工程问题背锅的万能旋钮。

本文以教程第 30～32 篇为线索，对照 OpenAI Docs 的 Models、Best practices 与 Import 章节，讨论模型选择、速度与上下文，以及从其他编码代理迁移。Windows 环境归入第五篇，完整项目交付归入第三篇；文中不固化易变的型号、价格和配额，而是提供能够跨版本使用的决策方法。

一、选模型之前先给任务分类 ​

1.1 复杂度决定需要多少推理 ​

查找符号、修改文案和机械迁移通常不需要最高推理预算；跨模块设计、并发缺陷和陌生代码库诊断，则需要更强的规划与长链推理。让所有任务都使用同一档模型，会在成本、速度或质量上浪费一端。

1.2 风险决定需要多少审查 ​

即使任务本身简单，只要涉及身份、支付、数据迁移或公开接口，仍应提高审查和验证强度。模型能力不能替代风险控制。

1.3 工具与环境可能比模型更关键 ​

模型若无法读取真实日志、运行测试或访问必要文档，再强也只能根据残缺信息猜测。相反，能力适中的模型在清晰范围、完整工具和快速反馈下，往往更稳定。

1.4 用小型基准验证选择 ​

可以从团队真实任务中挑选若干代表样本，比较完成率、修改范围、验证通过率、人工修正次数和总耗时。选择应建立在工作负载证据上，而不是只看榜单或单次惊艳演示。

二、速度问题先看端到端链路 ​

2.1 总耗时不只来自生成文本 ​

读取仓库、搜索文件、安装依赖、编译、运行测试、等待网络和人工审查都计入交付时间。只盯着模型每秒输出多少字，可能优化了最不重要的一段。

2.2 缩小范围是最便宜的加速 ​

明确相关目录、入口、错误日志和验证命令，可以减少代理无目的搜索。任务边界越清楚，工具调用和无关上下文越少。

2.3 给代理快速反馈回路 ​

优先运行最相关的单元测试或静态检查，确认局部修改后再扩大验证范围。每次都从完整构建开始，会让代理在简单错误上等待太久；只跑局部测试而永不全量验证，又会漏掉集成风险。

2.4 缓存与可重建环境同样重要 ​

复用依赖缓存、构建产物和稳定开发环境可以减少机械等待，但缓存必须有明确失效条件。无法解释来源的旧产物，会制造“本地通过、干净环境失败”的假象。

三、上下文管理决定长任务是否失真 ​

3.1 上下文不是越大越好 ​

会话历史、日志、文件内容和工具结果都占据注意力。无关内容越多，真正关键的约束越容易被淹没。长上下文提供容量，不代表所有内容都应该装进去。

3.2 用文件和记录承载稳定事实 ​

项目规则写入 AGENTS.md，进度写入 ROADMAP.md，架构决策写入专门文档，测试结果保留为文件或日志。稳定事实不必依赖模型记住整段对话。

3.3 在自然阶段边界压缩 ​

完成调查、方案或一个实现阶段后，可以保留目标、决策、改动文件、验证证据和待办，压缩冗长探索过程。压缩的目标是提高信噪比，而不是抹掉关键依据。

3.4 一个线程只处理一个主任务 ​

将无关问题不断追加到同一线程，会让权限、范围和完成条件相互污染。新目标若能独立验收，就应进入新线程或新工作树。

四、从其他编码代理迁移要迁移工作流 ​

4.1 不要逐个翻译命令名称 ​

不同工具在会话、权限、规则、插件和自动化上的概念并不完全一一对应。只寻找“某命令在 Codex 里叫什么”，容易保留旧工具的使用习惯，却错过新系统的原生边界。

4.2 先列出真正依赖的能力 ​

盘点现有工作流：项目规则放在哪里，常用自动化如何触发，外部工具怎样连接，权限怎样批准，任务怎样验证和发布。然后再为每项能力选择 Codex 中合适的配置、Skill、MCP 或脚本。

4.3 用一个真实项目做双轨验证 ​

选择规模适中、测试完备的项目，让旧流程和新流程完成同一组任务。比较结果质量、耗时、人工干预和安全边界，逐步迁移，而不是一次性替换全部团队工具。

4.4 清理重复事实源 ​

迁移期间最危险的是两套规则长期并存。确认新流程稳定后，应明确哪个文件是当前事实源，旧配置是归档还是废弃，避免代理读取相互冲突的指令。

五、一个可复用的决策框架 ​

当任务不理想时，依次检查：目标是否可验证，范围是否过大，上下文是否混杂，工具是否拿到真实证据，环境是否可重建，权限是否阻塞必要动作，验证是否快速可靠。只有这些条件基本成立，再评估模型是否需要更强推理或不同速度档位。

这套顺序能避免把工程系统问题误判成模型问题。换模型可能暂时改善结果，却不会修复缺失测试、错误目录、失效缓存或冲突规则。

六、把速度定义为“更快得到可信结果” ​

AI 编程的速度不应只统计首次补丁生成时间，而要统计从需求提出到证据齐全、可安全合并的总时间。一个慢几分钟但范围准确、测试可靠的结果，通常比瞬间生成却需要数小时人工排错更快。

模型选型、上下文压缩、环境治理和分段交付最终服务于同一目标：减少返工，让每一轮计算更接近可接受结果。

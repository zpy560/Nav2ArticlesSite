把 Codex 嵌进工程系统：SDK、App Server、GitHub、Slack 与 Linear 全链路 ​

当 Codex 只在个人终端里工作，任务边界由操作者临场维持；当它进入内部平台、GitHub、Slack 或 Linear，系统必须接住身份、会话、权限、幂等、审计和回写责任。集成的本质不是多接几个入口，而是把自然语言任务变成一条可验证的工程事件链。

本文以教程第 29 篇为线索，对照 OpenAI Docs 的 Developers 与 Integrations 章节，梳理 SDK、App Server、GitHub Action、Slack、Linear 和 MCP Server 的职责。教程把这些能力放在一个集成概览中，官方文档则给出更明确的选择边界：自动化 Job 优先 SDK，深度客户端优先 App Server，协作工具负责触发云端任务而不是替代仓库治理。

一、先分清六种集成解决什么问题 ​

1.1 Slack 与 Linear 是任务入口 ​

它们把频道讨论或工单转成 Codex 云端任务，适合把已有协作上下文带入编码流程。入口只负责触发和回传，不自动保证需求完整、仓库选择正确或改动可以合并。

1.2 GitHub Action 是 CI 执行单元 ​

官方 Action 在 Workflow 中安装并运行 Codex，可用于重复审查、生成补丁或发布前检查。它继承 GitHub 事件、Runner、Secret 和 Job 权限模型，适合有确定输入输出的流水线任务。

1.3 SDK 与 App Server 是两种嵌入层 ​

SDK 面向程序化 Agent 运行，适合脚本、后端 Job 和结构化输出；App Server 面向丰富客户端，提供认证、线程、历史、审批和流式事件。选错层会让简单自动化承担复杂会话协议，或让交互产品去解析脆弱的 CLI 文本。

二、SDK 适合可编排、可等待、可消费的任务 ​

2.1 应用拥有业务状态，Agent 拥有执行回合 ​

订单、工单、用户权限和重试状态应由外层应用管理；Codex 负责在一个 Thread 中理解任务、调用工具并返回结果。不要让模型输出成为唯一业务数据库，也不要用 Prompt 猜测任务是否已经执行过。

2.2 Thread 保留连续上下文 ​

官方 SDK 把一次持续对话抽象为 Thread，应用可以启动运行、继续同一线程，并处理结构化事件或最终结果。线程标识需要与业务对象建立明确映射，避免不同租户或工单共享上下文。

2.3 结构化输出比自由文本更适合集成 ​

机器消费的结果应有稳定 Schema、明确失败状态和可追踪产物。自然语言总结可以给人阅读，但后续程序不应依赖某句话的措辞判断是否允许合并、是否需要重试。

三、App Server 适合构建完整客户端 ​

3.1 它不是简单的 HTTP 包装 ​

官方 App Server 暴露线程与回合生命周期、工具事件、批准交互和流式通知，底层使用双向 JSON-RPC 风格协议。客户端需要先初始化，再启动 Thread 与 Turn，并持续消费通知。

3.2 协议版本必须跟随实际 Codex 版本 ​

App Server 可以从当前 CLI 生成 TypeScript 或 JSON Schema。集成方应以运行版本生成的 Schema 为契约，而不是从教程复制一份永久接口。实验性 WebSocket 传输尤其要核对当前支持状态和安全说明。

3.3 远程连接要单独处理认证与传输安全 ​

本机 stdio 或 Unix Socket 的风险面与非本机 WebSocket 不同。远程连接要使用安全传输、能力令牌或签名令牌，秘密通过受控文件或环境传入，不能把原始 Token 留在命令行和日志中。

四、GitHub Action 要从只读审查开始 ​

4.1 Workflow 权限比 Prompt 更重要 ​

Codex Action 能读到什么、能写回什么，由 Checkout 范围、GitHub Job 权限、Secret 和 Sandbox 共同决定。一个写着“只审查”的 Prompt，如果 Job 同时持有广泛写权限，仍然扩大了事故半径。

4.2 审查与改写应拆成不同阶段 ​

低风险起点是只读分析 Pull Request，输出报告和明确退出状态。需要生成补丁时，放到临时分支或产物中；评论、推送和合并使用后续 Job 与单独权限，让每个状态变化都有责任边界。

4.3 Prompt 文件也应进入版本控制 ​

固定自动化任务适合把 Prompt 放进仓库，和代码一起审查。任务输入、模型与推理配置、Sandbox、输出文件和验证命令都应可追踪，避免后台任务因临时界面配置悄然改变。

五、Slack 与 Linear 必须保留来源链 ​

5.1 对话不是完整需求合同 ​

频道里的讨论可能缺少仓库、版本、复现步骤、范围和验收条件。触发 Codex 前，应把目标、上下文、边界和完成条件整理清楚；长线程要在最新消息中重述关键事实，避免重要约束被埋没。

5.2 环境与仓库选择必须可见 ​

官方集成会根据用户可访问环境和请求上下文选择仓库，歧义时可能回退到最近使用环境。高价值任务应显式指定仓库或环境，并在结果中记录实际执行目标。

5.3 回写不是发布许可 ​

Slack 与 Linear 返回进度、摘要和任务链接，方便协作者继续同一上下文；这不代表改动已经通过 Review。最终 Diff、测试、PR、合并与部署仍遵循源代码平台的保护规则。

六、把 Codex 作为 MCP Server 使用 ​

Agents SDK 可以通过 MCP 调用 Codex，把编码能力作为更大 Agent 系统中的一个工具。外层 Agent 负责业务编排，Codex 在受控工作区执行代码任务，再把结构化结果返回。这个模式适合已有 Agent 平台需要调用专业编码执行器的场景。

边界必须清楚：上游指令仍是不可信输入，工作目录与 Sandbox 要隔离，工具超时与失败要可见，输出不能自动进入生产。MCP 解决连接协议，不替代身份、授权和审计。

七、集成平台必须补齐五类护栏 ​

身份映射要把 Slack、Linear、GitHub 和内部用户关联到真实责任主体；输入校验要识别仓库、任务和不可信外部文本；权限分层要让分析、写补丁和外部回写使用不同能力；幂等设计要避免重试产生重复评论、重复分支或重复部署；审计追踪要关联请求、Thread、仓库版本、工具事件、批准和结果。

任何一项缺失，都会让“自动化成功”难以证明。集成平台衡量的不是触发次数，而是一次任务能否从来源走到可验收结果，并在失败时准确恢复。

八、如何选择正确入口 ​

固定批处理、后端 Job 和 CI 编排优先使用 SDK 或 GitHub Action；需要线程、流式事件、工具过程和审批 UI 的自定义客户端使用 App Server；从团队讨论或工单派发云端任务使用 Slack 与 Linear；已有 Agent 平台需要把 Codex 当专业工具时使用 MCP Server。

选择标准不是哪个接口最“高级”，而是哪个接口最少承担额外责任。越靠近用户和组织状态，外层系统越要自己管理身份、权限、Schema、幂等和审计。
